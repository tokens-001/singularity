## 一、材料里的假前提（题目要求单独回答的一句话）

**§8.2 和 §8.7-1 的「`run_phase` 不认识 INTEGRATING/DELIVERING，走到就报'未知 phase'」是假前提——该分支 2026-09-11 就加了（`git log -S "INTEGRATING, Phase.DELIVERING"` 指向 09-11 的"fix: 四件旧账"，现 `workflow.py:337`，材料 09-13 才写），§8.2 那张表把已删除的 FIXING 也列成 run_phase 认识的阶段，是同一簇过期。**

两点展开。**其一**，这不推翻"两套驱动是真债"的判断——问题仍在，但病症已经变了：不再是"一个驱动不认识某些阶段"，而是"同一个 `phase` 字段两个写者、同一阶段两条路径行为不同"（REVIEWING 只由 orchestrator 跑验收，`run_phase` 的 REVIEWING 分支直接推 GATE3——注释现在如实承认这点，并靠 `set_phase` 的入门票 `gate3_no_evidence` 兜底披露）。基于"报未知 phase"的紧迫性论证需要重写，基于"双写者无所有权声明"的论证依然成立。**其二**，教训值得入性质清单 #11 的例证库：**材料在描述"已修的东西"时不带核于锚点，写完两天断言就死了**——这已经是"文档撒谎"族在材料侧的又一次发作，和 §42"报告会撒谎"同构。

## 六、Q5：最大的误判

**材料第四节的结论「成熟方案只能治 A 族，B 族换引擎也会原样留下来」——前半句对持久化引擎和结构化并发成立，对水位触发不成立，而水位触发恰是你们自己排第一的方案。** 论证：B 族的定义是"判据不成立而没人验过"；水位对账确实不修假判据，但它把 B 族的**后果**（该跑的没跑、该有的没有）变成缺席信号——案例 A 在水位世界里就是一条"consolidate_memory 活性缺席"的常驻条件。**水位化不治 B 族的判据，但消灭 B 族的静默**——失败模式从"不可见"变"常亮"，而常亮你们已有处理机制（chronic 桶，§62）。更深一层：B 族不是待治的存量，是每条新判据的**出厂状态**——"治 B 族"的真药是你们自己立的 §9.2（每个修复答得出"它失效了谁会知道"），材料把它写在方法学里却在第四节宣布这类无解，自己打了自己的架。这批 except 分类（out-01~14 → 修复 → 守卫钉住）正是"显形 → 修判据"流程在跑的实证。

前提敏感性：若 B 族里存在"判据假且后果也被判据自身掩盖"的子类（判据假 → 对账也查不出），我的结论变弱——但那类东西对任何引擎都不可见，恰好证明该靠 §9.2 的交付纪律。

## 七、Q6：「默认怀疑」怎么落地而不淹死筛子

**翻转的对象是"承诺清单"（约 30 条），不是 561 个代码行。** 你们已经不自觉地走了一半：`alert_summary(chronic_min=3)` 是"常驻条件"机制，`待验证清单`（51 条）是登记台账，守卫是增殖阻断。缺的最后一环是**承诺本身的显式登记**——一页 `承诺台账.md`：每条承诺登记（生产者 / 证据是什么、在哪 / 谁查缺席 / key 是什么）。落地动作：把 `_gate3_admission`、`reconcile_projects`、孤儿探测、守卫已覆盖的承诺枚举成这张表（半天），此后**新特性交付时申报一行**（把 §9.2 从"修复级"推广到"特性级"）。

为什么不淹筛子：缺席驱动的信号**天然低噪**——一条承诺一条常驻条件，兑现即消；事件驱动的告警才按次刷屏。材料 §3.3 的 88% 挤两个 key 恰恰证明：**事件流不可信，缺席流才可信**。最后一条兜底：缺席判据自己也会烂（永不清 → 常亮噪声），常驻条目要有 TTL——超两周的 chronic 必须升级成"必须处置"，不许挂着不管。

## 八、Q7：性质清单（20 条 v2）的直接批评

先承认：v2 把上一轮的三条批评（#2 措辞绝对化、#9 桌椅级、#17 缺两分法）全部改对了，#19/#20 两条新增和 A/B/C/D 分组直接来自外派答卷且核实采纳——这个吸收速度本身就是性质 10 的活实践。以下是**当前版**剩下的：

1. **缺「单写者」性质**。#14 管"一个定义处、一个入口"，没管"同一份数据的**写者数**"。§46（role_probe 第二进程撞 tmp）和 `_decompose` 双路（案例 B）的根都是**两个写者**，不全是两个入口。建议并入 #18 或独立："同一份持久化状态，写者要么唯一、要么每人都走同一个门"。
2. **缺「时间边界」性质**。§57 的规则"凡是可能不返回的调用必须有超时——没有超时的兜底 = 装死"没有独立条目；#8 只说"不是异常的失败也要算失败"，没给出口的**形态**。建议并入 #8："出口要么是超时、要么是会变旧的活性痕迹"。

4. **#5 的「怎么查」过期了**。还写着手工 grep + 561/420 估算——守卫和 baseline 已经存在，这条应该改成"跑 `test_no_silent_except.py`，看 baseline 差值"。否则下一个读者会照旧手工数一遍，然后得到一个和谁都对不上的数（我的 571/396 就是这么来的）。
5. **A 组的表观满足度虚高**。A 组 8 条里 #19/#20 是刚补的，且 #20 自己标注"原子那一半还没有"、#19 的实践（tick+watchdog）只覆盖调度循环一个循环——**A 组当前真正结构满足的只有 2/3/14**。这个诚实的计分恰好是 8c 算账的输入，建议在清单里给 A 组逐条标"满足/部分/未满足"三态——清单自己就该三态可分（#6 的自我应用）。

## 九、Q8：评架构（重点）

### 8a. 六条结构性问题逐条判定（按当前源码）

**#1 两套驱动——真问题，但材料对它的描述已过期，且危害已三重降级。** "不认识阶段"已修（09-11）；REVIEWING 双路径的假成功已被入门票披露（`_gate3_admission` + 分支注释如实承认竞态）；auto_mode 死循环已修（未放行即 break）。**残余的真问题**是所有权没有声明：REVIEWING 的验收只有 orchestrator 跑、`run_phase` 那条只解释不执行——这该用一张十行的 `_PHASE_OWNER = {phase: "user"|"scheduler"}` 表写成结构，而不是靠每个分支的注释自觉（性质 3：注释不是约束）。

**#2 边沿触发——真问题，六条里最深，但已经不是裸的。** 过去 48 小时落的三台仪器（strand_guard 收尾、loop_tick+watchdog 活性、reconcile 孤儿判据）把"接一次就不回头"的几种**已知的**断法全部兜住了。剩余风险恰是 B 族：**还没人想过的断法**仍然无声。所以这条的准确表述是：范式仍是边沿，但对账判据的覆盖面决定它的实际危险度——这把 #2 和方案 1 绑成了同一件事。

**#3 多入口——真问题，实证两起，点修已落、结构修未做。** `_decompose` 写清单 + 守卫测试关掉了这一处；`_ON_ENTER`（Q1-①）关掉这一类。

**#4 状态同时活在内存和磁盘——真问题，已大头修。** loop_tick、heavy_state、节流状态全部落盘。残余是"新增周期逻辑时还会忘"——那是 #5 守卫和清单 #12 的纪律问题，不是结构问题。

**#5 并发靠裸 future——真问题，已包扎，未根治。** strand_guard 让孤儿"必被收回"，但"先改状态后登记"的顺序还在（性质 20 自认原子半缺）。以单人维护的规模，我同意不做真正原子化——守卫 + 孤儿探测的组合已经把最坏后果（永久挂起）变成"必被发现"。

**#6 零数据库——不是债，是这个规模下的正确取舍，且利息已大头付清。** 维持原判，外加一条 48 小时前不存在的**新论据**：watchdog、守卫、reconcile、孤儿探测四台仪器能在两天内建成，**正因为状态全是文件**——30 行的标准库脚本直接读 `.qidian/` 就能对账；换成数据库，这四台仪器每一个都要重写（驱动、查询、权限）。grep 可排查性不只是排障便利，它是**这台机器的仪器化速度的来源**。真正的现债只有一条：role_probe 第二进程的**单写者问题**（#46 用 pid-tmp 修的是症状）——立一条"`.qidian/` 下每个文件一个写者，第二进程只读"的规矩，比引数据库便宜三个数量级。

### 8b. 要不要改？改哪一层？

**不换进程模型。** 分两层说清：

- **能在这个进程模型里改的（全部剩余项都在这层）**：入场动作表、`_PHASE_OWNER` 表、单写者规矩、reconcile 判据补全、存量 except 清账、REVIEWING 所有权声明。
- **必须换进程模型才能改的**：中途崩溃续跑（步骤状态进引擎）、多实例横向扩展、恰好一次语义。**这三条当前一条都不疼**——而且 48 小时的实践反过来证明：这个进程模型上的仪器化空间还远没挖完。

### 8c. 有没有更好的架构？——用你们自己的硬标准算账

材料 8c 的判据（好架构应让一批补丁作废）是对的，而你们在性质清单 v2 里已经把这道题做成了**可计算的**：A/B/C/D 四组里，换架构只对 A 组（结构化保证的 8 条）有收益。逐条问"Temporal 类引擎能让哪条自动成立"：#1 部分（引擎接管推进者）、#3 部分（步骤顺序成结构）、#4（每个 settle 有确认）、#20（状态变更与登记原子）——**约 3.5 / 8**；#19 部分成立但你们仍需进程外看护；B/C/D 共 12 条**一条都不会自动满足**。对照成本：重写编排层、自托管引擎本身成为一个新的静默失败面（§57 式挂死会被外购而非消失）、grep 排查能力丢失（而它是四台仪器的前提）。

**结论：修零件，不换设计。** 但要给这笔账一个**重算触发器**，否则它会变成"永远不换"的教条：当 A 组满足度缺口 ≥3 条、且其中至少两条同形状第三次复发时，重跑这张表。以当前轨迹（仪器化速度 > 出血速度），这个触发器短期不会到。
