# 专家团队架构

> 2026-06-27。借鉴 WorkBuddy 专家分工体系，重构奇点角色模型。

## 核心原则

- **分层不串行**：思考层（D）和实现层（E/E+）分开，思考层换帽子不换模型
- **专家不越界**：每个角色有明确的输入/输出 schema 和能力边界
- **人工卡三点**：定义完成、架构完成、交付完成，三处人审
- **并行不冲突**：同一阶段内角色并行产出，阶段结束时合成裁决
- **Observer 只做沟通和调研**：弄清楚用户想要什么、喜欢什么风格、市场上有什么。不做设计，设计归 D

## 团队全貌（13 角色）


## Observer 的边界

Observer 是一个便宜模型驱动的对话入口。**职责是搞清楚用户要什么，不是替用户做设计决策。**

| Observer 做的事 | Observer 不做的事 |
|----------------|-------------------|
| 问清楚需求、目标用户、核心功能 | 技术选型、架构设计 |
| 收集 UI 偏好（参考图、颜色、风格） | 出具体 UI 方案 |
| 竞品调研、技术可行性调研 | 做架构决策 |
| 汇总验收报告给人在 GATE3 看 | 判断交付物合不合格 |

定义层四个角色通过 Observer 对话完成，产出结构化文档后交人确认。通过后进入 D 层，真正的设计开始。

## 时序编排

```
阶段一：定义（Observer 对话）
  用户发起 → ①产品经理（问需求、出PRD）
         ↳ ②交互设计 + ③UI偏好        ← 串行推进
         ↳ ④研究员（拿到PRD后并行启动）  ← 与②③并行
  → GATE1 ✓（人审PRD+交互+UI方向+调研）

阶段二：架构（D 层，并行）
  ⑤系统架构 ∥ ⑥AI架构 ∥ ⑦前端架构
  三人拿同一份 PRD + 交互/UI方向 + 调研报告
  各出各的，互不看对方产出
  → 合成器裁决冲突
  → 统一架构 + 任务清单
  → GATE2 ✓（人审架构方案）

阶段三：实现（E/E+ 层，并行）
  ⑧前端 ∥ ⑨后端 ∥ ⑩数据 ∥ ⑪DevOps
  独立 worktree，互不干扰
  → 合并到主干
  → 自动跑测试
  → 测试不通过：自动修一轮，还不过升级到 D

阶段四：验收（D 层，并行）
  ⑫QA ∥ ⑬安全
  不写代码，只出报告
  → Observer 汇总两份报告
  → GATE3 ✓（人审交付物 + 报告）
  → 交付
```

## 打回路径

| 门 | 打回后去哪 | 什么情况打回 |
|----|----------|------------|
| GATE1 | 回到 Observer 对话，修正对应的那部分 | 需求不对、方向偏了 |
| GATE2 | 部分修正——打回具体那个架构师重做，不改动其他部分 | 某个架构方案有缺陷。除非完全偏离需求才全重做（可能性很小） |
| GATE3 | 回到架构阶段（GATE2），重新规划修复方案 | 交付物有严重问题。不直接改代码，先改架构方案 |

## 输入输出契约

每个角色有固定 schema。上游不按 schema 出，下游拒绝接收。

### ① 产品经理
```
输入：用户自然语言描述
输出：{
  "goal": "产品要解决什么问题",
  "scope": "做什么和不做什么",
  "features": [{"name": "...", "priority": "P0/P1/P2", "description": "..."}],
  "success_criteria": ["可验证的成功标准"],
  "constraints": ["已知约束"],
  "competitors": [{"name": "...", "strength": "...", "weakness": "..."}]
}
边界：不给技术方案，不做架构判断
```

### ② 交互设计师
```
输入：PRD
输出：{
  "user_flows": [{"name": "...", "steps": ["..."]}],
  "page_tree": [{"page": "...", "children": [...]}],
  "key_interactions": [{"trigger": "...", "feedback": "...", "edge_cases": ["..."]}],
  "state_machine": {"states": [...], "transitions": [...]}
}
边界：不设计视觉，不画具体 UI
```

### ③ UI 设计师
```
输入：PRD + 交互方案
输出：{
  "color_system": {"primary": "#...", "surface": "#...", ...},
  "typography": {"heading": "...", "body": "...", "scale": [...]},
  "spacing": {"unit": 4, "scale": [...]},
  "component_style": [{"name": "...", "appearance": "...", "states": [...]}],
  "responsive_breakpoints": {"mobile": 375, "tablet": 768, "desktop": 1280}
}
边界：不写代码，不定义组件实现细节
```

### ④ 研究员
```
输入：PRD（拿到后即可启动，与交互/UI设计并行）
输出：{
  "market_findings": [{"source": "...", "finding": "..."}],
  "tech_options": [{"name": "...", "pros": [...], "cons": [...], "fit": "high/medium/low"}],
  "risk_areas": [{"area": "...", "risk": "...", "mitigation": "..."}],
  "recommendation": "一句话建议"
}
边界：只调研不决策，决策权归产品经理
```

### ⑤ 系统架构师
```
输入：PRD + 交互/UI方案 + 调研报告
输出：{
  "modules": [{"name": "...", "responsibility": "...", "depends_on": [...]}],
  "data_model": {"entities": [...], "relationships": [...]},
  "api_contracts": [{"method": "GET/POST/...", "path": "...", "input": {...}, "output": {...}}],
  "tech_stack": {"language": "...", "framework": "...", "database": "...", "cache": "...", "mq": "..."},
  "constraints": [{"type": "security/performance/reliability", "rule": "...", "check": "如何验证"}],
  "tasks": [{"id": "...", "title": "...", "description": "...", "complexity": "low/medium/high",
             "layer": "frontend/backend/data/devops", "depends_on": ["task_id"], "acceptance": "验收标准"}]
}
边界：不做 AI 设计，不做前端架构
```

### ⑥ AI 架构师
```
输入：PRD + 交互/UI方案 + 调研报告
输出：{
  "model_strategy": {"tier": {"cheap": "...", "strong": "..."}, "routing": "simple/complex/fusion"},
  "prompt_templates": [{"name": "...", "template": "...", "variables": [...]}],
  "agent_topology": {"entry": "...", "sub_agents": [...], "handoff_rules": [...]},
  "context_strategy": {"window": "最近N轮+摘要", "persistent": ["项目信息", "用户偏好"]},
  "tool_definitions": [{"name": "...", "description": "...", "parameters": {...}}]
}
边界：不做系统架构，不做前端，不写代码
```

### ⑦ 前端架构师
```
输入：PRD + 交互/UI方案 + 调研报告
输出：{
  "component_tree": [{"name": "...", "children": [...], "props": [...]}],
  "state_design": {"global": {...}, "local": [...]},
  "route_design": [{"path": "...", "component": "...", "auth": true/false}],
  "performance_strategy": {"code_splitting": [...], "lazy_load": [...], "cache": "..."},
  "package_choices": {"ui_lib": "...", "state_mgmt": "...", "router": "...", "css": "..."}
}
边界：不写代码，不做后端，不做 AI 设计
```

### ⑧⑨⑩⑪ 实现层
```
输入：统一架构文档（系统架构 + AI架构 + 前端架构）+ 自己对应的任务条目
输出：{
  "changed_files": ["..."],
  "test_results": {"pass": N, "fail": M, "errors": [...]},
  "notes": "实现中的取舍说明"
}
边界：不改架构方案，发现架构问题上报不自行修改
各角色只取架构中自己相关的部分：
  - 前端工程师：取前端架构 + 系统架构中前端相关 task
  - 后端工程师：取系统架构 + AI架构中集成相关部分 + 后端相关 task
  - 数据/ML 工程师：取 AI 架构中向量库/模型/数据管道部分
  - DevOps 工程师：CI/CD 配置、Dockerfile、部署脚本、监控告警
```

### ⑫⑬ 验收层
```
输入：架构约束清单 + 代码 + 测试结果
输出：{
  "passed": [{"check": "...", "evidence": "..."}],
  "issues": [{"id": "..", "severity": "bug/warning/suggestion", "file": "...", "description": "..."}],
  "summary": {"total_checks": N, "passed": N, "failed": N, "verdict": "go/no_go"}
}
边界：不写代码，不修改任何文件
Observer 负责汇总两份报告成统一摘要给人看
```

## 测试策略

测试用例由用户提供，逐步迭代改进。

- **GATE2 阶段**：用户审架构方案时，一并提供初始测试用例（或让系统推荐，用户确认）
- **实现阶段**：自动跑测试，过不了的自动修一轮
- **验收阶段**：QA 工程师基于用户测试用例做补充验证
- **迭代**：每次跑完用户反馈测试用例的覆盖情况，系统记录并建议补充

## 合成裁决

架构阶段三人并行产出矛盾时，合成器介入：

```
三人产出 → 合成器（D 层，不带任何专家身份）
  ① 共识点 → 直接锁定
  ② 矛盾点 → 裁决，给理由（不投票）
  ③ 盲区 → 三人漏了的，补上
  → 输出统一架构文档
```

合成器用 `execution_judge.fuse_outputs()` 的五维分析逻辑。

验收阶段 QA 和安全各自出报告。两份报告由 Observer 汇总成一份摘要给人看，不做合成裁决（两人管的事不重叠）。

## 三层门

| 门 | 位置 | 审什么 | 人能做什么 | 打回去哪 |
|----|------|--------|-----------|---------|
| GATE1 | 阶段一结束 | PRD + 交互 + UI方向 + 调研 | 通过/打回修改 | 回对应步骤修正 |
| GATE2 | 阶段二结束 | 统一架构 + 任务清单 | 通过/打回部分重做 | 只修正有问题的那部分架构 |
| GATE3 | 阶段四结束 | 交付物 + QA报告 + 安全报告 | 通过/打回 | 回到GATE2重新规划 |

## 多模型碰撞策略

不是每个角色都多模型跑。只在**选错了代价大**的地方用。

| 角色 | 碰撞级别 | 原因 |
|------|---------|------|
| 系统架构师 | **3 模型** | 模块划分、技术选型一旦定错，后面全错 |
| AI 架构师 | **3 模型** | Prompt 设计、模型选型——不同模型对 AI 设计的判断差异大 |
| 安全审计师 | **3 模型** | 漏一个漏洞就是事故，不同模型安全盲区不同 |
| 研究员 | **2 模型（Self-Fusion）** | 多角度调研有价值，同模型两遍不同搜索词 |
| 产品经理 | 单模型 | 跟人对话澄清需求，碰撞不增值 |
| 交互设计师 | 单模型 | 用户流程是逻辑推导，非多视角问题 |
| UI 设计师 | 单模型 | 审美碰撞容易导致设计妥协成中庸 |
| 前端架构师 | 单模型 | 组件树和路由偏工程实现，歧义少 |
| 前端/后端/数据/DevOps | 单模型 | E/E+ 层照规格施工，不需要碰撞 |
| QA 工程师 | 单模型 | 按测试策略对照检查 |

架构层的碰撞 = 同一角色不同模型各出方案，查漏补缺。取并集 + 消矛盾 + 标盲区。
实现层的碰撞无意义——两个模型写同一个文件会冲突，且便宜模型盲区重叠大。

## 三层模型调度

| 层 | 谁跑 | 角色 | 碰撞 | 并行 |
|-----|------|------|------|------|
| Observer | 便宜模型 | 产品经理、交互、UI、研究员 | 研究员 2模型 | 调研与交互/UI并行 |
| D | 强模型，换 skill | 系统架构、AI架构、前端架构、QA、安全 + 合成器 | 架构/安全 3模型 | 架构并行+合成 |
| E/E+ | 便宜模型 | 前端、后端、数据、DevOps | 无 | 并行，独立 worktree |

## Skill 来源

1. **开源优先**：从 promptor、agent-rules-books、ai-agent-solution-architect 拉现成的改
2. **最小启动**：每个角色先写 200 字 prompt + 输出 schema，跑一轮
3. **自举迭代**：跑通后让 D 层自动生成其他角色的 skill，人工审核
4. **多模型碰撞生成**：关键角色（架构师、AI 架构师、安全）多模型各出一版 skill，合成最优

## 成本估算

一次完整产品方案（4 阶段完整走一遍）：

| 阶段 | 调用 | 模型 | 次数 | 并行后延迟 |
|------|------|------|------|-----------|
| Observer 对话 | 产品+交互+UI+研究员(2) | 便宜 | 5 次 | ~30s（AI生成）+ 人对话时间 |
| 架构 | 系统(3)+AI(3)+前端(1) | 强模型 | 7 次 | ~15s（并行） |
| 合成 | 合成器裁决 | 强模型 | 1 次 | ~5s |
| 实现 | 前端+后端+数据+DevOps | 便宜 | 4 次 | ~25s（并行） |
| 验收 | QA+安全(3) | 强模型 | 4 次 | ~10s（并行） |
| **总计** | | | **~21 次 LLM 调用** | **AI 延迟 ~85s + 人工对话时间** |

## 上下文传递

阶段之间怎么交接：

```
Observer 对话结束
  → 产出 4 份文档：PRD、交互方案、UI方向、调研报告
  → 存入项目目录 data/projects/<project_id>/
  → D 层架构师启动时，读取自己需要的：
      系统架构师 ← PRD + 交互方案 + 调研报告
      AI 架构师   ← PRD + 调研报告（关注模型相关）
      前端架构师 ← PRD + 交互方案 + UI方向

D 层产出
  → 合成器输出统一架构文档
  → 存入项目目录
  → GATE2 确认后：
      实现层各工程师读取自己对应的 task + 架构文档片段
      不读全量，只读自己的任务

实现层产出
  → 代码 + 测试结果 + 改动文件清单

验收层
  → 读取架构约束清单 + 代码 + 测试结果
  → 出报告
```

每个角色只读需要的，不往上下文塞全量。上游产出结构化 JSON，下游解析字段。

## 项目持久化

```
data/projects/<project_id>/
├── project.json           # 项目元信息（状态、当前阶段）
├── prd.json              # GATE1 产出
├── interaction.json      # 交互方案
├── ui_direction.json     # UI 方向
├── research.json         # 调研报告
├── architecture.json     # GATE2 产出（统一架构+任务清单）
├── test_cases.json       # 用户提供的测试用例
├── tasks/                # 每个任务的执行状态
│   ├── <task_id>.json
├── qa_report.json        # QA 报告
├── security_report.json  # 安全审计报告
└── lineage.json          # 操作日志（谁在什么时候做了什么决策）
```

追踪器（`tracker.py`）已有任务状态持久化。项目文档用现有 `project.py` 扩展，每个阶段产出存为一个 JSON 文件。

## 门交互

三个门是人在看。人看到什么、怎么操作：

### GATE1（审定义文档）

```
Observer 推一条消息：
"阶段一完成，请审核：
- PRD：<摘要>
- 交互流程：<摘要>
- UI方向：<摘要>
- 调研：<摘要>
请回复：通过 / 打回修改 [哪部分]"

人回复 → Observer 解析 → 通过 → 进架构 / 打回 → 通知修复
```

### GATE2（审架构方案）

```
Web 面板 / Observer 消息显示：
"架构方案已生成：
- 模块划分：<摘要>
- 技术栈：<摘要>
- 任务清单：<N个任务>
请查看 architecture.json 详情
请回复：通过 / 打回 [系统架构/AI架构/前端架构] [原因]"

人回复 → 合成器只重做被打回的角色
```

### GATE3（审最终交付）

```
Observer 推送：
"交付完成：
- QA报告：通过 M/N，X 个问题
- 安全报告：通过 A/B，Y 个建议
- 改动文件：<列表>
请回复：通过 / 打回 [原因]"

通过 → 项目标记 DONE
打回 → 回 GATE2 重规划
```

现有 `project.py` 已有 `Phase.GATE1/2/3` 和 `confirm_gate` 方法。门交互只需要 Observer 推送 + 解析用户回复。

## 落地顺序

13 个角色不一起上。从能用的最小闭环开始，逐步加人：

```
第 1 步：系统架构师（单模型）
  用 → 一个真实产品方案进去，看架构文档出得好不好
  改动 → roles.py + skills/system-architect/SKILL.md
  验证 → 人看输出质量

第 2 步：加合成器（3 模型碰撞）
  用 → 同角色 3 模型出 3 份方案，合成一份
  改动 → execution_judge.fuse_outputs()
  验证 → 对比单模型版，看合成版是否更好

第 3 步：Observer 对话（定义层 4 角色）
  用 → 人跟 Observer 聊，产出 PRD + 交互 + UI + 调研
  改动 → observer_agent.py 挂 4 个 skill
  验证 → 4 份文档结构完整、人能看懂

第 4 步：E 层实现（4 工程师 + 测试）
  用 → 架构 → 实现 → 测试 → 交付
  改动 → _exec.py 多 worktree 并行
  验证 → 代码能跑，测试能过

第 5 步：验收层（QA + 安全）
  用 → 实现完成后自动验收
  改动 → D 层挂 QA skill + 安全 skill
  验证 → 报告够详细，人能基于报告做判断
```

每一步跑通了再走下一步。只在当前步骤往回退，不跳着做。

## 关键设计决策

1. **Observer 只沟通不设计**：搞清楚用户要什么、喜欢什么风格、市场上有什么。真正的设计决策在 D 层。
2. **D 层换帽子不换模型**：一个强模型，切换 skill 切换思维框架。多模型碰撞只在架构层关键决策时用。
3. **架构三人并行 + 合成**：系统架构、AI 架构、前端架构三个维度各看各的，合成器查漏补缺。
4. **AI 架构师独立**：Prompt 体系、Agent 拓扑、上下文策略是专属技能，传统架构师不懂。
5. **实现层单模型照规格施工**：不需要多模型碰撞。测试不通过自动修一轮，还不过升级到 D。
6. **人工卡点不省**：GATE1/2/3 必须人审。AI 负责产出让人判断的材料，不替人判断。
7. **打回不重做**：GATE2 打回只修问题部分，只有完全偏离需求才全重做（可能性很小）。
8. **碰撞不滥用**：13 个角色只有 3 个用多模型。架构层碰撞有价值，实现层碰撞是浪费。
9. **测试用例用户提供**：用户给出初始测试用例，系统跑完后 QA 补充建议，逐步迭代改进。
