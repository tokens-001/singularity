## 项目定位

### 解决什么痛点

- **单 AI 写代码能跑但没架构、没测试、没安全审查**：一次性的代码片段不等于可交付的软件产品
- **多 AI 协作协调成本高**：谁先谁后、冲突了谁裁决、上下文怎么传递，这些没有系统内建
- **便宜模型干不了设计，全用贵的又浪费**：需要按任务复杂度分档调度
- **全自动不可控，全手动没效率**：黑盒交付你不知道里面有什么，一步步盯着又回到原点

### 一句话定位

**AI-native 软件开发流水线**——不是"AI 帮你写代码"，是"AI 团队按软件工程流程替你交付产品"。

### 不是

- 不是 Copilot（辅助你写代码）
- 不是 Cursor（IDE 里对话）
- 不是 Devin/Replit Agent（黑盒全栈，没有流程内的审查和测试）
- 不是 CrewAI/AutoGen（给你搭架子的工具，流程你自己写）

### 核心优势

| | Claude Code / Cursor | Devin / Replit Agent | CrewAI / AutoGen | **奇点** |
|---|---|---|---|---|
| **模式** | 对话式编码 | 黑盒全栈 | 搭架子自己写流程 | 按软件工程流程自动编排 |
| **角色分工** | 单模型 | 单模型 | 你自己定义 | 16 角色固定分工，阶段内并行 |
| **设计阶段** | 无，直接写代码 | 无 | 靠你的 prompt | 三架构师并行+合成器裁决 |
| **审查** | 无 | 无 | 无 | AI 审查+不通过自动修 |
| **测试** | 你跑 | 它跑但你看不到 | 你搭 | 两段：核心测→审查→全方位测 |
| **人工卡点** | 每一步 | 无（全自动） | 无 | 3 个 GATE，只在关键节点介入 |
| **多模型碰撞** | 无 | 无 | 无 | 架构/安全关键决策 3 模型交叉验证 |
| **上下文管理** | 塞满对话 | 黑盒 | 你自己管 | 阶段间结构化交接，下游只读自己需要的 |
| **模型成本** | 全用贵的 | 全用贵的 | 看你配置 | 定义+实现用便宜，架构+验收用强力 |

### 目标用户

- **独立开发者/小团队**：没有架构师、QA、安全工程师，但需要完整软件交付
- **产品经理/领域专家**：懂业务懂需求，不会写代码，想直接拿到可用的产品
- **外包替代**：预算不够请整支团队，但需要一个能独立交付的 AI 团队
- **内部工具/快速原型**：公司里需要工具但排不上开发资源

## 核心原则

- **流程为主轴**：定义 → 架构 → 实现 → 审查 → 验收 → 交付，六个阶段顺序推进
- **阶段内并行**：同一阶段角色并行产出，不串行等待
- **人工卡三点**：GATE1（定义完成）、GATE2（架构完成）、GATE3（交付），三处人审
- **审查分两层**：AI 自动审查在前，人工卡点在关键节点
- **测试分两段**：实现阶段核心功能测试（跑绿进审查），验收阶段全方位测试（QA+安全+回归+边界）
- **专家不越界**：每个角色有明确的输入/输出 schema 和能力边界

## 阶段详解

### 阶段一：定义（便宜模型）

Observer 驱动对话，搞清楚用户要什么。**只调研和沟通，不做设计决策。**

| 角色 | 干什么 | 模型档位 | 碰撞 |
|------|--------|---------|------|
| 产品经理 | 需求分析、用户故事、PRD | 便宜 | 单模型 |
| 交互设计师 | 用户流程、信息架构、页面结构、状态流转 | 便宜 | 单模型 |
| UI 设计师 | 视觉偏好收集、风格参考、品牌调性 | 便宜 | 单模型 |
| 研究员 | 市场调研、技术调研、可行性分析 | 便宜 | 2模型（Self-Fusion） |

产出：PRD + 交互方案 + UI 方向 + 调研报告 → GATE1 人工确认

### 阶段二：架构（强力模型）

强力模型，三人并行各出方案，合成器裁决冲突输出统一架构。

| 角色 | 干什么 | 模型档位 | 碰撞 |
|------|--------|---------|------|
| 系统架构师 | 模块划分、数据模型、接口契约、技术栈选型、任务拆解 | 强力 | **3模型** |
| AI 架构师 | 模型选型、Prompt 体系、Agent 拓扑、上下文策略 | 强力 | **3模型** |
| 前端架构师 | 组件树、状态管理、路由设计、性能策略 | 强力 | 单模型 |

（三人产出后交由合成器融合，合成器见「编排层」，不计入 13 业务角色）

产出：三人各自的架构方案 → 合成器融合 → 统一架构 + 任务清单 → GATE2 人工确认

### 阶段三：实现（便宜模型）

照架构施工，独立 worktree 并行。完成后跑核心功能测试，跑绿才能进集成合并。

| 角色 | 干什么 | 模型档位 | 碰撞 |
|------|--------|---------|------|
| 前端工程师 | UI 实现、交互逻辑、可访问性、动画 | 便宜 | 单模型 |
| 后端工程师 | API、数据库、业务逻辑、中间件 | 便宜 | 单模型 |
| 数据/AI 工程师 | 向量库、RAG、模型微调、数据管道、Prompt 模板工程化、Agent 拓扑落地、tool 定义实现 | 便宜 | 单模型 |
| DevOps 工程师 | CI/CD、容器化、部署、监控、日志 | 便宜 | 单模型 |

产出：代码 + 核心测试通过 → 自动进入集成合并

### 阶段三.五：集成合并（强力模型）

4 路独立 worktree 必须合并成一份可构建的代码，才能进审查。合并与集成测试失败 = 实现失败，走实现阶段测试上限。

| 步骤 | 做什么 | 失败处理 |
|------|--------|---------|
| 拓扑合并 | 按 task `depends_on` 拓扑序合并 4 路 worktree | 冲突 → 回写为架构问题，上报合成器重拆该子树 |
| 集成测试 | 跑 `test_cases.json` 中的 integration 用例 | 不过 → 计入"实现阶段测试修不过"上限（自动修 3 轮 → 打回架构） |
| 冒烟构建 | 容器/可执行产物能起来 | 起不来 → 打回 DevOps 工程师 |

产出：合并后的单一代码基线 + 集成测试结果 → 自动进入审查

注：本环节的冲突日志写入 `review_report.json` 的前置部分，供架构合规检查对照。

### 阶段四：审查（强力模型，AI 自动）

AI 审查。每项检查有独立失败处理，不通过先自动修一轮；累计达到上限一律**降级为人工兜底**（升 GATE2），绝不放行进入验收。

| 检查项 | 谁做 | 模型 | 不通过 |
|--------|------|------|--------|
| 代码质量 | `_review.py` | 强力 | 自动修一轮（计入审查上限） |
| 架构合规 | `validator.py` | 强力 | 打回实现（不消耗自动修次数） |
| 安全扫描 | 安全规则引擎 | 强力 | 标记 → 等待验收阶段安全审计师深度复核（不在此放行） |
| 测试通过 | pytest gate | — | 自动修一轮（计入审查上限） |

通过 → 自动进入验收阶段
任何一项触顶/超时 → **不进入验收**，升 GATE2 人工兜底

### 阶段五：验收（强力模型）

全方位测试。QA 对照需求验证，安全深度审计。不写代码只出报告。

| 角色 | 干什么 | 模型档位 | 碰撞 |
|------|--------|---------|------|
| QA 工程师 | 需求验证、回归测试、边界覆盖、功能完整性、E2E（对照交互 state_machine 跑） | 强力 | 单模型 |
| 安全审计师 | 权限、注入、密钥、依赖漏洞、隐私合规 | 强力 | **3模型** |

产出：QA 报告 + 安全报告 → Observer 汇总 → GATE3 人工确认 → 交付

### 阶段六：交付（DevOps 工程师收尾，便宜模型）

GATE3 通过后，把可交付物打包归档。不写新代码，只做打包/发布/导出。

| 动作 | 产出 |
|------|------|
| 代码归档 | 主分支打 tag，合并到 release 分支 |
| 产物打包 | 镜像 / 部署包 / 可执行产物（按 tech_stack 定） |
| 交付文档 | README + 部署说明 + 运行要求 + 依赖清单 |
| 归档 | test_cases.json、qa/security_report、lineage.json 一并归入交付目录 |

产出 schema：
{
  "deliverables": {
    "code_ref": "git tag / commit",
    "artifacts": [{"name": "镜像/包名", "type": "image/package/binary", "location": "..."}],
    "docs": ["README.md", "DEPLOY.md"],
    "reports": ["qa_report.json", "security_report.json", "test_cases.json"]
  },
  "deploy_hint": "是否已部署到环境，还是仅交付物",
  "handed_over_at": "时间戳"
}

边界：不新增功能，不改验收过的代码；发现新问题只能开新项目或在 lineage 记 issue。交付到生产环境涉及用户基础设施与密钥，风险高且不可逆，不自动部署，由人触发或单列部署阶段。

## 模型档位

按能力评级推荐（rating SSS+~A + recommended_for），不再用 E/E+/D 或 cheap/strong 两档：

| 档位 | 适用阶段 | 要求 |
|------|---------|------|
| **便宜** | 定义、实现、交付 | 快、便宜、够用 |
| **强力** | 架构、审查、验收 | 推理强、仔细、贵 |

审查用强力，因为代码审查+架构合规+安全扫描的质量直接决定后续走向，错放行的代价与架构选错同级。
拆解器/合成器（编排层）也用强力（架构阶段）。

碰撞策略不变：只在选错代价大的地方用多模型。

## 人工卡点

| 门 | 位置 | 审什么 | 能做什么 | 打回去哪 |
|----|------|--------|---------|---------|
| GATE1 | 定义完成 | PRD + 交互 + UI方向 + 调研 | 通过 / 打回修改 | 回对应步骤修正 |
| GATE2 | 架构完成 | 统一架构 + 任务清单 | 通过 / 打回部分重做 | 只修正有问题的那部分 |
| GATE3 | 验收完成 | 交付物 + QA报告 + 安全报告 | 通过 / 打回 | 按 issue.fix_route 分级路由（impl→实现层 / design→GATE2 / note→记录） |

---

## 测试策略

| 阶段 | 测什么 | 谁测 | 目的 |
|------|--------|------|------|
| 实现阶段 | 单元 + 集成（核心功能） | 自动跑 pytest | 跑绿才能进集成合并 |
| 集成合并 | integration 用例（跨工程师接口） | 自动跑 | 合并后基线可构建 |
| 审查阶段 | 全量回归 + 合规断言 | pytest gate | 不通过自动修，触顶升 GATE2 |
| 验收阶段 | 需求验证 + 回归 + 边界 + 安全 + E2E | QA + 安全审计师 | 交付前最后验证 |

审查前测"对不对"，审查后测"全不全/安不安全"。E2E 在验收跑，对照交互 state_machine 验证 success_criteria（如"用户能在 3 步内完成任务"）。

---

## 打回路径

| 门 | 打回后去哪 | 什么情况 |
|----|----------|---------|
| GATE1 | 回到定义阶段修正对应部分 | 需求不对、方向偏了 |
| GATE2 | 打回具体架构师重做，不改动其他 | 某个架构方案有缺陷 |
| GATE3 | **按 issue.fix_route 分级路由**（见下） | 验收发现问题 |

GATE3 分级路由规则（由 QA 报告 issue.fix_route 字段驱动，Observer 按 verdict 汇总裁定，人审兜底）：
  - `impl`    → 回实现层修复 → 重跑集成合并 + 审查相关项 → 重测   // bug/warning
  - `design`  → 回 GATE2 重新规划对应模块                                    // 架构性缺陷
  - `note`    → 记录进交付清单，不阻断交付                                  // suggestion
  - 多数 issue 为 impl 而 QA verdict 仍 no_go → 仍回实现层，不轻易升 GATE2

## 编排层（非业务角色，不计入 16 角色）

三个执行体负责阶段间调度、合成、拆解。它们不产出业务内容，只对业务角色的产出做调度与结构化。
同样遵守 schema 契约——它们是阶段衔接的咽喉，最该被约束。

### Observer（贯穿全程）

职责：定义阶段驱动对话与身份切换；阶段间状态感知；GATE 通知与报告汇总。

输入：对话流 + 项目当前状态文档（从 `.qidian` 读取 phase / 各 json）

输出（本身不产业务 schema，产出的是调度决策）：
```
{
  "role_switch": {
    "current": "产品经理|交互设计师|UI设计师|研究员|none",
    "trigger": "auto_upstream_done | user_explicit | fallback",
    "carried_context_ref": "上游产出文件引用",
    "next_action": "ask | present | wait_user"
  },
  "gate_summary": {                              // GATE 等待时产出
    "artifacts": ["prd.json", "interaction.json", ...],
    "highlights": "本次产出的要点摘要",
    "pending_decision": "需要人确认的点"
  },
  "verdict_rollup": {                            // GATE3 汇总
    "qa_summary": "...", "security_summary": "...",
    "fix_route_decision": "impl/design/note",
    "overall": "go/no_go/需人判断"
  }
}
```
边界：不做技术决策，不写业务内容；身份切换依据上游产出状态自动判定或用户显式触发

### 合成器（架构阶段）

职责：三人并行产出后，融合为统一架构文档；顺便生成 test_cases.json。

输入：三个架构师产出 + PRD + 调研报告

输出：
```
{
  "unified_architecture": {
    "modules": [...], "data_model": {...}, "api_contracts": [...], "tech_stack": {...},
    "constraints": [...],
    "ai_strategy": {...},          // 来自 AI 架构师
    "frontend_arch": {...}         // 来自前端架构师
  },
  "consensus": ["三人一致的点，直接锁定"],
  "resolutions": [{"conflict": "...", "decision": "...", "reason": "..."}],   // 裁决不投票
  "blindspot_fills": [{"area": "...", "added": "..."}],
  "tasks": [...],                  // 统一任务清单（自然语言描述）
  "test_cases": {...}              // 顺便生成，见「测试用例生成」
}
```
边界：不带任何专家身份，只做融合/裁决/补全；不重新设计，矛盾点必须给理由

### 拆解器（合成器子步骤，架构→实现衔接）

职责：把架构文档的自然语言 task 转成 `_exec.py` 可执行的结构化 task。

输入：`unified_architecture.tasks` + 架构文档

输出：见后文「架构 → 任务拆解」的可执行 task schema

边界：不改 task 语义，不改 acceptance，只做结构化映射 + 上下文片段提取

## 合成裁决

架构阶段三人并行产出矛盾时，合成器介入：

```
三人产出 → 合成器（强力模型，不带任何专家身份）
  ① 共识点 → 直接锁定
  ② 矛盾点 → 裁决，给理由（不投票）
  ③ 盲区 → 三人漏了的，补上
  → 输出统一架构文档
```

## 多模型碰撞策略

只在选错代价大的地方用：

| 角色 | 碰撞级别 | 原因 |
|------|---------|------|
| 系统架构师 | **3 模型** | 模块划分、技术选型定错，后面全错 |
| AI 架构师 | **3 模型** | Prompt 设计、模型选型——不同模型判断差异大 |
| 安全审计师 | **3 模型** | 漏一个漏洞就是事故 |
| 研究员 | **2 模型（Self-Fusion）** | 多角度调研有价值 |
| 其余角色 | 单模型 | 碰撞不增值或导致妥协 |

## 上下文传递

```
定义阶段结束
  → 产出 4 份文档：PRD、交互方案、UI方向、调研报告
  → 架构阶段启动，各架构师读取自己需要的：
      系统架构师 ← PRD + 交互方案 + 调研报告
      AI 架构师   ← PRD + 调研报告
      前端架构师 ← PRD + 交互方案 + UI方向

架构阶段结束
  → 合成器输出统一架构文档
  → GATE2 确认后
  → 实现层各工程师读取自己对应的 task + 架构文档片段

实现阶段结束
  → 代码 + 核心测试结果 + 改动文件清单
  → 审查通过后进入验收

验收阶段结束
  → QA 报告 + 安全报告
  → Observer 汇总两份报告
  → GATE3 人工确认 → 交付
```

每个角色只读需要的，不往上下文塞全量。

## 落地顺序

```
第 1 步：定义层（Observer + 4 角色）
  改动 → observer_agent.py 挂 4 个 skill + 编排层 Observer schema/切换协议
  验证 → 4 份文档结构完整，Observer 身份切换正确

第 2 步：三个架构师并行（系统/AI/前端，各单模型先跑通）
  改动 → roles.py 三个架构角色 + skills/*
  验证 → 三人各自 schema 输出齐全（此时喂入第 1 步的真实 PRD）

第 3 步：合成器 + 拆解器（编排层）
  改动 → execution_judge.fuse_outputs() + task 拆解器 + context 片段提取
  验证 → 三人真实产出融合出统一架构 + 可执行 task（此时第 2 步已提供真实输入，3 模型碰撞可真测）

第 4 步：实现层（4 工程师 + 核心测 + 集成合并）
  改动 → _exec.py 多 worktree 并行 + 集成合并环节
  验证 → 代码能跑，集成测试能过

第 5 步：AI 审查
  改动 → _review.py + validator.py + 安全规则引擎
  验证 → 审查报告准确，失败上限/超时降级正确

第 6 步：验收层 + 交付（QA + 安全 + 交付）
  改动 → 强力模型层挂 QA skill + 安全 skill + 交付打包
  验证 → 报告够详细含 E2E，人能基于报告判断；交付物清单完整
```

> 按真实流程顺序落地，每步用上一步的真实产出做输入。把"3 模型碰撞"和"拆解器"挪到架构师齐备之后（步骤3），否则测了也是空跑。集成合并随实现层一起做（步骤4），不单独成步——它强依赖 worktree 并行先就位。

## 关键设计决策

1. **流程为主轴，技术分类为辅**：六个阶段顺序推进，阶段内按角色并行。
2. **模型按能力评级推荐**：rating（SSS+~A）+ recommended_for 权威推荐，不强制分层。
3. **测试分多段**：实现期单元/集成测"对不对"，集成合并期跨工程师接口测"拼不拼得起来"，审查期全量回归+合规断言，验收期全方位+E2E 测"全不全/安不安全"。
4. **审查 AI 自动**：代码审查+架构合规+安全扫描不通过自动修，触顶/超时一律降级人工（升 GATE2），绝不放行进入验收。人工只在三个 GATE 介入。
5. **架构三人并行 + 合成**：系统架构、AI 架构、前端架构各看各的，合成器裁决。
6. **实现层单模型照规格施工**：不需要多模型碰撞，测试不通过自动修一轮。
7. **人工卡点不省**：GATE1/2/3 必须人审，AI 负责产出材料不替人判断。
8. **碰撞不滥用**：16 个角色只有 4 个用多模型。

## Observer 多角色对话流转

定义阶段是 Observer 和用户的一对一对话，4 个角色不是并行跑，而是按需切换身份。

### 切换逻辑

```
用户开口 → Observer（便宜模型，不带角色）
  │
  ├── 用户说"我想做..."    → 自动切到 产品经理，追问目标/范围/功能/成功标准
  ├── 产品经理产出 PRD 确认后 → 自动切到 交互设计师，画流程+页面树
  ├── 交互产出，Observer 问"要收UI偏好吗" → 用户给方向 → 切 UI 设计师
  ├── PRD 出来后              → 后台切 研究员（与交互/UI并行，不等用户）
  └── 用户想看调研结果        → Observer 展示研究员发现

切换规则：
  - 自动切换：基于对话上下文，上游产出完成 → 通知下游角色启动
  - 手动切换：用户说"让XX看看" → 直接切到指定角色
  - 回退：用户说"不对" → 切回上一个角色，带上用户反馈

角色状态机：
  idle → active（拿到上游输入）→ done（产出通过）→ locked（GATE1 确认后不可改）
           ↓
       blocked（等上游或用户输入）
```

### Observer 身份感知

Observer 每次回复前从项目目录读取当前阶段文档，自动感知"现在是谁、产出到了哪"：

```
项目状态示例：
  prd.json ✅         → Observer: "PRD已出，接下来我让交互设计师基于PRD画流程"
  interaction.json ⏳ → Observer: "交互方案生成中..."
  prd.json ✅ + interaction.json ✅ + ui_direction.json ⏳
                      → Observer: "交互方案出来了，UI方向还在收集中，要现在看交互流程吗？"
```

## 项目失败处理

### 失败类型与上限

| 场景 | 上限 | 超限后 |
|------|------|--------|
| 实现阶段测试修不过 | 自动修 3 轮 | 升级 → 打回架构重新拆任务 |
| 架构方案 GATE2 打回 | 重做 2 次 | 回到定义阶段重新澄清需求 |
| 验收不通过 GATE3 打回 | 重做 2 次 | 整个项目标记 BLOCKED，人介入决策 |
| 审查自动修不过（代码质量/测试） | 自动修 2 轮 | 仍不过 → 升 GATE2 人工兜底，不进入验收 |
| 模型 API 全不可用 | 等 5 分钟重试 | 暂停项目，通知用户 |
| 定义阶段聊不下去 | Observer 主动提"建议缩小范围/换个方向" | 用户选择：缩小 / 放弃 / 存草稿 |

### 项目终止状态

```
DONE       ← 正常交付
BLOCKED    ← 超限，需要人介入做决策（改需求/加资源/换模型/放弃）
ABANDONED  ← 用户主动放弃
DRAFT      ← 定义阶段中断，存为草稿
```

BLOCKED 状态下，系统保留所有中间产物，用户可随时恢复。

### 超时策略

| 阶段 | 超时 | 行为 |
|------|------|------|
| 定义 | 无硬超时（人在聊） | Observer 每 10 分钟提示"要继续吗" |
| 架构 | 30 分钟 | 3 个架构师并行，最慢的也超时了 → 合成器拿已完成的产出裁决 |
| 实现 | 60 分钟/工程师 | 单路超时不影响其他路，超时的那路标记失败 |
| 审查 | 10 分钟 | 超时一律判 FAIL（"审查不完整"），不进入验收，降级人工——打回实现修复或升 GATE2 兜底。安全/合规项超时绝不容许默认通过 |
| 验收 | 30 分钟 | 超时拿已出的检查项出报告，标记"验收未完成" |

## 测试用例生成

目标用户不会写测试。系统在架构阶段自动生成，人确认。

### 生成流程

```
架构文档出来 → 合成器顺便生成测试用例
  │
  ├── 从架构约束清单提取 → 单元测试骨架
  ├── 从 API contracts 提取  → 集成测试骨架
  ├── 从 PRD success_criteria 提取 → 验收测试用例
  ├── 从系统架构师 constraints(security 类) + 通用安全规则库 提取 → 安全测试用例
     （不依赖验收阶段的安全审计——那时还不存在；验收阶段安全审计师在此基础上做深度复核）
  └── 从交互设计 state_machine 提取 → E2E 测试骨架

输出：test_cases.json
  {
    "unit": [{"target": "模块/函数", "cases": [...]}],
    "integration": [{"endpoint": "GET /api/...", "cases": [...]}],
    "e2e": [{"flow": "用户登录→创建→查看", "cases": [...]}],
    "security": [{"check": "XSS", "target": "输入框", "cases": [...]}],
    "acceptance": [{"criteria": "用户能在3步内完成任务", "cases": [...]}]
  }
```

### 确认机制

GATE2 时一并给人看：架构方案 + 测试用例清单。人可以选择：
- 通过（全用自动生成的）
- 补充/修改（改完通过）
- 跳过测试（仅原型阶段，正式交付前必须补）

### 迭代

每次验收跑完，QA 工程师对比"人确认的用例"和"实际覆盖的"，自动建议补充缺失用例。

## 暂停恢复

### 项目持久化

```
.qidian/projects/<project_id>/
├── project.json           # {phase, status, created_at, updated_at, gate_status}
├── prd.json
├── interaction.json
├── ui_direction.json
├── research.json
├── architecture.json      # 合成器输出
├── test_cases.json        # 自动生成 + 人确认
├── tasks/                 # 每个 task 的状态
│   ├── <task_id>.json     # {status, assigned_to, worktree, attempts, result}
├── review_report.json     # 审查阶段产出
├── qa_report.json
├── security_report.json
├── lineage.json           # [{ts, actor, action, detail}] 全操作日志
└── checkpoint.json        # 当前中断点信息
```

### 恢复逻辑

启动时扫描所有非终态项目：

```
for project in projects:
    phase = project.phase
    gate_status = project.gate_status

    if phase == "定义":
        如果用户回来了 → Observer "上次聊到XX，要继续吗？"
        如果 7 天没人 → 标记 DRAFT

    if phase == "架构":
        架构师都跑完了 → 直接跳到合成器
        跑了一半 → 重跑没产出的，已产出的保留
        合成器跑完了 → 跳到 GATE2 等待确认

    if phase == "实现":
        有的 task 跑完了 → 只跑没完成的
        全跑完了 → 跳审查

    if phase == "审查":
        审查结果已出 → 跳到验收
        还没审查 → 重跑

    if phase == "验收":
        QA/安全出完了 → GATE3 等待确认
        没出完 → 重跑

    if phase == "GATE等待":
        展示当前产出 → 等人确认/打回
```

### 会话超时

```
GATE 等待 → 7 天无人 → 发通知 → 30 天无人 → 标记 DRAFT，清理 worktree
DRAFT → 保留 90 天 → 通知后清理
```

## 架构 → 任务拆解

### 架构文档到可执行 Task 的映射

系统架构师产出 task list 是自然语言描述，系统需要把它转成 `_exec.py` 能直接执行的结构化任务。

```
架构文档的 task 条目：
{
  "id": "task-3",
  "title": "实现用户认证 API",
  "description": "JWT based auth, POST /api/auth/login 返回 token...",
  "complexity": "medium",
  "phase": "backend",
  "depends_on": ["task-1"],
  "acceptance": "POST /api/auth/login 返回 200 + token，错误密码返回 401"
}

        ↓ 拆解器（合成器的子步骤）

可执行 Task（存入 tracker）：
{
  "id": "20260628_abc123",
  "project_id": "proj_xyz",
  "parent_task_id": "task-3",
  "description": "实现用户认证 API — JWT based auth...",
  "acceptance_criteria": ["POST /api/auth/login 200+token", "错误密码401"],
  "route_level": "cheap",       // ← 由阶段决定（cheap/strong），不再用 E/E+/D
  "depends_on": ["task-1的exec_id"],
  "sandbox": "worktree",
  "context": {
    "architecture_doc": "architecture.json",
    "relevant_sections": ["api_contracts[0]", "data_model.entities.user"],
    "test_cases": ["test_cases.integration[0]"]
  }
}
```

### 拆解规则

| 架构 task 字段 | 可执行 task 字段 | 转换逻辑 |
|---------------|-----------------|---------|
| `phase` | `route_level` | frontend/backend/data/devops → cheap（实现层统一便宜），不再用 E/E+/D |
| `complexity` | `max_retries` | low=1, medium=3, high=5 |
| `depends_on` | 拓扑排序 | 上游 task 执行完才能启动 |
| `acceptance` | `acceptance_criteria` | 直接映射 |
| — | `context` | 从架构文档提取该 task 相关的片段（不塞整份） |

### 跨阶段任务依赖

```
实现层 4 个工程师的任务是架构阶段拆出来的

如果验收阶段发现问题：
  → GATE3 按 issue.fix_route 分级：
     impl  → 回实现层，只重做有问题的 task（依赖该 task 的下游一并重测）
     design → 回 GATE2，架构师出修复方案 → 只拆出受影响 task
  → 其他 task 不变，已通过的部分不重测
```

### 上下文片段提取

拆解器从架构文档中只提取 task 相关的部分：

```
task "实现用户认证 API" → 拆解器扫描架构文档：
  ✅ 取：api_contracts 中的 /api/auth/* 条目
  ✅ 取：data_model 中的 User/Token 实体
  ✅ 取：constraints 中的认证安全约束
  ❌ 不取：前端组件树、路由设计（跟后端无关）
  ❌ 不取：AI model_strategy（跟业务无关）
```
