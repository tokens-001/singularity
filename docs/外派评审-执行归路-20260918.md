### ❷ 我说「没接」，实际是「接不了」

**我原话**：「验收层只报不改 + 闭环被砍 ⇒ 推进永远要人接手。」

**核到的事实**（这条是评审给的地基，我认）：

- `_run_verification` 的 QA 提示词里，`issues[].id` = **"约束标识"**；
  `validator.build_qa_report` 原样透传 ⇒ **QA 报告的 issue id 是约束 id**
- 而 `execution_judge.decompose_architecture` 交出来的**任务对象没有约束标识**
- `covers` 索引的是**调研报告的需求**，不是任务

⇒ **「哪条约束没过 → 该重跑哪个任务」这条边，在数据模型里根本不存在。**

所以 `workflow.handle_gate3_reject` 的 `impl` 分支只能写成
「把所有 DONE 任务 `force=True` 重置成 PENDING」——
**它的 docstring 写「只重做有问题的 task」，代码里没有这个筛选。**（这条我 09-18 上半天已读到，
但没把它跟"闭环为什么开不了"连起来。）

⇒ 不是"没人去接"，是**接不了**。差值很大：前者是排期问题，后者是**数据模型问题**。

## 二、它说重了的两处（我核完要收窄措辞）

### ① 「`validate.py` 是 9 行桩 ⇒ 那次硬化是装饰」—— 桩是真的，"装饰"说重了

桩确认存在（`data/knowledge/scripts/validate.py`，无条件
`print({"verdict": "通过"})`，注释自己写着 `ponytail: 默认通过，硬规则校验由
validator 主进程的 _hard_diff_rules 承担`）。

`validator.validate` 末尾那条判决梯子**确实有四个分支不可达**（"人工复核" / "信息不足" /
"未知" / else 兜底 —— 桩永远只给"通过"）⇒ **它这个数是对的。**

**但"装饰"说重了**，两点：

1. **故障态保护是活的** —— `_run_validate` 自己会在「脚本不存在 / 超时 / 解析失败」时
   返回 `{"verdict":"未知"}` ⇒ 走 `elif == "未知"` → `retry/abort`。
   **S5 那条「不默认通过」没死**，它死在梯子那层的只有**业务语义**。
2. **硬规则是真的** —— `_hard_diff_rules` 在主进程跑，`if not hard.get("passed"):
   verdict="阻断"; action="abort"`，**这是活的硬闸**。

⇒ 准确说法：**这不是"硬化是装饰"，是"一个接口还在、实现已搬走"的残留** ——
它让**业务语义级校验**这条能力看起来存在，实际没有。属「声明 vs 实际」那一族，成立，但没到"装饰"。

### ② 「`reset_count += 1` 无条件执行」—— 有守卫，说重了

代码里是：

```python
t = tracker.read_task(tid)
if t is not None and t.status == TaskStatus.DONE:      # ← 这个守卫在
    tracker.transition(tid, TaskStatus.PENDING, force=True)
    reset_count += 1
```

⇒ **不是无条件的。** 但它真正的点可能仍成立：`tracker.transition` 返回 `Optional[Task]`，
**这个返回值没判** —— 若它在不抛异常的前提下返回 `None`，`reset_count` 就会多算。
**这半条我没核，别当结论用。**
