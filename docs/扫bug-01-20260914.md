## 高

### 1. 刚跑完的成功任务会被误判成超时杀掉，成果整个丢弃
- 位置：`scheduler/orchestrator.py:466-468`
- 问题：超时检测循环对 `running_futures` 里剩下的 future 只看 `now - submitted_at > deadline`，**不查 `fut.done()`**。第一遍回收循环（:411-413）只 pop「当时已 done」的 future；finalize 里要跑 QA supervise（模型调用，秒级到分钟），一个长任务恰好在第一遍处理别人时完成、且 wall 时长已过 900s，就会被第二遍当超时：pop → 写 cancel → 转 FAILED「执行超时」→ salvage。**成功的 batch（含 merge_request）没人消费，改动留在 worktree 不合并**；而且残留的 cancel 文件会在下次人工 retry 这个任务时被 `_check_cancelled`（_exec.py:260-262）消费掉，retry 立即「被取消」。
- 怎么验：单测——造 fake future，`done()` 第一次返回 False、第二遍时 True，`submitted_at` 设成 901s 前；调 `_reap_futures`，断言任务被误标 timeout 且 batch 丢失（现状会）。

### 2. 「提前收尾」只有 openai_agent 生效，zhipu/anthropic/claude-cli 三条执行器照样干到被砍
- 位置：`scheduler/executors/base.py:128`（budget_s 只被赋值）；`executors/zhipu_api.py:104`、`executors/claude_cli.py:82`、`executors/anthropic_api.py:93`（各用固定 per-call 超时，每次 dispatch 从头算）；`executors/openai_agent.py:378`（唯一消费者）
- 问题：§67 的修法把 `budget_s` 传进了 `dispatch()`，但只有 openai_agent 读它。其余三个执行器每次 dispatch 重置预算，而 `_exec.run` 的 turn 循环（DEFAULT_MAX_TURNS=2）× fallback 链（:191 取前 3）× `_run_with_retry`（max_retries=3）叠起来轻松超 900s——主阵容若不是 openai-agent 型，任务照样被 900s 无声收割（正是 §67 修的那个病，只修了四分之一）。
- 怎么验：`grep -rn budget_s src/singularity/scheduler/executors/` 只有 base.py 赋值 + openai_agent 消费；或造一个 type=zhipu-api 的任务、mock `urlopen` sleep 250s 跑两轮 turn，期望 `error_kind="deadline"` 自收尾，实际等收割。

### 3. QA retry 的「重新入队」在同一轮调度里失效：任务被 `dispatched` 集合永久排除
- 位置：`scheduler/orchestrator.py:131`（只 add）+ `:82/:714`（`ready_tasks(exclude=dispatched)`）；`scheduler/_task_runner.py:337`（QA retry 转回 PENDING）
- 问题：`dispatched` 集合从不清空（grep 无 discard/remove）。finalize 把 QA-retry 任务转回 PENDING 时，其 id 已在 `dispatched` 里，`ready_tasks` 直接排除（tracker.py:346）→ 本次 run_queue 内永不再派发；`remaining` 为空就 break。web 模式要等整轮排空后由下一轮 `run_queue`（app.py:512）捡起——排着 50 个任务时 retry 1 号要等其余 49 个跑完；CLI 模式（_cli_tasks.py:155 单次调用）直接带着 PENDING 任务退出，重试永不发生。注释里写的「重新入队」名不副实。
- 怎么验：pytest——stub TaskRunner，finalize 里把任务转回 PENDING，跑 `_run_queue_v3`，断言任务在同一轮被再次 submit（实际循环直接 break）。

### 4. 存在 PAUSED 任务时调度循环 0.5s 一拍死循环、永不退出
- 位置：`scheduler/tracker.py:45`（PAUSED 在 `_SCHEDULABLE`）+ `:421`（`recover()` 只翻 `_INFLIGHT`，PAUSED 原样过重启）；`scheduler/orchestrator.py:711-719`
- 问题：重启后盘上有 status=paused 的任务（worker 线程已随进程死掉、没有 future），`ready_tasks` 会把它当 ready 返回 → `remaining` 非空 → 循环不 break；而 `_dispatch_ready` 对 PAUSED 两步 CAS 都不成立（:97 只认 PENDING/BLOCKED，:103 只认 ROUTED）→ 永不派发。结果 `_run_queue_v3` 以 0.5s 间隔空转到天荒地老，web 的 `_loop_worker` 卡在 app.py:512，reconcile / 记忆整合 / 交付推进全部停摆，且没有任何告警（`_warn_orphan_running` 只查 RUNNING）。
- 怎么验：写一个 `status: "paused"` 的任务 json 到 .qidian/tasks/，起线程跑 `run_queue({}, 1)`，观察永不返回；或单测断言 `TaskStatus.PAUSED in tracker._SCHEDULABLE` 且 `_dispatch_ready` 两步 CAS 均拒绝 PAUSED。

### 5. 暂停中的任务会被 900s 收割当超时杀死
- 位置：`scheduler/_exec.py:295-304`（PAUSED + 阻塞等待）+ `scheduler/orchestrator.py:466-490`（收割不看 PAUSED）
- 问题：`_check_paused` 无限轮询等恢复，但 orchestrator 的 900s 从 submit 起算、全文不认识 PAUSED。暂停超过剩余预算 → 任务被转 FAILED「执行超时」+ 写 cancel 标记 → `_check_paused` 轮询到 cancel → 以 `cancelled_during_pause` 终止。用户点了暂停、回来点恢复，任务已经死了，trace 里是「执行超时」。
- 怎么验：TASK_DEADLINE_S=60，任务第 1 轮后写 pause 文件，等 70s 再删 → 任务终态是 FAILED(timeout/cancelled_during_pause) 而非继续执行。

## 中

### 6. budget_s 也不覆盖委员会 / A 臂 / no_tools 路径
- 位置：`scheduler/_dispatch_exec.py:182-187`（committee/solo 收不到）、`:214-217`（只有单模型 fallback 循环传）、`:293`（`_run_no_tools` 调 `_run_executor` 不传 budget_s）
- 问题：委员会成员调用各自跑满单调用上限（claude-cli 300s / openai 240s），wave 数与 `_WAVE_TIMEOUT` 都不看任务级死线。带架构关键词、又没有 route_role 否决的任务（用户手打的「设计XX架构」类任务在执行阶段）进委员会后，整体墙钟可以越过 900s 被收割——与 #2 同族的第二处缺口。
- 怎么验：grep `_dispatch_exec.py` 里 budget_s 只出现在单模型那次 `_run_executor` 调用；对 `_dispatch_committee` 塞一个会 sleep 超预算的 stub，观察成员调用不被任务级预算截断。

### 7. 项目 JSON 的 load→改→save 不是事务，三线程并发丢更新
- 位置：`scheduler/project.py:526`（load 无锁）+ `:471-487`（save 只锁写盘段）；注释自己列出三个写者：调度循环 / `_merge_executor` / Flask 请求线程
- 问题：线程 A load 之后、save 之前，线程 B 完整 load→save，A 再 save 就把 B 的 phase/issues/review_failures/integrate_failures 整个盖掉（例：合并线程刚 set_phase(REVIEWING)+save，主循环线程拿旧副本 append issue 再 save → phase 退回 executing → 重新进 INTEGRATING 重复合并）。`_LOCK` 只挡住「同时写盘」，挡不住 lost update。
- 怎么验：pytest 起两线程各 200 次 load→append issue→save 同一项目，断言 issues 数 == 400（现状必丢）；或压测下抓 phase 回跳。

### 8. `escalation_exhausted` 已无生产者：D 方案自动修复、chancellor 升级告警成死分支
- 位置：`scheduler/_task_runner.py:259`、`scheduler/chancellor.py:77`（消费）；`scheduler/_exec.py:744-754`（生产者已改写 `no_escalation_path`，且 `escalate()` 恒 None）
- 问题：`_exec.py` 故意换了终态词，但两个消费者还在匹配旧词——「重试耗尽 + 有 D 方案 → 自动建修复任务」这条特性从改名那天起不可达；`tests/test_exec_internals.py:487` 手搓旧词喂 batch，测的是永远到不了的路（假绿）。
- 怎么验：`grep -rn "escalation_exhausted" src/` 只剩注释与测试手造；跑一次 escalation 耗尽的任务，term_reason 为 `no_escalation_path` 且不建修复任务、chancellor 不报 alert。

### 9. 删除失败任务会把依赖它的任务永久卡死在 BLOCKED，项目停在 executing
- 位置：`scheduler/tracker.py:261-266`（`_deps_satisfied`：dep 文件不存在 → False，永不满足）+ 消费方 `scheduler/_observer_tools.py:173-177`（批量删 status=failed 的任务文件）
- 问题：删掉 FAILED 任务后，所有 `depends_on` 它的任务：`_any_dead_dep` 查不到（None 不算死路）→ `_deps_satisfied` False → 标 BLOCKED 死等；不在 ready_tasks 里所以不可见、不会被级联失败。项目侧 `_auto_trigger_test_fix` 的 pending 判据（orchestrator.py:758-761，read_task None 被跳过）又把它当不存在——独立任务永久 BLOCKED；项目任务则让 pending 永不为空？不——它 read_task 为 None 时被跳过，项目能推进，但这个 BLOCKED 任务文件永远挂在盘上没终态。
- 怎么验：建 A（FAILED）← B（depends_on=[A]），删 A 的 json，调 `ready_tasks()` 断言 B 永不返回且状态恒 BLOCKED；再对该 task id 调一次批量删失败任务工具复现。

## 低

### 10. heartbeat 非原子写 vs check_stalled 并发读：活任务心跳可能被当损坏删掉
- 位置：`scheduler/witness.py:149`（`write_text` 截断重写）vs `:206-212`（读到半截 JSON → unlink）
- 问题：worker 线程写心跳的瞬间，web/observer 线程 `check_stalled` 读到截断文件 → 走「损坏即清理」把**活任务**的心跳 unlink，该任务到下一次 dispatch 前从 stalled 检测里消失（监测盲窗最长 810s）。
- 怎么验：并发压测 heartbeat+check_stalled，统计活任务心跳文件消失次数；或把 `heartbeat` 改走 `atomic_write_json` 后复跑。

### 11. 依赖阻塞的 merge 请求每个调度 tick 刷一条告警
- 位置：`scheduler/merge.py:120-124`（defer 即 warn）+ `scheduler/orchestrator.py:589/:722`（`_drain_pending` 每 tick 调 drain）
- 问题：blocked 请求留在队列里，每个调度循环 tick 都 warn 一次 `drain_dep_blocked`，alerts.jsonl 被刷屏、按 key 聚合后变成「常驻」假信号，淹掉真告警。
- 怎么验：造一个 deps 未 DONE 的 merge request 入队，跑 3 轮循环，数 alerts 里 `drain_dep_blocked` 条数随 tick 线性增长。

### 12. fallback 链被静默截断到前 3 个 agent
- 位置：`scheduler/_dispatch_exec.py:191`（`chain[:3]`，无注释无告警）
- 问题：用户在阵容里配了 4-5 个同层备用模型时，第 4 个起永远不被尝试，且无任何留痕——「为什么没轮到它」查不到。
- 怎么验：造 5 个全失败的 stub agent 跑一次 dispatch，数 breaker 里 record_failure 的模型数 == 3。

## 查过、确认没问题的点

- `tracker.read_task`（tracker.py:132-139）：文件不存在 → None（有 `p.exists()` 前置），损坏 → None，调用方的 `is None` 判法成立。
- `ready_tasks` 的 dead-dep 处理（tracker.py:350-360）：依赖 FAILED 会「降级运行」继续派发，不级联卡死——所以「依赖失败 → 循环空转」这个候选不成立。
- `_reap_futures` 正常分支的孤儿防护（:416-463）、`_strand_guard` 的 RUNNING 复查（:379-386）：最近修过，逻辑闭合。
- `MergeQueue.drain` 的 defer 判据（merge.py:113-133）：注释所述修复属实，`deferred >= len(queue)` 会 break。
- `project.save` 的跨进程 tmp（project.py:474-487）与 `tracker._LOCK`（tracker.py:20）：写盘原子性没问题（问题只在 #7 的读-改-写事务性）。
- `_model_breaker`（冷却/半开）、`_token_budget.record` 的锁与折叠落盘：没发现计数或边界错误。
- `_planner._topo_sort`/`materialize_plan` 的环检测与深度上限：成立（部分失败时子任务仍会被调度这一点在 materialize_plan:126 注释里自认，触发面是磁盘异常，未列入）。
- `openai_agent` 的 `_cap = min(240, 剩余预算)`（:932-936）与轮间看表（:385/:475）：§67 修复在该执行器内自洽。
