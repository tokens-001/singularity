# 「一次多动作」A/B —— 结果（2026-09-12）

> **一句话**：**没看到可观测的效果**。而且我们原来那个"不开开关时模型每轮只发 1 个工具"
> 的前提，**被数据证伪了** —— 基线本来就在合并。

## 想验什么

`QIDIAN_BATCH_TOOLS=1`（`executors/openai_agent.py`）给 SYSTEM_PROMPT 加一段
"互不依赖的工具调用一轮发完"。**假设**：开了之后每轮发多个工具 → **轮数变少**。

原假设的依据（现已作废）：探路3 第一轮重流程下 T3 的 `tool_batches = [1,1,1,1]`，一轮一个。

## 怎么跑的

- 两臂**同一份需求**、**同一个 flow（`light`）**、**同一份代码**，**只翻一个环境变量**
- 需求：`wordcount.py`（统计行/词/字符 + `--json`）+ 一个 pytest 文件
  —— 比 `txtstat` 小，为的是**不撞 900s**（第一轮撞了，见 §59）
- 两臂的后端都**用 `ps eww` 确认过环境变量真的在进程里**（不是"应该传进去了"）

## 数据（**按任务配对**，不是拿平均数硬凑）

两臂的任务分解是**结构平行**的（T1 实现 / T2 测试 / T3 README），所以能一一对上。

| 任务 | A 臂（无开关） | B 臂（开开关） |
|---|---|---|
| T1 实现 | 3 轮 · `[2,1,2]` · 合并 **2** · 共 5 次调用 | 3 轮 · `[2,1,1]` · 合并 **1** · 共 4 次 |
| T2 测试 | 4 轮 · `[2,2,1,1]` · 合并 **2** · 共 6 次 | 3 轮 · `[2,2,1]` · 合并 **2** · 共 5 次 |
| T3 README | **无 trace**（被我取消 + 重启杀掉） | 4 轮 · `[2,2,1,2]` · 合并 **3** · 共 7 次 |
| **合计** | **7 轮 / 合并 4 轮 = 57%** | **10 轮 / 合并 6 轮 = 60%** |

## 结论

1. **没看到效果。** 合并率 57% vs 60%，每轮调用数 1.57 vs 1.60 —— **差异在噪声范围内**。
2. **配对内部方向还不一致**：T1 是**不开开关反而更合并**（2 vs 1），T2 打平。方向乱了 ⇒ 更像噪声。
3. ⚠️ **更要紧的是前提被证伪**：**不开开关时基线自己就有 57% 的轮在合并**。
   原假设"基线从不合并"建立在**一个样本**（重流程那轮的 T3）上，是错的。
   ⇒ 这个开关要撬动的空间，**本来就比想象的小**。

## 局限（别把这当成定论）

- **样本极小**：A 臂 2 个任务、B 臂 3 个任务，各跑一次。**这不是结论，是"看一眼"。**
- **A 臂少一个样本是我造成的**（我中途取消任务 + 重启后端），**不是开关的效果** —— 别误读。
- B 臂的项目跑到了 `done` 而 A 臂没有，**同样是我造成的**，不是处理效应。
- 任务规模单一（单文件 CLI）。**换规模未必成立。**
- 度量本身有个已知坑：超时任务的 `tool_batches` 恒为 0（`docs/防御模式.md` §59），
  本轮已把超时任务排除出样本。
