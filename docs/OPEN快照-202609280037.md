## 🔴 停车（09-21 实测踩了两次，先看这个）

**「暂停」和「停整轮」是两件事，别混：**
- **任务级暂停是有的**（`POST /api/tasks/<id>/pause`，界面上是任务页那个按钮）。但它
  ① **不即时** —— `_exec._check_paused` 在**每轮开头**才读，`API 返回原文就是「当前 turn 结束后生效」`，
    飞出去的那次调用拦不住（单次最长 240 秒）；
  ② **是"占着位子等"** —— 实现是**卡住那个 worker 线程**每秒轮询，并发只有 2
    ⇒ 暂停两个任务 = **整个池子停摆**（不是腾出位子）；
  ③ **逐任务的**，不拦观察者建任务、也不拦它拉循环。
- 🔴 **没有任何"项目级/整轮"的停** —— 所有 `projects/<id>/…` 路由里只有
  `gate-confirm` / `run-phase` / `start` / `files` / `diff` / `cost` / `lineage` / `snapshot` / `traceability`
  / `lineup` / `flow-weight` / `research-raw` / `history`，**没有 pause、没有 stop**。
  全局只有 `/api/loop/stop`，而**观察者会把它拉回来**（见上）。
  ⇒ **"别烧钱了"这个需求现在只能靠杀进程。** ✅ **09-21 已修 `f7fdf49e`**（用户选 A）：
    `POST /api/projects/<id>/stop` —— 给该项目所有非终态任务发取消。
    **自己只有一句实质代码**（逐条喂给已有的 `task_cancel`），连"哪些算终态"都不自己判
    —— 第一版抄了份终态清单，而那正是我在同一个函数的注释里刚警告过的「两份逻辑迟早会漂」。
    5 条测试（含「`_check_cancelled` 真的拦得下」+ HTTP 路由两条接线）· **三次变异各咬中**
    （不喂 task_cancel / 两栏记反 / 路由空转）· 全量 1929 绿 · `make check` 过。
    ◐ **09-22 半验**：真点了两次（6 个 + 8 个取消信号），HTTP 200 + JSON 正常 ·
    `alerts.jsonl` 落 `project_stopped` · 任务真转 failed · **侧车无新文件 = 一次都没派发**。
    ⚠️ **只验了一半** —— 停的全是**还没派下去的**，"停一个正在跑的"没走到（那才是当初的动机）。
  🔵 **09-21 想清了最小解法，而且比我一开始想的更小**：**关键事实 —— 一个任务一旦进了
  `_exec.run()` 的回合循环，它就不再经过调度循环了**（`_exec` 自己一轮一轮地调 `dispatch()`，
  直到预算用完）。⇒ **"停循环"只能拦住"还没派下去的"**，拦不住正在跑的。
  而 `_check_cancelled` 是**每轮开头**读 `CANCEL_DIR` 的 ⇒ **写取消标记才拦得住在跑的**。
  ✅ **最小方案：加一个 `POST /api/projects/<id>/stop`，只做一件事 —— 给该项目所有非终态任务写取消标记。**
    为什么这就够：在飞的下一轮开头退出（最多再烧完当前这一次调用）· 排队没轮到的 worker 一起来
    就看到标记、立刻返回 · 还没派的 `ready_tasks` 不返回 RUNNING ⇒ 不会再被派 ·
    **调度循环照常跑也无害**（这项目没活干，它自己空转）⇒ **观察者那句"确保循环在跑"就不用去动它了**。
  ⚠️ **两条边界要你选**（这决定做哪一个）：
    · **「停」= 取消标记**（最小，上面那个）：语义是"人工取消" ⇒ 以后返工重置时这批任务
      **不会被重新拉起**（`held_back_user_cancelled`）。要接着跑得单独清标记。
    · **「暂停」= 项目级 pause 标记 + 派发前读一眼**：语义是"待会接着跑"，任务状态保留、
      标记删掉就续上。多一处读、但保住"可恢复"。
    ✅ **未定已定：用户选「停」**（09-21）。"暂停到一半接着跑"那套**没做**，理由照旧：
      为想不出使用场景的灵活性多写一套状态不划算；真出现需求时，(A) 的标记加个字段就能升上去。
