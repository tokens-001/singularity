# 经验该分层存 —— STAIR 那篇能借鉴什么、不能借鉴什么

> 2026-09-12。起因：看了《Reusing Past Repairs Through Hierarchical Trajectory Abstraction
> for Coding Agents》（arXiv 2607.29658）。
> 它批评的"平铺流水账"，**比我们现在做的还厚一层** —— 我们现在连流水账都没有。
>
> **本文只出方案，不动代码。**

---

## 一、论文做了什么（自报数字，我没跑过）

把历史修复轨迹切成**三个阶段**（定位 / 规划 / 执行+验证），每段单独建一棵**多级树**：
底层是单个动作（想了什么、做了什么、看到什么），往上逐级归纳，到顶只剩 2 个根节点。
每个节点带四样：**意图 / 关键动作 / 适用条件 / 常见坑**。

用的时候：按相似度捞 → 再用模型筛掉"像但不适用"的 → **再让模型改写成针对当前问题的具体计划** → 才喂给干活的智能体。

**自报成绩**：SWE-bench Verified **81.2%**（MiniMax M2.5）/ 79.2%（GPT-5），同基座比原来 +6.6 / +3.6；
**换个智能体、不改一行代码**，75.8% → 81.0%。

**消融（125 题，最能说明问题的一张表）**：

| 怎么存 | 通过 | 差 |
|---|---|---|
| **完整分层** | **100（80.0）** | — |
| 只存最底层 | 80（64.0） | −16.0 |
| 只存中间层 | 76（60.8） | −19.2 |
| 只存最高层 | 73（58.4） | −21.6 |
| **原始流水账** | **72（57.6）** | **−22.4** |

## 二、我们现在存的是什么（源码核过）

| 层 | 实际存了什么 | 在哪 |
|---|---|---|
| **原始轨迹** | **全都有** —— `agent_output` / `changed_files` / `validation` / `unverified` | `.qidian/traces/*.json` |
| 事件节点 | `content` = 任务描述，**写盘时截断到 200 字** | `EventNode.to_dict()`（`_memory_core.py:109`） |
| 经验记录 | `description` + status / model / elapsed_ms / tokens / failure_mode / files_changed | `archive_experience`（`_memory_experience.py:65`） |
| **真正进 prompt** | **任务描述的前 80 字** | `pre_search.py:56` |

**一句话**：原材料（轨迹）躺在磁盘上，**记忆系统从来没吃进去过**；它存的是标题，吐出来的还是标题。

`rebuild_from_traces()` 是唯一会回读 traces 的路径，但它只取
`task` / `changed_files` / `final_status` / `route` ——
**`agent_output`（"上次到底怎么修的"）从来没进过记忆。**

> 所以差距比论文那篇批评的更大：论文说的是"别存流水账"，
> 我们**连流水账都没存** —— 存的是流水账的标题。

## 三、借鉴方案（分三步，每步可单独停）

### 第 1 步：先把原材料喂进去（最小改动）

让归档 / 重建路径把 `agent_output` 也吃进事件节点。

- **不做任何抽象** —— 先让"怎么修的"这条信息别丢
- 代价：存储涨（一条 trace 现在 ~20 KB；截断到比如 2000 字）
- 风险：低。就算不抽象，全文检索也强过只有标题

### 第 2 步：按阶段切，不按任务切

现在**一条记忆 = 一个任务**。论文是**一个阶段一条**。
我们这边阶段是现成的：调研 / 架构 / 执行 / 审查。

- 好处：能回答"上次**架构**这步是怎么想的"，而不是"上次那个任务"
- 代价：条数 × 阶段数

### 第 3 步：分层抽象（论文的核心，也最贵）

每条阶段轨迹 → 底层动作 → 中层策略 → 顶层原则。

- 论文用 GPT-5 离线做：**≈ $0.44 / 条轨迹，全量 479 条 ≈ $211**
- **我们的量级**：单项目预算 `token_budget_total = 5.0`；今天这轮跑到现在 **$0.005**
- ⚠️ **这一步建议先否掉**：论文是拿 479 条轨迹换来 ≈$211 的原料。
  我们 `events.json` 才 73 条，**其中 62 条连 status 都没有**（见 `_memory_lifecycle.py:71-74` 的注释）。
  **先做第 1、2 步攒样本，够料了再谈第 3 步。**

## 四、不能照搬的三点

1. **论文限在同一仓库找历史**，我们跨项目找（`find_similar_across_projects`）。
   而消融显示**最高层（最能跨项目那层）单独用最差（58.4）** ——
   "跨项目检索"这个方向本身就该打问号，不是无脑加强。
2. **论文没有记忆生命周期**，我们有（`_memory_lifecycle` 的 hot/warm/cold、`_evict_if_needed`）。
   照搬会丢掉我们比它多的那块。
3. **论文的"计划"是喂给单个智能体当提示**，我们是**多阶段流水线**（架构 → 执行 → 审查）。
   计划该落在哪一步、谁负责改写，需要重新设计，**不是接个 prompt 就完事**。
