## ② `Async.tsx` 异步语义专审（九步都立在它上面）

**结论先行**：四态**渲染判据**层是干净的 —— `Loadable` 把"空"做成 ready 相的取值而非第四相、`AsyncBoundary` 的空判据是 `length === 0`、error/staleError 两条边界都有测试钉着（`Async.test.tsx` 7 条 + `McpTab.test.tsx` 14 条，我逐条读过，断言的是文字不是颜色）。但 `useResource` 的**时序层零防护** —— 在这个"SSE + 轮询 + 手动刷新"三路并发的前端里，这不是边角料，是九步铺开后每个页面的默认姿态。逐题说：

### ②-1 并发调用：无条件 `setState`，旧响应盖新响应（④a 的直接证据）

`load` 的成功路径是 `setState({ phase: 'ready', data })`，**无条件**；没有序号、没有 abort、没有"这还是不是最后一次请求"的判断。req#1（慢）和 req#2（快）并发时，#1 后到照样整包覆盖 #2 的新数据。同仓现成的解法就是 `Chat.fetchSeq` / `Projects.detailSeq` 的「`const seq = ++ref.current` … `if (seq !== ref.current) return`」，原语没有等价物。

### ②-2 反向同样中招：旧失败污染新成功（staleError 误报）

req#2 成功（进 ready）之后 req#1 才失败 → catch 里 `prev.phase === 'ready'` 成立 → `{ ...prev, staleError: raw }` —— 在**最新**的数据头上挂一条「刷新失败：… —— 下面还是最近一次成功加载的数据，不保证是现在」。**那句话在"旧失败后到"场景里本身就在撒谎**：屏幕上恰恰就是最近一次成功加载的数据。根因和 ②-1 同一条：状态机只看 `prev.phase`，不问这次结果属于第几号请求。注意：今天 `Tasks`/`AppLayout` 的"再取失败只 toast"**没有**这个误报模式 —— 铺开 useResource 会**新增**一种说谎，不只是"洞照旧"。

### ②-3 `reloading` 不是计数，是单布尔

两次 `load(false)` 并发：先结束的那个 `finally { setReloading(false) }` 把还在飞的那个的"在途"状态抹掉 —— 刷新按钮提前恢复可用、琥珀条出现时机错位。且 `load(true)` 完全不碰 `reloading`（只有 else 分支置 true），但 `finally` **总是**清它 —— initial 请求在飞时，任何一个更早的 reload 的 finally 都会把 `reloading` 清掉。谁后结束谁说了算，语义是"碰巧对"。

### ②-4 `initial` 的语义边界：意图参数，撞上相位机

`initial=true/false` 表达的是**调用方意图**，但所有落点只由 `prev.phase` 决定，交叉情形 README 的四态表一条都没覆盖：

- prev=ready 时 `load(true)`（错误态重试的正规用法之外若被误用在刷新上）会把数据整个吹掉进 loading —— 样板自己用 `load(false)` 做刷新避开了，但这只是约定，不是约束；
- initial 请求在飞时插进一个失败的 `load(false)`：prev 是 loading → 直接转 **error 相** —— 后台一次失败把首屏劫持成红字，随后 initial 成功又翻回 ready，闪一遭；
- 反过来 prev=ready 时 `load(true)` 失败 → 落 **staleError** 而非 error —— 用户明明点的是「重试」，看到的却是「刷新失败」琥珀条。能自圆，但语义由**到达顺序**决定，不是由意图决定。

### ②-5 卸载后再 setState：React 19 下无害，但请求不取消

`package.json` 是 react `^19.0.0`，React 18 起卸载后 setState 已是静默 no-op（警告都移除了），closure 之外无泄漏 —— **正确性上不是问题，不用修**。但没有任何 AbortController，fetch 本身照跑。另外 StrictMode 下这更是常态而非异常：`main.tsx` 全树包 `<React.StrictMode>`，dev 下 `useEffect(() => { void load(true) }, [load])` **双触发** —— 每次挂载都真有两只并发 load。`Async.test.tsx` 的 7 条全是串行 await 的时序、没开 StrictMode，**并发场景零覆盖**。

### ②-6 忘接线 = 永远转圈

state 初值 `{ phase: 'loading' }`，调用方若忘写 `useEffect(() => load(true))`，`AsyncBoundary` 就渲染一个**无超时的**「正在加载…」—— #16（Alerts 永远转圈）的形状被原语原样复活。低风险（测试能抓），值得进 README「已知边界」。

### ②-7 与 `fetchSeq`/`detailSeq` 打架吗？—— 打架，且原语的 API 让调用方没处安放序号

`load` 内部包 fetcher、返回 `Promise<void>`、结果只走 setState。调用方想复刻 fetchSeq 的"丢弃过期响应"只有两条路，都不通：
1. 在 fetcher 里判序号然后 **reject** → 触发 staleError/error 相 → 误报（②-2 同款）；
2. 过期时 resolve 一个哨兵值 → 类型上必须返回 `T`，且成功路径照样无条件 setState，哨兵数据照样进 ready。

**最小修法**（样板是 ⑥ 的产物、归你改，我只提不动手）：`load` 里加 `const mySeq = ++seqRef.current`，两个 setState 前各加 `if (mySeq !== seqRef.current) return`；`reloading` 改成在途计数（或 `finally` 里判 `mySeq === seqRef.current` 才清）。约 4 行，API 不变，README 的四态表一个字不用改。另建议补两条并发测试：慢请求后到不覆盖新数据；旧失败后到不污染新成功。

## ③ 铺开方案的内部一致性（九步 × 15 不该动 × DoD）

按杀伤力排序。C1–C4 是**会互相打架、必须改字**的；C5–C7 是措辞级。

### C1（最重）第 9 步会把 `SkillsTab` 打回"整页静默空"

第 9 步给 `api.skills` 加**缺键 throw**，而 ④2 冻结 `SkillsTab.tsx`（理由："刚修+5 条测试"）。它的 `fetch` 是 `await Promise.all([api.skills(), api.agents()])`，**无 catch** —— 缺键 throw 一落地，SkillsTab 从"正常页"变 "unhandled rejection + 「技能 (0)」+ 全页空白"，**正是全方案要杀的那个病**，出现在一张"不许动"清单保护的文件里。它的 5 条测试全在 mock `api` 层，运行时的形状漂移一条测不到。第 9 步的自辩逻辑（"1-8 先把消费端 error 态立起来，api 层才敢 throw"）**漏数了 SkillsTab 这个消费端**。修法三选一：step 9 的 throw 清单里划掉 skills；或 ④2 给 SkillsTab 解冻、给它的 `Promise.all` 补 catch；或 DoD 里写明"skills 维持现状不 throw"。
同类次级暴露面：`api.projects` throw 之后，`AppLayout.loadProjects` 只有 `catch → toast`（见 ①#14），侧边栏不会说人话；`Chat.fetchProjects` 同（catch → toast，主对话区无碍，可接受）。

### C2 第 6 步 #14 的修法按字面做，会造出新的"读不到=没有"

#14 的处方写的是"项目列表**空态文字**"。但失败路径和真空路径在 `AppLayout` 里是同一个 `projects=[]` —— 空态文字一上，后端宕机时侧边栏渲染「暂无项目」：**step 1 样板刚在全站消灭的病，在 step 6 自己手里复活**。必须写成"空态只在 ready 相显示"，或者 #14 直接升级成错误态（反正 C1 已经要求 `api.projects` 的消费端能接 throw）。

### C3 第 4 步 vs 规矩 7：`detailSeq` 悬在两句话中间

规矩 7（④0 红线）："竞态序号（`fetchSeq`/`detailSeq`）这些刚修好的时序件**不碰**"。第 4 步的作业面（#7 详情区）**正是** `Projects.toggle` 里 `detailSeq` 那一段。方案没有任何一句话说明二者如何共存 —— 而 ④1 第 5 步的口风（"fetch 包进 `useResource`"）会把执行人往"顺手把 toggle 的手写 fetch 也换掉"上带。换了 = 把刚修好的时序件替换成一个无竞态防护的原语（②-1/②-2），**比不动还坏**。修法：step 4 加一句"详情区保留 `toggle` 的 `detailSeq` 手写 fetch，只加错误渲染与重试；`useResource` 只用于列表"。详见 ④(b)。

### C4 第 7 步误诊：files 侧不是它以为的那个正面样板

#15 说"diff 侧没跟上自己（files 侧有 error 优先判据且注释写得很好）"。baseline 的事实是：**diff 侧已经有一模一样的 `if (d.error)` 分支 + toast**（和 files 树侧同款、同注释风格），两边失败后都落"toast 一声 + 空态文案"（树侧→「暂无文件」，diff 侧→「无变更记录」）。`FilePanel` 里真正当得起"正面样板"的是**文件内容侧** `openFile` 的 `setFileContent(`无法读取: ${d.error}`)` —— 内联、持久、可见。所以：
- #15 的**症状**成立（失败确实渲染成「无变更记录」）；
- "files 侧做对了"的对照**不成立**（树侧同样病）；step 7"照抄同文件 files 侧"按树侧抄 = 抄个寂寞（现状已是那样），按 `openFile` 抄才对。step 7 必须把"抄谁"写死，否则 DoD-5（停后端每一页说人话）在 FilePanel 上过不了。

### C5 `AsyncBoundary` 的数组约束 vs 步骤 2/4/8 的资源形状

`AsyncBoundaryProps<T extends readonly unknown[]>` 把空判据焊死在 `state.data.length === 0`。但 Usage 的资源是 `{ models, totals, days, earliest }` 复合对象、Projects 详情是对象、Alerts 是 groups —— README 的 `listState` 重切手法能救（样板 McpTab 自己就是靠这个过的，还为此踩过一次"exclude 藏类型错误"），可 ④1 第 2/4/8 步**没有一句**提到这个手法。鉴于教训恰恰是"这种约束错位 tsc 不一定叫"，建议：要么每步写明"主列表视角重切"，要么给 `AsyncBoundary` 加 `isEmpty?: (data: T) => boolean` 谓词、一次解决。

### C6 规矩 7 的"SSE 接线不碰" vs 第 3 步的必然动作

`Tasks` 的再取路径就是 `useSSE(() => { fetch(false) }, …)` + `setInterval` 轮询 + `act`/`create` 后的 `fetch()` —— 换 `useResource` 就**必须重指这些回调**。规矩 7 想说的应该是"别动 `useSSE` 内部与事件语义"，但字面上跟第 3 步直接冲突，执行的人只能靠猜。建议改词："SSE **订阅**不动；回调里调的取数函数可以换名，事件 kinds/debounce 不许变"。

### C7 三处小账

- ④2 GatePanel 行："把『像不像一份报告』的判据抽成共享 util **供 #17 用**" —— #17 是 api 层缺键 throw，跟 `GatePanel` 的 `qaUnverifiable`（判 QA 报告形状）对不上号，交叉引用悬空。
- ④0-2 的四条命令含两条样板专用，而第 1 步上位后样板目录即删 —— "样板期"实际上只有第 1 步本身；命令表措辞会让人以为贯穿九步。
- 测试增量"每步 4-8 条、完工 ~110（现 71）"：若样板的 21 条按 DoD-3 进默认收集，第 1 步后基线就是 92，再 8 步 ×4-8 → **124–156**，"~110 上下"偏低。不影响方向。

### DoD 自身没有毛病，但有一条要靠 C1–C4 改完才可达

DoD-5（停后端刷新，每页说人话、无「暂无 X」、无永远转圈）—— 按 C2/C4 的现状字面执行反而过不了（侧边栏「暂无项目」、FilePanel 空态）；DoD-1 的"#18 有书面不改理由"成立（④1 里"暂不动"就是）；DoD-3 与 README §五的三步提升互洽（两处 exclude 我核过：根 `tsconfig.json` 与 `vite.config.ts` 的 `test.exclude` 各一行，确实为样板而设）。

## ④ 三条线索，独立判真伪

### (a) `useResource` 没有竞态防护 —— **成立**

证据：`load` 成功路径 `setState({ phase: 'ready', data })` 无条件执行，无序号、无 abort、无过期丢弃。慢的先发后到整包覆盖新数据（②-1）；连错误侧都是"后到说了算"（②-2 的 staleError 误报）。`Chat.fetchSeq` / `Projects.detailSeq` 恰是同仓对这条洞的标准答案，原语没抄。

### (b) 方案自己前后打架（规矩 7 vs 第 4 步） —— **成立（按"未调和的矛盾"算）**

规矩 7 点名 `fetchSeq`/`detailSeq` 不碰；第 4 步的作业面正是 `Projects.toggle` 里 `detailSeq` 那一段（#7 的空白展开区就是它的失败分支）；方案没有一句话写"detailSeq 保留"。按第 5 步"fetch 包进 useResource"的惯性执行，`detailSeq` 大概率被无防护原语替换 —— 那不是"不碰"被违反一下，是**把刚修好的时序件拆了换上更裸的**。你说的位置对、矛盾真。唯一要补的精度：第 4 步**列表半边**（projects 列表，今天本无序号）换 useResource 并不违规，违规的触发点是**详情半边** —— 所以这不是"方案必错"，是"方案必须补一句才不出错"（C3 的修法）。

### (c) 洞是活的：`Tasks`/`AppLayout` 的再取路径会把它复制进 9 个文件 —— **成立，且比原话更准一档**

- `Tasks`：今天就没有序号。`fetch` 同时被挂载 `useEffect`、`useSSE`(debounceMs 400)、`setInterval` 10s（SSE 断时）、`act`/`create` 后的手动 `fetch()` 调用 —— **竞态今天就在**，不是换上 useResource 才有。
- `AppLayout`：`loadProjects` 被 `setInterval(loadProjects, 10000)` 和 `useSSE(loadProjects, { debounceMs: 400 })` 两路调 —— 同样无序号，慢请求 >400ms 就有重叠窗口。
- 所以准确的说法是：useResource **不引入**这条洞，它把"无防护"**制度化**并复制到 9 个文件；而且按 ②-2，还**新增**今天没有的 staleError 误报模式。三路调用里"慢的先发后到"在这两个文件不是理论值，是每周都在发生的调度。
