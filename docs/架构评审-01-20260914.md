## 2. 第 1 题：值得做的 2–3 个方案（避开已实现的 1、2 号）

### α. 对账仪器"常开化"——把方案 1 剩下的 20% 补完

**改哪里**：`orchestrator._run_queue_v3`（`orchestrator.py:693-725`）的 `while True` 顶部；`reconcile_projects`（`:525`）加第④项检查。

**现状的洞**：`reconcile_projects()` 只在 `app.py` 空转分支 `idle_ticks % 100 == 0` 时调（约 5 分钟空转一次）；`_warn_orphan_running()` 只在 run_queue 退出那一刻调（`orchestrator.py:716`）。**忙时——恰恰是孤儿和超时的高发期——两台仪器都不跑**。一个连续喂任务的队列可以让 run_queue 几小时不返回，对账就几小时不发生。

**大致怎么改**：

```python
# orchestrator.py _run_queue_v3 的 while True 顶部
now = time.time()
if now - last_reconcile > 300:          # 墙钟触发，不挑空转
    last_reconcile = now
    try:
        _reconcile_inloop(running_futures, pending_batches)
    except Exception as e:
        witness.warn("orch", f"reconcile_inloop:{type(e).__name__}:{e}"[:160],
                     key="reconcile_failed")     # 复用已有 key，别劈开常驻分组

# _reconcile_inloop 做两件事：
# ① 升级版孤儿探测：磁盘上 status==RUNNING 的任务 id，
#    减去 running_futures 里的 task id、减去 60 秒内刚 submit 的
#    （submit→running_futures 登记之间有窗口，直接比会误报），
#    差集非空 → 沿用 key="orphan_running_task" 告警（只报一次/任务，抄 _orphans_warned）。
# ② 调 reconcile_projects()，并加第④项：
#    磁盘上 RUNNING 且 updated_at 距今 > TASK_DEADLINE_S 的任务
#    ——那是"收割器看不见的任务"（有 future 的会在 900s 被收，
#    没被收说明它不在 running_futures 里，正是 §65 的形状）。
```

**怎么验证**：守卫测试（抄你们自己的变异验证规矩）——造一个假 RUNNING 任务 json（`updated_at` 设 1000s 前），跑一次 `_reconcile_inloop`，断言 `alerts.jsonl` 里出现 `orphan_running_task`；再把同一个 id 放进 `running_futures`，断言不告警。变异验证：删掉墙钟触发那三行 → 红。
**新静默失败自查**：(i) 对账自己抛 → 已被 `key="reconcile_failed"` 盖住（你们 09-13 已加）；(ii) submit 窗口误报 → 60 秒宽限 + 与 `dispatched` 集合求交；(iii) 常驻刷屏 → 沿用每任务只报一次；(iv) 注意别在 `_reconcile_inloop` 里读 `.result()`——只看 `fut.done()` 和 task id 集合，不消费结果，否则会改变收割语义。

### β. future 的异常必须有人读——方案 4 的最小切片，专补守卫自认的盲区

**改哪里**：`orchestrator._dispatch_ready`（`orchestrator.py:130` 登记 future 处）+ `_reap_futures` 超时分支。

**依据**：`test_no_silent_except.py` 的 docstring 自己写着射程边界——"**future 级吞噬（.result() 永不被调）明确不在射程**"。而 §59 实测过它的代价：超时分支 pop 掉 future 后 `fut.cancel()` 对已在跑的线程**必然失败**（Python 机制），线程继续跑、继续抛，**异常永远无人读**——和"静默 except"是同一种沉默，只是发生在 future 层。

**大致怎么改**：

```python
def _drain_future_exception(tid: str):
    def _cb(fut):
        try:
            exc = fut.exception()          # 读走它，别让它无声消失
            if exc is not None:
                witness.warn("orch",
                    f"orphan_future_exception:{tid}:{type(exc).__name__}:{exc}"[:180],
                    key="orphan_future_exception")
        except Exception:
            pass
    return _cb

# _dispatch_ready 登记处加一行：
running_futures[fut] = (t, route, snap, pre, time.time())
fut.add_done_callback(_drain_future_exception(t.id))
```

超时分支 pop 之后再跑的线程抛了异常，callback 仍会响（add_done_callback 挂在 future 上，不受 dict pop 影响）。

**怎么验证**：submit 一个必抛的假任务、不收割，断言告警出现；变异验证：删 `add_done_callback` 那行 → 红。
**新静默失败自查**：callback 自身抛 → 已包 try；某类任务常态性抛会让 key 常驻 → 那正是 `alert_summary` chronic 栏该接住的信号，不是这条方案的缺陷。
**顺手提一句**（同族）：`with ThreadPoolExecutor(...) as pool` 的 `__exit__` 是 `shutdown(wait=True)`——如果 `while True` 里冒出未兜住的异常（大都有兜底，但 `_dispatch_ready` 里 `route()` / `pre_search()` 若抛会直接冒出去），run_queue 会**先等最慢的任务跑满 900s** 才把异常交给外层 `loop error` 兜底。方案 4 包一层时要把 shutdown 策略显式化（`wait=False, cancel_futures=True` 或独立 daemon 池），别让"兜底日志晚 15 分钟"成为新的观测盲区。

### γ. phase 写入点矩阵守卫——不改运行代码，收"两套驱动"的策略漂移

**改哪里**：新增 `tests/test_scheduler/test_phase_writer_matrix.py`（零运行时代码改动）。

**做法**：AST 扫全仓 `set_phase(` 调用点，按 `(文件, 函数, 目标 Phase)` 建**棘轮基线**（机制整个抄 `test_no_silent_except.py`，包括 `test_baseline_keys_are_wellformed` 那种键校验）。再加一条语义规则：**REVIEWING 的出边只允许出现在 `workflow.py`**（统一成"只有 `run_test_fix_loop` 能出 REVIEWING"，消灭 `run_phase` 直推 GATE3 那条与 orchestrator 行为不一致的路——`_gate3_admission` 那层补丁就能退役）。

**怎么验证**：变异 = 在任意文件加一行 `proj.set_phase(Phase.GATE2, "test")` → 红。
**新静默失败自查**：基线文件烂掉 → 键格式校验守卫（抄现成）；"改文件名导致基线失效" → 基线不含行号（同 silent-except 的做法）。

## 7. 第 6 题：「默认怀疑」怎么落地而不糊死告警筛子

你们的翻转（"没报错就是没事" → "拿不出证据就是有问题"）落地时，**关键是按成本和噪声分三层投放，而不是平推成"到处加告警"**：

1. **第一层：从状态重算的报表（对账）——优先造。** O(1) 台仪器盖住 O(N) 个字段，零运行时噪声、只在有漂移时出声。你们已经建了（`reconcile_projects` + 孤儿探测 + watchdog）——这条路线是对的，补 α 的"常开化"即可。
2. **第二层：静态守卫测试——其次造。** 在测试期红，**不占运行时告警预算**。F821 族、silent-except 棘轮都是这个形状；继续把守卫判据往"带 key"和"schema 漂移"扩。
3. **第三层：运行时告警——最后造，且必须带 key。** 只有"运行时才知道"的事（超时、合并冲突、worker 异常）值得占这个通道。判据从"出声"升级为"出声且带聚合键"（第 3 题 #2 的 (b)）。

再加一条**告警预算制度**（你们缺的不是机制是责任）：`alert_summary` 已经把 chronic（n≥3）算出来了，缺的是"**每个 chronic key 必须在 N 天内变成 issue、修掉、或者删掉判据**"——没有这条，chronic 栏会变成"常驻理由簿"，`collect_changes` 那 12 条就是这么住下来的。§3.3 问的"会不会把筛子糊死"，答案不是少埋点，是**给常驻声设清退期限**（这跟 §45 棘轮计数器必须定义清零事件是同一条规则，用在告警上）。
