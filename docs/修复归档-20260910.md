**实测结论**：贵不在轮次多，也不在输出长（定稿吐 3 万字只用 63 秒）。贵在**思考 token** ——
glm-5.3-flash 一步吃掉 227.9 秒只产出 4849 字，三步合计占 **64% 的时间、21% 的字数**。

**注册表不可信（实测）**：`model_registry` 把 glm-5.3-flash / glm-5.2 / deepseek-v4-flash
全标成 `reasoning=False`，实测**三个都吐 reasoning_content**：

| 模型 | 同一道小题 | content | reasoning |
|---|---|---|---|
| glm-5.3-flash | 4.3s | 207 字 | 945 字 |
| glm-5.2 | 12.1s | 146 字 | 1160 字 |
| deepseek-v4-flash | 1.6s | 143 字 | 330 字 |

**推论（不是实测）**：把小题比例（reasoning ≈ 4× content）套到那一步 → 约 1.5 万 token / 228 秒
≈ 66 tok/s，正好是正常生成速度。**时间是被"想"掉的。**

**优化靶子**：① 辩论/确认两步的**模型选择**（glm-5.3-flash 在这两步是纯拖累）；
② `④ 确认 → 改稿` 循环（160 秒）值不值。
**注意**：`_V2_EXTRACT_DEFAULT` 的注释写着「必须是非思考模型」—— 这条纪律**只对提取步执行了**，
辩论/确认步从来没管过。

### #19 是重点 —— 它推翻了上一轮的结论

任务有**两条收尾路径**：

```
无 merge_request → TaskRunner.finalize          ← 做了三件归档
有 merge_request → orchestrator._drain_pending  ← 一件都没做（自己重写了收尾）
```

`_drain_pending` 自己写了一版收尾（transition + `_maybe_complete_parents` +
`_release_ref` + `_save_trace`），**唯独没调 `finalize`** —— 而三件归档只在
`finalize` 里。所以"复活"只复活了 `_save_trace` 那半：`events.json` 会长大，
**从外面看像是归档跑了**，其实 `archive_experience` / `record_tokens` /
`learner.record` 在合并路径上依然是死的。

**这正是本档开头那句"读到了 ≠ 生效了"的又一个实例 —— 而且这次骗过的是我自己。**

修完真机验证的**真实数据**：

## 五、方法教训（这轮最值钱的部分）

- **读到了 ≠ 生效了**。`route_role` 那条：写侧、读侧代码都"正常"，字段却不存在；
  09-07 那份诊断图甚至写着"route_role 只塞 prompt"——它读到了那个动作，没验证是否生效。
- **判据会撒谎，要看原始产物**。v2 探针第一轮报"疑似截断"，是我判据写成 `endswith("}")`，
  而 v2 产出带 ``` 围栏。**同一课在这个仓库已经踩过至少三次。**
- **测试必须在旧代码上因"这个 bug"变红**，不是因别的原因（AttributeError / 环境差异）。
- **自己写的工具也要独立重算**。本轮新写的 import 图生成器**错了三次**（包解析成 `__init__`、
  `executors` 路径判断、`from pkg.mod import sym` 从退回退），每次都是靠手工重算抓出来的。
- **静默失败仍是这个仓库的主要 bug 模式**。本轮又抓到 6 处，其中 4 处是 09-10 那轮
  "修过"的漏网（`route_role` 那条甚至只补了 warn 没修根因 —— 治了症状没治病）。
