## 0. 这是什么系统

一个**自部署的 AI Agent 调度平台**：输入一句话需求，它驱动多个大模型按角色、分阶段
把一个软件做出来，中间设三道人工门禁。

- 单机、零数据库。所有状态是 `.qidian/` 下的 JSON 文件，可 grep 排查
  （`scheduler/config.py:33` 起是路径常量表）
- 成品落在 `~/qidian-projects/<项目名>/`，每个项目一个独立 git 仓库
- **多模型是核心假设**：不同厂商的模型在架构阶段各出一份方案，再碰撞融合
  （这是唯一被实测验证过有价值的能力，见 §3.4）
- 驱动是**两套**：人手点"下一步"走 `workflow.run_phase()`；后台调度循环走
  `orchestrator`（`scheduler/orchestrator.py`）。两者认识的阶段子集不同 —— 见 §2

## 1. 全流程一图

```
TEMPLATE ──────────────── 立项，填需求描述
   │                      _needs_research() 决定要不要调研
   ▼
RESEARCHING ──(可跳过)─┐  调研员出报告
   │                   │
   ▼                   │
GATE1 ◄────────────────┘  ★人审   通过→PLANNING   打回→TEMPLATE（重写需求）
   │
   ▼
PLANNING                  架构师出方案 + 任务清单
   │                      ★ 命中架构关键词 → 多模型委员会 + 融合 v2（见 §3）
   ▼
GATE2                     ★人审   通过→EXECUTING  打回→RESEARCHING
   │
   ▼
EXECUTING                 拆成子任务写进 tracker，然后**交棒给调度循环**
   │
   ▼
INTEGRATING               非人门：多路 worktree 合并 + 集成测试
   │                      失败 ≤2 次 → 回 EXECUTING；触顶 → GATE2
   ▼
REVIEWING                 非人门：跑 5 项验收检查（★ 只报不改，见 §5）
   │
   ▼
GATE3                     ★人审   通过→DELIVERING  打回按 fix_route 分级（见 §1.2）
   │
   ▼
DELIVERING                非人门：打 tag + 收 README/打包配置 → delivery_manifest.json
   │
   ▼
DONE
```

`Phase` 枚举共 11 个值，定义在 `scheduler/project.py:22-33`：
`TEMPLATE / RESEARCHING / GATE1 / PLANNING / GATE2 / EXECUTING / INTEGRATING /
REVIEWING / GATE3 / DELIVERING / DONE`。

### 1.1 阶段流转的三张表

都在 `scheduler/project.py`：

- **人工批准** `_GATE_NEXT`（`:48-52`）：`GATE1→PLANNING`、`GATE2→EXECUTING`、`GATE3→DELIVERING`
- **人工打回** `_REJECT_FALLBACK`（`:37-42`）：`GATE1→TEMPLATE`、`GATE2→RESEARCHING`。
  **GATE3 不在表里**，走单独的分级逻辑（下条）
- **架构级返工** `_ARCHITECTURE_REDO`（`:45`）= `{EXECUTING, INTEGRATING, GATE3, REVIEWING}`
  —— 这几个阶段可以直接回 `PLANNING`

集成重试上限 `_INTEGRATE_MAX_RETRIES = 2`（`scheduler/project.py:55`）。

### 1.2 GATE3 打回是分级的

实现在 `scheduler/workflow.py:389` 的 `handle_gate3_reject`：

| fix_route | 回哪 | 动作 |
|---|---|---|
| `impl` | EXECUTING | 把已 DONE 的任务 `force=True` 重置为 PENDING 重做（`:435-444`） |
| `design` | PLANNING | 清空 `architecture` 字段重新规划（`:454-456`） |
| `note` | 不回退 | 只记 lineage，不阻断（`:448-451`） |
| **读不到 QA 报告** | **EXECUTING** | 无依据时回实现层、**不动架构**（`:426-428`） |

判据优先级（`:409-418`）：
`if "design" in routes → design; elif "impl" in routes → impl; else → note`。

> ⚠️ 该函数 docstring（`:395`）写的是"无 qa_report → 默认 design"，
> **与代码相反**（代码 `:426-428` 强制 impl）。以代码为准。见 §8。

### 1.3 唯一的阶段写入入口

所有流转都过 `ProjectState.set_phase(phase, reason)` 一个口
（`scheduler/project.py:220-236`，2026-09-11 起）：

- 值没变则直接 return（不记）
- 变了就 `add_lineage({"action":"phase", from, to, reason, ts})`（`:234-235`）
- **不落盘** —— 由调用方 `save()`（`:229-230` 注释）

`add_lineage` 在 `:212-218`，硬上限 1000 条。

之前是 21 处散点赋值，出事时落盘里只有最终 phase、**没有任何轨迹** ——
"点通过永远弹回 GATE2"那种死循环翻遍文件也看不出是谁推回去的。

GATE 确认入口是 `confirm_gate`（`scheduler/project.py:171-200`）：写
`owner_confirm[gate]=decision`；approved 时**先拦 GATE2 的 `arch_invalid`**（`:181-183`
不放行），approved GATE2 时清零 `review_failures` / `integrate_failures`（`:191-193`）。

### 1.4 什么情况会跳过阶段

`scheduler/workflow.py:147-159`：

- `_needs_research()`：`bug_fix` → 不调研；`product_dev / agent_dev / refactor` → 一定调研；
  其他模板看描述里有没有 `调研/参考/借鉴/架构/设计/方案/重构`
- `_should_skip()`（`:158`）：看 `owner_confirm[key] == "skip"`，只在调研（跳 GATE1，
  `_workflow_phases.py:31`）和架构（跳 GATE2，`:88`）两处被调用

架构产出的校验分两档（`_workflow_phases.py:172-196`）：致命（blocker 里含 "tasks"）
→ `arch_invalid` 硬拦；其他缺项 → `arch_warning` 只记。

## 2. 两套驱动（当前最硬的一条结构债）

同一个 `phase` 被两个入口写，各自认识**不同的阶段子集**：

| 驱动 | 触发时机 | 认识的阶段 |
|---|---|---|
| `workflow.run_phase()`（`scheduler/workflow.py:181-245`） | 人手点"下一步" / CLI | TEMPLATE / RESEARCHING / PLANNING / EXECUTING / GATE1~3 / REVIEWING / DONE |
| `orchestrator` 调度循环（`scheduler/orchestrator.py:246` `_run_queue_v3`） | 每一 tick 自动 | 额外驱动 **INTEGRATING / REVIEWING / DELIVERING** |

**交接方式不靠函数调用，靠共享状态**：`run_phase` 走到 EXECUTING 时把子任务写进
`tracker`，然后**直接 break**（`scheduler/workflow.py:199-201`，注释在 `:204-206`）；
调度循环读 `tracker` 里的 PENDING 任务自己跑。调度循环把 phase 推到
INTEGRATING/REVIEWING/GATE3/DELIVERING/DONE 后，`run_phase` 下次被调时读
`project.phase` 接着走。

INTEGRATING/DELIVERING 在 `run_phase` 里只是占位（`scheduler/workflow.py:203-210`）。

**调度循环每 tick 做什么**（`scheduler/orchestrator.py`）：
`_dispatch_ready`（`:78`）→ `_reap_futures`（`:114`）→ `_drain_pending`（`:191`）
→ `_auto_trigger_test_fix`（`:280`，推进项目的 INTEGRATING/REVIEWING/DELIVERING）。
任务超时阈值 **900 秒**（`:120`）。

## 3. 架构阶段：多模型委员会 + 融合 v2

这是整个系统里最复杂、也是唯一被验证有价值的部分。

### 3.1 什么时候触发

**两个条件都满足**（`scheduler/_dispatch_exec.py:59`）：
1. `_is_architecture_task(task)`（`scheduler/execution_judge.py:841-850`）
   —— 任务文本包含这 6 个**强短语**之一：
   `模块划分 / 数据模型 / API契约 / 技术栈 / 架构方案 / 系统架构`
2. 候选链长度 ≥ 2

> ⚠️ 这是**按任务文本内容判的，不看阶段**。所以一个"实现"阶段的任务，
> 只要描述里写了"模块划分"，也会进委员会 —— 而委员会走的是 no_tools 路径，
> 产出的是架构 JSON 而不是代码。见 §8。

### 3.2 席位规则

**委员 = 整条候选链，没有席位上限。**
`scheduler/_dispatch_exec.py:215` 的
`ThreadPoolExecutor(max_workers=min(len(chain), 4))` 里的 **4 是并发上限，不是席位数**——
`:218` 的 `for i, a in enumerate(chain)` 对链上**每一个**模型都提交一份初稿，
超过 4 个就排队跑，全都跑完才算数。

- 波次时限 **300 秒**（`_WAVE_TIMEOUT`，`:28`）。用显式 `shutdown(wait=False)`（`:242`），
  所以它是**真时限**（`:23-27` 注释解释了为什么不能用 `with`）
- 部分模型没产出 → 告警 `committee_partial:<拿到几个>/<总共几个>`（`:245-249`）
- 产出为 1 个 → 直接返回；0 个 → 抛异常（`:252`）
- **视角提示词默认关闭**（`:205-206`）：实测"给一句'你关注风险'的提示词"= 伪碰撞，
  不产生真实差异（`QIDIAN_COMMITTEE_PERSPECTIVE=1` 可打开，留着做 A/B）

### 3.3 融合 v2 的完整步骤

实现在 `scheduler/execution_judge.py:532-773`。输入 N 份方案全文，输出一份融合稿。

```
① 确定提取员                                               :542
     优先级：阶段配置的 extract → fusion.toml → 硬编码默认（:414-425）
     避嫌：提取员若在委员会里 → 自动换备选，告警 extractor_swapped（:572-577）
           换不到就照撞，但 _warn_same_model 一定留告警（:216-228, :578）

② 提取三类（共识 / 分歧 / 独有优点）                        :588-594
     失败 → 换模型重试（:605-621）
             先挑"不在委员会"的 → 再退到委员本人（:616-619 告警）
     全失败 → 告警 fusion_v2_extract_failed_all，整条融合返回空（:622-624）
     三样全空 → 告警 fusion_v2_empty_extract，返回空（:628-630）

③ 定稿人                                                   :482-493
     从委员里选，**不看配置**
     优先"历史范围纪律好"的（读 model_discipline.json 的违规/审计数）
     无数据 → 回退"提分歧最多的那个"（_first_speaker，:457-464）

④ 共享对话  仅在存在分歧时跑，最多 5 轮                      :635-710
     max_rounds = max(2, QIDIAN_FUSION_V2_ROUNDS or 5)      :640
     Round1  定稿人陈述                                      :654-659
     Round2  其余成员逐条 accept|insist                      :677-678
             空口 accept 会被降级为 question（_demote_bare_accept，:500-513）
     Round3  定稿人对 insist 回 agree|question               :689-704
     终止：复读 / 全 accept / 全 agree / 撞上限（:681-705）
     撞顶仍有 question → 告警 fusion_stuck（:708-710）

⑤ 分歧结论                                                 :712-729
     默认判给定稿人
     对方 insist 且定稿人 agree → 对方胜（:721-723）
     定稿人没确认票 → 标 basis="default_no_confirm_vote"（:725-728）

⑥ 独有做法                                                 :731-737
     **全体 accept 才采纳**（保守），其余 rejected

⑦ 定稿 + 确认                                               :739-773
     定稿人出稿（:747）；空 → 返回空
     其余委员各自确认（:751-767）
     有 issues 且是第一次 → 带 issues **重写一次**（:768-772）
```

**融合失败的整体兜底**（`scheduler/_dispatch_exec.py:276-325`）：返回空串 →
告警 `fusion_empty_fallback_synthesis` → 掉到"通用合成"（截断 3000 字，`:325-362`）。

2 席委员、**621 秒**、融合产物 **17158 字符**。
慢主要在提取那一步，不在委员本身。

## 4. 模型是怎么选的（最容易搞混的一块）

> 这一节是 2026-09-11 新加的机制。在此之前，「哪些模型上场」只有**一个**开关，
> 而它同时决定了三件事（候选链 / 委员会名单 / 审查员池），界面上完全看不出来。

### 4.1 激活池：谁有资格上场

`.qidian/agents_custom.json` 的 `any` 数组 = 有资格的模型池。
**数组顺序 = 优先级**（第 1 个是主力）。
读取入口 `dispatcher.load_agents()`（`scheduler/dispatcher.py:63-99`）。

### 4.2 阶段 → 模型：哪个阶段用谁

`scheduler/phase_models.py` + `.qidian/phase_models.json`（`:26` 定义五个 key）：

| key | 界面名 | 语义 |
|---|---|---|
| `researching` | 调研 | 第 1 个 = 主力，其余兜底 |
| `planning` | 架构 | **全部 = 委员会席位**（只配 1 个等于关掉多模型碰撞） |
| `executing` | 实现 | 第 1 个 = 主力，其余兜底 |
| `reviewing` | 审查 | **全部 = 审查员**（写手会被自动剔除） |
| `extract` | 融合提取 | 第 1 个 = 融合提取员 |

**留空 = 回退到旧行为**（= 用整个激活池）。这是设计里最重要的一条兼容边界。

统一入口 `selection(phase, project, level)`（`scheduler/phase_models.py:114-131`）三态：
1. 项目级 `agent_lineup` 非空 → `(项目名单, restrict=False)`
2. 全局阶段配置非空 → `(阶段名单, restrict=True)`
3. 都没有 → `(None, False)`（完全按旧行为走）

### 4.3 关键开关 `restrict_to_lineup`

`scheduler/dispatcher.py:241-245`。选人函数默认是"lineup 优先 + **把池里其余模型
追加在后面**"（`:274-295`）。所以光"指定"限制不住委员会席位 —— 想让"架构三家"
真的是三家，必须开这个开关（`:281-285`）：

- `restrict=False`（默认）：lineup 只是"优先"，其余仍作兜底 —— **旧语义**
- `restrict=True`：lineup 就是全部候选，不追加、**也不做学习器重排**

**指定的模型一个都解析不出来时 fail-open 回全池**，但一定留告警
`lineup_all_unavailable`（`:284-285`）——否则界面上配了东西却完全没生效，查都没处查。

### 4.4 会打乱顺序的三个地方（受限时会全部跳过）

1. **路由学习器重排**（`scheduler/dispatcher.py:330` 起）：按模型历史成功率
   （Hedge 权重）降序重排整条链。跳过条件在 `:335` 的 `not restricted`
2. **按任务关键词提链首**：`_prefer_by_strengths`
   （`scheduler/_dispatch_exec.py:171`），跳过条件在 `:53-54`
3. **重试升级**：任务重试 ≥2 次时把含 `glm`/`opus` 的模型提前
   （`scheduler/_exec.py:310-319`），跳过条件在 `:314` 的 `not exec_restrict`

> 不跳过的话，界面上点"主力"只影响 worktree 创建，实际调的是学习器挑的模型 —— 语义撒谎。

### 4.5 提取员的优先级链

`_v2_extractor_model()`（`scheduler/execution_judge.py:414-425`）：

`阶段配置的 extract[0]` → `fusion.toml [custom].extract_model` → 硬编码
`_V2_EXTRACT_DEFAULT`（`:407`，值 `glm-5.3-flash`）。

- 备选表 `_V2_EXTRACT_FALLBACKS = ("glm-5.2", "deepseek-v4-pro")`（`:411`）
- 输出上限 `_V2_EXTRACT_MAX_TOKENS`（`:399-400`），默认 131072
- **避嫌规则**：提取员在委员会里 → 自动换掉（`:573-577`），告警 `extractor_swapped`

### 4.6 审查员怎么定

`_pick_reviewers`（`scheduler/_review.py:77-108`）：

- 配了 `reviewing` 名单（`:87`）→ 按名单：剔除写手（`:92-94` 告警
  `designated_reviewer_is_writer`）、逐个验可用性（`:96-102`）
- **且不再自动扩容**（调用方 `:305` 跳过）—— 扩容会调**未启用**的模型，真花钱
- 没配 / 配了但一个都不剩（`:103-107` 告警）→ 退回旧逻辑：
  全池排除写手，**取前 2**

扩容逻辑 `_expand_review_pool`（`:40-74`），`QIDIAN_REVIEW_POOL_EXPAND=0` 可关（`:53`）。

## 5. 审查层：有什么、缺什么

> 它**不是空壳**，在跑。缺的是闭环。

### 5.1 每轮跑哪些检查（按顺序）

实现在 `scheduler/_review.py:163-567` 的 `run_post_exec_checks`：

| # | 检查 | 触发条件 | 失败后果 | 行 |
|---|---|---|---|---|
| 0 | 本地安全扫描（正则） | 有改动就查 | 置信度 −0.3、打回 | `:207-227` |
| 1 | 项目测试 | 非 trivial 改动 | 失败/超时 → −0.3、打回 | `:238-291` |
| 2 | 多模型审查（每文件） | 非 trivial 改动 | critical → 打回 | `:293-454` |
| 3 | QA 约束验收 | 有约束清单 | needs_fix → −0.25、打回 | `:456-501` |
| 4 | 需求符合性对账 | 有 project_id | **只写软信号，不拦** | `:503-519` |
| 5 | 安全审计（LLM 五维） | 非 trivial 改动 | 仅 critical/high 硬拦 | `:521-567` |

检查超时统一 **600 秒**（`_REVIEW_TIMEOUT_SEC`，`:19`）。
第 4 项走 `supervisor.check_requirement_conformance`（`scheduler/supervisor.py:403-505`），
`_review.py:503` 的注释自认"只写软信号 + warning，**先不设 hard gate**"。

**审查结论怎么生效**：`scheduler/_exec.py:457-458` 的
`validation.confidence = min(validation.confidence, quality.confidence)`
—— 这是审查惩罚真正落地的地方（`:453-456` 注释解释了原来传不回来）。

### 5.2 两个"整段不跑"的口子

1. **改动被判定为 trivial** —— `_is_trivial_change`（`scheduler/_review.py:122-132`），
   条件：**单文件 且 diff < 50 行**。命中就跳过上表 #1~#5（**#0 照跑**）
   > ⚠️ 已知缺陷（`:229-233` 注释自认 P0-1）：worktree 里改动在检查前已被
   > `commit_wt` 提交，所以里面那句裸 `git diff` **恒为 0 行**
   > → **单文件改动恒判 trivial = 恒跳过审查**。当前代码只做披露、不改判据，见 §8
2. **架构没产出 `constraints`** → 约束清单为空 → 验收整段跳过（`:134-138` 注释）

### 5.3 成本控制：只审前 3 个文件

`if len(changed) > 3:`（`scheduler/_review.py:320-330`）→ 告警
`review_files_truncated` + 写进 `unverified`（"N 个改动文件未审查"），
然后 `:331` 的 `for f in changed[:3]` 只审前 3 个。
**注释明确这是有意为之，不是 bug** —— 但如实记入"未验证"，不谎报已审。

### 5.4 自动修的上限

`_REVIEW_MAX_AUTO_FIX = 2`（`scheduler/_review.py:17`），触顶 →
`check_review_fail_limit`（`:570-579`）→ `escalate_to_gate2`。
（实现层的上限是 3 轮）

### 5.5 缺的那一环

```
发现问题的 AI  →  ✂️ 自己改  →  再验
                 ↑ 这一环被删了，没装替代品
```

所以责任链是 **AI 报告 → 人判 → 人决定改不改**。"发现"能力还在，"自动修"没了。

## 6. 执行层

### 6.1 单任务的执行循环

主函数 `run()` 在 `scheduler/_exec.py:254`，主循环 `:344` 起：

```
外层（:253）：按候选链逐个模型试（熔断的跳过）
  内层（:344）：每个模型最多 N 轮（默认 2，config.DEFAULT_MAX_TURNS）
    1. 心跳 / 取消检查（:349）/ 暂停检查（:354）
    2. 组装本轮任务文本 _build_effective_task（:53）
       = 全局底线 + 角色 + 记忆 + 项目上下文
    3. 建独立 worktree（:333，仅 sandbox=worktree）
    4. 调模型 disp_mod.dispatch（:367-371）
    5. 校验 val_mod.validate + post_execution_hook（:424-438）
    6. 审查 run_post_exec_checks（:444）
    7. QA 门禁 supervise（:466-502）：fail/block → 清合并请求、置信度压到 0.3
    8. cascade 决策 _decide_cascade（:197）→ 返回 / 换模型 / 同模型重试
  收尾：清理 worktree（finally :539-540）
```

### 6.2 cascade 的三档阈值

`_decide_cascade`（`scheduler/_exec.py:197-250`）：

| 置信度 | 动作 | 行 |
|---|---|---|
| `>= 0.75` | **接受**，跳过升级 | `:225-232` |
| `0.35 ~ 0.75` | **同模型重试**（带反馈） | `:236-242` |
| `< 0.35` | **立即换模型** | `:234-235` |

另有两个特殊档：`failure_kind == soft_quality` 且已跑 ≥2 轮 → 直接判失败
（`:216-223`）；其他（rollback/abort）→ 返回失败（`:244-250`）。

### 6.3 熔断与重试

- 模型熔断：连续失败 3 次 → 冷却 300 秒
  （`scheduler/_model_breaker.py:25-26`）。**fail-open**（全池熔断则不过滤）
- 任务重试上限：3 次（`scheduler/tracker.py:76` 的 `max_retries`），
  外层循环 `_run_with_retry`（`scheduler/_exec.py:549-593`）
- **升级路径从未生效**：`disp_mod.escalate(level)` **恒返回 None**，`_ESCALATION` 是空表
  —— `scheduler/_exec.py:523-533` 的注释自认，终态统一写
  `no_escalation_path`（`:532`）。见 §8

### 6.4 worktree 与合并

- 每个任务一个独立 git worktree，上限 50 个（`scheduler/_worktree.py:115`），
  超限降级用仓库根（已告警）
- 合并走 `MergeQueue`（`scheduler/merge.py:76-226`），两层判定：
  ① 改动文件不重叠 → 直接合（`:144-178` 的 Layer1）；
  ② 否则精确探测是否真冲突（Layer2）
- 真冲突 → `_park`（`:186-205`）写 `.qidian/parked/` 并标 `CONFLICT_HELD`
- 人工解决 `resolve`（`:207-226`）：`manual`（重新 merge）| `abort`（标 FAILED）

## 7. 横切能力

### 7.1 角色

**一段注入给模型的提示词，绑定研发阶段。**
`.qidian/phases.json` 可改（读入口 `roles.get_phase_role`，
`scheduler/roles.py:129-141`；默认表 `_DEFAULT_PHASE_ROLES`，`:121-126`），改完立即生效。

- 调研/架构/审查：角色的 `system_prompt` 直接拼在 prompt 最前面
  （`_workflow_phases.py:36-41`、`:103-107`；`validator.py:323-326`）
- 实现：角色 key 绑到任务的 `route_role`（`_workflow_phases.py:303,338`），
  执行首轮由 `_exec._inject_role_context`（`scheduler/_exec.py:87-97`）注入

**角色不决定用哪个模型** —— 模型由 §4 的「阶段 → 模型」管。

### 7.2 技能

**给模型加装的能力，绑定到"模型"（不是阶段）。**
绑定读取 `skill_loader.get_agent_skills`（`src/singularity/skills/skill_loader.py:253-265`），
存 `agents_custom.json` 的 `_skills[level][model]`。

两种类型（`skill_loader.py:9-12`）：
- `prompt` 型 → 那段文本追加进 system prompt
- `tool` 型 → 注册成一个模型可主动调用的工具

注入点 `_load_skills_for_agent`（`scheduler/_dispatch_skills.py:57-88`），
带 `(level, model)` 缓存；最终在 executor 里
`tools.extend(skill_tools)` + `system_prompt += skill_prompt`
（`scheduler/executors/openai_agent.py:232,235-236`）。

**相关性过滤** `_ntilc_filter`（`scheduler/_dispatch_skills.py:14-54`）：
绑超过 3 个时（`:19-20`），按"任务描述 ↔ 技能描述"的语义相似度挑（阈值 0.3，
不足 2 个取前 2，`:23-39`）；嵌入不可用时降级为关键词重叠（`:43-54`）。

> 绑定在模型上的后果：**换了模型，技能就丢了**。而这跟 §4 的「阶段 → 模型」
> 天然冲突 —— 架构阶段换个模型，绑在旧模型上的技能就静默消失了。

### 7.3 记忆（MAGMA）

- **注入时机**：每个任务的**第一轮、且没有打回反馈**时
  （`scheduler/_exec.py:69-72`）→ `_inject_memory`（`scheduler/_exec_context.py:44`）
- 分三层金字塔（`:44-104`）：摘要（始终）→ 完整描述（相似度 ≥0.3）→
  原始文件（≥0.5，受 token 预算限，默认 80）
- **写入时机**：任务终态收尾写 trace 时（`scheduler/_exec.py:634-655`）
- 去重：Jaccard > 0.75 直接早退（`scheduler/_memory_core.py:334-339`）

### 7.4 用量统计

- 单任务：`_task_runner._archive_task_outcome`（`scheduler/_task_runner.py:79-142`）
  调 `record_tokens`（`scheduler/_token_budget.py:357-363`），**`tokens > 0` 才记**
- 系统调用单独记（不入任务账）：`record_system_tokens`（`:366-379`），
  level 分 `fusion` / `router` / `observer` / `memory` / `goal`
- 单价存在独立文件（模型表会被整行重建擦掉），费用**读时现算**，
  查不到就显示"未配置价格"，**绝不兜底成 0**（`scheduler/model_prices.py`）

## 10. 请你评审什么

按重要性排，欢迎只答你最有把握的几条：

1. **融合 v2 的机制有没有结构性缺陷？**（§3.3）
   提取共识/分歧 → 定稿人陈述 → 其余人 accept/insist → 定稿人 agree/question →
   默认判给定稿人 → 定稿 → 其余人确认 → 有异议重写一次。
   *具体想听*：这个流程会不会系统性地偏向某一方（"默认判给发言方"）？
   "独有做法需全体 accept 才采纳"（`:731-737`，保守）合不合理？
   5 轮上限（`:640`）是拍脑袋的吗？

2. **委员会"全链参与"合理吗？**（§3.2）
   现在激活池 5 个模型，架构阶段就是 5 席并行出稿再融合。没有席位上限。
   *具体想听*：席位多了是增益还是噪声？有没有更好的选席策略？
   （同厂模型算不算"两个视角"已是已知问题，`:216-228` 有告警）

3. **这三层抽象对不对？**（§4.2 / §7.1 / §7.2）
   - 「阶段 → 模型」：五个 key，各是一份有序模型列表，留空 = 用整个池
   - 「角色」：绑**阶段**，是一段提示词
   - 「技能」：绑**模型**，是提示词或工具
   *具体想听*：技能绑模型而不是绑阶段，是不是一个设计错误？
   这三者的职责划分有没有更清晰的方式？

4. **审查层的五个检查，顺序和权重合理吗？**（§5.1）
   安全扫描 → 项目测试 → 多模型审查 → QA 约束验收 → 需求对账 → 安全审计。
   只有 0/1/2/3/5 能真正拦截，第 4 项是软信号。
   *具体想听*：哪些软信号应该升级成硬拦？"只审前 3 个文件"这个成本控制值不值？
   §8 第 3 条（单文件恒跳过审查）该怎么修？

5. **两套驱动（人控 + 调度循环）是结构债，该怎么收？**（§2）
   它们认识的阶段子集不同，靠共享状态（tracker 里的任务）交接而非函数调用。
   *具体想听*：是应该统一成一个状态机，还是这种分工本身合理、只是边界没划清？

6. **§8 那 8 条里，哪几条是真问题、哪几条可以先不管？**
