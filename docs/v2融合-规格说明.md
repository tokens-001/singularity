# v2 架构融合机制 — 规格说明（供外部评审）

> **这份文档的用途**：把 v2 融合的完整机制摊开，请另一个模型判断「有没有更优解」。
> 自包含 —— 不需要读代码。所有数字都来自实测，推测处已标注。
>
> 版本：2026-09-11。代码位置：`src/singularity/scheduler/execution_judge.py`（`fuse_architecture_v2`）。
> ⚠️ 本文只描述**机制**。哪些已验证、哪些没验，集中在第 9 节，**请重点看那节**。

---

## 1. 它在整个系统里的位置

奇点是「多模型按角色协作开发软件」的调度平台。流水线是
`调研 → 架构 → 实现 → 审查`（4 个核心阶段，中间夹 3 个人工确认门）。

**架构阶段**要做的事：N 个模型**并行各写一份完整架构方案**（含模块划分 / 数据模型 /
API 契约 / 技术栈 / 任务拆解 / 风险），然后**合成一份**统一方案交给下游拆成子任务。

v2 就是这个「合成」环节。

**它替换掉的旧机制（下称 v1）**：整份方案互评 → 五维差异分析 → 重写全文。
v1 的致命问题：规则只有"加"没有"删"（共识锁定 + 独有做法补充 + 盲点补缺），
**取并集**，实测输出膨胀到输入之和的 **1.8 倍**，撞 max_tokens 被腰斩
（真实案例：brief 3 因此丢过整个 `tasks` 段）。

---

## 2. 目标与判据

**目标**：多模型各出方案 → 得到一份**优于任何单份输入**的共识方案。

**判据（用户定）**：

```
融合 ≥ max(输入单稿)        ← 理论上必然；不满足 = 机制或实现有问题
长度 ≈ 单稿的 1.1~1.3 倍    ← 硬约束，防膨胀
```

---

## 3. 整体时序（一次融合 = 5~10 次模型调用）

```
① 各出方案（N 份，并行）           ← 不属于 v2，由委员会并行完成

② 提取三类（1 次调用）              ← 秘书模型，输入 N 份方案全文
   ├─ 失败（空 / JSON 解析失败 / 三样全空）→ 整条 v2 放弃，回退 v1
   ↓
③ 共享对话（0 ~ 2 个来回）
   ├─ 轮1（1 次）：定稿人对**全部分歧点**逐条陈述己方理由
   └─ 循环（每轮消耗 2 个轮次计数）：
        ├─ 其余成员【并行】逐条回应 accept/insist（1 波）
        └─ 定稿人确认 agree/question（1 次）
   ↓
④ 定稿 + 确认（2 ~ 4 次）
   ├─ 定稿（1 次）：按委员会结论写统一方案
   └─ 其余成员【并行】确认（1 波）；有问题 → 定稿人改 1 稿（1 次）→ 再确认（1 波）
```

**并行度**：只有「其余成员」那两处（轮2 回应 / 定稿确认）是并行的；
提取、轮1、轮3、定稿都是串行。

---

## 4. 每一步的细节

### ② 提取三类

| | |
|---|---|
| 模型 | `fusion.toml [custom].extract_model`，默认 `glm-5.3-flash`；**若该模型在委员会里则自动退到 `glm-5.2`**，再不行 `deepseek-v4-pro`（避免"选手给自己出题"） |
| 输入 | 原始需求（截断 4000 字）+ N 份方案全文（单份 ≤40000 字，合计 ≤120000 字按 N 均分） |
| 输出 | JSON：`consensus[]` / `disagreements[{id,dimension,point,positions,raised_by}]` / `unique_gains[{id,content,from,impact}]` |
| 规则 | consensus 只列点不展开；disagreements 只列**真正互斥**的（措辞差异不算）；unique_gains 只列确实只有一家提的 |
| 上限 | `max_tokens` = `MODEL_MAX_TOKENS`（131072） |

### ③ 共享对话

**定稿人（writer）怎么选**：
1. 优先查 `.qidian/model_discipline.json`（历史"范围纪律"：违例数/审计次数，越低越好）
2. 没有数据 → 退回「**提出分歧最多的那一方**」

**轮1**（定稿人）：对全部分歧点逐条陈述己方理由 + 对其余成员的独有做法表态。

**轮次循环**（`while rounds < max_rounds`，`rounds` 每轮 +2，起始 1）：

| 顺序 | 动作 | 计数 |
|---|---|---|
| 1 | 其余成员**并行**逐条回应：`accept`（被说服）/ `insist`（坚持+解释对方哪里误判） | +1 |
| 2 | 收敛检查（见下） | |
| 3 | 定稿人对 insist 的条目确认：`agree`（接受反驳）/ `question`（仍然质疑） | +1 |
| 4 | 若全部非 question → 收敛 | |

**收敛判据（四选一即停）**：
1. **全 accept**
2. **复读** —— 本轮投票与上轮完全相同（再辩也没新信息，别烧 token）
3. 定稿人**全部 agree**（有人让步才算结论）
4. 撞轮数上限

> ⚠️ **注意 `max_rounds` 的实际效果**：默认 5，但每轮消耗 2 个计数，且循环条件是
> `rounds < max_rounds` —— 所以**实际最多只有 2 个来回**，不是 5 轮。

**防作弊**：没写理由的"空口 accept"会被**降级成 question**（不算数）。

### ④ 定稿 + 确认

**定稿输入**（注意顺序即优先级）：
```
原始需求 → 已达成共识 → 分歧结论（逐条已定） → 采纳的独有做法 → 已驳回的（明确不许写）
→ 各成员原稿全文（供核对细节、补字段）
```
> 原稿是**素材**不是模板。提示词明写「与上面结论冲突之处一律以结论为准」。

**定稿的 5 条要求**（原文摘要）：
1. 分歧按结论采用对应立场 —— **不折中、不两个都写**
2. 只写采纳的独有做法；驳回的一条都不要出现
3. 长度控制在单稿 1.1~1.3 倍
4. **逐条核对需求边界** —— 需求没要求的一律不写进主方案（哪怕某成员提了、评审也通过），
   确有必要就写进 `risks` 并标「范围外建议」
5. 生成 `test_cases`

**确认**：其余成员并行检查三件事 —— 分歧结论有没有落实？有没有把驳回的写进去？有没有明显缺失？
→ 不认可就列出 issues → 定稿人**带 issues 重写 1 稿** → 再确认一次（**只重试一轮**，不回 ③）。

## 5. 判定规则（代码级）

**分歧归谁**：
```
默认：发言方（writer）胜
例外：对方 insist 且 发言方 agree（认输）→ 对方胜
其余（question）→ 发言方胜
```
> 已知局限：N>2 时多个 insist 方立场不同，**只记第一个**（实际分歧点几乎都是两家对立）。

**独有做法采纳**：**全体 adopt 才采纳**（有一家 reject 就不加）。保守是刻意的 —— 长度就是膨胀主因。

| 参数 | 默认 | 环境变量 |
|---|---|---|

| 委员会收集超时 | 300s | `QIDIAN_DEBATE_TIMEOUT` |

## 7. 失败与回退链

```
v2 返回空（提取空/解析失败/定稿空）
   → warn: fusion_v2_failed_fallback_legacy
   → 多轮辩论 _debate（失败则 warn: debate_failed，用初稿继续）
   → v1 两阶段 fuse_architecture（失败则 warn: fusion_failed）
   → 通用合成（每条产出截断到 3000 字）← 这是**降级**不是等价替换，有 warn
```

v2 内部各自的失败点也会单独告警（提取空、确认空、JSON 解析失败、撞轮数上限仍有 question…）。

## 8. 实测数据（brief 3，2 模型阵容）

### 8.1 耗时（同一批缓存稿，只切一个变量）

| 步骤 | A：glm-5.3-flash 参与辩论 | B：换成 deepseek-chat |
|---|---|---|
| ② 提取 | 34.2s | 45.4s |
| ③ 轮1 陈述 | 25.3s | 20.0s |
| **③ 回应** | **227.9s** | **7.9s + 6.2s** |
| ③ 确认 | 36.7s | 14.5s + 12.6s |
| ④ 定稿 | 62.9 + 64.5s | 60.1 + 79.1s |
| **④ 确认** | **79.8 + 95.1s** | **4.8s + 4.9s** |
| **合计** | **626s / 8 次** | **255s / 10 次** |

**关键观察**：
- 省下的 371 秒（59%）**全部**来自 ③回应 与 ④确认
- **定稿步一点没省**（127s → 139s）—— 那是输出密集型，跟模型无关
- B 多跑了一轮辩论，仍然快 2.45 倍
- 根因：**这些模型会输出不进入 `content` 的 reasoning**。同一个模型在小 prompt 上
  reasoning 是 content 的 **4~10 倍**。模型注册表把它们标的 `reasoning=false` **是错的**
  （实测三个都吐 reasoning）

### 8.2 质量对比（配对比较，位置随机翻转，中性裁判 `deepseek-v4-pro`）

```
A 2 : 4 B      ← B 胜。n=6，样本很小，只看方向
```

裁判给的理由都是**内容层面**的（不可变账本、numeric 精度、租户隔离、账单重算、
不引入多余 MQ），不是文风 —— 说明差异是实的。

**长度对照**（设计目标是单稿的 1.1~1.3 倍，单稿最长 31347 字）：

| | 融合稿 | 相对最长单稿 |
|---|---|---|
| A（慢阵容，跑 1 轮辩论） | 32155 字 | **1.03×** ← 低于设计下限 |
| B（快阵容，跑 2 轮辩论） | 40061 字 | **1.28×** ← 落在设计区间内 |

> A 比最长单稿还短，值得警惕 —— 有可能是"融合不充分"而不是"克制"。

### 8.3 融合稿的内容来源（12-gram 覆盖，对重新排版免疫）

| | glm-5.3-flash | deepseek-v4-flash（**定稿人自己**） |
|---|---|---|
| 融合稿被该稿覆盖 | **48%** | 18% |
| 该稿自身进入融合稿 | **65%** | **17%** |
| 只看"该稿独有"的行（按字数） | 44% | **0.75%** |

融合稿另有约 **46% 是两稿都没有的新内容**。

> **这推翻了设计时的一条假设**：原以为「谁当定稿人，谁的设计就被保留」（定稿人自我偏好）。
> 实测是**反的** —— 定稿人几乎完全放弃了自己那稿。
> ⚠️ 保留意见：两稿针对同一需求，措辞有天然重叠；n-gram 对"哪稿更模板化"敏感。
> **方向可信，具体数字别当真。**

## 9. 已知缺口 / 未验证（**请重点评审这节**）

### 9.1 没验证过的

1. **never 与 v1 做过头对头比较**。现有全部证据都是「融合 vs 单稿」。
   已决定不做（v1 有致命缺陷、不是可用备选，见 §1）。
2. **没做过"关掉辩论"的消融**。所以**不知道辩论这 290 秒值不值** ——
   定稿人本来就拿得到全部原稿，完全可能辩论只是"仪式"。
3. **提取员召回率约 90%**（3 题 29 条真分歧，默认提取员提到 26 条）。
   约 10% 的真分歧**永远进不了讨论**。没加第二个提取员（"漏了会伤产物"缺证据）。
4. **确认步只重试 1 轮** —— 这个数字是拍的，没有实测支撑。

### 9.2 机制上的已知局限

5. **轮数上限形同虚设**：默认 5，实际最多 2 个来回（见 §4 的警告框）。
6. **N>2 的歧义没处理**：多个 insist 方立场不同只记第一个。
7. **极端不对称**：定稿人自己的内容 17% 进了产物，非定稿人 65%。
   如果这个不对称是稳定的，那"多模型碰撞"可能退化成"一个模型的稿 + 另一个模型的改写"。
8. **成本随 N 线性涨、收益未知**：N 份初稿 + 提取 1 + 对话 2~4 + 定稿 2~4。

### 9.3 环境/实现的坑

9. 提示词里 `max_tokens` 给到 131072（为了让思考模型不把预算烧光），
   但没验证过**给这么大是否反而让模型"想更久"**。
10. 定稿人选择依赖 `.qidian/model_discipline.json`，**没有数据时退回"提分歧最多者"** ——
    这个回退跟"范围纪律"毫无关系，为什么它会是个合理的默认？

## 10. 请你评审的问题

1. **这个机制相对于"让一个强模型直接写一稿"的核心增量是什么？**
   考虑到定稿人本来就拿得到全部原稿，辩论环节是否可省？省了会失去什么？
2. **"全体 adopt 才采纳独有做法"是否过于保守？**
   N=2 时意味着任何一家反对就丢弃。有没有更好的聚合规则？
3. **收敛判据「有人让步才算结论」** —— 会不会导致僵持的分歧被默认判给发言方（writer）？
   而 writer 又是"提分歧最多"的那个（无纪律数据时）。这是否让最激进的一方系统性获胜？
4. **定稿人选择**：目前用"历史范围纪律"（违例/审计），无数据时退回"提分歧最多者"。
   有没有更合理的定稿人选择标准？
5. **轮数上限的语义**：现在每轮消耗 2 个计数导致实际最多 2 个来回。这是 bug 还是 feature？
   如果要让上限真正可调，应该怎么改？
6. **有没有一种根本不同的合成范式**（不是"提取→辩论→定稿"）能同时满足
   「不膨胀」和「优于最好单稿」？例如：结构化合并、投票制、分层聚合、或直接让强模型看全部原稿自由发挥？
7. **§9.2 第 7 条的不对称**：如果定稿人总是放弃自己的设计，会不会应该**取消"定稿人"这个角色**，
   改成"全体成员轮流当秘书"或"用一个中立模型定稿"？
