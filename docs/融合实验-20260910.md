# 融合实验 2026-09-10：从坏尺子到可信结论

> 一天的实验记录。主线不是"改机制"，是**先发现测量方法本身是错的**，重建尺子，然后才拿到第一个可信结论。

## 摘要

| 发现 | 结论 |
|---|---|
| 旧尺子（绝对打分） | **不可信** —— 同一批稿子两次评分差 9 分，换个裁判结论从 −5 翻到 +8 |
| 新尺子（配对比较 + 双向） | 同档裁判和跨档裁判**结论一致** |
| 位置偏好 | **82%，所有模型通病**（S 档与 SS+ 档完全一样） |
| 同档模型当裁判 | **够用** —— 噪声来自范式，不是判断力 |
| 融合效果 | 3 个任务 × 2 个对手，**全胜** |
| 失败模式 | 范围蔓延（取并集），已定位并修复验证 |

## 一、旧尺子为什么不可信

一直用「绝对打分」：让一个模型给几份稿子打 0-10 分。实测：

- 同一份单稿（一字未改），同一裁判，两次独立评分：**43 分 → 34 分**
- 同一批稿子，裁判从 glm-5.2 换成 deepseek-v4-pro，融合 vs 最好单稿的结论：**−5 → +8**

噪声 ±9，而要测的效应只有 ±5。**拿读数误差比信号还大的尺子做实验，结论纯属碰运气。**

历史上的两次误判都与此有关（见 `AB融合实验-20260909.md`）。

## 二、新尺子

`tests/integration/pairwise.py`（工具早就有，一直没用起来）：

1. **配对比较**：一次只给两份，问"哪份更好"，不要求跨时间的稳定标准
2. **双向**：AB + BA 各评一次，位置偏好互相抵消
3. **Bradley-Terry 聚合** + bootstrap 置信区间
4. **判据换掉**：不看"赢几分"，看"两个选手的 CI 分不分得开"—— CI 重叠就是分不开，别谈差距

## 三、位置偏好：所有模型的通病

同一批稿子，两个不同档位的裁判：

| | glm-5.2（S 同档） | deepseek-v4-pro（SS+ 跨档） |
|---|---|---|
| 位置偏好 | **14/17 = 82%** | **14/17 = 82%** |

**完全一样。** 不是模型强弱的问题。

**但双向比较能抵消它**：在这两个裁判下，融合 / glm-5.3-flash / deepseek-v4-flash 的**排序完全一致**。

### 结论：验证困境有解

之前认为"同档裁判不可靠 → 只好用强裁判 → 强裁判违反同档约束 → 无法验证"。

**这个链条的第一环就是错的。** 同一个同档裁判（glm-5.2），在绝对打分下结论乱翻，在配对 + 双向下与跨档强裁判结论一致。

> 噪声来自**范式**，不来自**判断力档位**。

## 四、干净数据上的结论

三个任务，融合稿 vs 两份单稿，配对比较双向：

| 任务 | 融合 vs glm-5.3-flash | 融合 vs deepseek-v4-flash |
|---|---|---|
| brief 1 | 4:0 | 4:0 |
| brief 2 | 3:0 | 4:0 |
| brief 3（修前） | 4:0 | **0:4** |
| brief 3（修后） | 4:0 | **3:1** |

- 对较弱的单稿：**11:0**，CI 完全不重叠
- 修复范围约束后：**3 个任务 × 2 个对手全胜**

**局限**：每对只有 4~8 次比较，CI 仍重叠（融合 1.94~10.00 vs deepseek 0.22~5.29）。"赢"是稳的，"赢多少"测不准。

## 五、失败模式：范围蔓延

brief 3 修前输给 deepseek 单稿 0:4。诊断：

需求原文只要求「多租户计费模块：按用量计费，套餐/超额/退款，账单生成与对账，租户隔离」——**一个字没提支付网关、账本、缓存**。

关键词计数：

| 关键词 | glm-5.3-flash | deepseek | 旧融合稿 |
|---|---|---|---|
| payment | 22 | 0 | 17 |
| ledger | 16 | 0 | 14 |
| 账本 | 10 | 0 | 13 |
| Redis | 7 | 1 | 6 |

**融合稿的超范围内容全部继承自 glm-5.3-flash**，不是定稿人编的 —— 定稿人没发挥，它是照搬。

**根因**：机制只约束**长度**（"不取并集、不堆砌"），不约束**范围**。需求没要求的模块，只要某成员提了、评审没驳回，就会进终稿。

裁判原话（四次一致）：
> "方案甲范围更聚焦，未引入支付网关/缓存/账本等超范围复杂度"
> "甲方案更贴合需求边界，无过度设计"

## 六、修复与验证

**修复**：`_V2_FINALIZE` 加第 4 条 —— 逐条核对原始需求，`modules / data_model / api_contracts / tasks` 每项必须能指回需求中的某一条；需求没要求的一律不写进主方案，确有必要写进 `risks` 标注「范围外建议」。

**验证（干净 A/B，唯一变量是这条约束）**：

```
约束前：融合 vs deepseek-v4-flash = 0:4
约束后：融合 vs deepseek-v4-flash = 3:1
```

裁判理由明确点名："需求边界精确度 —— **明确排除支付网关**"。

关键词也随之下降：payment 17→1、支付 12→2、Redis 6→0、网关 6→2。

**ledger 仍留在正文（14→23）** —— 但可能是对的：需求写了"账单生成与对账"，账本是实现对账的一种数据模型设计，deepseek 那份不用账本也实现了对账（另一条路）。这是判断，不是遗漏。

## 七、同一批实验里修掉的其他问题

- **定稿人看不到原文**：`_V2_FINALIZE` 原本只喂"提取员的转述"，转述漏掉的字段定稿人补不回来（实际发生过整段 tasks/risks 丢失）。已改为附带各成员原稿全文。
- **输出额度**：那是上一轮修的（`MODEL_MAX_TOKENS=131072`），本轮验证有效 —— 修复后所有稿子 JSON 完整、tasks/risks 齐全。

## 八、截断坑（第三次）

做 A/B 前必须验证**两臂都写完整**。这一天里踩了第三次：

- 第一批缓存（`.ab_cache_3v_nodebate.json`，9/9 跑）里融合稿断在字符串中间、无 tasks/risks → 得出"融合惨败"，**作废**
- 发现方式：**裁判的 reason 字段**里反复出现"内容被截断且缺失任务拆解"

**教训**：看这类实验不能只看 winner，理由里藏着真相。验证方法：剥掉 markdown 围栏后看是否以 `}` 结尾 + 必填段是否存在。

## 九、工具与复现

```bash
  .venv/bin/python -u tests/integration/pairwise_run.py
```

- `pairwise.py` — BT + bootstrap CI 库（自带自检 `python pairwise.py`）
- `pairwise_run.py` — 配对比较实验脚本（本轮新写）
- `v2_fusion_run.py` — v2 融合端到端
- **`QIDIAN_STALL_TIMEOUT` 必设**：长输入（86k 字）prefill 出的首 token 会超过默认 90s，被误判成停滞掐断

## 十、定稿人决定产物的范围纪律（当天晚些时候）

一个意外发现，比范围约束本身更重要。

**实验**：同一批单稿、同一条需求、同一个机制，**只换定稿人**（`_first_speaker` 决定，默认取"提分歧最多者"）：

| 关键词 | glm-5.3-flash 当主角 | deepseek-v4-flash 当主角 |
|---|---|---|
| ledger | **23** | **1** |
| RabbitMQ | 7 | **1** |
| 字数 | 38339 | 32216 |
| 融合稿范围违例 | 4 处 | **0 处** |

- **glm 当主角时把两家的超范围内容都收进来**（自己的 ledger + 对方的 RabbitMQ）→ 乘法器
- **deepseek 当主角时连自己的 RabbitMQ 都砍了** → 过滤器

**原规则是「谁提分歧最多谁执笔」（`_first_speaker`），跟范围纪律毫无关系。** 这也是"先说的一方全胜"的根子：先开口的人不但赢下辩论，还拿到执笔权，顺手把整份稿子的风格定了。

**已改成按纪律选人**：`_pick_writer` 读 `.qidian/model_discipline.json`（由 `coverage_audit.py` 累积的违例率），低的优先；无数据时回退原规则。当前表 `deepseek 1.0 / glm 3.0` → 会选 deepseek。

**不是写死规则，是让数据自己选** —— 换模型、换阵容，表会自己更新。

## 十一、5.3 的归因纠正（重要）

我们原本写的是"**融合稿有取并集倾向**"，把责任推给了模型的性格。5.3 指出这是**管线设计出来的行为**：

第②步那三类里有一类叫 **「采纳的独有做法」** —— 一条明文的采纳指令，采纳权在提取员一个模型手里，**没有任何溯源要求**。glm 的支付网关写得漂亮、deepseek 没写，按这套分类法它就是教科书级的"独有做法"，被并进去是流水线按设计执行。

**数据反过来证明定稿人在克制**：payment 22→17，它顶着采纳指令砍了近四分之一。

所以正确的问题不是"怎么让它舍得砍"，而是"**是谁、在管线哪一步，把这份内容合法地送到它面前的**"。

## 十二、审计表的定位（实测修正 5.3 的建议）

5.3 建议用"独立审计 + 代码比大小"替代配对比较，并给了验证方法："让审计排名复现双向配对的排名"。

实测**这个验证会失败**。第一次审计（对象是 glm 主角版融合稿）：

```
审计排名（违例少者优）   deepseek(2处) > 融合(4处) > glm(5处)
配对比较排名             融合 > deepseek > glm          ← 前两名相反
```

（注：第二次审计换了 deepseek 主角版的稿子，融合稿 0 处违例，排名确实变成了 `融合 > deepseek > glm`——但那一版没有跑配对比较，**不能作为"审计排名复现配对排名"的证据**。）

原因：审计表只覆盖**两个维度**（该有的有没有、不该有的有没有），测不到"做得好不好"；而裁判在配对时权衡全部维度，融合稿在完整度/严谨性上更厚，所以赢。

**结论**：审计表做门禁成立（结构检查），替代质量排序不成立（质量判断）。两者各司其职，别混为一谈。
