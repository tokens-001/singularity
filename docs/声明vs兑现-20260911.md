# 声明 vs 兑现 —— 架构 schema / prompt 承诺的字段，有多少真的被消费

> 2026-09-11 晚。**判据：`被读到` ≠ `被兑现`。**
> 起因：GLM-5.3 指出 `constraints[].check`（prompt 明写"必须可机器检查"）和
> `token_budget_total`（"预算 $5"）都**只有声明、没有兑现**。这两条经核实**都成立**，
> 而且是同一个病 —— 于是把这一类一次扫完。

## 四档判据

| 档 | 含义 |
|---|---|
| **机械** | 真的执行 / 比对 / 枚举校验 —— 内容会影响结果 |
| **喂 LLM** | 只拼进 prompt，交给模型判断 |
| **仅校验存在** | 只看 key 在不在、非不非空，**内容直接丢弃** |
| **无** | 全仓找不到消费点 |

⚠️ **扫描的两个已知局限**（自己的工具也要独立验证）：
1. 主扫描按 `\.get("字段")` / `["字段"]` 精确匹配 —— **漏掉"先写文件再从文件读"的间接消费**。
   例：`test_cases` 写进 `test_cases.json` 后由 `orchestrator.py:539` 真跑，不走 `.get`。
2. "仅校验存在"是**人工判定**的（不是自动分类）—— 自动只给出命中行，分档靠读那些行。

## 一句话

**17 个字段里：2 个真机械、5 个只喂 LLM、7 个只校验存在、3 个完全没人读。**
（`fusion_notes` 尤其扎眼 —— 委员会每轮都算它，零消费。）

最大的那条仍然是 `constraints[].check`：**它在 prompt 里被明确承诺"必须可机器检查"，
而管线从来没查过。** 这不是"少做了一步"，是**系统对外宣称了一件事、自己没做到** ——
和 09-11 全天在治的是同一个病（`_SnapProxy` 门禁恒空、`_usable` 恒返回可用、
REVIEWING 双入口……）。

## 修法建议（按性价比）

1. **`check` 落地**（收益最大，也是"信任上限"的地基）：架构师把 check 产成
   `{cmd, expect_exit, expect_stdout/file}`，验收层加机械 runner。
   ⚠️ **安全前提**：这等于让**模型生成的字符串变成平台要执行的命令**，
   而架构 JSON 来自委员会、受任务描述影响（prompt injection 面）。
   必须：命令白名单 + 非 shell + 限在 worktree 内 + 超时 + 无网络；
   **并且把命令在 GATE2 展示出来给人批** —— GATE2 本来就是人对架构的门，
   批命令是自然的延伸。这样它从"危险的自动化"变成"人在环里的机械化"。
2. **`fusion_notes` 要么消费要么删**：它记的 `resolved_contradictions` /
   `adopted_insights` / `filled_blind_spots` 正是"融合值不值"的证据 ——
   现在算完就扔。接到 GATE2 面板上，成本极低。
3. **`risks` / `mitigation` / `interfaces` / `data_model` / `tech_stack`**：
   要么接到下游（风险→审查关注点、接口→跨任务一致性检查），要么从 schema 里删掉。
   **留着不用的字段比没有更糟** —— 它让 prompt 显得丰满，让评审以为有这些能力。
4. **预算真实化**：项目花费到 80% 告警、100% 硬停等人工。

## 附带发现

`_validate_architecture` 只对 `complexity` 做了枚举校验，其余字段全是"非空即过"。
`estimated_files` 也校验了（必须是 list）。这说明**这个校验器有能力做机械校验，
只是覆盖面很窄** —— 把 `layer`、`acceptance` 之类纳入枚举/格式校验是低垂果实。
