## 🔴 已核实的安全口子（不来自 ZCode，是我顺着评审的话读出来的）

`src/singularity/scheduler/executors/openai_agent.py:662-669`

```python
def _check_permission(self, tool_name: str, args: dict) -> tuple[bool, str]:
    """Permission 检查。如注入 checker 则调用，否则默认允许。"""
    if self._permission_checker:
        try:
            return self._permission_checker(...)
        except Exception:
            pass                      # ← ① 吞掉
    return True, ""                   # ← ② 默认放行
```

**同一个函数里叠了两个 fail-open**：
1. `_make_permission_checker()`（`_dispatch_skills.py:176`）自己坏了会 `return None`
   ⇒ `if self._permission_checker:` 为假 ⇒ **直接 `return True`**。
2. 就算 checker 在，**它一旦抛异常**（`request_approval` 超时/IO 挂等）⇒ `except: pass`
   ⇒ **还是 `return True`**。

⇒ **权限检查这条链上任何一环坏掉，工具就静默获得全部放行。**
作者注释写的是"如注入 checker 则调用，否则默认允许"——**"默认允许"是 fail-open**，
而这里正是 §25「门禁类必须 fail-closed」该管的地方。

**与 ZCode 挖出的另两条是同一方向**（`router.py:159` / `_observer_tools.py:135`）：都是"挂了就往宽松走"。

### ⚠️ 「按方向找」也不行 —— 我试了，两头都不对（2026-09-14 00:5x）

按 key 会漏，所以我想"那就按方向找"（扫 `except` 吞掉 + 函数里有放行/中性的 `return`）。
**写了扫描器跑了一遍，结论是这条路也不通：**

- **太窄**：只认 handler 体是 `pass` 的 ⇒ 漏掉**赋值型**的。
  实测 **25 个候选里，两处已知 fail-open 一处都没有** ——
  `router.py:159` 是 `except: result = RouteResult()`、`_observer_tools.py:135` 是 `except: gate = False`，
  **都是赋值不是 pass**。
- **太宽**：25 个候选里**大部分是对的**（`_cleanup_terminal_heartbeat` 清理失败返 False、
  `tracker.transition` 的 CAS 失败返 False —— 本来就该这样）。

⚠️ **而且第一版扫描器返回 0 处** —— 因为它要求 `return` 紧跟在 `try` 后面，
而 `_check_permission` 的 `return True` 在 `if` **外面**。**"0 处"不是"没有"，是我的规则错了。**
后来加了**阳性对照**（找不到已知那一处就自报失败）才定住。
**这就是守卫 docstring 里那句"扫不到东西的守卫比没有更坏"** —— 这次是我自己踩的。

**结论：这一族没有便宜的判据，得人看。** 判据是**这个默认值是不是"往宽松走"**，
而不是形状 —— `cleanup` 返 False 是对的，`权限/门禁/路由` 返 True 才有问题。

### ✅ 已经人看完了（2026-09-14 01:0x）—— 结论：**只有 1 处真坏，就是已知那处**

| ✅ 方向对 | 15 | 见下三类 |

**15 处"方向对"的三类**（都不是毛病，**别改**）：
- **fail-closed**：`request_approval` 异常 → `return False`"按拒绝处理"；`_is_safe_api_url` → `False`；

### 🔑 由此得到的结论：**别为这一族造判据**
