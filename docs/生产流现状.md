## 一、实际流转图

```
TEMPLATE
  │  立项：填 description；_needs_research() 决定要不要调研
  ▼
RESEARCHING ──(可跳过)──┐
  │  调研员出报告        │
  ▼                     │
GATE1 ◄─────────────────┘      人审        打回 → TEMPLATE（重写需求）
  │
  ▼
PLANNING
  │  架构师出方案 + 任务清单
  │  ★ 架构类任务 → 多模型委员会（见 §三）
  ▼
GATE2                          人审        打回 → RESEARCHING（回调研）
  │
  ▼
EXECUTING
  │  拆任务 → tracker → orchestrator 逐个执行
  ▼
INTEGRATING                    非人门
  │  多路 worktree 合并 + 集成测试
  │  失败 **第 1 次** → 回 EXECUTING；**第 2 次即触顶** → GATE2
  │  （`project._INTEGRATE_MAX_RETRIES = 2`，判据是 `>=`。原文写"失败 ≤2 次才回"是错的）
  ▼
REVIEWING                      非人门
  │  跑验收：QA 报告 + 安全审计 + E2E（★ 只报不改，见 §四专条）
  │  ⚠ 架构没产出 constraints 时整段跳过
  ▼
GATE3                          人审        按 fix_route 分级打回，见下
  │
  ▼
DELIVERING                     非人门
  │  打 tag + 收 README/打包配置 + 归档报告 → 写 delivery_manifest.json
  ▼
DONE
```

**GATE3 打回是分级的**（`handle_gate3_reject`）：

| fix_route | 回哪 | 说明 |
|---|---|---|
| `impl` | EXECUTING | 重置 DONE 任务为 PENDING 重做 |
| `design` | PLANNING | 清空 `architecture` 重新规划 |
| `note` | 不回退 | 只记录，不阻断 |
| **读不到 QA 报告** | **EXECUTING** | 无依据时回实现层（**不动架构**），见 §四 |

## 二、两套驱动（**原来的债已修，残余是"分工只活在注释里"**）

> ⚠️ **本节 2026-09-14 改过一次** —— 原话说"`run_phase` 不认识 `INTEGRATING`/`DELIVERING`，
> 走到就报 `未知 phase`"，**那句自 2026-09-11（`a41f590`）起就是假的**，但一直没改。
> 外派材料照抄了它 ⇒ 写出一个假前提 ⇒ 评审-02b 又花力气推翻。
> **现在`test_doc_facts.py` 钉住了这句话，再出现会先红。**

同一个 `phase` 被**多个入口**写。`run_phase` 与调度循环**都认识全部阶段**：

| 驱动 | 什么时候跑 | 认识的阶段 |
|---|---|---|
| `workflow.run_phase()` | 人手点"下一步" / CLI | **全部**（`INTEGRATING`/`DELIVERING` 走"交棒给调度循环"的分支，不再报未知） |
| `orchestrator._auto_trigger_test_fix()` | 调度循环每一 tick | 推 `INTEGRATING` / `DELIVERING` |
| `_api_projects.project_gate_confirm()` | 人点通过 | 启 `planning` 等 |
| GATE3 打回路径 | 人点打回 | 按 `fix_route` 分级回 `EXECUTING`/`PLANNING` |

🔴 **残余的债（降级了，但没消失）**：**"哪个阶段归谁推"只写在
`_api_projects.py:198` 的注释里**（原话："planning —— 只有 run_phase 能推"）。
约定会漏 —— 案例 B（跑得最多的那条路不写清单）就是这么漏的。
治法是把这份分工变成数据（`PHASE_DRIVER` 表）+ 越权告警 + 调用点守卫测试，**还没做**。

**2026-09-11 起**：所有流转都过 `ProjectState.set_phase(phase, reason)` 这一个口，
自动留痕（from / to / reason / ts）。以前 21 处散点赋值，出事时落盘里只有最终
phase、**没有任何轨迹** —— "点通过永远弹回 GATE2"那种死循环，翻遍文件也看不出

## 三、多模型委员会（唯一验证过有价值的能力）

**触发条件**（两个都满足）：
1. `_is_architecture_task(task)` —— 任务文本含 `模块划分 / 数据模型 / API契约 / 技术栈 / 架构方案 / 系统架构`
   （架构阶段的 prompt 天然全含；普通用户任务一般不含）
2. `len(chain) >= 2` —— 候选链至少 2 个模型

**链条**：并行出方案 → `fuse_architecture_v2`
（提取共识/分歧 → 辩论若干轮 → 定稿 → 其余委员确认 → 有异议重写 1 次）
> 轮数 = `max(2, QIDIAN_FUSION_V2_ROUNDS)`，**默认 5**（原写"1~3 轮"）——
> `execution_judge.py` 里那句 `max_rounds = max(2, int(os.environ.get(...)))`

**席位**：取的是**该阶段配的模型名单**（`restrict_to_lineup` 那条路）——**没有 4 席上限**
（4 是委员会收集初稿时的线程池并发，两回事）。
**去重**：按 `api_store.canonical()` 归一 —— 两个 id 指向同一实际模型时只留一个
（别名由 `openai_agent` 在响应路径上对账写入，`/v1/models` 看不出来）。

**实测**：委员 2 席、621 秒、融合产物 17158 字符。
⚠ 慢主要慢在**提取员**那一步（见 §四），不在委员本身。

### 专条：流程重量分级（#1，2026-09-12 已修）

**先说清一件本文件初版没写对的事：重流程是「两个独立开关」，不是一个。**

| | 开关 | 位置 | 成本 |
|---|---|---|---|
| 6 维度调研 | `_needs_research` | `workflow.py` | 1 次便宜调用（`no_tools`）+ GATE1 人审 |
| **3 方案文档** | `_is_architecture_task` | `execution_judge.py` | **多模型委员会：N 并行起草 + 融合** |

架构阶段的 prompt **本身就含**「模块划分/数据模型/API契约/技术栈/架构方案」
→ `_is_architecture_task` 恒真 → **委员会每次必开**。
所以初版那句"走同一套 6 维度调研 + 3 方案文档"是对的，但**只改 `_needs_research` 碰不到贵的那一半**。

**修法**：判据收敛到**唯一入口** `project.resolve_flow(project) -> FlowDecision`
（两个开关在同一次调用里一起出来，防御模式 §5）。新增 `ProjectState.flow_weight` 字段：

- **`auto`（默认）** —— 调研沿用旧启发式；**委员会一律开**。
  ⚠️ 刻意的非对称：auto **永不否决委员会** —— 凭中文子串猜"这活小"就砍掉贵的那半，
  正是 §47 禁的那类静默失败。**拿不准 → 跑贵的。**
- **`light`** —— 两样都省（跳过 RESEARCHING + GATE1，架构由单模型出）。
- **`heavy`** —— 两样都跑。

**默认值就是今天的行为**（存量项目文件没有这个键 → 读出来是 `auto`），**零迁移**。

**谁定**：系统**只建议**（`suggest_flow`：描述 ≤100 字且无调研触发词 → 提示"看着像小活"），
**人点了才生效**（`PUT /api/projects/<id>/flow-weight`）。不点就还是重的。
建议器**不写任何状态**，所以误判的代价只是"用户没点那一下"。

**留痕**（防御模式 §44）：立项时写一条 `flow_weight` lineage，
带 `weight/source/research/committee/reason` —— 跳过必须是**带理由的显式事实**，不能是"没发生"。
进 `lineage` 而不是 `issues`：`issues` 的**整体清空在 `workflow.run_test_fix_loop` 里**（`project.issues = []`，
在验收之前那一段）—— 原文写"在 `_run_execution` 开头"是错的，那个函数不清 issues。

**没做的**（免得下次重复提）：不动 GATE2/审查/交付（那是质量底线不是流程排场）；
不自动判轻量；~~不碰那三套对不上的模板表（后端 4 / API 收 8 / 前端给 5）~~ —— **已修**：
API 改成从 `TEMPLATES` 派生，三处现在都是 4。

测试：`tests/test_scheduler/test_flow_weight.py`（纯函数、不调 LLM）。
⚠️ **条数别写死**（原来写 18，现在 22 —— 它只会跟着增删漂）：要现数就
`.venv/bin/python -m pytest tests/test_scheduler/test_flow_weight.py --collect-only -q | tail -1`。

### 专条：审查层到底有什么、缺什么

> 2026-09-11 更正：本文件初版写成「审查层是空的」。**说过头了** —— 它在跑，只是不闭环。

**有的**（都在执行路径上）：

| 检查 | 位置 |
|---|---|
| QA 工程师报告（`qa-report.md`） | `_run_verification`（调 LLM） |
| 安全审计师报告（`security-report.md`） | 同上，并行 |
| 结构化 QA 报告（passed/issues/verdict/fix_route） | `validator.build_qa_report` |
| 需求符合性核验 | `supervisor.check_requirement_conformance`（LLM 主 + 机械兜底） |
| 约束清单验收 | `validator.qa_acceptance_review`（定义在 validator；`_review` 里是调用点） |
| 每个任务后的机械检查 | `run_post_exec_checks`（定义在 `_review.py`；`_exec.py` 里是调用点）（**软信号**） |
| E2E 用例执行 | 对照 `test_cases.json` |

**缺的**（被 `d3c117e` 删掉的那一环）：

```
发现问题的 AI  →  ✂️  自己改  →  再验
                 ↑ 这一环没了
```

所以责任链是 **AI 报告 → 人判 → 人决定改不改**。"发现"能力还在，"自动修"没了。

**两处会让它不跑 / 不拦**：

1. **前置条件能整段跳过**：架构没产出 `constraints` → `constraints_checklist` 为空 →
   `_run_verification` 直接 `return`，上面那张表**一行都不执行**
2. **一部分是软信号**：需求符合性对账的注释自己写着「只写软信号 + warning
   （机械关键词，**先不设 hard gate**）」—— 发现了也不拦

**为什么它仍然是理论边界的约束**：「能自动验证到多大，才能自动推进到多大」——
现在验证有了、闭环没有，所以推进仍然要人接手。
