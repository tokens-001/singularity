## 一、实际流转图

```
TEMPLATE
  │  立项：填 description；_needs_research() 决定要不要调研
  ▼
RESEARCHING ──(可跳过)──┐
  │  调研员出报告        │
  ▼                     │
GATE1 ◄─────────────────┘      人审        打回 → TEMPLATE（重写需求）
  │
  ▼
PLANNING
  │  架构师出方案 + 任务清单
  │  ★ 架构类任务 → 多模型委员会（见 §三）
  ▼
GATE2                          人审        打回 → RESEARCHING（回调研）
  │
  ▼
EXECUTING
  │  拆任务 → tracker → orchestrator 逐个执行
  ▼
INTEGRATING                    非人门
  │  多路 worktree 合并 + 集成测试
  │  失败 ≤2 次 → 回 EXECUTING；触顶 → GATE2
  ▼
REVIEWING                      非人门（★ 空壳，见 §四）
  │  进去立刻跳 GATE3
  ▼
GATE3                          人审        按 fix_route 分级打回，见下
  │
  ▼
DELIVERING                     非人门
  │  打 tag + 收 README/打包配置 + 归档报告 → 写 delivery_manifest.json
  ▼
DONE
```

**GATE3 打回是分级的**（`handle_gate3_reject`）：

| fix_route | 回哪 | 说明 |
|---|---|---|
| `impl` | EXECUTING | 重置 DONE 任务为 PENDING 重做 |
| `design` | PLANNING | 清空 `architecture` 重新规划 |
| `note` | 不回退 | 只记录，不阻断 |
| **读不到 QA 报告** | **EXECUTING** | 无依据时回实现层（**不动架构**），见 §四 |

## 二、两套驱动（这是当前最硬的一条债）

同一个 `phase` 被**两个入口**写，各自认识**不同的阶段子集**：

| 驱动 | 什么时候跑 | 认识的阶段 |
|---|---|---|
| `workflow.run_phase()` | 人手点"下一步" / CLI | TEMPLATE / RESEARCHING / PLANNING / EXECUTING / GATE1~3 / REVIEWING / FIXING / DONE |
| `orchestrator._auto_trigger_test_fix()` | 调度循环每一 tick | 还会推 **INTEGRATING / DELIVERING** |

**`run_phase` 不认识 `INTEGRATING` 和 `DELIVERING`** —— 走到就报 `未知 phase`。

**2026-09-11 起**：所有流转都过 `ProjectState.set_phase(phase, reason)` 这一个口，
自动留痕（from / to / reason / ts）。以前 21 处散点赋值，出事时落盘里只有最终
phase、**没有任何轨迹** —— "点通过永远弹回 GATE2"那种死循环，翻遍文件也看不出
是谁把它推回去的。现在直接读 `project.lineage` 里 `action == "phase"` 的条目。

## 三、多模型委员会（唯一验证过有价值的能力）

**触发条件**（两个都满足）：
1. `_is_architecture_task(task)` —— 任务文本含 `模块划分 / 数据模型 / API契约 / 技术栈 / 架构方案 / 系统架构`
   （架构阶段的 prompt 天然全含；普通用户任务一般不含）
2. `len(chain) >= 2` —— 候选链至少 2 个模型

**链条**：并行出方案 → `fuse_architecture_v2`
（提取共识/分歧 → 辩论 1~3 轮 → 定稿 → 其余委员确认 → 有异议重写 1 次）

**席位**：从候选链里取，最多 4。
**去重**：按 `api_store.canonical()` 归一 —— 两个 id 指向同一实际模型时只留一个
（别名由 `openai_agent` 在响应路径上对账写入，`/v1/models` 看不出来）。

**实测**：委员 2 席、621 秒、融合产物 17158 字符。
⚠ 慢主要慢在**提取员**那一步（见 §四），不在委员本身。

## 四、已知的窟窿（都还开着）

| # | 什么 | 位置 / 症状 |
|---|---|---|
| 1 | **`run_phase` 不认识 INTEGRATING / DELIVERING** | 走人手路径遇到这两个阶段 → `未知 phase` |
| 2 | **REVIEWING / FIXING 是死代码** | 进去直接跳 GATE3。AI 自审已删、**替代品没装** —— 审查责任全在人 |
| 3 | **架构校验只警告不拦** | `_validate_architecture` 查出"缺少必填字段"只往返回文案塞一句 `(⚠阻塞: …)`，照样进 GATE2 |
| 4 | **流程重量不分级** | `_needs_research` 只看 template + 关键词。单文件工具和多模块系统走同一套 6 维度调研 + 3 方案文档 |
| 5 | **重入语义没定义** | 重进一个阶段时哪些痕迹该清、哪些计数归零，没有声明，各写入点自行其是（防御模式 #44/#45 是它的两个投影） |
| 6 | **提取员默认是硬编码** | `execution_judge._V2_EXTRACT_DEFAULT = "glm-5.3-flash"`；已在 `fusion.toml` 显式覆盖为 `deepseek-flash`，但**它同时是委员会成员**（自己评自己，代码有告警） |
