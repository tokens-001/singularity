## 要回答的问题

**"多家模型互相评审 + 融合"到底值不值？**

换句话说：同样一笔钱，花在"**一个强模型自己多改几轮**"上，会不会比"**两家各出初稿再融合**"更好？

现在的架构押的是后者（P2 说的"多视角碰撞是唯一验证过的核心价值"）——
但那次验证只证明了"**机制能跑**"（2 席 / 621 秒 / 产出 17158 字），
**没证明"比单模型强"**。这个实验就是补那一刀。

## 三个臂

| 臂 | 怎么干 | 为什么是它 |
|---|---|---|
| **A** | 最强的**单个**模型 + 等预算下多轮自我修订 | 如果它赢 → **砍掉一半复杂度和成本** |
| **B** | 现在的**对称委员会**（两家各出初稿 → 融合） | 现状，对照组 |
| **C** | **非对称**：1-2 家起草 + 1 家**专职挑刺** + 定稿 | 论文没验过这条路；攻击者是**不同的任务**，不是给起草者换个提示词 |

⚠️ C 不是"给起草者贴个'请挑刺'的标签"——那是已经证伪过的做法（盲评 31 vs 32）。
C 的挑刺方**只干挑刺**，不参与起草。

## 定什么、量什么

每个臂都跑**同一个任务**、**同一份需求描述**，走完整流水线到交付。然后量三样：

1. **质量** —— 配对比较（盲评）
2. **机械可验率** —— 用 `_machine_checks.coverage()`（2026-09-12 刚落地）
3. **成本与时长** —— 从 `token_usage.json` 按项目取（现在有累计口径了）

### 盲评怎么做（**必须遵守已有的那条尺子**）

`[[fusion-measurement-method]]` 记的结论：**绝对打分不可信、位置偏好 82% 是通病**。所以：

- **配对比较**，不是打分
- **双向**：A vs B 跑一遍，B vs A 再跑一遍（对调位置）
- 三对都要比：A-B、B-C、A-C

## ⚠️ 风险与不确定（写在最前面，别事后补）

1. **每个臂只跑一次，噪声极大。** 论文是 500 道题取平均；我们 N=1。
   **所以这个实验只能"看一眼"，不能"下结论"。**
2. **要真下结论**得每臂重复 5-10 次 —— 成本和时间都翻十倍，那是另一个量级的决策。
3. **任务类型单一**：单文件 CLI 上的结论，未必推广到多模块系统。
4. **A 臂的"等预算"怎么才算等**是个设计问题：按 token 等？按钱等？按轮次等？
   三种口径可能给出不同结论 —— **跑之前要定死一个，并写下来**。
