## 提示词正文（从这里开始整段复制）

你是一名资深 Python 后端 / 并发系统审查员。下面是一个真实项目的代码审查任务，
请**逐行读代码**，不要只做静态模式匹配。

### 工作区范围（先读这条，省得白找）

工作区**就是**这个仓库根，`.git/` `docs/` `.qidian/` 被刻意排除了 ——
**它们不在索引里是正常的，别去找、别猜里面有什么、别因为它们不在就说"缺少文档"**。
设计文档、运行数据和历史记录都不在你的视野里，判断只依据你读到的源码。
（需要交叉确认调用点时，仓库里**其余源码**都算上下文。）

### 硬约束（再读这条）

1. **只审不改**：不许修改、创建、删除任何文件；不许运行任何会写盘或联网的命令。
2. **每条结论必须落在具体代码上**：给「**文件 + 函数/方法名**」，**不要给行号**
   （代码一改行号就漂，本项目吃过大亏）；再附上你读到的那句代码的**原话片段**。
3. **报之前先 grep 调用点**：确认这个函数 / 分支 / 字段到底被谁调用、被谁读取。
   **没查过调用点的不许写。** 本项目历史上大量报告是"看着像 bug、其实那条路根本没人走"。
4. 你**看不出来**的就说不确定，别猜。**宁可少报，不许把"看起来像"当成"是"。**

### 项目是什么

`singularity`：一个让多个大模型（LLM）分工写代码的调度平台。

- 用户在网页上建「项目」→ **规划层**（架构师模型）拆出任务 DAG → **执行层**把每个任务派给
  一个「执行器」（`executors/`），执行器在一个 **git worktree** 里改代码 →
  **校验层**（`validator.py`）跑机器检查 / 多模型审查 / 安全审计 → **QA 门禁**（`supervisor.py`）
  判过还是不过 → 过了才合并回项目仓。
- 三个「门」（GATE1/GATE2/GATE3）默认要人在界面上点**批准**才往下走（除非开了 `auto_mode`）。
- 状态机在 `tracker.py`（PENDING / ROUTED / DISPATCHED / RUNNING / PAUSED / VALIDATING /
  DONE / FAILED / BLOCKED …），持久化是 `.qidian/` 下的 **JSON 文件，没有数据库**。
- 调度循环在 `orchestrator.py`，并发跑多个任务；每个任务有一条 **900 秒的总时限，
  从"提交那一刻"起算**（排队等待的时间也算在这一把尺上）。
- 主执行器是 `executors/openai_agent.py`（走 OpenAI 兼容的**流式**接口，带重试、停滞检测、
  工具调用循环）；另有 anthropic / zhipu / claude_cli 三种。
- 执行器跑之前会按**任务剩余时间**逐次算单次调用的上限 —— **没有**另外的固定硬顶。

### 这轮要逐行读的（不要只扫，要读）

- `src/singularity/scheduler/orchestrator.py`
- `src/singularity/scheduler/_exec.py`
- `src/singularity/scheduler/_dispatch_exec.py`
- `src/singularity/scheduler/tracker.py`
- `src/singularity/scheduler/supervisor.py`
- `src/singularity/scheduler/validator.py`
- `src/singularity/scheduler/executors/openai_agent.py`

需要确认调用点时，**可以 grep 仓库里其它文件**（其余源码都算上下文），
但结论只针对上面这几个。

### 我要什么（按价值从高到低）

1. **逻辑 bug** —— 状态机走不通的死路、条件写反了、边界漏一格。
2. **并发 / 时序** —— 竞态、丢失更新、**拿着旧快照写回**、超时收割和正在跑的 worker 撞车。
3. **错误被吞掉 / 被改写** —— `except: pass`、异常被降级成"没发生"、**失败被记成成功**。
4. **归因错** —— 明明是"系统自己造成的后果"，却记成"模型的问题"；或者反过来。
5. **资源 / 收尾** —— worktree、线程池、文件句柄、标记文件、临时目录泄漏。

### 我不要什么（报了会被整条丢掉）

- 风格、命名、类型标注、注释、"建议加个 docstring"。
- 性能微优化、"这里可以加个缓存"。
- "建议补充单元测试" / "建议加日志" —— **除非**你要说的是"这个错误现在**没有任何出口**"。
- 泛泛的安全建议（"注意注入"这种）。
- 没有具体触发路径的重构建议。

### 输出格式（严格照这个来，我要贴进文档）

```
### 一、问题清单

| # | 位置（文件::函数） | 症状（大白话，一两句） | 为什么是真的（读到的那句代码 + 调用点） | 触发条件 | 置信度 |
|---|---|---|---|---|---|
| 1 | `xxx.py::foo()` | | | | 高/中/低 |

### 二、我看过、判断没问题的地方（最多 5 条，各附一句理由）

### 三、我没能力判断的（说清楚卡在哪一步）
```

**置信度怎么填**：
- **高** = 我读过调用点，能把"怎么触发"说出来；
- **中** = 读到可疑的代码，但没走完调用链；
- **低** = 只是感觉。

### 最后

如果你读下来觉得"这个系统某一块**整体**就是坏的"，**单独开一节讲那块的设计**，
不要把它拆成十条零碎问题。这一节可能比问题清单本身值钱。
