## 一、状态机与门禁

### 1. 终态可以被改判
- **症状**：已 merge 的任务被二次执行 / 二次合并，产出重复提交。
- **根因**：`transition()` 不校验旧状态，DONE 也能改回 PENDING / FAILED。「终态」只是约定，不是约束。
- **规则**：终态只放行白名单内的流转（`_TERMINAL_EXIT`）；GATE3 打回这类显式重置必须显式写
  `force=True`，别让默认路径能改判。

### 2. QA 门禁排在 DONE 之后
- **症状**：QA 判定 fail，任务照样 DONE、照样合并 —— 门禁形同虚设。
- **根因**：`finalize()` 先标 DONE 再跑 QA，门禁结果无处生效。
- **规则**：门禁必须排在**不可逆动作之前**（merge 前、标 DONE 前）。改 finalize 先看 DONE 在哪一行。

### 3. 写入的字段 ≠ 决策读的字段
- **症状**：审查打了低置信度，cascade 仍 `accept` 放行。
- **根因**：审查写 `quality["confidence"]`，决策读 `validation.confidence`，两条数据流没接上。
- **规则**：改「打分 / 评级」类字段时 `grep` 出所有读取点；写入方与读取方对不上就当场接线
  （如 `min(旧, 新)`）。

### 4. 审查路径上多个 bug 叠加
- **症状**：修完「审查打回失效」的一个原因，打回还是不对。
- **根因**：同一条路径叠了 3 个独立 bug（NameError + JSON 解析坏 + 需求核对缺失），修一个不够。
- **规则**：修「整条路径失效」的 bug 后，**跑一遍真实路径**确认真的通了，别假设「修了那个就好」。

### 5. 同一动作有多条入口
- **症状**：GATE 确认在一处生效，另一处绕过。
- **根因**：confirm 逻辑分叉成多条路径。
- **规则**：同一语义动作收敛到单一入口（如 `confirm_gate`），其他入口转发而非复制。

## 二、路径与仓库边界

### 6. worktree 任务里的路径基准用错
- **症状**：worktree 里语法坏掉的文件被放行合并；或测试文件被误判「删除测试」而拦下。
- **根因**：检查拿「项目根」去查 worktree 里的文件（用了 `repo_root_for(task)` 而非 `cwd`）。
  py_compile / ruff 找不到文件就**静默跳过**。
- **规则**：worktree 任务里一切路径检查的基准是 **worktree 根（cwd）**；工具「没找到文件」不能当通过。
- **同类已复发两次**：`_exec` 的 QA 门禁传参（09-09）、`no-delete-tests` 硬规则（09-07 `9bca7cd`）。

### 7. 跑任务前工作区是脏的
- **症状**：任务 merge 时把没提交的改动一起卷进「agent changes」提交。
- **根因**：merge 前会 `git stash`，脏工作区被卷走。
- **规则**：跑任务 / 让 agent 改代码前先 `git commit` 或 `git stash`；改前先 `git status`。

- **规则**：跑任务 / 让 agent 改代码前先 `git commit` 或 `git stash`；改前先 `git status`。

## 三、子进程、并发与清理

### 8. SSE 断线重连不清理队列
- **症状**：反复断连重连后 `_sse_clients` 越积越多，到上限后新连接被 503 拒。
- **根因**：断开时没把该连接的队列从注册表摘掉。
- **规则**：注册与注销成对，用 `try/finally` 兜住；队列要有界，满了丢旧而不是拒新。

### 9. 清理只发信号、不等停稳
- **症状**：留孤儿进程；迟到的事件打到已销毁的对象上。
- **根因**：清理流程发完终止信号就返回，不等子进程真正退出。
- **规则**：dispose 要等到**完全停稳** —— 发信号后等子进程退出；先关监听器 / 通知注册表，
  再终止进程。

### 10. 分发器里一个回调抛异常，饿死后面的
- **症状**：一个监听器报错，后面的监听器全不执行，或整个 promise 被 reject。
- **根因**：分发循环没有逐个隔离回调异常。
- **规则**：分发循环逐个 `try/except` + 记日志；订阅者行为不端不得破坏核心生命周期。

### 11. 把异步状态当同步结果
- **症状**：把 idle / running 当成「某次调用完成了」—— 多条排队消息、中途引导、取消共用同一区间。
- **根因**：后台任务完成与轮次边界存在竞争，状态是共享的，不是某次调用的返回值。
- **规则**：要判定「某次运行」就自己定义区间（如从回执到下次 idle）；等待的转换可能永不发生，
  必须显式处理「无需等待」分支。

### 12. worktree / 临时资源用完没清
- **症状**：worktree 残留、磁盘堆积。（演化史仅记名目：v2.1「worktree 泄漏」）
- **根因**：异常路径没清理，正常路径没配对。
- **规则**：创建即登记，`try/finally` 配对清理；失败路径也要清。

### 13. 跨线程改共享状态没守锁约定
- **症状**：任务 JSON 写坏 / 状态读串。（演化史仅记名目：v2.1「线程安全」）
- **根因**：多线程同时读写同一份文件或全局 dict。
- **规则**：改 tracker / config 这类共享状态必须走既有锁（`_LOCK`）与原子写（临时文件 + rename）；
  别在锁外直接写文件。

## 四、模型调用与结果判读

### 14. 架构任务给模型开了工具
- **症状**：架构任务写着写着去改代码，卡在「达到最大轮次」。
- **根因**：thinking 模型触发 tool_choice 降级，被注入「必须调用工具」。
- **规则**：纯思考类任务（架构 / 评审）禁工具（`tools=[]`）；需要工具的任务才开。

### 15. 空 tools + tool_choice=required
- **症状**：测试通过即停的收尾轮卡住 —— 没有工具可调，却要求必须调。
- **根因**：`tool_choice` 硬编码 `required`，与动态清空的 `tools` 冲突。
- **规则**：`tool_choice = "required" if tools else "auto"`；任何「按需清空 tools」的代码旁边都要检查
  tool_choice。

### 16. 让模型自己决定用 python 还是 python3
- **症状**：pytest 没跑起来，模型以为测试过了。
- **根因**：prompt 没写死解释器，模型敲 `python`（macOS 上常不存在 / 指向别处）。
- **规则**：prompt 里写死 `python3 -m pytest`；别指望模型猜对环境。

### 17. 模型调用超时设太短
- **症状**：reasoning 模型（kimi-k2.6 / glm）输出长 JSON 慢，请求被 120s 超时掐断，任务卡住或报错。
- **根因**：httpx 请求超时设太短（120s），不够慢模型出长 JSON。
- **规则**：reasoning / 慢模型把超时放宽（已调 240s）。识别慢模型别只看 toml 的 reasoning 标志——
  models_custom.json 的 speed/reasoning 字段可能覆盖它（慢模型识别失效）。

### 18. 正交结果独立上报
- **症状**：进程已超时却 exit 0（捕获了终止信号），调用方误判为正常成功。
- **根因**：把一个标志的上报嵌在另一个标志的分支里。
- **规则**：每个独立事实（`timedOut` / `signal` / `exitCode`）单独上报，不嵌套。

### 19. 公共约定两侧都要遵守
- **症状**：消费方猜不出捕获的异常来自 provider 还是 wrapper。
- **根因**：同一结果有多种表示（异常 / error 分片），没在公共 API 出口规范化。
- **规则**：适配层统一规范化错误出口并在类型定义处写明；消费方覆盖每种来源形式。

- **规则**：适配层统一规范化错误出口并在类型定义处写明；消费方覆盖每种来源形式。

## 五、环境、凭证与外部输入

### 20. setdefault 不覆盖已存在的环境变量
- **症状**：换了 key，服务仍读旧值 → 401。
- **根因**：`os.environ.setdefault` 只在变量不存在时写入；shell 里残留的旧值优先。
- **规则**：改配置后要么显式 `os.environ[k] = v`，要么确认进程环境干净；排查 401 先 `env | grep KEY`。

### 21. 别把环境变量 / 可预测路径暴露给不可信输出
- **症状**：凭证经命令输出、`env` 或 spill 文件泄漏；临时文件被符号链接竞态利用。
- **根因**：启动的子进程继承了完整环境；临时文件用可预测路径 + 全局可读权限。
- **规则**：子进程环境清掉 `*KEY*` / `*SECRET*` / `*TOKEN*` / `*PASSWORD*`；临时文件放 0700
  私有目录、随机名、`'wx'` + `0o600`。

### 22. 用 unlink 删链接形态的路径
- **症状**：删「目录」时递归穿进符号链接 / junction 的目标，删掉别人的东西。
- **根因**：直接递归删会跟随链接。
- **规则**：先 `lstat().isSymbolicLink()` 判定，是链接就 `unlink`（只删链接本身）；真目录才递归删。

### 23. 外部输入拼进 shell
- **症状**：命令注入。（演化史仅记名目：v2.1）
- **根因**：命令用字符串拼接，交给 shell 解释。
- **规则**：`subprocess` 用列表参数、禁 `shell=True`；外部值永远不拼进命令串。

### 24. 凭证进仓库
- **症状**：PAT 明文提交到 Git。
- **根因**：把密钥写进代码 / 配置后提交。
- **规则**：凭证只走环境变量或未跟踪的 `.env`；提交前 `git diff --cached` 扫一遍。

## 六、错误处理、配置与静态扫描

### 25. fail-open 漏报
- **症状**：检查自身崩了，却被当成 pass 放行。
- **根因**：异常分支默认返回「通过」。
- **规则**：门禁 / 校验一律 fail-closed —— 检查失败 = 拦下并报错，不是放行。

### 26. 前端异常直接透成 500
- **症状**：后端异常直接透成 500 页面 / 空白。（演化史仅记名目：v2.1「前端 500」）
- **根因**：handler 未捕获异常，前端无兜底。
- **规则**：API handler 统一 `try/except` 返回结构化错误；前端对非 200 有兜底 UI。

### 27. 循环 import 用延迟导入破
- **症状**：`ImportError: partially-initialized module`，但只在「谁先被导入」时出现。
- **根因**：`dispatcher ↔ _dispatch_exec` 互相 import，导入顺序决定成败。
- **规则**：这是既有设计（延迟导入破循环），**不是 bug**。改导入时别把延迟导入提到模块顶层；
  报这个错先确认是不是从非真实入口（`web.app`）导入的。

### 28. API handler 返回 200 却没接真实动作
- **症状**：接口「成功」但什么都没发生；或者调用必 500。
- **根因**：handler 只写了返回，没调真正的 store / rollback 实现。
- **规则**：新增 / 改 API handler 后，用真实调用验一遍**副作用**（数据真的落盘 / 真的回滚），
  别只看返回码。
- **2026-09-12 实测两例**（同一个病的两个变种，都修了，但形状要记住）：
  1. **`run-phase` 对 `template` 项目是空操作** —— 回 `{"ok":true,"started":true}`，
     实际后台线程只 append 一句"等待 Owner 填写需求"就 `break`，而且那句 `msgs`
     被 `_worker` 丢了 → **外面看着像启动了**。真正入口是 `POST /start`。
     修法：对"自己不会推进"的档（template / gate1-3）**直接回 409 + 说清该用哪个接口**。
  2. **批准 GATE 之后没有人启动下一阶段** —— `gate-confirm` 的 `approved` 分支
     只 `confirm_gate` + `save`，而 `planning` **只有 `run_phase` 能推**
     （调度循环只管 EXECUTING 之后，前端又没有 run-phase 调用者）→
     **从界面批准 GATE1 后项目永久卡在 planning**。实测空等 14 分钟。
     ⚠️ 这条**当时被我误判成"前端会做第二步、改 API 会跑两次"** ——
     实际前端只调一次（`api.runPhase` 定义了但没人用）。**"我以为前端会做"本身就是没核。**
  - **共同点**：返回体里有"看着像成功"的字段（`ok` / `started` / `next_phase`），
    而外面**没有任何东西能分辨"真启动了"和"只挪了指针"**。
    判据：**返回的每个表示成功的字段，都要能追到一个具体的副作用。**

### 29. 硬编码常量覆盖配置
- **症状**：registry 里配的 max_turns 不生效；模型白名单因写死精确版本号而滞后。
- **根因**：代码里写死的值优先于配置 / 注册表；白名单写死精确版本号。
- **规则**：可配置项只从 registry / config 读；必须硬编码的用「系列 + 数字」通配，别写死精确版本。

### 30. 字段语义复用当缓存键
- **症状**：Router 缓存永不过期，路由结果一直用旧的。
- **根因**：把关键词列表塞进本该存时间戳的字段，比较永远不相等。
- **规则**：缓存条目显式带 `cached_at`；别复用语义不同的字段存别的东西。

### 31. 静态扫描「0 引用」≠「没人用」
- **症状**：删完死代码，仓库外的脚本 / 装饰器注册 / 反射调用当场坏掉。
- **根因**：grep 扫不到注册表调用、`visit_*` 反射、`import *` facade、仓库外消费者。
- **规则**：删除前逐条复验并排除已知误报类；删后复扫一轮抓连带孤儿；清单只当记录，
  不得照单删（见 `docs/死代码清单-20260909.md`）。

## 七、数据统计与持久化（09-11 用量统计轮新增）

### 32. 静默兜底 = 编造数字
- **症状**：界面上显示的金额是假的，且**没有任何提示**说明它是猜的。
- **根因**：`rates.get(model, 0.50)` —— 查不到就用一个默认值兜底。用户实际在用的模型
  不在那张写死的 8 模型表里，于是所有金额都按 $0.50/百万 算。验证方法很直接：
  `375188 ÷ 100万 × 0.50 = 0.187594`，与界面显示分毫不差。
- **规则**：**查不到就返回 `None`，绝不兜底**。让调用方如实显示"未配置"。
  这条适用于所有"估算类"数值：宁可没有数字，也不要一个看着可信的错数字。
  同类还有 `_planner` 的"混合均价 ~$0.5/M"、`_cli_projects` 的门禁估算、
  `proj.token_spent`（全仓无赋值处，恒 0，连带"预算将超支"是死代码）。

### 33. 缺失值在前端被 `|| 0` 渲染成 0
- **症状**：后端返回 `null`（未配置），前端显示 `$0.00` —— 用户以为真的没花钱。
- **根因**：`(usage?.daily_cost || 0).toFixed(2)`。
- **规则**：金额一律走统一出口（`lib/money.ts`），缺失显式渲染成"未配置价格"。
  **"绝不把缺失值渲染成 0"这条规则只能住在一个地方**，散在各处就一定会漏。

### 34. 写盘时算 derived 值 → 历史被污染
- **症状**：改算法后，存量数据的值还是旧的错的。
- **根因**：`cost_est` 在写入时算好存盘，所以算法一改就得迁移/回填。
- **规则**：**能在读时算的就别写时算**。改成读时现算后：零迁移、旧假值随上线消失，
  而且**修正输入（如补上单价）时历史数据自动变对**。
- **推广到"派生路径"**（2026-09-11）：同一条规则也管**路径常量** ——
  `_MEMORY_DIR = config.QIDIAN_DIR / "memory"` 这种在模块级算好的派生路径，
  导入后就锁死了。生产没影响（`QIDIAN_DIR` 启动定死），**但测试隔离会失效**：
  `monkeypatch QIDIAN_DIR` 对它无效 → 测试往**真实**的 `.qidian/` 写。
  实测代价：一条测试把假洞察写进了生产的 `.qidian/memory/insights.json`。
  **一天内同一个形状出现三次**（`skill_loader._QIDIAN_DIR`、`_INSIGHTS_PATH`、
  `route_learner._LEARNER_PATH`）—— 说明"能读时算就别写时算"当时只当成了一句
  **排错经验**，没当成**写代码的规矩**。
  现在：内存模块 + `route_learner` 全改成函数（`_events_path()` / `_learner_path()`…），
  `tests/conftest.py` 里那几刀多余的补丁跟着撤了，
  并由 `tests/test_scheduler/test_isolation.py::test_derived_paths_are_computed_at_call_time` 钉住。
  **只剩 `config` 自己的 `*_DIR`**（它是根，按定义就该在那儿）和
  `web/app` 的 `_ad`/`_key_file`（导入时一次性初始化，用完就消耗，本来就不该跟着变）。

### 35. 折叠按天聚合时，只重算"今天"会重复计
- **症状**：每天过午夜，昨天的量被重复算进今天。
- **根因**：原始记录窗口**不按天过滤**（`_daily` 存的是最近两天的行）。只重算
  `days[今天]` 就会把昨天的行一起算进今天。
- **规则**：**每条记录归到它自己那天**，再按分量合并。合并用 **max** 而非相加的前提是
  「桶里每个字段对行集合单调不减」—— 谁加"平均""最大间隔"这类非单调字段，max 立刻就错。

### 36. "先剪枝后归位"会静默丢数据
- **症状**：过去日期的记录还没进历史就被删掉（我第一版就这么写，4 条测试当场红）。
- **规则**：`record()` 里**先折叠归位 → 再剪枝 → 最后写盘**。顺序写进注释，
  这类"三步顺序不能换"的地方必须显式标注，否则后人重构时必踩。

### 37. 流式响应默认不带用量
- **症状**：走流式的调用（架构融合）在统计里完全没有用量，**连想补都补不了**。
- **根因**：OpenAI 兼容 API 的流式响应默认不返回 `usage`，要显式申请
  `stream_options={"include_usage": True}`。
- **规则**：任何走流式且需要计量的调用都要带上这个参数。先例见 `openai_agent.py`。

### 38. 只统计了一部分调用路径
- **症状**：统计里的钱比实际花得少，用户以为"统计坏了"。
- **根因**：全仓 6 条调用大模型的路（任务执行 / 观察者对话 / 任务分类 / 架构融合 /
  记忆整合 / 目标循环），**只有 1 条记账**。
- **规则**：加计量时，**先把所有调用大模型的入口 grep 一遍**再动手，
  别只修用户报的那一条。用 `level` 区分用途，`by_level` 就能按用途拆开看。

### 39. 把内部记录塞进会被"整行重建"的地方
- **症状**：用户手填的配置，跑一次某个功能后**静默归零**。
- **根因**：价格曾打算存在模型条目里，而"跑基准""扫描导入"会把该条目
  **每个字段重新传一遍** —— 没被显式带上的字段就没了。
- **规则**：**人类手工维护的数据，不要和机器会整体重写的记录放一起**。
  独立的文件/表让这种失败在结构上不可能（而非"靠测试兜住"）。

### 40. 删字段前先看有没有 `Cls(**row)` 的载入路径
- **症状**：删掉一个"没人用"的字段后，**整份历史静默消失**（被 `except` 吞掉）。
- **根因**：`_load()` 走 `UsageRecord(**r)` —— 删了字段，存量行就抛 `TypeError`，
  被 `except Exception` 吞掉后 `self._daily` 变空。
- **规则**：删字段前 grep `**r` / `**row` / `from_dict` 这类反序列化入口。
  确认只能"保留但不再读写"，就**留字段 + 注释写明为什么不能删**。

### 41. 测试里的模块级单例不吃 conftest 的隔离
- **症状**：测试往**生产数据目录**里写假记录。
- **根因**：单例（如 `_budget = TokenBudget()`）在 import 时就绑定了真实路径；
  conftest 改 `config.QIDIAN_DIR` **改不到已经构造好的单例**。
- **规则**：测这类模块必须 `monkeypatch.setattr(mod, "_singleton", fresh)`。
  所以 API handler 要**函数内 import** 单例（这样才 patch 得到）。

### 42. 翻告警日志不看时间 = 把已修的问题当现存 bug
- **症状**：差点报一个"已经修好"的 bug（5 条告警，看着触目惊心）。
- **根因**：`alerts.jsonl` 是**累积**的，翻旧账会误判。
- **规则**：看告警先看时间戳，对照修复提交的时间。同样地，**报告里的 file:line 会撒谎**
  （审计报告的文件行号几乎全错），**当前源码不会**。

### 43. 加"轮换/分摊"类机制前先问清列表的语义
- **症状**：给"主力 + 备用"的清单加了轮换，反而让归因变难、成本忽高忽低。
- **根因**：那个模型列表的语义是**优先级**（永远用第一个、挂了才用下一个），
  不是"负载均衡池"。我把"配了多个却只用一个"当成了 bug，其实那是设计。
- **规则**：改选择逻辑前先确认那份配置**语义是什么**。想让用户"看见"配了哪些，
  靠**列表全展示**（含未使用/不可用状态），而不是靠制造使用。

### 44. 承诺类字段必须三态可分（这是一整类的总纲）
- **症状**：一天之内挖出六个缺陷，**没有一个报错**。GATE3 看不到 QA 报告、
  验收被跳过不留痕、`deepseek-flash` 从扫描列表里凭空少一个、点文件只弹「定位失败」……
  共同形状都是「系统没做或做错了，但从外面看一切正常」。
- **根因**：事实从发生到被看见要经过若干次交接（执行→状态、状态→序列化、序列化→界面、
  过滤前→过滤后），**每次交接都靠约定维持、没有任何对账**，而且所有交接点的默认行为
  都是把"拿不到"解释成"没有/正常"。静默失败 = 一次断掉的交接 × 一个良性的默认解释。
- **规则**：**承诺类字段必须三态可分 —— 未运行 / 运行了·无发现 / 跳过(原因)。**
  消费方不得把缺失解释为良性（"没有报告"不等于"没问题"）。
  **过滤类操作必须留落选账**（滤掉了谁、为什么）—— 白名单对"厂商的命名"是开放集合，
  永远补不全，补丁只能当第一道防线，落选账才是那个能被发现的。
  已落到代码：`to_dict()` 派生于 `dataclasses.fields()`（省得手抄清单漏字段）、
  `list_all`/`load` 读不出时写 `witness.warn`、扫描把 `dropped` 聚合进 `alerts.jsonl`、
  前端 `errText(e, fallback)` 不再吞后端原因。

### 45. 计数器只增不减 = 单向棘轮，能把人永久锁死
- **症状**：用户在 GATE2 点「通过」，界面 2 秒后弹回同一个 GATE2，再点、再弹，
  **永远出不去**。而界面一切正常：没有报错、没有红色，用户只会以为自己点错了。
- **根因**：`review_failures` 触顶后，`_run_integration_merge_async` **在集成合并已经成功
  的情况下**仍打回 GATE2；而该计数全仓**没有任何地方重置**。人工批准这个"兜底动作"
  没有复位计数器 —— 于是批准 → 执行 → 合并成功 → 检查计数仍超限 → 回 GATE2 → …
- **规则**：任何"到阈值就采取动作"的计数器，**必须同时定义清零事件**，否则它就是个棘轮。
  本仓库的定案：**人工介入（批 GATE2）= 人到场兜底，自动重试配额随之恢复**。
  写这类计数器时先问一句「它什么时候归零」，答不出来就是还没写完。

### 46. 确定性 tmp 路径 + `threading` 锁 ≠ 进程安全
- **症状**：一个项目从界面上凭空消失，没有任何提示 —— 文件其实还在磁盘上。
- **根因**：`save()` 用原子写（写 `<id>.tmp` → `os.replace`），但 tmp 是**确定性路径**，
  而 `_LOCK` 是 `threading.RLock()`，**只挡同进程的线程**。后端调度循环和
  `tests/integration/role_probe.py`（独立进程）会同时 save 同一个项目：A 的 replace
  成功后 tmp 就没了，B 的 replace 撞 ENOENT（`alerts.jsonl` 里实见）；或两边写入交错
  → 项目 JSON 末尾多出一个 `}` → 解析失败 → `list_all()` 静默跳过。
  `save()` 的注释显示作者**专门加过锁**防"两个线程共用同一 tmp"—— 防住了线程，漏了进程。
- **规则**：进程内锁只解决进程内问题。tmp 路径带上 pid
  （`p.with_name(f"{p.name}.{os.getpid()}.tmp")`），锁仍保留（同进程多线程还是共用同一个 pid 的 tmp）。
  验证：`multiprocessing` 起 4 个进程 hammer 同一个项目 —— 旧代码会复现出与
  `alerts.jsonl` 一字不差的 `FileNotFoundError`。

### 47. 代理对象漏字段 = 下游判据恒假，而且查不出来
- **症状**：单文件任务**永远跳过审查**（项目测试 / 多模型审查 / QA 验收 / 需求对账 /
  安全审计五道一起跳），多文件任务的审计也对着**空 diff** 跑。而披露文案写的是
  "改动被判为小改动(单文件, diff<50行)" —— 看起来像是自己改得少，完全不像 bug。
- **根因**：`_exec.run` 构造的快照是 `_SnapProxy(ctx.snapshot_ref)`，而这个类
  **只设了 `ref` 和 `worktree_path`，没有 `method`**。`validator._diff_base` 的判据是
  `getattr(snap, "method", "") == "git"` —— 对 proxy 恒为假 → **基准恒为空串**。
  基准一空就退回裸 `git diff`，而 worktree 里改动在审查前已被 `commit_wt` 提交，
  裸 diff 恒 0 行 → 恒判 trivial。
  **上一轮审计其实"修过"这条**（P0-1：改用执行前快照的 ref 当基准），但它只核到
  `_exec.py` 写了 `base_ref=val_mod._diff_base(snap)` 就收工了，**没往下算这个表达式
  求值成什么**。而那个测试文件里原有的用例用的是**鸭子类型假对象**，恰好有 `method`
  —— 真身漏字段，假对象测不出来。
- **规则**：
  1. **测"接线"要用真身，别用假对象**。鸭子类型假对象只验证"名字对得上"，
     不验证"真实现有这个属性"。凡是被测代码对对象做 `getattr(obj, x, 默认值)` 的，
     默认值就是一条隐藏的失败路径 —— 测它必须用真实类型。
  2. **核"修好了没"要往下算一步**：`base_ref=<表达式>` 不等于基准非空。
     改完贴一行运行输出，别停在"代码看起来接上了"。
  3. **门禁类判据的默认值一律 fail-closed**：取不到基准就**不判**"小改动"，
     宁可多跑一遍贵的审查。`getattr(..., 默认)` 让"拿不到"和"拿到了但不等"同路，
     这正是 §44「承诺类字段必须三态可分」在判据层的又一例。

### 48. 用了没 import 的名字 → NameError → 被 `except` 吞成"正常的默认值"
- **症状**：功能**一直在跑、结果看着也正常**，但它其实一直走降级路径 ——
  因为 `except Exception` 把"我写错了"和"环境不可用"一起吞了。
  2026-09-11 一天出现**两次**，两次的症状都是"看不出来坏了"：
  · `_memory_core._get_embed_model` 用 `SentenceTransformer` 但**没 import**
    → 每次抛 NameError → 被"下载失败就降级"那句 except 吞掉 → **嵌入路径
    从来没生效过**（技能过滤退化成"取前 2 个"、记忆语义检索永远返回空）
  · `execution_judge._usable` 用 `model_registry` 但**只 import 了 `api_store`**
    → 恒抛 NameError → 被"查不了就别拦"那句 except 吞掉 → **提取员可用性检查
    从来没生效过**（每次都白撞，还会换到用户已停用的模型上真发调用）
- **根因**：`except Exception: <用一个安全的默认值>` 是重灾区。默认值通常**刻意的
  等于旧行为**（"保持原行为"），于是"新代码没生效"和"新代码生效了但没触发"
  在外部完全同形。**代码看着完整** —— 缺的那行 import 在同一个文件里，
  上一行就有（`_resolve_api` 里 import 了 `model_registry`，`_usable` 里没抄）。
- **规则**：
  1. **降级路径必须留痕**（`witness.warn`）。"降级"和"没写"分不开，就永远查不出来。
  2. **判断"检查类代码修好没"，必须让它真的跑一次并观察输出** ——
     `grep -c is_available` 数到 8 处也可能一行都不执行。
     这条是 2026-09-11 我自己犯的：复验审计报告时数到引用就标了 ✅。
     **grep 命中数 ≠ 行为。**
  3. **别靠读码找这一类**：`ruff check --select F821` 一次全扫出来。
     已在 `tests/test_scheduler/test_no_undefined_names.py` 挂成守卫
     （F821 ≠ 0 就红，豁免要写理由，且带"豁免过期"检查）。

### 49. 阶段调用的 cwd 漏传 → 在没有隔离的地方跑
- **症状**：跑一个"字数统计工具"的项目，奇点**自己仓库的根目录**里冒出 `wc_lite.py`
  和 `examples/`。项目仓库却压根没被创建。
- **根因**：`_safe_dispatch()` 调 `disp_mod.dispatch()` 时**没传 `cwd`**，而 `dispatch`
  的默认值是空串，执行器再兜底成 `cwd or config.PROJECT_ROOT` —— **PROJECT_ROOT 就是
  奇点仓库自己**。走这条路的四个阶段（调研 / 架构 / QA 验收 / 安全审计）**全都在主仓
  根目录里跑，且没有 worktree 隔离**（worktree 只给执行阶段用，见 `_exec.py:326/336`）。
  **同一形状此前已经踩过一次** —— `_dispatch_exec.py` 里委员会合成那段注释写着
  "把目标项目的架构直接写进了奇点仓库的 docs/"，当时**只修了那一处支路，根因没动**。
- **规则**：
  1. **"这个参数能不能省"的答案 = "看它的默认值兜底到哪"**。凡是被执行器 `or` 兜底的
     参数（cwd / 模型 / 路径），漏传 = 静默走一个**没人看过**的分支。
  2. **修一处支路时必须问"同形状还有几处"**。这类 bug 的判据在**调用点**（谁没传），
     不在**实现点**（谁兜底错了）—— 只改后者就漏掉所有兄弟调用点。
  3. 非执行阶段**没有 worktree**，cwd 就是唯一那道边界。取不到项目目录时**绝不退回
     PROJECT_ROOT**，宁可自己 mkdir 一个空目录（`workflow._phase_cwd()`）。

### 50. 产出契约是"一段文本"的阶段，别给工具
- **症状**：调研员**不写调研报告，直接去写代码** —— 在项目仓库里把整个项目实现完
  （主程序 + 测试 + 跑了一遍），工具轮次耗尽，报告只剩一句
  `(达到最大工具轮次, 已产出文件)` → JSON 解析失败 → GATE1 无物可审，这轮白烧。
- **根因**：调研阶段的产出契约是"吐一段 JSON"，但平台给它的是**带 `write_file` /
  `run_command` 的干活执行器**。模型看到"做一个字数统计工具"，很自然就去做了。
  `openai_agent` 早就备好了 `SYSTEM_PROMPT_NO_TOOLS`（委员会那条路在用），
  调研/架构这条**单模型**路径没接上。
- **规则**：**工具面要跟产出契约一致**。产出是"一段结构化文本"的调用一律 `no_tools=True`
  （现在：调研 + 架构）。判断标准不是"它会不会用到工具"，而是**"它用了工具之后产物去哪"**
  —— 产出的文本会被丢进 `try_parse_json`，那工具就是纯干扰。

### 51. "强制输出"那一轮落在了循环边界外 → 模型永远没机会答话
- **症状**：任务**活干完了**（`changed_files: ['wc_lite.py', 'tests/test_wc_lite.py']`），
  交付报告里却一个字总结都没有，`raw_output` 是一句占位串
  `"(达到最大工具轮次, 已产出文件)"`。
- **根因**：执行器的工具循环是 `for turn in range(1, max_turns + 1)`。判"该撤工具、
  逼模型出终答"用的是 `tool_turns >= max_tool_turns + 2`，而 `max_turns=5` /
  `max_tool_turns=3` 时 **`3+2 = 5` 恰好等于最后一轮** —— 注入那条
  "现在必须直接输出最终答案"的系统消息后紧接 `continue`，**循环当场结束，
  那次模型调用从未发生**。占位串就是这么来的。
  连带：agent 拿不到收尾那一轮 → 没法自我总结；post-hook 还会按
  `output <80 chars`（`validator.py:129`）扣一次信心分。
- **⚠️ 一度把因果写反过（教训）**：第一版把"任务失败"也算在这条头上，理由是
  `term_reason` 里带着 `post_hook: output <80 chars`。**那句只是拼进字符串，
  不决定成败**（`_exec.py:574`）—— 真正的失败判据是 `batch.ok == False`，
  而它是 §52 的 `action=retry` 驱动的。**日志里出现的字样 ≠ 判决依据。**
- **规则**：
  1. **凡是"注入一条系统消息然后 continue"的机制，都要问一句"下一轮还存在吗"**。
     阈值型判据（`>= n+2`）必须跟循环上界对账，否则最想触发的那次恰恰触发不了。
  2. **判失败原因要顺着判据链走，别拿 `term_reason` 里的字样当结论** ——
     那是个拼接串，什么都会往里塞。§52 也是这么误判出来的（见其症状描述）。
  3. 测试用真实配置对账：`tests/test_scheduler/test_force_output_turn.py`
     直接钉住 `force_output_at(5, 3) < 5`。

### 52. 拦截类判据必须能说出"拦的是什么"
- **症状**：`unverified` 里出现 `'QA 约束验收 0 条未满足: '`（冒号后面空的），
  同时 `action: retry` —— **拦住了，但说不出为什么**；下一轮必然同样结果，循环收敛不了。
- **根因**：`_review.py:492` 只在 `qa.verdict == "needs_fix"` 时写这条消息，主体是

  拦了不说是**比不拦更坏**的状态：它把任务拖进一个没人能修的重试循环。
  （同族见 §44「承诺类字段必须三态可分」—— 这里是"拒绝"这个态没带载荷。）

### 57. 挂起不是异常 —— `except` 拦不住它
- **症状**：跑"字数统计工具"项目，调研阶段**无报错、无告警、无 trace、无模型调用**，
  卡满两分半不动，`phase` 停在 `researching`；外面看像"启动了没反应"。
  同一个项目重跑，**每次都卡在同一处**。
- **根因**：`_run_research` 里的 MAGMA 记忆检索（`pre_search.py:117` → `memory.query`）
  要加载本地嵌入模型，而 `sentence_transformers` **即使模型已在缓存里，也要先联网查
  `huggingface.co` 的 metadata**（看要不要更新）。那域名不通 → `huggingface_hub`
  的 `http_backoff` 退避重试 → **挂死**。
  而整段包在 `try/except Exception: pass` 里（`pre_search.py:126-132`），注释写着
  "记忆挂了不阻塞" —— **挂起不是异常，`except` 拦不住它。**
- **实测证据**（`py-spy dump`，C 帧看不出来、`sample` 也看不出来）：
  ```
  do_handshake → http_backoff → get_hf_file_metadata → hf_hub_download
    → cached_file → from_pretrained → _get_embed_model → _embed
      → find_similar → query → pre_search → _run_research
  ```
  加上 `HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1` 后，**同一份代码 50 秒跑完**。
- **规则**：
  1. **`except` 只能拦异常，拦不住挂起。** 凡是"出问题不该阻塞主流程"的调用，
     光包 `try/except` 是**假保险** —— 必须同时给**超时**。没有超时的兜底 = 装死。
  2. **本地有缓存 ≠ 不联网。** `transformers` / `sentence_transformers` 加载缓存模型时
     仍会做 metadata 检查。离线环境必须显式 `HF_HUB_OFFLINE=1`（或
     `TRANSFORMERS_OFFLINE=1`），否则**首次调用随机挂死**。
  3. **判断"有没有走网络"不能只看 `lsof`。** 失败的连接已经关掉了，`lsof` 里看不见
     —— 我据此误判过一次（"没有对外连接 = 没走到网络"）。要看的是**栈**，不是 socket 表。
  4. 排查姿势：`sample` 只看得到 C 帧，**`py-spy dump` 才看得到 Python 函数名**
     （macOS 上要 root）。这类"卡住不报错"的问题优先上 `py-spy`，别猜。

### 58. "模型没按协议来"被当成了"模型没干活"
- **症状**：任务判失败，理由 `[completeness] 无文件改动`。而它的 `agent_output`
  有 **9599 字**，开头的全文就是它"写的那个文件"（连文件头的注释都在）。
  模型**以为写成功了**。
- **根因**：模型（DeepSeek 系）不回 OpenAI 的 `tool_calls`，而是吐**自家的 DSML**：
  `<` + 两个**全角竖线 U+FF5C** + `DSML` + 同 + `invoke name="write_file">…`。
  平台只读 `msg["tool_calls"]` → 这一整段被当成"模型的普通回答" → 工具一个没跑
  → `changed_files: []` → 判"无产出"。
  **讽刺的是 prompt 里早就写着"不要输出 `<invoke>` 块"** —— 知道这个格式，
  却**只有禁令、没有解析器**。
- **规则**：
  1. **"没按协议来"和"没干活"必须分开。** 前者多数是我们该适配的（厂商协议差异），
     后者才是模型的问题。混在一起处理，就会把**干完了的活**判成没干。
  2. **prompt 里的禁令 ≠ 处理。** 写"不要输出 X"只在你面对**同一个模型**时管用；
     换个厂商、换个版本，X 就回来了 —— 而这次的代价是**整批工作蒸发且无声**。
     凡是"模型可能吐出 N 种格式"的地方，要么都认，要么**认不出就明报**。
  3. **肉眼分不出全角半角。** U+FF5C（全角竖线）和 `|` 在终端里几乎一样。
     第一版正则按 ASCII 写，**拿真实输出一跑才发现对不上** —— 又验证了那条：
     写解析器必须拿**真实样本**验，不能拿自己手搓的形状验。
  4. 现在的处置：`_parse_xml_tool_calls` 两种格式都认（半角/全角、1 根/2 根竖线），
     **认出来就告警**（`xml_tool_calls_recovered` / `_unparsed`）——
     这是"模型没按协议"，不是正常路径，得能查得到。

### 59. 超时 ≠ 停了 —— 执行器线程还活着；且 §55 的"账"那半仍未兑现

- **症状**：任务 A 在 05:30 撞 900s 被杀。**8 分钟后（05:38:47）**告警里还在报

  的 `subprocess.run(..., cwd=self._cwd)`），而 `self._cwd` 已经不存在。
- **规则**：
  1. **"超时"不等于"停了"。** 写超时处理前先问一句：被超时的那个东西**现在还在跑吗**？
     在跑的话它会继续改磁盘、继续调 API（**=继续花钱**）。

### 61. 同一份"架构 schema"存在两份拷贝，字段漂了 —— `covers` 按构造必丢

- **症状**：重流程（开委员会）跑出来的架构，8 条约束的 `check` **全是**结构化的
  `{"argv":[...], "expect_exit":0}`，但 `covers` **一条都没有**（字段名都不存在）。
  于是 `_machine_checks` 的覆盖率只能报 `no_covers=8` ⇒ "8/8 条需求没人验"。
- **根因**：系统里**有两份架构 schema，内容不一致**——

  | 出处 | 给谁看 | `constraints[]` 长什么样 |
  |---|---|---|
  | `workflow.py:41 _ARCHITECT_CONTEXT` | **架构师席位**的 prompt | `{"type","rule","check":{"argv":[…],"expect_exit":0},"covers":[0,2]}` ✅ 有 covers |
  | `execution_judge.py:205 _ARCH_SCHEMA` | **委员会定稿**的 prompt（`:837 schema=_ARCH_SCHEMA`） | `{"type":"","rule":"","check":""}` ❌ 没 covers，`check` 还是字符串 |

  → `_V2_FINALIZE`）⇒ 定稿模型**根本没被告知有 `covers` 这个字段**。
- **为什么 `check` 却对了**：定稿 prompt 里带了【各成员原稿】全文，原稿里是结构化的
  ⇒ 它**照抄了形状**。**不是 schema 起了作用** —— 这一点最容易误判成"prompt 生效了"。
- **规则**：
  1. **同一份契约只能有一个定义点。** 两份拷贝必然漂，而且漂的是**其中一份**，
     出问题时你盯着 prompt 找原因，根因在另一个文件里。
  2. **判"prompt 有没有起作用"，要挑一个原稿里没有、只有 schema 里有的字段看**——

  `check`，`_V2_FINALIZE` 补规则 6 说清 covers 语义。⚠️ 它是 `.format()` 模板，
  **字面花括号必须写 `{{ }}`** —— 漏了转义 18 个 fusion 测试当场全红（`KeyError: '"argv"'`）。
- **留了漂移检查**（`tests/test_scheduler/test_machine_checks.py::TestArchSchemaCoversContract`）：
  两份 schema 的 constraints 字段集必须一致。**光修一次不解决规则 1** ——
  下次谁再改其中一份，这条会红。变异验证过：从任一份删掉 `covers` 它立刻失败。

### 63. 执行器一圈表都不看 —— 唯一的"总时限"是外面那次无声收割（2026-09-13）

- **症状**：任务撞 900s 被杀。杀完 trace 里 `turns=0` / `changed_files=[]` /
  `token_count=None`，**看上去像"这个任务什么都没干"**（2026-09-13 复查的 8003）。
  一度据此判断成"模型一上来就卡死"，是**误读**。
- **根因（两层）**：
  1. **执行器的 turn 循环没有总时限检查** ——
     `executors/openai_agent.py` 的 `for turn in range(1, max_turns+1)`（默认 15 轮）
     **一圈表都不看**。唯一在看表的是 `orchestrator._reap_futures` 里那个硬编码的
     `deadline = 900`，到点写取消标记 + 判 FAILED。**执行器根本不知道有这回事。**
  2. 所以"跑多久"**完全由任务自己决定**，最后一定停在"被砍"那一刻，且砍得无声：
     取消标记是**判死之后**才写的，而读它的两处（`_exec.py` 的 `_check_cancelled`）
     在执行器 turn 循环**外面**，够不着正在跑的那次调用。
- **误诊是怎么来的（教训）**：`turns=0` **不能**当"没调过模型"的证据 ——
  `_persist_partial_usage` 只在 dispatch **返回之后**落盘，被砍的任务永远落在这一步之前
  ⇒ `turns` 恒 0、`token_count` 恒 `null`。**拿上报口径的缺失当事实，会得出相反的根因。**
  （同族：§59 的边界。）
- **顺带排除的两个猜想**（都查过，都不是）：
  - ❌ "`max_workers=1`，任务排队被误杀"：`_dispatch_ready` 确实一次性 submit 所有就绪任务，
    但 8003 是 `depends_on=[8002]`（等依赖），快照 `1789225670` → 判死 `1789226581`，
    **实打实占了 worker 911 秒**。
  - ❌ "一次 API 卡死凑满 900s"：引擎本身有界 —— 流停滞 90s（`_STALL_TIMEOUT`）/
    单次尝试 240s / **单次调用**重试总预算 600s（`_RETRY_TOTAL_BUDGET`）。
- **规则**：
  1. **凡是有"外部超时"的长循环，循环自己必须知道这个超时。** 否则它唯一的终点是"被杀"，
     而被杀一定发生在"还没来得及交账"的时刻。
  2. **【上报口径】和【事实】要分开。** 字段是 0/None，先问"是没发生，还是没落盘"，
     再下结论。这条已经咬过两次（§59、本条）。
  3. **别把"两种形状"当成两个毛病**：`8003`（0 轮 0 文件 无账）和 `8384/8386`（4-5 轮、
     改了 2 个文件）看起来是"卡死"和"活多"，其实是**同一件事的两端** —— 都是执行器一直
     干到被杀，差别只在杀之前落了多少盘。
- **改法（2026-09-13）**：
  - `config.TASK_DEADLINE_S = 900` / `TASK_WRAPUP_MARGIN_S = 90` 做**单一来源**，
    orchestrator 和执行器共用（以前 orchestrator 硬编码 900，执行器不知道）。
  - 执行器在 **轮间看表**（`time.time() >= self._deadline_at` → 收尾）+ **单次调用封顶**
    （`_stream_call` 的 httpx timeout 取 `min(240, 剩余预算)`）。
    ⚠️ **只做轮间看表是不够的** —— 一轮本身可能跑几分钟（8384/8386 实测约 200s/轮），
    看完表再开一轮照样冲过 900s。两处都要。
  - 收尾返回 `error_kind="deadline"` + **已烧的 token / 改过的文件 / 跑过的轮次**。
    `_exec` 收到这个 kind **不换模型**，`_run_with_retry` 见 `BatchOutput.deadline_wrapup`
    **不重试** —— 两者都会把剩下的时间再烧一遍，烧完照样被无声收割，**且这份账也保不住**。
  - 预算可用 `QIDIAN_EXEC_BUDGET` 覆盖 ⇒ **真机验证设个小值就能几十秒撞上这条路径**。

  而且它会让"卡死"那类**更晚**才被发现。

## 九、方法论：动手之前先问的两个问题

> 前八章是「**这类坑怎么修**」。这一章是「**我这次修得全不全**」——
> 它管的不是某个 bug，是**修补这个动作本身**。
> 来源：12 案外部答卷的方法学一节（§一·修正三 / §二·6），2026-09-13 立法进这里。

### 9.1 缺陷的不可见性分三层 —— 检测手段和层级错配时，缺陷等于不存在

| 层级 | 什么形状 | 什么手段看得见 |
|---|---|---|
| **终态可见** | 跑一轮就露 | 跑一遍真机 |
| **单次不可见、跨运行聚合可见** | 恒默认值 · 判据恒假 · 契约漂移 | **跑一百次也看不见**；静态扫 / **聚合**一抓一个准 |
| **聚合也够不着** | 竞态 · 时序 · "加两行诊断就不复现" | **只能埋点后再跑** |

**动手修之前先答**：这个缺陷属于哪一层？我打算用的手段**够得着那一层吗**？

- ⚠️ **最常错的是第二层**：拿"跑一轮"去验一个跨运行才可见的缺陷，会得出"没问题"。
  本项目的实例（2026-09-13 一天撞两次）：
  · `_consolidate_calls % 10` —— 判据挂在**每次重启归零**的模块级变量上 ⇒ 永远到不了阈值，
    功能从未执行。**单跑一轮看不出来**（那个字段就是空的，和"跑了没发现"长得一样）。
  · `add_inferred_causal_edge` 没导入 —— 每个任务各自看起来都正常，
    **251 条告警聚合之后**才浮出 6 条 `consolidate:name '...' is not defined`。
- ⚠️ **第二层要求"聚合视图"存在**。告警平铺着放，第二层的缺陷和在噪声里没区别 ——
  这就是 `witness.alert_summary` 存在的理由之一。

### 9.2 修复交付标准 —— 答不出"怎么发现它失效"，就等于没修完

每个修复必须回答：**用什么手段能发现这个修复失效了？** 三选一，答不上来算没修完：

1. **守卫测试**（最好）—— 而且要**变异验证过**：把 bug 放回去，它真的会红。
   ⚠️ **守卫"有"不等于"覆盖"**：问一句"它在哪些输入上会沉默"。
   实例：F821 守卫建得对、判据也对，但在**任何带 `from X import *` 的文件里拒绝报**
   —— 全仓 10 个文件在盲区里（§64）。
2. **埋点**——留一条能被**聚合**看见的痕迹（不是一条孤零零的告警）。
3. **真机观测**——写明**看什么、看到什么算过**。

**为什么要有这条**：**补丁的修复半径 = 发现它的检测半径 × 验证半径，而这两个半径
都小于形状的真实分布。** 补丁不是修错了，是**作用域天然小于病灶**。
本项目的实例：`"只看得见未提交的改动"` 这个形状在 validator / orchestrator 抢救 /
crossover_review **各修过一次**才被按形状扫一网打尽（§55 一族）。

⇒ 两条合起来的用法：**先按 9.1 定位层级、选够得着的手段；按 9.2 交付时，
把"怎么发现它失效"一起交出去。** 这两条就是"按形状全仓扫 + 往下算一步 + 守卫钉住"
的可执行版本。

### 65. 先改状态、后登记 —— 中间断了就留下一个**没人管**的 RUNNING 任务（2026-09-13）

- **症状**：任务被标成 `running`、快照也拍了，之后**一个字节都没跑** ——
  0 日志 / 无 sidecar / 无心跳 / 无取消标记 / 无 trace，`run()` 的入口日志从没打过；
  过了 1100 秒（> 900）**收割也没触发**。任务就那么挂着，**外面看是"在跑"**。
- **怎么定位的**（`py-spy dump`，很关键）：
  · dump 里**没有任何 ThreadPoolExecutor 工作线程** ⇒ 那个 future 根本没在跑；
  · `_loop_worker` 停在 `app.py:512 = time.sleep(3)`，即**空转分支**
    ⇒ 循环活得好好的，只是**认为没活干**。
  两条一合：任务被标 RUNNING 了，但 future **从来没登记进 `running_futures`**。
- **根因（结构）**：`_dispatch_ready` 的顺序是
  `transition(RUNNING)` → `dispatched.add` → `pool.submit(...)` → `running_futures[fut]=…`。
  **从 `transition` 到 `running_futures` 之间任何一步抛，任务就永远挂着**：
  没有 future ⇒ 循环看不见它 ⇒ `ready_tasks()` 也不返回它（它是 RUNNING 不是 PENDING）
  ⇒ **900s 收割永远够不着**。那三步里唯一会抛的是 `pool.submit`。
  ⚠️ **异常原文没留下** —— 见下面第 2 条，"submit 抛的"是**强推断，没证实**。
- **为什么一直查不出来（这条最该记）**：`_loop_worker` 的兜底是
  ```python
  except Exception as e:
      _push_event("error", f"loop error: {e}")   # 只推 SSE
      time.sleep(5)
  ```
  **不落日志、不进 `alerts.jsonl`** ⇒ 一次"任务被孤立"的事故**连一条持久痕迹都没有**，
  聚合视图也照样看不见它。排障只能靠猜（当晚确实是靠猜，猜错了两次方向）。

- **规则**：
  1. **"状态"和"登记"要么原子，要么失败可回滚。** 先改状态、后做会抛的事，
     中间那段就是**孤儿制造机** —— 而且孤儿的表现是"看起来在跑"，最坏的那种。
  2. **循环级异常的兜底必须进持久通道**（`witness.warn` / 日志），不能只推 SSE。
     **"推给界面"不等于"记下来"** —— 消息飘一次就没了，事故复盘时等于没发生。
     ⚠️ 反过来说：**当天造的聚合视图也救不了没被记下的东西**。有视图不等于有数据。
  3. **给不变量配一个"此刻不该出现"的检查**。本循环是唯一派发方 ⇒
     走到"没 future、没 pending、没就绪任务"那一刻，**不该有任何 RUNNING 任务**。
     这一个判据就能让孤儿自己浮出来（`_warn_orphan_running`）。
     **只报不改** —— 自动"纠正"会把真问题抹平成假的一致（同 `reconcile_projects`）。
- **已修（`e3a835d`）**：① 派发失败转 FAILED 不留孤儿；② 循环兜底加 `witness.warn`；
  ③ 孤儿探测。测试 5 条，**变异验证过**。
  ⚠️ **变异验证顺手抓出我自己一条假测试**：直接调函数的那种，**把接线删掉照样绿** ——
  "函数对"和"接线通"是两件事（补了接线测试）。
- ⚠️ **真机没验**：孤儿不好主动造。能看到的样子是"下一轮真跑时 `alerts.jsonl` 里
  没有 `orphan_running_task`"——**没出现 = 没发生，不是"修好了"**。

**补记（同日稍晚）：按这条形状全仓扫了一遍，又扫出 4 处。**

判据：**"future / batch 已经消费掉、后续那步却没兜底"**。全仓 5 处（含上面那处）：

| 位置 | 会抛的 | 为什么会出孤儿 |
|---|---|---|
| `_dispatch_ready` | `pool.submit` | future 没登记上（真机抓到的那处） |
| `_reap_futures` | `mq.submit(...)` | future 已 pop，又没进 `pending_batches` |
| `_reap_futures` | `runner.finalize(...)` | future 已 pop，没人再碰这个任务 |
| `_drain_pending` | `transition`/`_release_ref`/`_save_trace` | batch 已 pop |
| `_reap_futures`（超时分支） | `_salvage_timed_out` 那段 | 不会出孤儿（已转 FAILED），但**会中断整个 reap 循环**，后面同样超时的 future 这轮不再处理 |

统一用 `orchestrator._strand_guard(t, exc, where)` 兜底：**只在任务还停在 RUNNING 时才改**
（`finalize` 可能已经把它推到 DONE/FAILED 了），同时进告警通道。

⚠️ **2026-09-13 补一笔：上面这句"统一"当时是假的。** 核对（外派答卷回收时）发现
`_strand_guard` **全仓只有 4 个调用点** —— 而**真机抓到的那一处（`_dispatch_ready`）
压根没走它**，是自己手写的 `tracker.transition(FAILED)`，**少的正是"改之前先重读"那道检查**。
`_strand_guard` 的 docstring 却早写着"同一形状 5 处…共用的兜底"——
**声称跑在行为前面，而外派答卷就信了它**（据此判"已经建了 80%、再包一层一天活"）。
**已修**：`_dispatch_ready` 改走 `_strand_guard`（`where="dispatch"`，告警 key 仍是
`dispatch_failed`，不劈开已有分组），docstring 的话这才成真。
**规则**：**"统一兜底"这种说法，要能一口气数出调用点才算数。**

⚠️ **别拿"终态没被覆盖"当这道判据的测试** —— `_TERMINAL_EXIT[DONE]` 是空集，
`done→failed` **本来就被状态机挡掉**，那种测试是**假绿**（绿是状态机给的，跟判据无关）。
这条**同一天被踩了两次**：`test_strand_guard_only_touches_running` 第一版，
以及给 `_dispatch_ready` 补测试时**我又写了一遍一模一样的** —— 两次都是变异验证抓出来的。
**要在测试里挑一个状态机不管的中转态**（如 `RUNNING→PENDING` 合法、`PENDING→FAILED` 也合法），
判据失效时它才会真的红。

⚠️ **为什么这里"自动改状态"不违反「不许自动纠正」那条规矩**：那条管的是**猜**
（"状态和磁盘对不上，谁对？"）；这里不猜 —— **没有 future 就是没在跑**，是确定的。
留着 RUNNING 才是谎报。

**两个教训（都是变异验证逼出来的）：**

1. **"假绿"测试**：我给兜底写的第一条对照测试是"终态没被覆盖" ——
   它**通过的原因是状态机自己拒绝 `done→failed`**，跟被测判据毫无关系，
   把判据删掉它照样绿。**测出来的绿，要能说出是"谁"让它绿的。**
2. **变异本身也会失败**：有一次"拿掉守卫"的变异其实**没改到文件**
   （我是从 shell 里拼 Python 代码，引号把语句弄坏了），于是测试全绿，
   差点得出"这个守卫没用"的反向结论。**变异之后要确认变异真的落地了** ——
   否则你在用一次没发生的实验证明一个错误的结论。

### 66. 字段删了、调用点没扫 —— `from_dict` 恒抛，接口恒 500（2026-09-13）

- **症状**：`GET /api/tasks/<id>/trace?format=md`（把任务 trace 导成 markdown）
  **恒 500**。真机打那个接口一眼就看到，日志里是
  `TypeError: RouteResult.__init__() got an unexpected keyword argument 'level'`。
- **根因**：`RouteResult` 在"两档"改造里**删掉了 `level` 字段**
  （`orchestrator._dispatch_ready` 的注释写着："两档后 `RouteResult` 不再带 level；
  `route_level` 仅作 trace 标签存于 task"）。但 `neijinglu.DeliveryReport.from_dict`
  **还在传 `level=`** —— 它是那条接口的**唯一调用点**，于是每次都抛。
- **规则**：
  1. **删字段 = 全仓扫调用点**。删的一方和用的一方在两个模块里，
     静态检查（F821/属性扫描）**只看名字存不存在，不看 kwargs 对不对** ——
     这正是今天补的那两个守卫**够不着**的一类（它们查"存不存在"，不查"调得对不对"）。
  2. **`**kwargs` 和 dataclass 的 `__init__` 不吃拼写错**，但只在**跑到那一行**才炸。
     所以"这个函数有没有人调"要问清楚：`from_dict` 这种看着像内部工具的类方法，
     实际挂着一条 HTTP 接口。
- **顺带**：`from_dict` 转一圈回来会把 `tool_batches` 报成全 0
  （raw `tool_events` 不落盘，重建时现算只能算 0）—— **导出的报告说"0 轮"，
  而 trace 文件里明明是 2 轮**。已修（`stored_tool_batches`：存下来的那份优先）。
  同族教训：**上报口径缺失不要当事实**（§59 那条的又一个变体）。
- **已修**：`from_dict` 去掉 `level=`；`to_dict` 优先用存下来的 `tool_batches`。
  测试 1 条（真落盘 → 读回来 → 导 markdown），**变异验证过两处**；
  全量 `pytest tests/` 1156 绿。真机复验：`?format=md` **200 + 正常 markdown**。

**补记（09-13 真机验完之后才知道的两件事）：**

1. **预算的粒度是"每次 dispatch"，不是"整个任务"** —— 执行器实例是 `_run_executor`
   每次调用新建的，`_EXEC_BUDGET` 从**它自己的 `start`** 算。
   ⇒ 所以"任务跑了 14 分钟"和"预算 60 秒"**不矛盾**（那次每个 dispatch 只花 29~47 秒，
   模型比预算快，**压根没触发过收尾**）。**别拿任务的墙钟时长去推收尾有没有发生。**
2. **"不重试"这条判据，必须让第一次尝试就收尾才判得出来** ——
   预算 60 秒那次收尾恰好落在 `max_retries=3` 允许的**最后一次**尝试上，
   于是"之后没再起一轮"**两种解释都成立**（守卫生效 / 次数用完）。
   压到 **15 秒**才逼出"第一次就收尾" ⇒ 判据变成干净的"`executor.run` 只出现一次"。
   ⚠️ **通用教训：判据要挑"只有一种解释"的那个。** 数值挑得太宽松，
   观测到的现象就会有两种成因，等于白测。

**补记（09-13）：§59 那个边界兑现了 —— 两种"没账"从此分得开。**

`_persist_partial_usage` 只在 dispatch **返回之后**落盘，所以被收割的任务
`token_count = None` 有**两种成因**：① 压根没发起过调用 ② 发起了但没落账。
以前一律报"一次都没落盘"—— **分不出就等于没有这个信号**。

- `_mark_dispatch_started(task_id)`：dispatch **开始**时落一个 `{"started_at": …}`
  （只写第一次，后面的 dispatch 不覆盖）。`_persist_partial_usage` 累加时**必须带着它
  一起写回去**，否则一次正常落盘就把这个事实抹了。
- `_salvage_timed_out` 按 sidecar 在不在分两种说法：
  **在** → "dispatch 已经开始了，是没落账，不是没调用"；**不在** → "一次 dispatch 都没进去过"。

⚠️ **token 的语义没变** —— 它照样是**下界**，别当准确数。这个标记只回答"进没进过"。

**又一条测试写法的教训（同 §65 那两条）：桩会顺着模块属性改到别的模块上。**
`install_stubs()` 里 `_exec.tracker.read_task = …` / `_exec.witness.heartbeat = …`
改的是 **tracker / witness 模块本身**，不是 `_exec` 的属性。
所以"跑完这条测试再跑别的会挂"时，只还原 `_exec` **等于没还** ——
要连被穿透的那几个模块一起拍快照再还原。
（症状很好认：**单独跑是绿的，合起来跑是红的**。）

### 67. 预算的"时钟原点"和"消费者"不在同一层 —— §63 的改法在生产值上基本不会触发（2026-09-13）

- **症状**：§63 那一整套（轮间看表 + 单次调用封顶 + `error_kind="deadline"`）
  上完之后，**真机上 900s 超时照样撞、照样整轮全灭**（09-13 晚轮 4）。
  代码在、单测绿、`QIDIAN_EXEC_BUDGET=15` 也真的收尾过 —— 但在生产值上就是不动。
- **根因**：**两级预算的时钟原点不是同一个东西，而且谁都没发现。**
  - orchestrator 的 900s 从 **future submit 那一刻**算（`orchestrator.py:453`
    `now - submitted_at > deadline`），**任务级，跨 dispatch 一直跑**。
  - 执行器的 810s 从 **它自己 `run()` 里的 `start = time.time()`** 算
    （`openai_agent.py:328` → `:366`），而 `_dispatch_exec._run_executor:248`
    **每次 dispatch 都新建一个 executor 实例** ⇒ **每 dispatch 归零一次**。
  - 而 `_exec.run` 那个外层 `while True`（遍历 fallback_chain）× 内层
    `for turn in range(1, DEFAULT_MAX_TURNS+1)`（=2）**自己一圈表都不看** ——
    全函数 `time.time()` 只有 4 处，全是打时间戳，没有一处是判预算。
  ⇒ 只要一个任务跑过 **≥2 次 dispatch、且每次都没到 810s**（模型每轮几十秒时**常态**），
  执行器的自收尾**永远不触发**，而这任务早过了 900s 被外面无声收割。
  **收尾逻辑是对的，装在了一个永远走不到的层上。**
- **为什么当时没看出来**：这个事实**已经在文档里了**（上面 §63 补记 1："
  预算的粒度是每次 dispatch"），但它是作为**测试口径的注意事项**记下来的
  ——"别拿任务墙钟时长推收尾有没有发生"。**同一句话，正着读是"测量要小心"，
  反着读才是"生产上它基本不会发生"。** 记了事实不等于记了它的后果。
- **规则**：
  1. **一个判断"该收了"的预算，它的时钟原点必须和它的消费者同一层。**
     任务级的行为（被任务级的刀砍）不能用"每次调用归零"的计时器来挡。
     写完问一句：**这个计时器在什么情况下会重置？重置的那一方知道吗？**
  2. **凡是在生产值上"就是不生效"的守卫，先怀疑它装错了层，再怀疑阈值。**
     调参（90 → 180）永远修不好"它压根没跑"—— §63 那条"窗口比检查间隔窄"的推断
     属于**同一层内的**解释，套在**跨层**失效上自然对不上。
  3. **别把"这次验证用的值"和"生产值"混着下结论。** §63 是用 `QIDIAN_EXEC_BUDGET=15`
     验的 —— 15s 档下**每一次 dispatch 都会超预算**，所以收尾必然触发，
     "每 dispatch 归零"这个形状被**完全掩盖**。**用小值验，验不出"层错了"。**
- **量尺（09-13 已落，未真机验）**：`_persist_partial_usage` 多收一个 `elapsed`，
  每次 dispatch 往 sidecar 追加一条 `{"at": …, "elapsed": …}`。
  超时任务走不到收尾 ⇒ 只能落盘（跟 token 一个理由）。
  为什么用 dispatch 级而不是 turn 级：`ExecutorResult.elapsed` **本来就是这次 dispatch
  的墙上时间**，白捡；turn 级要动执行器热路径。
  测试 1 条（含"整份重写 payload 没抹掉上一批"）、**变异验证过**；全量 1192 绿。
- **修法（2026-09-13，已落，⚠️ 真机没验）**：**把执行器自己的钟拆掉，改成从任务那把尺倒推。**
  - `RunContext` 多一个 `deadline_at`（任务死亡时刻的**绝对值**），
    由 `_task_runner` 在 worker 线程开头落：`time.time() + TASK_DEADLINE_S`。
    那一点离 orchestrator 记 `submitted_at` 只差线程调度，**和它同一把尺**。
  - `_exec._dispatch_budget_s(ctx)` = `deadline_at − now − TASK_WRAPUP_MARGIN_S`，
    **每次 dispatch 都重算** ⇒ 上几次 dispatch、重试、中间等人审花掉的时间全扣掉。
  - 这个数经 `dispatch(budget_s=)` → `_run_executor(budget_s=)` 挂到执行器实例上，
    `openai_agent` 用 `min(_EXEC_BUDGET, budget_s)` 定 `_deadline_at`。
    取 `min` 是为了**保住 `QIDIAN_EXEC_BUDGET` 那个真机验证开关**（小值优先 ——
    不取 min 的话 §63 那套验法会**悄悄失效**）。
  - `deadline_at == 0`（goal_loop / 阶段级那条路没给）⇒ `budget_s = None` ⇒
    **退回老行为**。**`None` 不是 0** —— 当成 0 会让那两条路一个模型调用都不发就判死。
- ⚠️ **那个"暂停该不该算"的问题，这个改法把它变成了起点处的单行改动** ——
  `deadline_at` 怎么算只写在 `_task_runner` 那一行，执行器不再自己算绝对时间。
  下面是它为什么**先不动**。
- 🔴 **暂停：先不动，因为它现在是唯一的安全阀。** 查过三件事：
  1. **orchestrator 那 900s 是连着暂停一起算的** —— `running_futures[fut] = (…, time.time())`
     在派发那刻起表，`now - submitted_at > deadline` 到点就砍，而
     **`orchestrator.py` 全文 0 处提到 PAUSED** ⇒ 暂停时 future 还挂在 `running_futures`
     上，表照走。
  2. 所以**"按已花掉的 dispatch 时间之和扣"是错的**：`elapsed` 只覆盖"dispatch 在跑"那段，
     而两次 dispatch 之间的校验/门禁/worktree 操作、以及暂停，外面那把尺**全都算**。
     照它改，执行器会以为"还剩 700 秒"、外面 30 秒后砍了它 ——
     **症状跟今天一模一样，只是换成执行器自己算错**。刀在 orchestrator 手里，这个决定得在那一层做。
  3. **暂停时那个工人线程是被堵住的**（`_check_paused` 里 `while pause_path.exists(): sleep(1)`），
     而 `run_queue` 的默认并发是 **1**。⇒ 一旦"暂停不计入预算"，**一个暂停的任务能把唯一的
     工人占死、整个队列停摆**。今天的 900s 恰好是这个的安全阀。
  ⇒ 要让 `confirm_changes`（每轮等人点头）真能用，得**先解决"暂停的任务不该占着工人"**，
  那是另一个量级，**别用执行器的算法去绕**。**没动手。**
- ⚠️ **仍未真机验过**：单测 6 条（含三处接线 + 开关优先级）、**逐条变异验证过**（6 处掐断全红）、
  全量 `pytest tests/` **1200 绿**、独立 `tests/test_exec_run.py` **41/41**。
  **手工边缘路径**：真 `_run_executor` + 真 `OpenAIAgentExecutor`、每次调用 0.6s、
  任务尺给 3s ⇒ 实测 **3.1s 自己被叫停**（`error_kind="deadline"`、25 token / 10 条工具事件
  全带回来）；把任务尺拨到今天之前再派一次 ⇒ **0.03s 一步不跑直接收尾**。
  ⚠️ **但这仍是"离线真代码"，不是真机** —— 真机要验的是"真撞 900s 时它先自己收尾"，
  验法见 `docs/待验证清单-20260912.md` §三·七。

### §67 补记（2026-09-14）：同一个病，下面还有两层 + "起点"也算尺的一部分

上面那把尺（"从任务死线倒推"）改完之后，外派「改动审阅」又指了两处，**都核实为真、都已修**：

1. **"每次归零"不止 dispatch 那一层。** `_dispatch_exec` 的 fallback 链是
   `for attempt, agent_cfg in enumerate(chain[:3])`，**每次尝试都用同一个 `budget_s`**
   调 `_run_executor` —— 等于每轮把预算重置一遍，最坏 **3× 超时**。
   改法：进函数先把相对量折成绝对时刻（`_budget_deadline = now + budget_s`），
   每轮重算 `_budget_deadline - now`（跑光就是负数 ⇒ 执行器第 1 轮收尾，正是想要的）。
   ⚠️ `budget_s is None`（阶段级那条路"调用方不管"）必须**保持 None**，不许变成 0 ——
   0 会让执行器第 1 轮就收尾、**一个调用都不发**。

2. ⚠️ **只有 `openai_agent` 一个执行器消费 `budget_s`。** `claude-cli`（**默认类型**）/
   `anthropic-api` / `zhipu-api` 三条路各自用固定的 `CLAUDE_CLI_TIMEOUT`(300s) /
   `ZHIPU_API_TIMEOUT`，**完全不看任务那把尺** ⇒ 撞上就还是被外面那把 900s 的刀无声砍。
   三处都改成 `max(1.0, min(原上限, budget_s))`（取 min 保住原上限；下界 1s 免得起空子进程）。
   `zhipu_api` 还多一处：**限流退避重试**也要看预算，跑光了就不再重试。

3. 🔴 **起表的位置也是错的。** `deadline_at` 原来在 **worker 线程开头**算，而任务是
   先 `pool.submit` 进队列、**排到之后**才起来的 ⇒ 两把尺差一个**排队时间**。
   并发默认 1、单任务可跑 810s ⇒ **排队几分钟是常态**；差 > `TASK_WRAPUP_MARGIN_S`(90s) 时
   自收尾照样晚于收割。改成由 `orchestrator._dispatch_ready` 在 **submit 之前**算好、
   当参数传给 `TaskRunner.execute`（`deadline_at == 0.0` 才退回本线程起算，测试/直接调用走这条）。
   ⇒ **"同一把尺"不只是"同一个常量"，还包括"同一个起点"。**

⚠️ **这条最该记的是我自己那次"差不多"**：§67 正文原来写的是
「这里就在**同一个 worker 线程的开头**、离派发**只有线程调度那点差**」——
**把"差不多"当成了"就是同一刻"**。差的那一点在池子排队时**不是线程调度，是几分钟**。
⇒ **凡是要写"只差一点点"的地方，都先问一句：这一点在什么条件下会变大？**

### 68. 写侧的护栏查在**读之前** —— 「第一次触碰」时闸门形同虚设（2026-09-14）

- **症状**：配置文件**损坏**时，本该"拒绝重写"的闸门**没拦**，文件被整份重建 ——
  历史没了，而**文件名一模一样、内容看起来完全正常**。实测（隔离到临时目录复现）：
  · `model_discipline.record()` 返回 **True**，表里只剩刚记的那一条，之前的模型历史全丢；
  · `set_projects_root()` **没抛异常**，`settings.json` 只剩 `{"projects_root": …}`，
    `user_theme` 等别的用户设置全没。
  ⚠️ **注意它不是"完全没护栏"** —— 第二个人再碰一次就会被拦住。所以它**时好时坏**，
  只有"进程起来之后第一次碰它"那一次会中。

- **根因（结构）**：四个"读改写"接入点的形状都是
  ```python
  if is_quarantined(path): 拒写          # ← 查的时候，标记还是 False
  got = load_json_or_quarantine(path)    # ← 第一次真正读：判坏、置标记、返回 None
  data = got if got is not None else {}  # ← None 被吞成 {}
  write(data)                            # ← 整份重建发生了
  ```
  「已隔离」这个标记**要有人先读过才会有**，而**第一次触碰**时，正是**写侧自己那次读**
  才把它置上 —— 太晚了。而"第一次触碰"恰恰是**常态**（进程刚起、那个坏文件还没人读过）。

- **规则**：
  1. **判据必须是"我这次读出来的是什么"，不是"有没有人来读过"。**
     护栏的正确形状是**读在前、判在后**（`_io.load_for_rewrite` 把这个顺序焊进了函数里，
     调用方拿 `writable=False` 就出声 + 拒写）——**别把顺序要求交回给调用方**，它会写错。
  2. **凡是"先查状态、再做事"的护栏，都要问一句：那个状态是谁置上的、什么时候置上的？**
     如果答案是"另一个动作置上的"，那这个护栏在**那个动作还没发生时是失效的**。
  3. 对照：同仓 `_process_ledger.record()` 一开始就是对的 —— 它直接用**三态返回值**判
     `None` ⇒ 拒写。**同一批改动里对的形状是现成的，四个错的没照抄。**

- **为什么测试全绿（这条最该记）**：`test_io_quarantine.py` 里**每一条**"写侧拒写"用例，
  都**先手动读一次**那个坏文件（注释里写着"置上损坏标记"）——
  **那一行正是缺陷的前提，被固化成了测试的前置步骤。** ⇒ 测试在**替代码把洞填上**，
  再断言"洞不存在"。**见 §69。**

### 69. 测试把**缺陷的前提**固化成了前置步骤 —— 于是洞永远测不出来（2026-09-14）

- **症状**：一整套"写侧拒写"测试全绿，而那个洞在**第一次触碰**场景下 100% 复现。
- **根因**：测试为了让被测代码"走到拒写分支"，**先构造好了它需要的条件**——
  而那个条件（"已经有人把损坏标记置上了"）**恰恰是生产过程里不成立的那一半**。
  测试实际上在测"**第二个人**碰到坏文件会怎样"，而从来没测"**第一个人**"。
- **怎么发现的**：外派评审不是先读代码，是**先问"测试为什么没抓住"**，
  再回去读测试，一眼看到每条用例开头那句"置上损坏标记"。
- **规则**：
  1. **写"护栏生效"的测试时，先问一句：真实世界里，护栏被触发时，哪些东西是**还没发生**的？**
     那些东西**不许在测试里预先造好**。本文这条：**不许预读**。
  2. **看一条测试的"前置步骤"，比看它的断言更能发现假绿** ——
     断言往往是对的，**错的是它站在什么起点上**。
  3. 同族：`变异测试全绿` 也可能是因为变异点在**测试前置**覆盖不到的路径上。

### 70. 拒写/失败的原因在**端点层**被丢掉 —— 后端喊了，前端只看到"没反应"（2026-09-14）

- **症状**（两条同族，同一天）：
  · `agent_skill_update` 拒写时 `set_agent_skills` 返回 `False`，**端点把这个返回值丢掉**、
    照回 `{"ok": true}` ⇒ 界面高亮成功 → 刷新即回退 → **一个字都不报**。
  · 读侧更糟：`agent_skill_list` 在文件损坏时回 **200 + `{skill_names: []}`**，
    而前端区分"读不到"和"没有"的判据是 `catch`（HTTP 错误）⇒
    **那条三态在最该起作用时必然失效**，显示"0/N 已绑"，用户一勾就把真绑定整份覆盖。
- **根因**：后端的"失败"有**三种形状**，消费端只认其中一种：
  ① 抛异常（→ 500）② 返回错误码 + `{"error": …}` ③ **200 + 空数据**。
  第三种最难查 —— 它在线上**长得和成功一模一样**。
- **规则**：
  1. **拒写/失败必须让调用方看得见** —— 要么抛、要么回非 2xx + 原因；
     **绝不用"空数据"表达失败**。
  2. **前端判据落在 `catch` 上时，后端那条路必须真的抛** —— 否则判据是死的。
     写前端三态时要回后端确认"失败时它回什么码"，**别假设**。
  3. 错误原因要**原样透到用户面前**（这仓 `request()` 已经会把 `error` 提出来，
     端点把原因放进去就行）；**吞掉中文原因 = 白写**。

### 71. 变异实验留下的**脏 `.pyc`** —— 源码还原了，跑的却是变异过的字节码（2026-09-14）

- **症状**：跑完一轮变异实验、源码已经还原（`git status` **全干净**），
  但**那几条用例开始稳定地红**，而且红的是**跟本轮改动无关**的地方：
  `test_memory.py::TestMAGMAMemoryEviction` 两条断言 `evicted == 5/1`，实测 `0`。
  更迷惑的是：**把函数体原样抄一遍直接跑，结果是对的（5）** —— 同一个函数名、
  `is` 还是同一个对象、`inspect.getsource` 打出来的源码也完全正确，
  可**执行起来就是另一个行为**。
- **根因**：`__pycache__/*.pyc` 的失效判据是 **(源文件 mtime 的整秒, 源文件大小)**。
  变异-还原的循环如果**在同一秒内完成、且替换前后文件大小相同**
  （我那次是 `<=` → `>=`，两个字符对两个字符），
  那么"变异版本编译出的 .pyc"在还原之后**依然被认为有效** ⇒
  下次 import 拿到的是**变异过的字节码**。`>=` 那句在 `len=15 / max=10` 下
  直接早返回 0 —— 症状和"源码被改坏了"一模一样。
  ⚠️ 本例还有一层：`inspect.getsource` 读的是**磁盘上的 .py**，
  而执行用的是 **.pyc** —— 两者不一致时，**"我看了源码"完全不能当证据**。
- **规则**：
  1. **跑变异实验一律带 `PYTHONDONTWRITEBYTECODE=1`**（本仓审计外派件的"方法"一节
     本来就写着这句 —— **读了没照做，就是这次的全部原因**）。
  2. 还原之后如果出现**无法解释的红**，先 `find . -name __pycache__ -exec rm -rf {} +`
     再复跑一遍，**别急着去查业务逻辑**（我差点去查 `_evict_if_needed` 的实现）。
  3. **判据**：**"`git status` 干净" ≠ "跑的是干净的代码"** ——
     前者只证明**源码**没改，证明不了**字节码**没被污染。

     它可能只是**还没写完**。替别人定格 = 替他做决定（同族：删别人的东西前先留退路）。


### 73. 判据的检查点挂在「事件到达」上 —— 而故障恰恰是「事件不到达」（2026-09-16）

- **症状**：项目卡死在 `planning`，**两轮、各 30+ 分钟**，项目文件不再被写。
  线程栈停在 `_ssl__SSLSocket_read → PySSL_select → poll`（在等一个永远不来的响应）。
  **`stream_over_budget` 全库 0 次** —— 判据一次都没响。
- **根因**：这条判据**写在了它防不到的地方**。
  ```python
  for line in resp.iter_lines():        # ← 阻塞；按**行**吐
      if time.time() >= _call_deadline: # ← 判据在循环体【里面】
          _over_budget = True; break
  ```
  服务端只要**一直在发字节、却凑不满一行**（`httpx` 的 `LineDecoder` 会把不满一行的
  片段**一直缓冲**），这个循环**一行都收不到** ⇒ 循环体一次都不进 ⇒ 判据永远轮不到。
  与此同时 `httpx.Timeout(read=)` 是一把"**两次读之间**"的尺 —— 每来一个字节就**重置**，
  所以它也**永不触发**。⇒ **两条保护各自独立地被绕过，中间那条缝没人管。**
- **怎么坐实的**：`py-spy dump` 要 root、拿不到；改用 **macOS 自带的 `sample <pid> 3`**
  （**不用 root**）拿到全线程栈。三种"服务端不吐东西"的长相用一个**独立探针**
  （本地 server + 裸 httpx，`read=3s`）实测：
  · 纯静默 → read 超时 3.0s 就抛，✅ 兜得住；
  · 保活整行 → read 超时被重置，但循环体在跑 ⇒ 总时长判据兜得住；
  · **吐字节凑不满一行 → 两条都兜不住** ← 真机死的就是这种。
- **规则**：
  1. **判据的检查点不能挂在"事件到达"上** —— 要挂**周期性发生的那个东西**上
     （这里是"收到一批字节"，不是"收到一整行"）。同族已出现多次：
     **告警没出口 · 静默 except · 交付清单空** —— 每次都在旁边补一个，所以下次还来。
  2. **写"总时长"判据时，先问：它会不会被"有流量"重置？** 会，就换个载体
     （`iter_text()` / 定时器 / 独立线程），别指望 `read=` 那种"间隔"尺。
  3. **同形的第二处**：`execution_judge._stream_once`（融合那条路）
     **连判据都没有**。改一处**必须扫同族**（这次是靠"测试替身报 `AttributeError`"
     才发现的 —— 替身只实现了 `iter_lines`，被我换掉后立刻炸出来）。
  4. **测试要用真东西**：这条的回归用例**必须起真 HTTP 服务器**。
     手搭的替身只会把我猜的"`iter_lines()` 会缓冲"再喂回给我 —— **那测的是我的假设。**


### 74. 共享的 MPS 模型被并发使用 → **整个后端进程无声消失**（2026-09-16）

- **症状**：后端**直接没了**。日志停在上一行、**没有任何 traceback**、
  HTTP 全部连接被拒（`curl` 回 `HTTP 000`）。**从 Python 侧看什么都查不到。**
  ⚠️ 这类故障**没有第二次机会**：进程一没，调度循环、在跑的任务、SSE 全丢。
  真机现场：`POST /start` 之后 8 秒进程消失，**重试一次又消失**（可复现）。
- **怎么坐实的**：Python 层没痕迹，就去 **macOS 崩溃报告**里找 ——
  `~/Library/Logs/DiagnosticReports/Python-<日期>-<时分秒>.ips`（**文件名带崩溃时刻**）：
  ```
  EXC_BAD_ACCESS / SIGSEGV / KERN_INVALID_ADDRESS
  libtorch → at::native::mps::copy_cast_kernel_mps → mps_copy_ → to_device
  ```
  崩在 **PyTorch 的 Metal(MPS) 后端**。本仓唯一的 torch 用户是记忆/技能那条的
  `SentenceTransformer`（`_memory_core`）。
  **实测坐实**：单线程 `encode()` 完全正常（`device = mps:0`）；
  **8 线程同时 `encode()` 同一个模型 = 必崩**（退出码 **139 = SIGSEGV**）。
- **根因**：**MPS 不是线程安全的**，而**委员会的卖点就是多模型并行 dispatch** ——
  每个并行分支都来查记忆/技能 ⇒ 一起进同一个模型。
  ⚠️ 加载里那句 `SentenceTransformer(...).to(mps)` **也是崩点**，不只是推理。
- **修法**：所有进模型的路径收进一把 **RLock**（加载＋推理都要）。
  `_get_embed_model` 拆成"加锁的壳 + 不加锁的 `_load_embed_model`"，避免改一大段缩进。
- **规则**：
  1. **共享的模型 / GPU 句柄 / 客户端，并发使用前先问"它线程安全吗"** ——
     **不确定就当不安全**，套锁。MPS/CUDA 这类"看着像纯函数"的推理调用尤其容易漏。
  2. **"进程消失且没有 traceback" = 去崩溃报告里找，别在日志里找。**
     Python 层留不下 C++ 崩溃的痕迹 —— 我第一反应是翻 `alerts.jsonl` 和
     `logs/`，那里**一个字都不会有**。
  3. **`sample <pid> <秒>` 是 `py-spy` 的免 root 替代**（macOS 自带）。
     `py-spy` 在 macOS 上要 root，而这个会话拿不到终端输密码 ——
     **卡在这一步就该换工具，不是放弃看栈。**


### 75. 判据盯错了信号（第三、第四次）：量「有没有字节」而不是「有没有可用进展」（2026-09-16）

- **症状**：项目跑到 `executing`，两个任务 failed，而**前几轮干出来的活全丢了**。
  真机现场：`test_fizzbuzz.py` **185 行**躺在项目仓一条**悬空提交**里，
  配上已合并的 `fizzbuzz.py` 拷出来跑 —— **25 个测试全过**。
  任务终态只写着一句什么都没说的 `未知: no_escalation_path (level=any, last_action=abort)`。
- **链条**（trace 顶层 `unverified` 里写着，一处不编）：
  ```
  provider 抽搐（流吐 0 字）
    → 每次调用烧满 240s 上限（stream_over_budget:329s / 696s / 900s，chars=0）
    → 执行器撞自己的 810s 预算 → deadline_wrapup
    → verdict=未知 / action=abort（_exec.py:594）
    → break → escalate() 恒 None → no_escalation_path
    → 任务 failed → 不合并
  ```
- **根因**：**判据盯错了信号，而这已经是同一个形状的第三、第四次。**
  `_STALL_TIMEOUT` 那句注释本来就写着「多久**没新 token**」——
  **是实现没跟上它自己的语义**：
  · `read=` 量的是 **socket 读** ⇒ 服务端只要一直在发字节就永不触发
    （保活 / 凑不满一行的半截分片 / 这次的**完整行但 `delta` 全空**）；
  · 「按批字节看表」的总时长判据（§73 才加的）只管**时长**，不管**有没有用**。
  ⇒ 一次调用可以烧满 240s 而**零产出**，几轮就把 810s 预算烧光。
- **修法**：每次收到字节时比一比 `content/reasoning/tool_calls` 的**长度** ——
  「又收到一包字节」不算进展，**变长才算**。超过 `_STALL_TIMEOUT` 没进展 ⇒
  **抛 `_NetworkError` 换 agent**。
  ⚠️ **必须是"抛"，不能是"出声后照常返回空"** —— 返回空会被上层当成
  "这次调用**成功**了、只是模型没说话"，于是同一个卡住的模型继续被派下一轮。
  （对照组：真正的 `read=` 停滞本来就是抛的，那个会 failover。）
- **规则**：
  1. **写判据前先问：这个信号，故障的时候到底会不会变？**
     §73 那次是"事件不来"，这次是"事件来了但没用" —— **两次都是信号选错，不是阈值选错。**
     加阈值/调参数之前，先确认**量的是不是那个东西**。
  2. **"成功"和"没报错"要分开**：函数返回一个空结果，调用方默认这就是"成功" ——
     于是"上游什么都没给"被读成了"上游给了空的"。**静默的失败长得像成功。**
  3. **看"改了多少"要连"做了什么"一起看**：任务判死时，
     `changed_files` 明明非空、文件明明有 185 行，却没有任何地方说
     "它其实做出了东西"。⚠️ 同族见 `1849b1c`（"验收只看改没改、不看有没有东西"）。

### 76. 三个"只做了一半"的形状 —— 不变量、前提、文件（2026-09-16 晚，一晚撞见三个）

**这一条是三个独立的洞，但它们是同一个形状**：某条规则**只在它的一半上落实了**，
另一半**看起来一切正常**。夜里连着撞见三个，说明它不是运气问题。

#### 76.1 不变量**只在读的一侧**执行 —— 写侧没拦

`api_store` 的 `_` 开头是**元数据键的保留前缀**（`_observer` / `_quota_dead` 靠它藏）。
这条规则 `_load` 认（`if not k.startswith("_")`）、`_save` 也认（保留元数据键），
**只有 `add()` 不认**。

⇒ `POST /api/api-store {"id": "__probe"}` → 200、**写进文件了**；然后
`GET` 列不出来（读侧跳过它）、`DELETE` 回 `{"ok": false}`（`remove()` 里
`if api_id not in entries` —— 它压根看不见这个键）。**建得进、看不见、删不掉**，
只能手改 `.qidian/api_store.json`。

- **规则**：**不变量写在哪一侧，另一侧就是洞。** 判据要提成**一个函数**给两边共用
  （这里做成 `api_store.is_reserved_id()`），而不是在两处各写一遍 `startswith("_")`
  —— 两份判据会漂，而**这个 bug 本身就是"判据只在一侧"造成的**。
- ⚠️ 顺带一个棘轮冲突：第一版写成 `try/except ValueError → 400`，被 **静默-except 棘轮**
  判成"既不出声也不上抛"（它按 AST 形状看，看不出报文交给了调用方）。
  **别去动基线** —— 改成两边共用判据、不用异常。

#### 76.2 「禁工具」是**四条路**的共同前提，而它拦不住时只是**出个声**

`no_tools` 是塞进 `agent_cfg` 的一个字段。自带工具面的执行器（`claude-cli`，
`honors_no_tools=False`）**直接忽略它**，而四处代码都只出一条告警就往下跑：
委员会成员 · A 臂自修订 · 单模型"只出 JSON"的阶段（调研/架构）· **委员会合成那一步**。

代价是实测过的（本仓自己的记录）：**调研员在项目仓里把整个项目实现完了**
（`wc_lite.py` + 测试 + 真跑一遍），另一处**合成 agent 把目标项目的架构写进了奇点自己的 `docs/`**。

- **规则**：**"出声"不等于"拦住了"。** 当一条禁令是**某条路的前提**时
  （"委员会 = 纯文本出方案、别改磁盘"），拦不住就**别让它跑** ——
  返回 None / `continue` 试下一个 / 全不行就"无可用 agent"（fail-closed）。
  **出声只适用于"拦不了的后果可接受"**（如 `_warn_if_profile_not_enforceable` 那种
  "界面别假装生效"），不适用于"跑了会坏掉前提"。
- ⚠️ **前提不成立时，代价全落在下游**：那次"零产出 + 撞上限还返回空回答"
  ⇒ 执行器的 turn 循环不看 `raw_output`、直接进下一轮 ⇒ **三轮把 810s 预算烧光**。

#### 76.3 一个文件**只有读的人、没有写的人** ⇒ 整条检查**静默跳过**

`<项目仓>/test_cases.json` 有**三个读者**（集成测试 / E2E 清单 / 融合），
架构里也**明明有** `test_cases`（`unit`/`integration`/`e2e`/`security` 都齐，
真机那轮是 3/5/3/3 条），`execution_judge` 也在内存里拿它匹配 `acceptance` ——
**但全仓没有任何一处把它落盘**。

⇒ `orchestrator._run_integration_merge` 的 `if tc_path.exists()` **恒假**：
**集成测试从来没跑过**（真机那 5 个用例一次没动过），而且**是静默的** ——
没有告警，跟"本来就没有集成用例"长得一模一样。

- **规则**：一个"约定文件"（谁读它、路径写死在哪）要能回答**"谁写它"**。
  答不出来就是死输入 —— 而**死输入的破坏方式是"静默跳过"，不是报错**。
- ⚠️ **补上写入端之后才炸出第二个 bug**（这就是"修一层露一层"）：
  那段检查跑的是**写死的** `pytest -k test_integration`，而清单声明的名字是
  `test_normal_path_output_n5` 这类 —— **一个都不含 "test_integration"** ⇒
  一条都选不中 ⇒ pytest 退 **5**（no tests collected）⇒ 老代码 `!= 0` ⇒ **整轮交付判失败**。
  **只补写入端会让下一次交付直接炸。**
  改法：按**声明的名字**拼 `-k`；退 5 ⇒ **出声 + 放行**（判失败会因"名字一变"误伤整轮交付，
  静默又正是这个洞的成因），真失败照旧判失败。
- ⚠️ **推论**：**一条"从来没被激活过"的检查，激活它的那一刻要当成新代码来验**，
  不能假设它是对的（它从没跑过，凭什么对）。

#### 这次验证时我自己踩的三个坑（记下来免得再犯）

1. **变异打偏**：`流停滞` 在文件里有**两处**（`_lines()` 里用 `_idle` 的那条才是被测的，

3. **变异会挂住整个测试进程**（死锁类变异）：① 线程要 `daemon=True`（否则非 daemon

  而它们**同时出现在 `~/OPEN.md`、记忆正文、`docs/演化史.md` 三处** ——
  **格式对、内容旧，比缺失更坏**（下一轮会按旧账把验过的事再验一遍）。

### 77. 一整夜的形状：判据都在量「声明」，而故障全在「声明与实际的差」（2026-09-17 真机）

**背景**：这一轮是**第一次拿真实规模的项目跑**（JSONL 日志统计 CLI，5 个模块、11 个任务），
不是前十几轮那种单文件小工具。**11 个任务 / `concurrent=2` / 71 分钟 / 6 成 5 败 / 39% token 打水漂。**
下面是这一夜挖出来的七个形状。**它们看着不相干，但收口时发现是同一个病。**

#### 77.1 依赖失败 ⇒ 合并队列永久 defer ⇒ 调度永久自旋、任务永久卡 RUNNING（🔴 已修 `4eae901`）

- **症状**：整轮停摆。任务状态 `running`，但**侧车 49 分钟没动、心跳 50 分钟没跳**；
  两个工人在 `_queue_SimpleQueue_get` **睡着**、循环在转 JSON 解析 ——
  **和 09-13 那次 py-spy 栈一模一样**。实测 **1731 条 `drain_dep_blocked` / 2 分钟、44 分钟 CPU**。
- **根因**：`merge._deps_satisfied` 要求依赖**全部 DONE**，而 **`FAILED` 是终态、永远到不了 DONE**
  ⇒ 只要一个任务的依赖失败了，它的合并请求就永远满足不了依赖：
  ```
  drain 永远 defer → 返回空 → _drain_pending 不 pop
  → 任务永远留在 pending_batches
  → 循环睡觉条件 `not running_futures and not pending_batches` 恒 False → 全速空转
  ```
- **这是「修了一半」的第四个**（同 §76）：`merge.py` 的注释早就写着
  「**1 个依赖未满足就能让 `drain()` 永不返回**……卡住 = 整个调度停摆」——
  **他们只修了内层**（让 `drain()` 自己别死循环，改成 break + 报警），
  **外层循环仍把「队里有东西」当成「有活干」**。内层的死循环换成了外层的空转。
- **规则**：**「等成功」和「等不到」是两个判据，别用同一句话**。
  依赖到**终态**（成功/失败/放弃）就意味着它不会再变了 —— 该放行的放行，该降级的降级。
  判据里出现 `!= DONE` 这种"只要成功"的写法时，问一句：**失败的时候它怎么办？**
- **修法**：`_deps_satisfied` 改认 `tracker.is_terminal`；循环加"这一圈有没有进展"的睡觉条件。
  ⚠️ **边界要钉住**（写了测试）：`None`（任务文件不存在）仍算没满足；依赖还在跑仍要等。

#### 77.2 调度循环没有退避 —— 而且这不是卡死独有的，是**常态**

`orchestrator._run_queue_v3` 的 `while True:` 里，**只有**
「`not running_futures and not pending_batches`」那条分支 `time.sleep`；
**只要有任务在跑就一点不睡**，全速转 `_reap_futures` / `_drain_pending` / `_auto_trigger_test_fix`
（最后这个**每圈 glob 全部项目文件**）。作者自己知道它转得快 —— 唯一被节流的是孤儿扫描。

⇒ 平时任务少、轮次短，没人注意；11 个任务跑一小时才露。
**重启后立刻复现**（新进程 3 分钟又刷 2292 条）⇒ **与卡死无关，平时就这样。**

- **规则**：**热循环的判据要是"有没有进展"，不是"表里有没有东西"。** 后者会让"永远不会有进展"
  和"正在进行中"长得一模一样。

#### 77.3 孤儿探测量的是「登记表里有没有名字」，不是「有没有人在干」

`_warn_orphan_running` 的定义是 `live = running_futures ∪ pending_batches`，
`if tid in live: continue  # 有人管`。**而故障恰恰是"名字还在表里、人早走了"**
⇒ 探测一看"表里有它"就跳过了。

⚠️ docstring 还专门**夸过**这个选择：「精确的'不在表里'，**不是'多久没动静'那种超时猜法**
（后者会被慢模型/人审等待/暂停误伤）」。**动机对，代价是对"future 永远不会完成"完全瞎。**

- **规则**：**登记 ≠ 活着**。「在表里」证明的是"有人登记过它"，不是"有人在干它"。
- ❌ **2026-09-19 更正：这里原先写的替代判据**（「`running_futures` 非空 ∧ 池子里的工人
  全空闲」）**实测站不住，别照它做**。拿真的 `ThreadPoolExecutor`（Python 3.14.5）量过：
  · **"未完成 future 数 > 工人数"是正常的**（5 个提交 / 池子 2 ⇒ 未完成 5、工人 2），
    那只是排队 ⇒ 不能当矛盾；
  · 空闲工人在 `get()` 上等，新任务一来就取走 ⇒ **"全空闲 ∧ 有排队项"只存在于
    `submit()` 到工人醒来之间的几微秒**，按它报警是赌竞态（要么假警报、要么永不触发）；
  · 工人线程即使被 `sys.exit` 带走，**future 也会被标成 done**（CPython 的 `_worker`
    捕 `BaseException` 后照标）⇒ "工人死了没人收"在 CPython 里基本不可达。
- 🔵 **那真正的缺口是什么**：不在判据，在另外两处 —— ① **调度器从不调 `check_stalled`**
  （只有观察者调，见 §77.5）；② 告警只报事实、不报为什么/怎么办（**2026-09-19 已修**）。
- ✅ **"心跳陈旧"这条判据本身是站得住的**，但前提别记错：心跳写在 `_exec.py` 的
  `for turn` 循环开头，而**一个 turn 跑的是一整次 dispatch**（不是一次模型调用）
  ⇒ 上界是 `TASK_DEADLINE_S − TASK_WRAPUP_MARGIN_S` = **810s**，而 `STALLED_AFTER_S`
  = **1200s** 本来就在它上面（`test_stalled_threshold_exceeds_one_legitimate_dispatch`
  钉的就是这个）。**"新鲜度上界 = 单次模型调用的 240s" 是错的** —— 别再照那句话修。

#### 77.4 告警轮转把诊断证据冲掉了

`witness._ALERT_KEEP = 1000`，超阈值只留最后 1000 行。
而注释写的假设是「**告警量小(一次任务几十条)，不值得做轮转**」——
**自旋当场破了这个假设，而轮转做的头一件事就是把你要用来诊断这次自旋的证据删掉**
（开跑前 2714 行 → 事后 2175 行）。

- **规则**：**"正常量级"的假设要写清，异常量级要有别的出路。** 一个只在异常时才触发的机制，
  不能把异常的证据当成"过量的垃圾"清掉。

#### 77.5 观察者的喇叭是空的 —— **谁来监督守护者？**

- **背景**：`check_stalled()`（阈值 `STALLED_AFTER_S = 1200s`）全仓**只有观察者和一个 admin 接口**在用，
  **调度器/编排器一次都不调** ⇒ **观察者是唯一会主动发现停滞的角色**。今晚卡了 50 分钟，**早该响**。
- **它为什么没响**：告警**广播给 `_pending_replies`**，而那个字典**几乎永远是空的** ——
  唯一正经的注册入口 `register_client` **全仓零调用者**（`.py/.ts/.tsx/.js/.sh` 全搜过）；
  唯一写入点是聊天路径（**有人问问题的那一刻**才写），而 `unregister_client` **也是零调用者**。
  ⇒ **没人聊天时，广播给一个空字典，无声消失。而且一个字都不落盘**
  （`_check_anomalies` 只 `return` dict，没有 `witness.warn`；全量搜 alerts = **0 条**）。
- ⚠️ **最讽刺的一处**：桥里**有现成能用的广播通道** `bridge.broadcast_observer`
  （走 Observer Server、带频道、还返回"发给了几个客户端"）—— `app.py` 的**调度事件就在用它**，
  **偏偏停滞告警没走它**。
- 🔵 **只"接上线"不够 —— 它要治的病和它得的病是同一个**：
  · 任务**静默地**停滞了，没人知道 ／ 它**静默地**失效了，没人知道；
  · 它在跑、在监听、循环在转 —— **外部看一切正常**；它的失效方式是"什么都不发生"，
    而"什么都不发生"与"一切正常"**长得一模一样**；
  · `check_stalled` 量的是**任务**有没有心跳，**没有任何东西量观察者自己**
    ⇒ "接线断了"**不可能被发现**，因为发现它需要一个"更上一层的观察者"，而那个位置是空的。
- **规则**：**每个"守护者"都要有自己的、可被证伪的活性痕迹**，而且
  **必须落在"它失效时你一定会看的地方"**（`alerts.jsonl` / 界面），
  **不能只落在它自己的日志里** —— 那等于没说给任何人听。

#### 77.6 `.pyc` 一个根因打了三枪

项目仓**没有 `.gitignore`** ⇒ `__pycache__/*.pyc` 被 git 跟踪：

1. **合并冲突**：多个任务碰同一模块 ⇒ 各自编译出不同二进制 ⇒ 合并必冲突（T3/T5 held）；
2. **集成检查判「工作区不干净」**：跑测试会重新生成 pyc ⇒ `git status` 里 7 个 ` M`
   ⇒ 集成检查**在第①步就返回**（它那条判据是"工作区必须干净，`??` 除外"）
   ⇒ `integrating → executing` 来回打转；
3. 🔴 **交付物被污染**：`git archive release/<tag>` 导出后，
   **包里躺着 7 个 `.pyc`** —— 坑一路漏到了收件人手里。

- **规则**：**生成物进版本库，代价会在三个地方分别出现**（合并 / 判据 / 交付），而且每次都像新 bug。
- ⚠️ 前十几轮没撞见是因为 FizzBuzz：**单文件时写实现和写测试碰的是不同路径的 pyc，不交叉**。

#### 77.7 判据要的输入，没有传到产出它的人手里（**这一夜撞见两次**）

**第一次（`test_cases.json`）**：三个读者都按 `<项目仓>/test_cases.json` 找它，**全仓没人写**
⇒ 集成测试从来没跑过。补了写入端之后又发现：读取端拿声明的 `name` 去拼 `pytest -k`，
**而前提"声明的 name 就是测试函数名"没有任何地方强制**（架构 schema 里 `name` 就是 `""`）——
上一轮 5/5 全中是**运气**。

**第二次（`constraints[].check.argv`）**：架构声明 10 条约束，每条指定一个测试文件
（`tests/test_contract_normal.py` 这类），**10 个全没被创建** ⇒ 机器检查 `ran=10 passed=0`。
根因：`execution_judge.py:996` 构造执行器上下文时**只传 `rule` 的文字，不传 `check`** ⇒
**干活的人从头到尾没见过那个文件名**。

- **规则**：**加一个"读者"之前，先确认"写者"存在，而且写者知道要写什么。**
  判据的**输入**必须和判据**一起**交付给产出它的人 —— 否则那不是判据，是许愿。

#### 77.8 排队等的时间会被算进执行预算 ⇒ 排队够久就「上场即死」

`deadline_at = pool.submit 那一刻 + 900s`，而 `_dispatch_budget_s = deadline_at − now − 90s`
⇒ **submit 之后在池子里排队的每一秒，都从执行预算里扣**。
⚠️ **这是 2026-09-14 有意的设计**（为了让执行器自收尾早于外面那把 900s 的刀），
**它没错，但它没兜住「并发=2 + 任务多」这个区间。**

实测排队空等：4s / 4s / 213s / 213s / 660s / 660s / **972s** / **1471s** / **1732s** ——
**前 7 个正常交付，972s 那个开始出问题**（零产出、末次派发只拿到 `cap=6s`）。

- ⚠️ **同族**：`_budget_exhausted`（09-16 修）只在预算 **≤0** 时才拦 ——
  而 `cap=6s` 是**正数**，照样发起了一次注定空的调用。**"太小也是没有"这个区间没人管。**
- **规则**：**判据用"到没到点"，要配一条"够不够用"。** 只判前者的，会在临界的正数上漏过去。

#### 77.9 `resolve` 解完冲突后任务永远卡在 `conflict_held`

`MergeQueue._mark_merged` **只改内存里那几个字段，不 `tracker.transition`** ——
而 `_park` 是**会** transition 的 ⇒ **进得去、出不来**。
且 `resolve` 在 transition 之前就把 parked 记录 pop 掉 + 删了盘上文件 ⇒ 没有回退路径。
而阶段推进的 `pending` 集合里 **`conflict_held` 算 pending** ⇒ **项目永远推不进 `integrating`**。
**而且没有任何 API 能把任务从 `conflict_held` 挪出来**（`retry` 只收 FAILED/ROLLED_BACK，
`update` 只能改 description，`cancel` 只能标 FAILED —— **那是假的**）。

- **规则**：**"进得去"的状态，要有一条"出得来"的路，而且那条路要能被外部触发。**
  加状态机转移时，成对地问：谁负责把它转出去？转不出去时人能怎么办？

#### 77.10 调研报告解析失败 ⇒ 界面上是个空框，一个字不提示

真实规模这轮的调研报告 20KB，模型吐的 JSON **字符串里带裸换行、还漏了闭引号和逗号**
⇒ `try_parse_json` 那几层修复（围栏 / `}?` / 尾逗号 / 截断修复）**一层都不覆盖**
⇒ 走兜底 `{"raw_output": raw[:5000], "parse_error": True}`
⇒ 前端 `ResearchReport` 只读 `competitive_analysis.products` / `pitfalls` / `recommendation`，
**兜底那份一个都没有** ⇒ **渲染成空框**；而**前端压根不认识 `parse_error`**（全仓 grep 零命中）⇒ **静默**。

- ⚠️ **全文没丢**（`<id>.research.md` 20KB 完整），但 **UI 没有入口**（`/files` 跳过 `.md` 和 `.qidian/`）。
- **规则**：**兜底值也要有形状。** 一个"字段全缺"的兜底对象，在只读字段的渲染器里
  **和"还没有数据"长得一模一样** —— 那不是兜底，是把故障藏起来。

#### 🔵 收口：这一夜的形状（**每层都在用"我的声明"证明自己**）

把上面七个放在一起看，会发现它们不是七个 bug，是**一个病在七层上复发**：

| 谁在说 | 它说的 | 实际 |
|---|---|---|
| 任务 | 「我在跑」 | 没人管它 |
| 调度循环 | 「我在转」 | 没有进展 |
| 合并队列 | 「我在等依赖」 | 那个依赖永远不会来 |
| 告警 | 「我出声了」 | 没人听 |
| 观察者 | 「我盯着呢」 | 喇叭是空的 |
| 代码仓 | 「这是我的源码」 | 一半是字节码 |
| 判据 | 「我检查过了」 | 检查的东西没人被要求造 |

**每一层的判据都在量「声明」（状态字段、登记表、文件名、消息数），
而故障永远发生在「声明与实际之间」。**

⇒ **每修一次只覆盖想到的那几处，所以会一直有新的一处。**
解法不是再加第 8 处 guard，是**加一层对账** —— 定期问一句
**「我声明的和实际的，对得上吗」**，而且**对账时不能拿登记表当实际**（§25 的孤儿探测
方向本来就对，只是对账时用了登记表）。

**配套的两条**（都是这一夜用血换的）：
1. **每个守护者要有可被证伪的活性痕迹**，落在"它失效时你一定会看的地方"（77.5）；
2. **加了"读者"先确认"写者"存在且知道写什么**（77.7）。

#### ⚠️ 78.1 验证这条路时踩的两个坑（差点又得出假结论）

**① 批准 GATE2 在"任务全终态"的项目上 = 执行层 1 秒冲过，逐任务的路压根不走。**
`run_post_exec_checks`（闸门所在）的唯一入口是 `_exec.py:704`，**逐任务**触发。
我批准了 round f（14 个任务全是终态）⇒ `executing → integrating` **只花 1 秒** ⇒

### 80. "没动过"被当成"有产物" —— 原语在空输入下返回了**别人**的东西（2026-09-18）

**症状**：任务 `…835` 被判「无文件改动 + 偷懒」，而 `salvageable_refs()`
**说它有可打捞产物** —— 点进去是它哥哥 `…833` 的文件。**没产出的，被说成有产出。**

**根因**：

```python
def commit_wt(wt):
    if _has_changes_in_wt(wt):          # 只有"有改动"才 commit
        _run(["add","-A"]); _run(["commit", ...])
    return _wt_head(wt)                 # ← 没改动时，返回的是工作树的 HEAD
```

工作树是从 `ctx.snapshot_ref` 建的 ⇒ **没动过时 `_wt_head` 就是基线本身，是别人的提交**。
而调用方 `_exec.py:361` **无条件**把它锚成"这个任务的产物"、并构造合并请求。

**规则**：

1. **原语在"空输入"下要返回"空"，不能返回"当前状态"**。
   `commit_wt` 对"没有改动"返回 HEAD，在另一个调用方（`merge_back`）是合理的
   （合并 HEAD = 空操作），**在这里就是错的** —— 于是修在**调用方**
   （`branch_ref != ctx.snapshot_ref`），不是改原语。
   🔵 **同一句话在不同调用方含义不同时，判据要放在调用方。**
2. ⚠️ **别用 `_has_changes_in_wt` 当判据**：它看的是"**未提交**改动"，而
   **agent 自己 `git commit` 过之后工作区是干净的** ⇒ 用它判断会把**真的产出**
   当成没产出、**连合并都不做** —— 比原 bug 更坏。**跟基线比才是对的。**
   （这条路径 `_track_changed_files` 的注释里早就写过"会被'改动已提交'骗到"，同族第三次。）
3. **这是上游那棵树的下游果子**：835 能走到"提交/锚定"这一步，是因为更上游
   「被掐断的半截思考被当成正文」⇒ `success=True`（见 §79）。
   **修上游会顺手掐掉这里的大部分触发面，但不等于这里的洞不存在** ——
   任何"成功但没产出文件"的任务照样会踩。

**没产出的对照**：835 自己的工具日志只有 run/read、**一次 `write_file` 都没有**，
还专门读了 `parser.py` 拿到「(不存在)」—— 它是真没产出，不是被冤枉。

### 81. 惰性 `__getattr__` 把 **importlib 的 dunder 探测**当成了请求（2026-09-18）

**症状**：`lazy_spoke_import_failed:_dispatch_exec:cannot import name
'_load_skills_for_agent' from partially initialized module '_dispatch_skills'`，
跨三天 80+ 次。2026-09-16 判它是**并发竞态**（"两个线程同时进来，T2 拿到半成品模块"），
为此加了 `_LAZY_SPOKES_LOCK` —— **没治好**。

**真机制**（挂探针记录每次 `__getattr__` 的入参 + 调用栈，跑全量测试实测；不是推断）：

    from singularity.scheduler.dispatcher import X     ← **一条普通的 import 语句**
      → importlib 的 `_handle_fromlist` 第一件事：`hasattr(module, "__path__")`  ← 判断是不是包
        → 本模块有 PEP 562 的模块级 `__getattr__` ⇒ **这一问被转发进了惰性转发循环**
          → 循环去导 `_dispatch_skills`；而它模块体第 3 行**自己**就是一条
            `from singularity.scheduler.dispatcher import (...)`
            ⇒ 又一次 `hasattr(module, "__path__")` ⇒ **重入**
              → 循环里 `import_module("_dispatch_skills")` 拿到**半成品**（它正在被导入）
              → 接着导 `_dispatch_exec` → 第 8 行
                `from _dispatch_skills import _load_skills_for_agent` → 名字还不存在 → 炸

**关键**：**同一个线程自己绕回来**，不是两个线程。RLock 是同线程放行的 ⇒
那把锁**从原理上**就挡不住这个形状。**"加了锁"和"治好了"是两回事。**

**量到的规模**：一次全量测试，惰性循环被白跑 **103 次**（`__path__` 64 + `__test__` 26
+ `__bases__` 13）—— 每一条 `from ...dispatcher import ...` 都会贡献一次。

**规则**：

1. **模块级 `__getattr__`（PEP 562）必须先把 dunder 挡掉**：
   `if name.startswith("__") and name.endswith("__"): raise AttributeError(name)`。
   否则**每一条 from-import** 都会（a）白跑一遍你的惰性逻辑、（b）有机会在导入中途重入。
2. ⚠️ **别急着信"并发"这个解释**。这次判对了症状（半成品模块 + 名字不存在），
   判错了**主体**（跨线程 → 其实是同线程重入）。判错主体的代价是**修在不生效的地方**，
   而且因为"改了、看起来合理"，**下次还会先怀疑锁不够**。
   ⇒ **能挂探针量出调用栈时，先量再改**；"读码推出来的形状"要标清楚是推断。
3. ⚠️ **告警账本会被测试污染，而它是查故障用的那份**。
   同一个 bug 的副产品：跑一次 `pytest tests/` 就往**真** `.qidian/alerts.jsonl` 写 1 条，
   因为 **pytest 导入测试模块（收集）发生在任何 fixture 生效之前**，而测试模块顶层就是
   `from ...dispatcher import ...`。我当天**差点拿它算出"后端空转时反复失败"**这种错误结论
   （那几条全是我自己跑测试写的）。
   ⇒ 修法：`tests/conftest.py` 在**导入期**就把 `QIDIAN_DIR` 指向临时目录。
   **判据**：把故障源放回去跑全量，真账本**增量必须是 0**。
4. 🔵 **写测试时被自己的断言抓到一次**：我第一版写"辐条里一个 dunder 都没有"，
   当场红 —— `_dispatch_exec` 有 `__annotate__` / `__conditional_annotations__`
   （**Python 3.14 / PEP 649 给每个模块自动加的**）。**别把解释器自动挂的东西
   当成模块自己导出的。**

### 82. 四个"静默失败"的现场 —— 它们的共同形状是**删掉/丢掉了自己唯一的输入**（2026-09-19 凌晨）

> 来源：清 `~/OPEN.md` 时按优先级修的 4 条（都不是新发现，是 09-17/09-18 外派评审
> 挖出来、一直挂在清单上的）。四条**表面毫不相干**，修完发现是同一个形状：
> **系统把自己赖以判断的那份输入弄没了，而且不吭声** —— 之后一切都"看起来正常"。
> 这和 §77 是一族，但方向相反：§77 是**量了声明**，这里是**连声明都删了**。

#### 82.1 `tracker` 读路径静默吞错 ⇒ RUNNING 幽灵（S5）

- **症状**：一条 RUNNING 任务**在工作树没了、侧车不动、心跳陈旧**的情况下照样"在跑"，
  界面上**根本查不到它**（09-18 round g 现场复现，见 §77.3 那一族）。
- **根因**：`read_task` / `ready_tasks` / `recover` / `_load_all_tasks` **四处**读路径
  一律 `except (JSONDecodeError, TypeError, ValueError): return None / continue` ——
  **零留痕**（实测：tmp 里 `alerts.jsonl` 从头到尾没被创建）。
  最毒的一环：`Task.from_dict` 结尾是裸 `cls(**d)`，**不丢未知键** ⇒ 一条 RUNNING
  任务只要**多一个键**（回滚到旧版本 / 手工改过盘 / 迁移写了一半）就读成 `None`
  ⇒ **`recover()` 永远不碰它** ⇒ 它**永远是 RUNNING 的幽灵**。
- **修**：四处合成 `_read_task_file()`，走 `_io.load_json_or_quarantine`
  （09-14 就是为这个形状加的）；`from_dict` **丢掉**未知键而不是抛。
- ⚠️ **读侧必须自己去重**：`ready_tasks` 每 2 秒把全部任务文件扫一遍，
  照搬"每读一次报一次" = 一份坏文件**每 2 秒刷一条**告警 —— 正是 §79 那条
  「留痕写成每轮一条」的坑。闸门用 `_io.is_quarantined`（复用它只做去重；
  **写侧没有任何人拿它挡任务文件**，已 grep 核实）。
- ⚠️ **代价如实记**：`to_dict()` 是 `asdict(self)`，丢掉的键在下次整份覆盖写时
  **真就没了**。但那比"丢整条任务"轻得多，而且这条会出声（`_warn_task_once`）。

#### 82.2 `witness` 删掉自己唯一的输入，且一声不吭

- **根因**：`check_stalled` / `_heartbeat_task_levels` / `force_cleanup_heartbeats`
  三处 `except: p.unlink()` **都没有 warn**；而写侧 `heartbeat()` 用的是**裸
  `write_text`**（全 `.qidian` 唯一不走 `_io.atomic_write_json` 的状态写入）⇒ **能撕**。
- **代价**：一次撕裂 = **一个真卡死的任务从告警系统里消失**，之后"没心跳"
  = "不在跑" = 看起来正常（`check_stalled` 扫的正是这个目录）。
- **修**：写侧改原子写（在写侧堵死比在读侧补救便宜）；读侧统一走
  `_drop_corrupt_heartbeat()`，删之前**先报一条**（走 alerts.jsonl，不走日志 ——
  "静默删输入"这个毛病说的就是**告警通道没收到**，换成日志等于没修）。
  task_id 从**文件名**取（坏掉的 JSON 里取不到）；取不到就原样报。
- 🔑 **`heartbeat()` 的原子性可以真测**：patch `Path.write_text` 造"写到一半就崩"，
  断言**正式文件还是崩之前那一份**。裸 `write_text` 版本上这条会红。

#### 82.3 超时写的"停"标记，冒充了用户取消

- **根因**：调度器超时会写 `CANCEL_DIR/<id>.json` 让执行线程提前收手
  （`fut.cancel()` 拦不住已经开始跑的 future，那时它还在烧 token）——
  而这个标记和**人工取消**共用同一个文件、同一个消费者 `_check_cancelled`，
  那里只会读成 `cancelled_by_user` ⇒ **我们自己的超时被记成"用户取消了"**。
  原来写的是 `"{}"` —— 全仓唯一一个**空 body** 的取消标记
  （`task_cancel` 写的那个带 `{"task_id","cancelled_at"}`），**没有任何东西能区分这两件事**。
- **修**：body 带 `{"by": "timeout"}`，消费者分两种报
  （`cancelled_by_timeout` / `cancelled_by_user`）；两种都保留 `"cancelled"` 前缀，
  因为全仓消费方判的是前缀，语义都是"**别重试**"。
  读不出 `by`（旧格式 / 空 body / 坏 JSON）→ **退回旧行为 = 用户取消**，且不静默。
- 🔑 **修之前先把"泄漏面"核完**（这条原来标着"没核完"）：会重新派 FAILED 任务的
  只有 `task_retry`，而它开头就调 `cleanup_task_artifacts`；`handle_gate3_reject`
  只重置 **DONE**；`tracker.recover` 只捞 `_INFLIGHT`（**不含 FAILED**）。
  ⇒ **三条重排队路都不泄漏**，要修的是"冒充用户"这件事本身，
  **不是**"标记该不该写"。**别把"没有泄漏"当成"这个 bug 不存在"。**
- 🔴 **2026-09-20：第四条路出现了，上面的核验随之作废 —— 而它是靠"只重置 DONE"成立的。**
  `handle_gate3_reject` 的 `impl` 返工开始**也重置 `FAILED`**（A 档，用户拍板：
  不补这一半的话，失败的任务永远不被重派 ⇒ 返工 = 把做成的推倒重做、没做成的照旧缺 ⇒ 转圈）。
  ⇒ 超时那条路写的 `cancels/<id>.json` **重新暴露**：标记不消费的话，重派下去的任务
  一上场就被 `_exec._check_cancelled` 判成"取消"（白跑一轮，账还记在"取消"上）。
  **修**：`workflow._clear_cancel_marker_for_rewind` —— 重置**之前**先处置标记，
  三支：没有 ⇒ 直接重派 · `by: timeout` ⇒ 删标记再重派 · **其他 / 读不出 ⇒ 不重派**（尊重"别继续"）。
  判据沿用本条定的口径：**读不出 `by` 一律当用户取消**；读不出来要**出声**
  （"且不静默"是本条自己写的），但"没有 `by` 键"是合法旧格式、**不报**（报了就是常亮的假红）。
- 🔑 **本条真正该记的规则**：**"泄漏面已核"是一个带前提的结论，不是永久事实。**
  它的三条路里有一条的前提是"那一支只重置 DONE" —— 后来改了那一支，
  结论就**静默失效**了，而文档里那行字看着还跟对的一样。
  ⇒ 改**任何**"重排队 / 重新派任务"的路径之前，先 grep 这里，把前提核一遍。

#### 82.4 「绝不能 mkdir」的兜底路径，被只读的调用点 mk 出来了

- **根因**：`project.repo_dir()` 的兜底分支注释**明令"绝对不能 mkdir"**
  （理由：建出来的空目录让 `load()` 依旧返 `None` 而目录却"在"，现场就成了
  "空目录在、JSON 没了"，看起来像**项目文件自己消失**），
  而 `_git_worktree._worktrees_dir()` 拿它的返回值 `mkdir(parents=True, exist_ok=True)`
  ⇒ `.qidian/projects/<id>/` 下**只剩一个 `.repo-worktrees`**（盘上已坐实）。
- **修**：`_worktrees_dir()` 改成**只算路径**。四个调用点里**只有一个真要建**
  （`create()`），而它调的是 `git worktree add` —— **git 自己会建父目录**
  （2026-09-19 实测，别猜）。另外三个是只读的（`.glob()` / `.iterdir()`）。
- 🔑 **判据选"可观察的行为"而不是"调了哪个函数"**：一条测只读用法**没有**把目录建出来，
  一条测去掉 mkdir 之后 `create()` **照样能建**（证明不是在拿 create() 换）。

**这四条共同的规则**：

1. **判"我删掉/丢掉了什么"之前，先问"这东西是不是我唯一的判据"**。
   心跳是"在不在跑"的唯一凭据；任务文件是"有没有这个任务"的唯一凭据；
   取消标记是"谁叫停的"的唯一凭据。**删掉它 = 删掉判据本身**，
   而剩下的系统状态**长得和健康一模一样**。
2. **"静默"这个词要落到"哪个通道没收到"**。这几条的正解都是**往告警通道说一声**，
   而不是 `logging` —— 告警通道才是 observer 讲给人听的那条路。
3. **修"每轮都会走到"的地方时，去重是功能不是优化**（§79 的账：1850 条/天）。
4. **先核泄漏面再动手**：82.3 的"没核完"三个字，核完发现**三条重排队路都够不着** ——
   结论从"标记要清"变成"标记要自报来历"，**修法完全不同**。

### 83. 批量改代码时，**判据被"形状"顶替了**（2026-09-19 清 lint 债 · 一夜踩三次）

背景：为了让 CI 的 ruff 能绿，一晚清了 1021 条债。**三次栽在同一个形状上** ——
改的时候用的是"看起来像什么"，而不是"精确是哪一处"。

#### 83.1 自动修把**再导出**当死 import 删了 ⇒ 53 个测试文件 ImportError

- **症状**：`ruff check --fix`（F401）跑完，`pytest --collect-only` **53 errors**。
- **根因**：`executors/base.py` 里那四行是**再导出** —— `anthropic_api` / `zhipu_api` /
  `openai_agent` 和两个测试文件都 `from ...executors.base import _BLOCKED_PATTERNS` 等，
  而 base.py **自己一个都不用** ⇒ ruff 判"死 import"。
  ⚠️ **而它就长在那句注释底下**：「名字保持不变：全仓有别的模块
  `from ...executors.base import _BLOCKED_PATTERNS`」——
  **那句话是给人看的，ruff 不读注释。**
- **第二次踩（同一个坑换个面）**：改用 `from X import Y as Y`（ruff 文档里认的再导出写法）
  之后，**只有同名别名留住了** —— `is_blocked_path as is_blocked_path` 保住了，
  而 `BLOCKED_PATH_PATTERNS as _BLOCKED_PATTERNS`（**改过名**）照删。
  ⇒ **ruff 的再导出识别要求"别名 == 原名"**，不是"有个 `as` 就算"。
- **修**：改名的那两行挂抑制注释，同名那两行保留 `as`。
  并**用副本做决断实验**确认标记真在承重（把标记拿掉 ⇒ ruff 立刻报那 2 条）。
- 🔑 **规则**：
  1. **"静态分析说没人用" ≠ "没人用"** —— 它看不见跨模块。
     **删 import 之前先 `grep -rn "from <本模块> import"`。**
  2. **注释不是判据**。它写在那儿很久了，工具没读，**我也没读**。
  3. **别一次性 `--fix` 全仓**（那次 55 文件 / 275 处）—— 出事时定位成本高。
     分文件、分规则跑，**每步之后跑测试**。
  4. 本仓自带最后一道防线 `test_no_undefined_names.py::test_from_import_targets_exist`
     （扫全仓 `from M import N`，判 N 在不在 M 里）—— **但它只扫 `src/`**，
     测试目录里的引用看不见。**它是兜底，不是保证。**

#### 83.2 B007 是按**列号**点名的，我按"位置"猜 ⇒ 改错了变量

- **症状**：`workflow.py` 的 `for tid, t in tasks:` 被 B007 报了，我把 `tid` 改成 `_tid`。
  两个测试红了：`task_file_overlap`（文件重叠检测）**整条失效**。
- **根因**：B007 报的是 `:887:14` —— **列 14**，那是 **`t`**，不是 `tid`。
  而 `tid` 在循环体里**用了四次**（`_changed_files_of(tid)` / `mine[tid]` …）。
- 🔑 **规则**：**按列号定位，别按位置猜**。元组解包里"哪个变量没用"由列号定死，
  扫一眼觉得"像"就动手，会把**有用的那个**改掉。

#### 83.3 改推导式变量 = 改**整个推导式**，不是那一行

- **症状**：E741（歧义名 `l`）4 处，我按行号只换了报错那一行 ⇒ **F821 undefined name `l`（3 条）**。
- **根因**：推导式**跨行**（`[l for l in xs` 一行、`if l.startswith(...)]` 另一行）。
- ⚠️ **同一晚还有一次假修复**：验证脚本里写 `assert "\bl\b" in line` ——
  **非 raw 字符串里的 `\b` 是退格符**，不是词边界 ⇒ 断言恒假、修复没落盘，而我以为改好了。
  **量尺写错时，先怀疑尺子。**

**这三条共同的规则**：

> **批量改代码时，定位必须来自"工具给出的精确坐标"（列号 / 全部出现位置），
> 不能来自"这一行看起来是要改的那个"。**
> "形状匹配"在**一个**文件里够用，在**一次几百处**的批量里就是抽样 ——
> 而抽样漏掉的那一处，**测试不一定抓得到**（83.2 抓到了，83.1 差点没有）。

### 86. 「有事实」是个 bool，而**事实分三档** —— 弱的那档把强的顶掉了

#### 86.1 症状

一轮真机跑完，**5654 行产出、进仓 0 行**。项目详情里判词是
`QA:fail: [completeness] 无文件改动`，而 `salvageable_refs()` 上明明列着三条 ref。

（2026-09-20 `round-20260920b`，T3/T4/T6 三个任务，同一形状：

| 任务 | pending ref | 产物 | 判死时刻 |
|---|---|---|---|
| `…318` | `d90998c` | **+1008 行**（`filters.py` 515 · `types.py` 493） | 01:02:24 |
| `…320` | `83c228d` | +251 行 | 01:02:25 |
| `…323` | `acabb9a` | +1178 行 | 01:12:32 |

三个都晚于各自 ref 的提交时间 19~105 秒 —— **活干完了才判的死**。）

#### 86.2 现场怎么读出来的（**不用重跑**，全在盘上）

四样东西一对就出来了（`tasks/` · `traces/` · `partial_usage/` · 项目仓的 `refs/qidian/pending/`）：

```
trace.token_count = 4920        ← > 0
trace.changed_files = []        ← 空
trace.validation.turns_used = 1 ← 只有 1 轮
trace.unverified[0] = "执行器到达总预算主动收尾: 单次调用撞上限被掐断，正文零产出
                       （工具轮 4 次，改动 0 个文件）"
partial_usage 最后一条 = attempt 3 / turn 1 / elapsed 54.0
项目仓 refs/qidian/pending/…318 → d90998c，+1008 行
```

`trace` 和三样对得上（`token_count` / `elapsed` / `unverified` 全是**最后一次派发**的），
⇒ **trace 记的是那个空壳，不是真干出来那份。**

对照组成立（重要）：T5 `…321` 同样判这句话，但它 `token_count = 0`、**压根没有 ref**
⇒ **锚不是无脑打的** ⇒ 上面三个的 ref 是"真有产物"的证据，不是噪音。

#### 86.3 根因：两处，都在 `_run_with_retry`

`_batch_has_facts` 是个 **bool**（"有没有事实"），而事实**不是一个档次**：

| 档 | 判据 | 含义 |
|---|---|---|
| 3 | `merge_request is not None` | worktree 已 commit + 已锚到 `refs/qidian/pending/` —— **最硬** |
| 2 | `changed_files` 非空 | 交了文件，还没构成合并请求 |
| 1 | `token_count > 0` | **只花过钱**，一样产物都没有 |
| 0 | 其余 | 连调用都没发起的空壳 |

① **替换规则**：`if prev_batch is None or _batch_has_facts(batch): prev_batch = batch`
—— 档 1 也返回 True ⇒ **档 1 顶掉了档 3**。

② **交回规则**：`if deadline_wrapup: return batch` —— 即使 ① 保住了 `prev_batch`，
这一句**无条件交 `batch`** ⇒ 真产物**永远到不了**
`orchestrator` 的 `if batch.merge_request: mq.submit(...)`。

⇒ 两处一起才是完整的链：`finalize` 读到 `changed_files=[]` ⇒ 判「无文件改动」⇒
`merge_request=None` ⇒ 不进合并队列 ⇒ 产物烂在 ref 上。

#### 86.4 修法

判据从「**有没有**事实」改成「**哪个更硬**」（`_batch_evidence()` 返回 0~3）：
**弱的不许顶掉强的**，两处都用它（交回那句是"手里更硬就交手里的"）。
`_batch_has_facts` 保留成 `_batch_evidence(b) > 0`，但**"要不要用这一批"不许再调它**。

测试 `tests/test_scheduler/test_exec_empty_shell.py` ③：四条新用例
（分档 · 只烧钱顶不掉带合请的 · 撞预算交回更硬的 · 手里没有更硬的照旧）。
**变异验过**：把 ① 退回 bool ⇒ 2 条红；把 ② 退回无条件 `return batch` ⇒ 1 条红。

#### 86.5 规则

1. **"有没有"答不了"留哪份"**。只要一处代码要在**两份候选之间选**，
   bool 判据就是缺一维 —— 而且**缺的那一维平时看不出来**（两份都非空时行为一样），
   只在"一强一弱"那一刻错，恰好在真机上错。
2. **"收尾"是一件事，"交哪一份"是另一件事**。同一个函数里这两件事**必须各自判一次** ——
   只修"留哪份"，收尾那句照样把好东西扔掉。**修一半比不修更危险**：它让盘上多了个
   "已经修过"的错觉（本仓 §77.8 已经栽过一次同样的形状）。
3. **同族旧账**：`_exec.py` 里那句「上一轮真干出来的账整份丢掉（09-16 真机：判『无文件改动』，
   产物在 pending ref 上）」**就是这个形状** —— 修过一次，**没修干净**。这次是第二次。
4. **"账全在盘上"时别再跑一轮**。这一条的机制**没加一行打印就坐实了**：
   `traces/` + `partial_usage/` + `pending ref` 三样一对，时间和数字全对上。
   **先问"盘上有没有"，再决定要不要再花一轮钱。**

### 87. 「被掐」的两张脸：**正文 0 且工具 0** 是打转，**正文 0 但调了工具**是正常

#### 87.1 症状

|---|---|---|---|

⚠️ **光看"正文 0"会得出错误结论** —— 因为**没被掐的那 44 条正文也是 0**。
把第三个维度加上去，两张脸立刻分开：

| 形状 | 是什么 |
|---|---|
| 正文 0 ∧ **工具调用 > 0** | **正常**：思考完直接动手（说不说人不重要，做了就行）。<br>没被掐的 40 条里，**100% 是这一种** |
| 正文 0 ∧ **工具调用 = 0** | **打转**：整轮只在想、一次手都没动，直到被掐。<br>被掐的 11 条里 **10 条**是这样 |

#### 87.3 顺带否掉的一个方案

「按模型设不同的 cap」——**治的不是这个病**：

- 被掐的 11 条里 **7 条是最快的 `deepseek-flash`**（858 字/秒），慢的 `glm-5.3-flash` 只占 4；
- `elapsed` 分布 `21 30 52 62 373 386 657 674 906 942 948` 秒 ——
  **有 4 条在 21~62 秒就被掐了**，离 240 秒差得远（那是被**任务剩余预算**掐的：
  `_cap = min(240, 剩余)`）⇒ 加 cap 对它们一点用没有。

✅ **GLM 慢是真的**（首字节 0.85s vs 0.20s、272 字/秒 vs 858），但那是**另一个问题**。
**"谁慢"和"谁在打转"是两回事，别混。**

#### 87.4 规则

1. **"没产出"要拆成"没说话"和"没做事"两件事再说。** 这一族栽过很多次了，
   每次都是**少看一个维度**：`out_chars` 没拆正文/思考算是少一个维度，
   这次是正文 0 没拆"调没调工具" —— **同一个病，换了个字段**。
2. **判据要看"应该有的动作有没有发生"，不是"输出是不是空的"。**
   模型的职责是**动手**，不是说话；"正文空"从来不是问题，"手没动"才是。
3. **拿现成的账回答悬着的问题，别急着跑新实验。** 这条从 09-18 挂到 09-20，
   而**答案早就在盘上了**（`ca4987d` 把字段拆开的那一刻就该能答）。

### 88. 「契约冻结」和「实现」在两个 worktree 里跑，从没对过 —— 而静态审查看不出来

#### 88.1 症状

2026-09-20 round c（`验证-日志统计-20260920c`）：交付的 CLI **跑一次就崩**，
而 QA 的判词是「jsonlstats 五模块实现代码**质量高**、静态审查与各约束设计意图相符，**但**……」

**"质量高"和"跑一次就崩"同时成立。** 矛盾的那一头才是信息。

#### 88.2 判据（三层都要量，少一层就得不出结论）

1. **真跑一次** ——
   `python3 -m jsonlstats <任意.jsonl>`
   ⇒ `内部错误 TypeError: StatResult.__init__() got an unexpected keyword argument 'warnings'`
2. **跨模块对字段** —— `stats.py` 的 `Accumulator.result()` 传了 `StatResult` **没有的 3 个字段**
   （`warnings` · `source_cardinality` · `source_cardinality_limit`）。
3. **那批测试没丢** —— `refs/qidian/pending/*` 上有 **1,680 行**；
   捞回来跑：**38 红 / 31 过**。

⚠️ **第 3 步不做，前两步会被误读成"实现没写完"**（我一开始就是这么误读的，见 88.5 规则 5）。

#### 88.3 真根因（**第三版 —— 前两版都错了，见 88.6**）

🔴 **架构文档自己把这个病预言了。** 它的 risk 段原文：

> `"risk": "契约漂移：并行任务各自定义 Record/StatsResult 字段，集成时字段名或缺失值语义不一致"`

**架构也开了药方** —— T1 的任务描述原文：

> 创建 …`CONTRACTS.md`… **`CONTRACTS.md` 必须逐字段冻结 Record / FilterSpec / StatsResult
> 三个契约，声明字段名、类型、缺失值语义，后续任何模块不得增删字段。**
>
> acceptance：`python3 -c "import jsonlstats"` 退出 0；
> **`CONTRACTS.md` 列出三个契约的全部字段与缺失值语义**；pyproject 中 dependencies 为空数组。

**而实测（逐条核过）：**

| 该有的 | 实际 |
|---|---|
| `CONTRACTS.md` | **全历史从没存在过**（`git log --all --diff-filter=A -- '*CONTRACTS*'` 空） |
| `pyproject.toml` | **不在主线**（`git ls-files` 里没有） |
| 8 条机器检查里查 `CONTRACTS.md` 的 | **0 条** |
| T1 的终态 | **`done`** |

> ⇒ **架构预言了病、开了药、药没吃 —— 而「药吃了没」没有被检查。**
> acceptance 的三条里两条的产物根本不存在，**任务却判了 done**，因为那两条**没进机器检查**。

**链条：**

```
架构：预言"契约漂移" + 开药（T1 产 CONTRACTS.md 逐字段冻结）
   ↓
T1：没产 CONTRACTS.md（也顺手没产 pyproject.toml）—— 但 acceptance 没人机器化
   ↓
T1 判 done  ⇒  后面 T2–T6 全都以为"契约冻结过了"
   ↓
T4：按任务描述里的 StatsResult（注意架构写的是带 s 的类名）实现，
     围绕"基数"建了整套 —— 而主线上的类叫 StatResult，且没有那些字段
   ↓
主线跑一次就崩
```

**⇒ 这是「绿声明 fail-closed」的缺失，不是"两个 worktree 没对过"**：
T1 说"契约冻结好了"，而"冻结好了"的判据（文件在不在、字段列没列全）**从没被机器验证**。

**⚠️ 顺带更正一条我曾经的说法**：T1 的产物 **T4 是看得到的** ——
`git merge-base --is-ancestor 715efcf 78759ea` 为真，T1 的 `types.py` 提交是 T4 提交的祖先。
**所以不是"看不到契约"，是"没有一份契约值得看"。**

**⇒ 静态审查看不出跨模块的字段对不上** —— `stats.py` 和 `types.py` **各自都是自洽的**，
不一致只存在于两者之间。QA 说"质量高"就是这么来的。

#### 88.4 更狠的一层：**测试被扔掉 = 把 bug 洗白**

🔴 **T9 / T10 的死法是「写了测试、`tests failed: 退出码 1` ⇒ 判 failed ⇒ 不合并」**
—— 而它们红的原因**正是主线实现的那个 bug**。

```
实现的 bug 让测试红  →  测试任务判 failed  →  产物扔掉（连测试一起）
        ↑                                              ↓
        └────────  bug 没人发现，下一轮重来  ←──────────┘
```

**唯一能抓到实现 bug 的那把尺子，每轮被扔掉。**

#### 88.5 规则

1. **"代码质量高"这类判词，静态读过不算数 —— 先跑一次。**
   跑不起来的东西，静态看是自洽的。
2. **跨模块的接口对不上，静态审查看不出来** —— 两个文件**各自都是自洽的**，
   不一致只存在于**两者之间**。⚠️ 别急着把锅推给 worktree 隔离：
   实测这次 T1 的提交**是 T4 的祖先**（`git merge-base --is-ancestor` 为真），
   **T4 看得到契约** —— 问题是**没有一份契约值得看**（见 88.3）。
3. **失败的产物不要当"没有"。** 「任务 failed」和「产物不存在」是两回事 ——
   实测 1,680 行测试躺在 `pending` ref 上，**没有任何东西会告诉你有**。
   🔵 捞法：`scripts/pending_refs_probe.py <project_id>`（**只读**，在临时克隆里跑）。
   ⚠️ **别直接改项目仓** —— 那是「奇点产出长什么样」的证据，动了证据就没了。
4. **判"孤儿"的判据别用"任务还在不在"。**
   `delivery_facts --refs` 报「孤儿 0 条」，而 19 条 pending ref 的产物**一条都没进主线**
   —— **它量的是声明，不是实际**。
5. 🔴 **验收条件写了、但没变成机器可判的检查 = 没写。**
   T1 的 acceptance 白纸黑字写着「`CONTRACTS.md` 列出三个契约的全部字段」，
   而那个文件**全历史不存在**，任务**照样判 done** —— 因为 8 条机器检查里 **0 条**查它。
   ⇒ **改任务描述时顺手问一句：这条 acceptance 由谁判？判不出来的就得补检查。**
   （同 §78「假门比没门坏」的邻居：**写了不判的验收，比没写更坏** —— 它让你以为验过了。）
6. 🔴 **我在同一个判断上栽了三回**，每一次都被后来更深的证据推翻：

### §89. 改一个字段的**形状**，要扫的是**全部**消费者 —— 而"扫过了"不等于"扫全了"（2026-09-21）

**症状**：点「📁 文件」侧滑面板（`ProjectMaterials` → `ArchitectureDetails`）**整个白屏**，
页面上只有一句 `Minified React error #31 ... args[]=object with keys {check, text}`。
React #31 = "对象不能当 React 子节点"。

**根因**：`bf571c57` 把 `acceptance` 从 `str` 改成 `[{text, check}]`。
改的时候扫了后端 4 个消费者（`_workflow_phases` / `orchestrator` / `supervisor` / `_review`），
下一轮补扫又抓到第 5 个（`_exec_context` 把新形状原样插进执行器提示词），
**而前端那一处（`{t.acceptance}` 直接进 JSX）是第 6 个，直到用户点出来才被发现。**

**规则**：

1. **换字段形状时，"扫消费者"要按**出现的位置**扫，不是按"我记得的那几处"扫。**
   判据：`grep -rn '<字段名>'` 全仓跑一遍，**逐个看见到哪一跳、怎么渲染**；
   前后端、prompt、落盘 JSON、测试桩都算消费者。
2. **前端这种"把值直接塞进 JSX"的地方，改形状的爆炸半径是"整页白屏"**，
   而错误信息（React #31）**完全不提是哪个字段** ⇒ 现场排查等于海底捞针。
   能提前做的一件小事：渲染前统一走一个 `xxxText()` 拍平函数，
   旧形态**原样透传**（盘上还有老项目的 JSON，不能让它们白屏）。
3. **"我上一轮已经扫过一遍了"不是证据** —— 这一条上我扫过两次，
   第二次还专门写进了 commit message（"第 5 个消费者"），
   结果第 6 个在**另一个仓的正确位置**（前端）躺着。**扫描要跨层，不是在下游再加一次。**

**边界**：本次只核了 `acceptance` 这一个字段。`bf571c57` 同一批还动了
`constraints[].check`（形状没变，只是复用了 `parse_check`）—— 那个**没扫**。

### 9.3 转述外部输入也要能就地核实 —— 「上下文里有」≠「用户说过」

> 这条不是代码的坑，是**我自己的动作**的坑 —— 所以归 §九（它管的就是"修补这个动作本身"）。

- **症状**（2026-09-21）：我把一句**我自己编出来的话**当成用户说过的话。
  先对着它回了句"收到"；用户回"？"之后，我**又回头向他陈述**
  「你那条消息只有 `Acknowledge with 'Received'.` 一句，是我该多问一句」
  —— **拿伪造的证词去纠正对方**。
- **怎么发现的**：用户说"我没发信息啊"。我把这个会话的 transcript 按 `role=user`
  逐条列出来 —— 他真正发过的只有 6 条（`继续` / `这几天太烧钱了…` / `先修bug吧…` /
  `1` / `？` / `我没发信息啊`），那句**命中 0 次**；全文搜那两个词的每一处
  **都在我自己的输出里**。hook 也只配了两个（`UserPromptSubmit` 的 `cat OPEN.md` +
  `PreToolUse` 的 `pre-commit.sh`），**没有任何东西能往会话里注入用户消息**。
- **根因**：**转述没有凭据。** 我唯一的来源是"上下文里出现了这段文本"，
  而**"上下文里有"和"用户说过"是两件事** —— 前者还包括我自己生成的内容、
  工具回显、以及任何被读进上下文的东西。我拿前者当后者用，并且**一次都没去核原始记录**。
- **规则**：转述外部输入（用户的话 / 外部文档 / 工具输出）时，
  判据是**能不能在原始记录里就地找到那一条**：
  · 用户的话 → `~/.claude/projects/*/<session>.jsonl` 里 `role=user` 的条目；
  · **找不到就不能说"你说过"**，只能说"上下文里出现了这段文本，**来源不明**"。
- 🔴 **加重的那一条**：**要拿它去纠正用户的时候**（"这是你说的，是我该多问一句"），
  **先核一遍** —— 这类句子是把错误**转嫁给对方**，而对方会开始怀疑自己的记忆。
  本项目的实例就是这一条：真正该说的是"我不知道这句从哪来的"。
- **为什么危险**：**不是"回错两个字"，是没人能发现它**。我当时是**确信**的
  （思考里白纸黑字写着"用户的消息就是这句"）⇒ **自证不可行**，
  这次纯粹是靠用户一句"我没发信息"才戳破。
- **怎么发现它失效**：每次要引用用户原话，先 `grep` 该 session 的 jsonl 里
  `role=user` 的条目。**这次就是这么发现的**（不是靠"我回想一下"）。
- **同族**：`失败形状.md` 的「**表述比事实强**」—— 这条是它的**外部输入版**。
  上次是把自己的推断说得比证据硬；这次更靠前一步：**把来源本身编了**。
