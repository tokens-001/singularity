## S1 是这堆的地基 —— 而它跟一条老 bug 同一个根

**它写的是一个写入者，实际是一整族。**

`save()` 是**整份覆盖写**（`ProjectState.to_dict()` 全量 → 写盘），没有字段级合并、
没有版本号、没有"盘上那份是不是比我新"的检查。而 `.qidian/projects/<id>.json` 的写入者至少有：

| 写入者 | 手里那份是哪来的 |
|---|---|
| `_api_projects._start_background` 的四条后台路 | 请求线程 `load()`，**在后台线程里活几分钟** |
| `orchestrator._auto_trigger_test_fix` | 每 tick `list_all()` 一份新的 |
| `orchestrator._run_integration_merge_async` | ✅ **这条是对的**（收 id，进线程再 load） |
| 观察者 `_maybe_report_gates` | 读盘快照 → 调模型 10~20 秒 → 整份写回 |
| 任意 HTTP 请求 | 各自 `load()` 一份 |

⇒ **谁最后写谁全赢。手里那份越旧，抹掉的越多。**

### 这正好解释 `OPEN.md` 上那条还挂着的 🔴

> 「观察者汇报把项目状态整体写回 ⇒ 人的批准被抹掉」（09-17 真机抓到，**最重**）

**同一条根。** 09-17 我们打算的修法是"写回前重新 load（20 秒 → 毫秒）"——
**那是修一个写入者，不是修机制**。今天 S1 证明：同样的形状还有**四条**（`_api_projects` 那四条后台路，
手里那份比观察者更旧、活的更久）。

⇒ **只修观察者，下一个照样来。** 这是本轮最值钱的一句话。

### 修法（分层，别一次做大的）

1. **立刻（小）**：`_start_background` 四个调用点改成传 `project_id`，`_worker` 里 `load()` ——
   跟隔壁 `_run_integration_merge_async` **已有的正确写法**对齐。diff 小、可测。
2. **次之（中，先只报不改）**：`save()` 加一道"我这份比盘上旧吗"的检查 ——
   load 时记下盘上的 `updated_at`/mtime，save 前比对，不一致就 `witness.warn`。
   **先把这一类从静默变可见**（本仓一贯做法：先造量尺，再谈拦）。
3. **不做**：字段级合并 / 乐观锁 —— 动的是状态机核心，**真机验不过来**，
   而现在最紧的约束恰恰是"改了没验"。

## S2 的修法（一句话）

`_worktrees_dir` 不该替调用方 mkdir —— 或者 `repo_dir` 的兜底分支该**抛**而不是返回一个
"看起来合法"的路径。两个函数各自都对，**合起来违约**；这类要挑一个地方定死。

⚠️ 现场已经在盘上了（`.qidian/projects/1789475332592/.repo-worktrees`）——
**删之前先确认它真的空**（我看到的 `find` 只有这两层，没往下看）。

## S4 它说得最好的一句

> 「这个函数的全部职责就是在**任务装死时报警**；它**删掉的是自己唯一的输入**。」

`check_stalled` 读坏 → unlink → 之后这个任务"没有心跳" = "不在跑" = **看起来完全正常**。
一次撕裂（这条没走 `os.replace`，ENOSPC/掉电/并发同 pid 都能撕）就能让一个真卡死的任务
**从告警系统里消失**。这是本轮里"最安静"的一条。
