Strong #1.2 碎片化

6 个 API 子模块全是薄壳

_api.py (103L) + _api_tasks.py (341L) + _api_projects.py (187L) + _api_agents.py (155L) + _api_skills.py (39L) + _api_mcp.py (51L) + _api_monitor.py (108L) = 984 行。 每个文件 3-5 个函数，每个函数一行调用核心。拆分降低了导航效率。

Before: 7 文件，每个 50-340 行，跨文件找 handler
After: 1 个 _api.py 984 行，section comment 分组

方案：合并回单个 _api.py，用 section comment 分组。984 行远低于 1200 行限制。

内存持久化分散在 4 个文件

memory.py + _lifecycle.py (85L) + _memory_consolidator.py (108L) + _memory_io.py (32L) + _memory_experience.py (176L) = 5 文件 400+ 行。

Before: 5 文件，_lifecycle 4 函数，_memory_io 3 函数

方案：合并 _lifecycle/_memory_io/_memory_consolidator 进 memory.py 或单个 _memory_internal.py

Strong #3.1 局部性违反

decompose() 被调用两次，可能发散

planner 输出在 worker 线程被 decompose() 解析，然后在主线程被 materialize_plan() 再次解析。 如果 raw output 在两次调用间变化，或 JSON 解析不同，产物就发散。无测试覆盖此路径。

Before: 两次解析，数据路径分叉
After: BatchOutput.planner_subtasks 传递解析结果，主线程直接使用
Strong #3.2 局部性违反

_save_trace 从 worker + 主线程 4 处调用

_exec.py worker 写一次，orchestrator.py 主线程 4 处也写。可能双写或数据不一致。

Before: 5 个调用点，可能双写
After: 只在 _finalize_result 写 trace，worker 通过 BatchOutput 传数据
Strong #4.1 泄漏的缝

tracker._read() 被 9+ 模块调用，暴露内部格式

"私有"方法 _tasks_dir() 和 _read() 被 orchestrator, _exec, _planner, workflow, witness, _api, _api_tasks, merge, _api_projects 调用。 换存储格式要改 9+ 模块。

方案：定义 ReadOnlyTracker 接口（get_task, ready_tasks, list_pending），worker 线程只用接口

Strong #5.1 / #5.2 不可测代码

_exec.run() 193行 + _finalize_result 141行，零单元测试

_exec.run() 有 7 层缩进，依赖 tracker/dispatcher/validator/worktree/witness。 _finalize_result 有 8+ 分支路径。两者都在 smoke_test 和 test_exec_run 中间接覆盖，但无独立测试。

Before: 核心逻辑不可独立测试，改一行需要全量集成测试
After: 注入式 services 对象 + 状态机 handler 拆分 + 属性测试

🏆 Top Recommendation

先修 #4.1 — 定义 ReadOnlyTracker 接口。

这是回报最高的一步：它同时解决 9+ 模块的耦合问题，为后续测试铺路（worker 线程只需 mock 一个接口），且改动范围可控（加接口，不改存储格式）。

第二位：#1.2 — 合并 6 个 API 子模块。纯机械操作，无行为变更，几分钟搞定。
第三位：#3.1 + #3.2 — 消除双解析和双写路径，防止数据一致性 bug。
