## A. 确认的问题（原文，按它排的严重程度）

### 1. 两个审查模型判 abort，任务照样 ok=True 合并

**现象** `_review.run_post_exec_checks`：verdicts 里 ≥2 个模型回 retry/abort 时只设 `validation.action="retry"`，不扣 confidence、不写 warnings、不写 unverified。而 `_decide_cascade` 的第一判据是 `conf >= 0.75` → 接受并合并。算术：`validator.post_execution_hook` 基线 0.5，长输出 +0.1、含 "passed" +0.15 = 0.75，测试通过再 +0.1 = 0.85。

**影响** 审查层最明确的否定结论被"省钱分支"吃掉，任务进 DONE 并合并进项目仓。同一段的 critical 分支（-0.25 → 0.60）能拦住，恰好说明这里只是漏了。

**改法** verdicts 分支照 critical 那支补三件：`quality["warnings"].append`、`validation.unverified.append`、`quality["confidence"] = min(quality["confidence"], 0.7)`。另把 `_exec._decide_cascade` 的接受门槛改成 `conf >= 0.75 and quality.get("failure_kind","ok") == "ok"` —— 否则"测试通过(+0.1)"正好抵掉"审查警告(-0.1)"，soft_quality 承诺的那轮软修永远轮不到（warning 档停在 0.75，直接 accept）。

### 2. 审查层是短路链：越重要的检查越跑不到

**现象** `_review.run_post_exec_checks` 五步全部门控在 `validation.action == "pass"`，第 1 步项目测试一失败，后面多模型审查、QA 约束验收、需求对账、安全审计整段不跑，unverified 里只留测试那条。

**影响** 覆盖率与"出问题的程度"反相关：最需要安全审计的改动恰好拿不到。工作流文档 §5.1 表里写的触发条件"非 trivial 改动"也不成立，真实条件还包含"前面全 pass"。

**改法** 安全审计 与 QA 约束验收 的门控只看 `changed and not _trivial`，与 `validation.action` 解耦（它们不改代码，不冲突）。想保留省钱的短路，就在函数末尾把跳过的项如实写进 `validation.unverified`（"因测试失败未跑：安全审计/QA 约束验收"）。

### 3. 整段验收同步跑在调度循环线程里，期间全局停摆

**现象** `orchestrator._auto_trigger_test_fix` 直接调 `workflow.run_test_fix_loop`，里面是 `_run_verification`：最多 10 条 `_machine_checks.run_check`（`DEFAULT_TIMEOUT=60.0` → 单条 60s）+ 2 次模型调用。同文件顶部 F1 注释已经把集成合并异步化的理由写死了（"否则全局任务派发/SSE 停摆"），并给了现成范式 `_submit_integration_merge`；REVIEWING 这条更长、还带 LLM，却仍同步。

**影响** 一个项目验收的几分钟里，`_run_queue_v3` 不转 ⇒ 其它项目的派发、reap、900s 超时收割（收割本身就在这个循环里）全部停摆。

**改法** reviewing 分支改成向 `_get_merge_executor()`（或单开 `max_workers=1` 的 verify 池）提交 `_run_verification_async(proj.id, agents)`；占位/撤回与告警照抄 `_submit_integration_merge`（含"提交失败就把 `_merge_inflight` 撤回来"那半），守卫语义不变。

### 4. 不是两套驱动，是三套；第三套在降级时绕开 INTEGRATING

**现象** `web/app.py` 的 `_loop_worker` 结果处理块自己判"任务全终态"就调 `run_test_fix_loop`，与 `orchestrator._auto_trigger_test_fix` 干同一件事，两处终态集合还不一致（`app.py` 那份少 DECOMPOSED）。正常路径它不触发（orchestrator 先把 phase 推成 integrating），但 `_auto_trigger_test_fix` 是一个 try 套住整个 `for proj in list_all()` ⇒ 任一项目抛错，本轮它后面所有项目都不推进 ⇒ `app.py` 那块接手，把项目从 EXECUTING 直接送进 `run_test_fix_loop` → GATE3。

**影响** 落进降级路径的项目跳过了 `_run_integration_merge` 的"工作区必须干净 + 集成测试"整道门，而人看到的是完整的 GATE3。这就是 §10.5 的答案：分工本身没错，边界没划清 + 重复实现。

**改法** ① `_auto_trigger_test_fix` 的 try 收进循环体，per-project 隔离；② 删 `app.py` 那段推进逻辑（orchestrator 已经在每 tick 里跑）；③ 在 `project.py` 顶部写一句归属表并让 `_api_projects`/CLI 照它来：EXECUTING/INTEGRATING/REVIEWING/DELIVERING 只归调度循环，TEMPLATE/RESEARCHING/PLANNING/GATE* 只归 `run_phase`。

### 5. 观察者的 GATE 批准丢了 confirm_gate 的返回值 = 把没放行说成放行

**现象** `_observer_answer._answer_question_inner` 三处自己 `confirm_gate(...)` + `save_project(...)`，不接返回值。`ProjectState.confirm_gate` 在 GATE2 架构无效时返回 None 且不推进；HTTP 那条 `_api_projects.project_gate_confirm` 接住了并回 409。聊天里回话硬编码 "✅ GATE2 已通过。进入实现阶段…"。

**影响** `owner_confirm["gate2"]="approved"` 落盘、phase 还在 GATE2、用户以为过了人工门。GATE1 那条同理：批准后进 PLANNING，而 HTTP 路径专门写了 `_start_background(...,"planning",...)`（注释里记着"实测空等 14 分钟"），聊天路径没点，回话却说"已进入架构规划阶段"。

**改法** 三处批准全部转 `project_gate_confirm(project_id, gate, "approved")`，回话按 `data["next_phase"]` / `data.get("error")` 生成 —— 和同一个文件里 `_gate_reject_reply` 已有的写法一致（打回那侧已经收敛过，批准这侧漏了）。

### 6. 委员会席位的两端都没管：上限被并发/时限偷偷截，下限静默关闭

**现象** `_dispatch_exec._dispatch_committee`：`max_workers=min(len(chain),4)` + `wait(timeout=_WAVE_TIMEOUT=300)` 后只取 done。席位 >4 时第 5 家要么没开始，要么在波结束后继续跑完、token 照花、结果被扔，而 `member_usage` 里没有它 ⇒ 这笔钱不进账。另一端：本机 `.qidian/phase_models.json` 的 planning 现在只有 1 个模型 ⇒ `_committee_allowed` 的 `len(chain)>=2` 不成立 ⇒ 委员会静默不开，全仓没有任何告警（grep 无 `committee_not_engaged` 之类），工作流文档 §9 写的"planning 三家"已失真。

**影响** 加到第 5 席 = 付费丢稿 + 漏账；减到第 1 席 = 核心价值主张静默关闭，GATE2 上看到的一份单模型方案没有任何标记说"没碰撞"。

**改法** ① 席位与并发钉在一起：dispatch 处就 `chain[:4]`，把 `_WAVE_TIMEOUT` 从"结果截断"降级为纯等待上界（`_log_arm_event` 里记 seats/abandoned）；② `_run_planning` 拿到 lineup 后，若 `len(lineup)<2 and resolve_flow(project).committee` → `witness.warn(key="committee_not_engaged")` + 一条 GATE2 issue"这份架构是单模型出的，没碰撞"。§10.2 的答案：3 是当前结构能诚实支撑的上限，席位增益的瓶颈不在碰撞在提取。

### 7. 融合 v2 是"朝定稿人的单调过滤器"，不是合成

**现象** `execution_judge.fuse_architecture_v2`：分歧默认 `winner = writer`；对方胜出的唯一路径是"insist 且 writer 回 agree"；没确认票标 `basis="default_no_confirm_vote"` 但仍判 writer 赢；unique_gains 只减不加（全体 adopt 才进）。而 `_pick_writer` 无纪律数据时回退 `_first_speaker` = 提分歧最多的人。

**影响** §10.1 的直接答案：是，系统性偏向一方，而且是自我强化的 —— 列分歧越多的模型越容易既当执笔人又当默认胜者；辩论轮在数学上只能删掉别人的东西，不能把任何别人的东西变成结论。2 席时融合稿 ≈ writer 原稿减去对方独有做法。

**改法** 两处小改就够：① 把"没有 writer 确认票"从"判 writer"改成 `basis="unresolved"`，并在 `_V2_FINALIZE` 单列一段"未裁决分歧：不许采用任一方，写进 risks"；② `_pick_writer` 的回退从 `_first_speaker` 换成与分歧计数无关的确定性选择（`members[0]`），别让选择规则和默认胜者规则同源。5 轮上限不是拍脑袋但也没依据：rounds 已经落进 rulings，先攒 20 场真机看第 3 轮之后还有没有 question 收敛，再决定砍不砍。

### 8. unique_gains 的"全体 accept"只在收到的票上执行

**现象** `execution_judge.fuse_architecture_v2`：`stances = [v for (m,i),v in gain_votes.items() if i == str(g["id"])]` → `if stances and all(s=="adopt")`。缺票不反对。writer 第 1 轮 JSON 解析失败（`a1={}` ⇒ 一票没有）或某成员走了 `fusion_round2_json` 那条告警，剩下几张 adopt 票就是"全体"。

**影响** 一条只有部分成员表过态的做法被采纳，且 rulings.adopted 事后看是全体一致 —— 这是给 §10.1"保守合不合理"的答案：规则合理，实现没执行它。

**改法** 同处改成 `if len(stances) == len(members) and all(...)`，否则 rejected 并记 `basis="missing_votes"`；顺带对分歧点也加一条"该 id 投票人数 < len(others)"的告警（现在只有解析失败才响，responses 少给条目就不响）。

### 9. 验收证据是唯一一类非原子写的状态文件，而"读坏了"被当成"没跑过"

**现象** `workflow._save_phase_output` 裸 `p.write_text`。`project.save()` 和 `_io.atomic_write_json` 都是 tmp+os.replace，只有 `.qa_report.json` / machine-checks.json / research.md / architecture.md 不是。消费端 `workflow.handle_gate3_reject`：`except: has_qa = False`。

**影响** 一次撕裂写 ⇒ GATE3 打回的 fix_route 静默落到 impl（`route_source="default_no_qa"`，说的是"没有报告"）；`orchestrator._run_delivery` 的 `.exists()` 又把坏文件计进交付清单的报告数。`app.py` 在展示侧已经区分了 `qa_report_unreadable`，决策侧没做。

**改法** ① `_save_phase_output` 里 `.json` 结尾走 `_io.atomic_write_json`，其余走一个 tmp+replace 小助手（`_io` 里已有 `_sweep_stale_tmps`，顺带补上 `project.save()` 那份缺的清理）；② `handle_gate3_reject` 加第三种 `route_source="qa_report_unreadable"` 并写进 `add_lineage`，文案明确"报告存在但解析失败"，与"没有报告"分开。

### 10. decompose_architecture 里有一段嵌进自己 if 里的重复块

**现象** `execution_judge.decompose_architecture`：`_chk = _argv_of(c)` 和那段 "↳ 机器检查会真跑这条命令…" 的 `ctx_parts.append` 写了两遍，第二遍嵌在第一遍的 `if _chk:` 里面（连 2026-09-17 那段注释也复制了一份）。

**影响** 从那次修复起，每个任务 context_snippet 里每条机器可跑约束都出现两次：10 约束 × ~150 字 × 20 任务 ≈ 30K 字符纯重复 prompt，每个任务各付一遍；同时稀释了"它引用的文件必须存在"那句本意要强调的话。

**改法** 删内层那份（留外层），并把这段字提为模块级常量 `_MACHINE_CHECK_HINT` —— 一份文案只留一个出处。

## C. 它按 §10 六个问题给的收口

1. **融合结构性缺陷** → 有，见 A7 + A8。根因一句话：默认裁决方 = 执笔人，而执笔人的选拔又由"谁列的分歧多"决定；"全体 accept 才采纳"方向对但实现成"收到的票里全体"。
2. **全链参与** → 不是"全链"，是 4 并发 × 300s 波，超出部分付费丢稿且漏账（A6）。选席建议：按厂商去重后取前 3（已有 `_warn_same_model`，把它从告警升级成选席约束）。
3. **三层抽象** → 「阶段→模型」+「角色→阶段」认为是对的；技能那条代码已经改成**阶段级优先**（`skill_loader.get_agent_skills`），而工作流文档 §7.2 通篇写的是"模型级优先、阶段级兜底"并给了相反的理由 —— **发给评审的文档在这条上是错的，先改文档**。建议收成一句：模型 = 谁干，角色 = 以什么立场干，技能 = 手上有什么工具，三者一律只绑阶段，不绑模型。
4. **审查层顺序与权重** → 顺序按成本排是对的，门控按 pass 排是错的（A2）。该升硬拦的软信号只有一个，且不是第 4 项：verdicts ≥2 needs_fix（A1）。机械检查建议不下沉成任务级硬门，而是把 `_machine_checks.run_check` 直接接进 `_review` 第 3 步替掉一部分 LLM 验收 —— 现在 `qa_acceptance_review` 用模型判约束，而 `check.argv` 就躺在同一条 constraints 里没人执行，于是每个任务都过了 LLM 验收、最后一次性发现机械检查全红、只能整项目回 GATE2。
5. **两套驱动怎么收** → 见 A4：删重复的第三套 + per-project 异常隔离 + 一句话归属表。不必统一成一个状态机，tracker 交接是合理的。
6. **§8 那 8 条** → 还该动的只有 #1（docstring 撒谎，顺手和 B5 一起改）和 #5（phases.json 死键，一行删除）；#2/#3/#4/#6/#7 已闭环，#8 是数字漂移。新账：A6 的 §9 配置快照失真、A10 的重复块、C3 的文档与代码在技能优先级上相反。
