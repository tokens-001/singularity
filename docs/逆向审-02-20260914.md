## 二、重点①：S1 那族"读降级、写拒写"

### 你问的问题：有没有哪处**文件好的时候**也会走到"拒写/降级"？

**没有找到。** 逐项排过的误伤源：

1. **顶层类型**：每个接入点的 `expect` 与写侧实际形状逐一核对——`process_ledger` 读写都是 list，其余 8 处读写都是 dict，没有一处写 A 读 B。
2. **第一次运行**：文件不存在 → `expect()` / `_default_configs()`，不经过判坏路径（`mcp.py:538`、`api_store.py:97` 等都先查 exists）。
3. **空文件**：所有写侧都是整文件写（`atomic_write_json` / `write_text` 全量），代码不会自发产生 0 字节文件；空文件只能来自撕裂写/外部破坏——那**本来就是"坏"**，判坏是对的。
4. **编码**：`json.loads(path.read_bytes())` 走 `detect_encoding`，UTF-8 BOM 的**字节**输入会按 utf-8-sig 解掉，不会误判（之前我担心的"BOM 误杀"不成立，实测库行为如此）。
5. **粘住语义**：`is_quarantined` 进程内粘住、修好文件也要重启才恢复写——docstring 写明是有意设计，且每次拒写都双通道出声，不构成无声堵死。

### 但反方向有一个系统性洞：**文件坏的时候，闸门是"第二次触碰"才开始拦的**

四个读改写接入点（总表前四行）的形状都是：

```python
if p.exists() and is_quarantined(p):   # ← 检查时标记还没置上
    refuse
got = load_json_or_quarantine(p)       # ← 第一次真正读：判坏、置标记、返回 None
data = got if got is not None else {}  # ← None 被吞成 {}
write(data)                            # ← 整份重建发生
```

`_io._QUARANTINED` 只在**有人读过坏文件之后**才有这个路径，而检查偏偏在读之前。对照组 `_process_ledger.record()`（`_process_ledger.py:61-64,114-122`）是**对的**：它直接用三态返回值判断 None → 拒写，不依赖"别人先读过"。四个洞改成账本那个形状即可。

**测试为什么没抓住**：`test_io_quarantine.py` 里所有"写侧拒写"用例都**先手动读一次坏文件**（`:187`、`:231`、`:248`、`:291`、`:331/352`、`:389` 的注释自己写着"置上损坏标记"）——测试把"得有人先读过"这个缺陷前提**固化成了前置步骤**，恰好把洞盖住。其余接入点（`_dispatch_crud`、`model_registry`、`api_store._save` 主库、`save_mcp_configs`）没问题，是因为它们的每个写入口**在同一个函数里先读后写**，顺序天然正确。
