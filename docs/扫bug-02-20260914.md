## 一、高危

### 1. GATE 关键词匹配："不通过"先命中"通过"→ 打回被当成批准；聊天随口带"好/行/ok"就过门
- 位置：`scheduler/_observer_answer.py:156`（GATE2）、`:165`（GATE3）、`:132`（GATE1）
- 类别：逻辑错 + 误触发
- 描述：批准分支是 `any(w in q for w in ("通过","继续","确认","同意","ok","yes","好","可以","行"))`，打回分支是它后面的 `elif`（含"修改/不对/重来/不通过"）。**"不通过"包含子串"通过"**，永远先被批准分支吃掉。且用户在观察者聊天里任何碰巧含"好""行""ok""可以"的句子（如"这方案行不行？""之前的 bug 修好了吗"）都会直接 `confirm_gate(..., "approved")` 过门——GATE2/GATE3 是人审门，等于聊天区一个词就能放行。
- 怎么验：把项目推到 GATE2，向观察者发"不通过"→ 返回"✅ GATE2 已通过"；发"这方案行不行"→ 同样返回已通过。三个 gate 同型。

### 2. api_store：4 处裸 write_text 非原子写 + 读到损坏 JSON 即用种子数据整库重置
- 位置：`scheduler/api_store.py:313`（note_api_success）、`:338`（record_alias）、`:405`（note_api_error）、`:428`（set_observer_model）非原子写；`:63-73`（_load 损坏即 `_seed()`）；`:168-175`（_save 自己倒是用 atomic_write_json）
- 类别：资源/数据一致性 + 并发
- 描述：这四个写入口都是 `_load_raw() → 改 → write_text(json.dumps(...))`，非原子、无锁，彼此之间和与 `_save()` 之间是丢更新竞争。更糟的是放大链：任何一次撕裂写让并发读者拿到半截 JSON → `_load()` 落进 `except (json.JSONDecodeError, KeyError): pass` → 返回 `_seed()` → `_seed()` 末尾 `_save(entries)` **把整个 api_store.json 覆盖成种子数据**——所有 provider 状态、欠费标记（_quota_dead）、别名表全灭，且无备份（对比：memory 的 `_read_json` 会先改名留底）。

### 3. MCP stdio 客户端：响应不按 id 匹配 + 读超时后响应错位
- 位置：`scheduler/mcp.py:222-231`（_rpc_stdio 发完盲等下一行）、`:241-254`（_recv_stdio：select 30s 超时返回 None；`readline()` 本身无超时）、`:265`（cfg.timeout 只用在 http 路径）
- 类别：时序错 + 协议实现缺陷
- 描述：`_recv_stdio` 拿到哪行算哪行，不看 JSON-RPC id。服务器只要先吐一行 notification（日志、`tools/list_changed`）就会被当成响应用掉，真响应留给下一次调用。stdio 工具调用超过硬编码 30s：调用方拿到 None（"调用失败"），但服务器还在跑，**迟到的响应会被下一个 RPC 吃走**——之后所有调用结果整体串位。另外 select 判可读后 `readline()` 无超时，服务器慢慢吐半行可无限挂起。
- 怎么验：起一个 stdio MCP server，每 responding 前先发一行 `{"jsonrpc":"2.0","method":"notifications/message"}` → `discover_tools()` 返回 []。再让它对 tools/call sleep 35s 后才答 → 第一次调用报失败，紧接着的第二次调用拿到第一次的结果。

- 位置：`scheduler/chancellor.py:41`（`_CORE_FILES = {"core.py","tokenizer.py","graph.py","search.py","config.py","tracker.py"}`）、`:53-63`；调用方 `_task_runner.py:386`（传的是**任务的** changed_files）
- 类别：逻辑错（语境错配）
- 描述：这串名单是奇点**自己的**核心文件，但 assess 拿它去匹配任务改动文件——项目任务的 changed_files 在**用户项目** repo 里。用户项目自己写一个 `config.py`/`search.py`，就会触发"核心文件被修改…调度器瘫痪"级的 critical 奏报。
- 怎么验：`assess("实现配置模块", "", changed_files=["src/config.py"])` → severity="critical"。

### 17. bridge：WS 服务未启动时 `_get_loop()` 造一个永不运行的 loop，广播假成功
- 位置：`scheduler/bridge.py:93-97`（_get_loop 惰性 new_event_loop）、`:80`（broadcast_json 对每个 client `run_coroutine_threadsafe(..., _get_loop())` 后无条件 `count += 1`）
- 类别：时序错 + 资源泄漏
- 描述：`start_ws_server` 未跑（或已 stop）时，`_get_loop()` 新建的 loop 无人 `run()`——run_coroutine_threadsafe 把协程挂上去永远不执行，future 永不 resolve，但调用方拿到 `count>=1` 的"成功"。loop 对象本身泄漏。
- 怎么验：不调 start_ws_server，手工 `add_client(_WSClient(fake_ws))` 并置 authenticated，调 `broadcast_json({"x":1})` → 返回 1，协程永远 pending（fake_ws.send 从未被调）。

### 18. 经验归档/失败模式：无锁读改写，并发丢记录
- 位置：`scheduler/_memory_experience.py:77-81`（archive_experience）、`:84-100`（_match_failure_pattern：load→改 count→save）
- 类别：并发（lost update）
- 描述：memory 写路径在 `_memory_core` 里都套了 `_LOCK`，这两个没有。两个任务同时收尾（一个归档、一个失败打模式标签）时 experiences.json / failure_patterns.json 后写者覆盖先写者。
- 怎么验：两线程各调 `archive_experience(...)` 100 次（status 不同），结束后 `len(json.load(experiences.json))` < 200。
