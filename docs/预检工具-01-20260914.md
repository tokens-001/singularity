## 1. 判据（每个形状：按什么判 / 为什么 / 已知会漏什么）

### 形状 A：护栏查在读之前（`A-guard-before-read`）

**按什么判**（三步，全是 AST 上的真数据流，不靠名字猜）：

1. **状态元**（state cell）：模块顶层赋值的名字（如 `_io._QUARANTINED`），或类里出现过的
   `self.X`。
2. **每个函数算读写摘要**：读 = 函数体直接引用该状态元（`is_quarantined` 的函数体里有
   `_QUARANTINED` ⇒ 它直接读）；写 = 本体或调用链（跨模块走 import 解析，含函数内懒导入）
   对该状态元有赋值 / `.add()` / `.update()` 等变更。**写分两档**：
   - 无条件写：存在一条全无条件调用路径能写到它；
   - 仅失败路径写：所有写路径都经过 `except` 块或"判坏 → bail"分支。
   - bail 的判定：`raise`、裸 `return`、`return None/常量/简单值`。
     **`return f(...)` 这种委派型 return 不算 bail**——这是调试中抓出来的规则
     （`MCPClient.connect` 里 `return self._connect_stdio()` 曾把被委派函数的无条件写
     全污染成"仅失败路径写"，造成一条懒加载误报；修正后该误报消失）。
3. **命中条件**（全部满足）：函数 F 里有 `if <test>: bail` 守卫，test 直接引用状态元 S
   或调用一个**直接**读 S 的判定函数（如 `is_quarantined(p)`）；守卫**之后**（源码顺序）
   有一个对 S **仅失败路径写**的调用（如 `load_json_or_quarantine(p)`，它在 except /
   类型不对分支里 `_QUARANTINED.add`）；F 在该读之后还有**写盘动作**
   （调用名含 write/save/dump/replace…）——"读改写函数"本来就是形状定义的一半。

**为什么这么定**：病灶本质是"守卫的真值要等人读过才存在，而第一次触碰恰恰是写侧自己
那次读"。静态等价物就是：**守卫读的状态，被它后面那次调用在失败路径上写**。用真数据流
而不是字符串相似，是为了每条报出都能指着三件事审：这个守卫读 S、这个调用仅失败路径写 S、
读后还有写盘。

**已知会漏**：判定与读分居两个函数且中间隔回调/多态；状态不走变量/属性（直接问盘上的
另一种判定）；经动态 import / 反射的调用链解不出就不报；守卫与读在不同文件但跨模块
import 只能解一层。

### 形状 B：同一个判据在多处，已经不一致（四个子判据）

**B1 · deny-list 家族分歧**（成绩单④前半）
- 判：**按文件合并**该文件里所有变量名像 deny-list（`blocked/sensitive/blacklist/deny/
  forbidden/secret/banned/disallow`）的字符串集合字面量，**只做跨文件配对**；
  归一化（小写、剥 `*.`/前导 `.`）后共享 ≥2 条"两侧原文都像文件模式"（含 `.` `*` `/`）的
  条目才算同族，同族即互报条目差集。
- 为什么按文件合并：web 侧一张黑名单拆成 `_SENSITIVE_FILES/_SENSITIVE_PREFIXES/
  _SENSITIVE_SUFFIXES` 三张，逐张配对会把④的缺口切碎；按文件合并才对得上"对面整张表"。
  "两侧原文都像文件模式"这条硬门槛是挡 `_ENV_SENSITIVE_SUBSTR`（环境变量子串表）混进族。
- 漏：名字不像 deny-list 的名单（刻意保守）；条目经运算拼出的名单；共享文件模式条目 <2。

**B2a · 死词**（成绩单③）
- 判：匹配位（`==/!=/in/startswith/endswith`）上的字面量 L，**按它自己的匹配语义**
  对全仓任何产出值都永不命中（`in` 位要求 L 不是任何产出值的子串、`startswith` 位要求
  没有产出值以 L 开头……），且存在一条**同通道**的同族现役词作见证（通道 = 匹配位
  "草垛"侧的变量/字段名 == 生产位的赋值目标/关键字名，共享 ≥4 字符 token）。
- 为什么带语义判与通道见证：单报"查了没人产的字面量"会把 CLI 旗标、HTTP 方法、HTTP 头
  这类外部产出物全咬上来（第一版就这么泛滥过，60+ 条）；`in` 位必须按子串判，否则
  修复后消费侧用 `in` 收现役词会被反咬。
- 漏：写侧和消费侧用完全不同措辞的词（无共享 token）；词经 f-string 动态拼接产生
  （`exit=0` 那条误报就是这来的，见 §3）。

**B2b · 窄前缀判据**（成绩单②）
- 判：`startswith/endswith/in` 匹配位上的字面量 L 自己有生产者，但同族词 P（首 token
  按 `_` 切、≥4 字符相同）也在**同一通道**上产出，且按该匹配语义 P 不被 L 覆盖
  ⇒ 报"P 也会出现，这个判据接不住"。大小写变体（`Error:` vs `error:`）不算同族。
- 为什么：②的 `cancelled_by_user` 是真词，坏在**判得窄**，与 B2a（词死了）互补。
  通道要求把第一版 98 条的洪水砍到个位数。
- 漏：同族词无共享首 token；判据用正则/多条件组合绕开单字面量的；两个不同对象恰好
  共用同一个字段名（`conflict_held` 那条误报就是这来的，见 §3）。

**B3 · 同一件事写了两遍、只改了一遍**（成绩单④后半）
- 判：**同一个文件**里两个函数（方法 vs 模块级也算）都调 `subprocess.*` 命令 sink，
  归一化 token 袋（调用点名、常量、kwargs 名；`self.` 归一掉）的 Jaccard ≥ 0.45
  ⇒ "同一件事的两份实现"，然后列出两份在 sink 实参上的差（谁传了 `env=` 谁没传、
  shell True/False、实参值差）。
- 为什么限 subprocess sink + 相似度：阈值兜"是不是复制出来的两份"，sink 实参差集兜
  "改的时候只改了一遍"。只看同文件是第一版收窄（跨文件的重复见 §4）。
- 漏：跨文件的重复实现；相似度掉到阈值下的；sink 不是 subprocess 的两份重复。

**B4 · 同一资源的成组管理函数，存储面不一致**（成绩单⑤）
- 判：同文件里调用**同一个资源读取器**（`load_/get_/read_*`）的函数算一组；读取器必须是
  "模块级访问器"（裸名调用，或**模块别名**上的属性调用——`m.load_mcp_configs` 算，
  `request.get_json` 不算，否则 Flask 的取请求体助手把整个 web 层并成假资源组）。
  组内若有兄弟触达**单例存储**（调 `get_*` 并在拿到的对象上操作），而 F 一次都没碰、
  且 F 对该资源有写动作（`save_*`）⇒ 报"F 管这个资源但只动了配置面"。
- 为什么：add/delete/reconnect/refresh 都管 MCP 服务器这一份资源，reconnect/refresh 喂
  `get_registry()`、add/delete 不喂——这个差集就是"一处动了、一处没动"。
- 漏：资源读取器名字不统一的组；组内没人碰第二存储面（静态看不出"该碰"）；跨文件管理组。

## 4. 「我扫不出来的形状」

判据写死的结构边界（不是调参能救的）：

1. **跨函数/跨文件时序的形状 A**：判定在 A 函数、真读在被传进来的 loader 里、
   或经多态/回调/动态 import 解不出来——调用图解不到的地方一律不报。
   现在只覆盖"同一函数体内，守卫 + 后续调用链写同一状态元"。
2. **f-string / 动态拼接的词表**：`f"exit={code}"` 运行时拼出 `exit=0`，
   静态只见静态段——B2a 对这类必误报（§3 第 4 条），且无法既不误报又不漏报。
3. **注释与文档里的语义豁免**：`.crt` 不拦是注释定的案，工具读不到注释，
   每次都会把这类"有意不一致"重新咬出来（这也意味着：**工具没法区分"漏改"和"有意"，
   这一层永远是人的**）。
4. **同通道不同对象的字段名碰撞**：通道只取名字（`term_reason`、`status`），
   两个不同状态机共用字段名就会互相污染（§3 第 5 条）。要解需要类型/对象身份分析。
5. **跨文件的重复实现（B3 只看同文件）**：三个 executor 的相似函数族历史上有意保留
   复制（注释"原各自复制一份"），放开到跨文件会把它们全部咬上来——
   第一版试过，量太大。要收成"跨文件但要求 sink 实参差"得另做一轮标定。
6. **B2a 无通道见证的死词**：如果消费侧匹配的对象是匿名表达式（不是有名变量/字段），
   见证机制找不到同通道现役词，宁可漏报——这是拿召回换精度的刻意选择。
7. **B1 名单的名字门槛**：变量名不像 deny-list 的黑名单不进家族配对。
8. **`live` 的边界**：`_QUARANTINED` 是进程内存集合，工具只能从盘上痕迹
   （`.corrupt`、alerts.jsonl）反推——进程内当前粘着哪些路径、谁正在降级中，
   不重启就问不出来；alerts.jsonl 不是全量历史（512KB/1000 条轮转裁剪），
   "最近的"之外的旧账可能已被裁掉。

## 5. 自评：它能替代"人肉扫一轮"吗？

**不能。默认答案在这个仓被再次证实。** 它做到的与做不到的：

**能做到的（有成绩单背书）**：
- 把"人撞见过一次"的形状变成**可复跑的断言**：12 个历史现场点 0 漏报，
  且①在 `312584b` 上恰好 4 条、在其余所有版本上 0 条——精度边界也是精确的。
- **回归闸门价值**：基线上形状 A 零命中 = `8e46dee` 的四处修复没有复发、也没有新长同类。
  这是人肉扫一轮**给不了**的保证（人扫完一周后就过期了）。
- 排查时的**坐标生成器**：B1 直接给出缺什么条目的清单（.netrc/id_rsa 族…），
  B3 直接给出谁传了 `env=` 谁没传——人拿到的不是"有嫌疑"而是"差在哪"。
- 真机现场的自查与恢复指引（live），把"有没有被静默降级"从记忆题变成命令。

**做不到的（必须人来的）**：
1. **区分"漏改"与"有意"**：`.crt` 豁免、双词兼容都是注释里的人的决定，
   工具每次都会重新报。误报判词需要"这仓为什么这么写"的记忆。
2. **语义等价的识别**：`mr.status` 和 `task.status` 是不是一回事、
   两份相似函数是不是同一件事——工具只敢看名字和形状，最终裁决在人。
3. **形状本身的人肉发明**：这五个判据每一个都来自"人先撞过一次"。
   下一种新形状（比如这一夜的第 4、5 种）工具事先扫不出来——
   它是**既往教训的固化器**，不是未知教训的发现器。
4. **替代不了一次完整的真机轮**：live 只能看盘上痕迹与告警，
   告警被轮转裁掉的、没走到告警那一步的静默（比如写侧还没触发拒写），
   都不在它的视野里。

**结论**：当"回归闸门 + 坐标生成器"用——每次改动后跑一遍（5 秒级），
报出来的逐条人判；**别**把它当"扫过就安全"的橡皮章。这仓的原话教训
（形状判语义问题，精确率和召回率会同时烂）依然成立：我把两个方向都往判据里
焊了语义（数据流/通道/匹配语义），代价就是 §4 那一串结构性盲区——这是诚实的代价，
不是可以调参消掉的。
