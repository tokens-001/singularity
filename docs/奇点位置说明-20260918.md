## 1. 一句话

**一个自部署的 AI 软件工厂**：输入一句话需求，它驱动多个大模型按角色、分阶段
把软件做出来（调研 → 架构 → 实现 → 集成 → 验收 → 交付），中间设**三道人工审批门**。

单机、零数据库、数据全落本地 JSON。成品是**独立 git 仓库**，不是代码片段。

## 3. 它怎么干活

```
立项(填需求) → 调研(可跳过) → [GATE1 人审] → 架构+任务清单 → [GATE2 人审]
   → 实现(逐任务,worktree 隔离) → 集成合并 → 验收(QA/安全/E2E) → [GATE3 人审] → 交付
```

- **三道门全要人点**。其余是自动的（集成 / 验收 / 交付称为"非人门"）。
- **架构阶段会开多模型委员会**：多个模型各出一份方案 → 提取共识与分歧 → 辩论
  → 定稿。这是**唯一被实测证明有价值**的多模型用法（其余多模型用法实测无增益）。
- **验收层是"只报不改"**：出 QA 报告 + 安全审计 + E2E，**不改代码**，
  责任链是「AI 报告 → 人判 → 人决定改不改」。
- **打回是分级的**：按问题类型回实现层 / 回架构层 / 只记录不阻断。

## 4. 真机现状（难看的地方不藏）

跑了 4+ 轮完整真机（同一道题：JSONL 日志统计 CLI）。**能从头跑到交付**，但账很难看：

| 症状 | 数（2026-09-17 凌晨那一轮） |
|---|---|
| 任务 | **11 个：6 成功 / 5 失败**（约 45% 失败） |
| 单轮总耗时 | **71 分钟** |
| **token 打水漂** | **39%**（花掉但没产出可用结果） |

> 更早一轮（09-13 前后）是 **5 个任务 2 成功 / 3 失败**。
> ⚠️ **样本很小，别当稳定指标看** —— 我们把它列出来是因为"打水漂 39%"和
> "失败近半"这两件事**同时发生**，不是想说"失败率是 X%"。

**而且**：修 bug 的速度**长期快于**验证的速度 —— 一周的节奏基本是
"今晚修一批，明晚验上一批"，经常出现"修了 N 条，真机全没验"。
commit log 里反复出现「**更正上一版的根因**」—— 即**上次那个没修到根，这次翻案**。

> 这一条我们认为是**最值得外部审计的信号**，比失败率更值得看。

## 5. 我们知道的窟窿（已经写进仓库文档的）

| # | 什么 |
|---|---|
| 1 | **验收会因为上游少一个字段整段不发生** —— 架构没产出约束清单时，验收层直接返回，一项检查都不跑。<br>（⚠️ **不是静默**：它记了一条"验收跳过"并当成人审门的入门票。但"没输入"在我们的标准里应该是**验收失败**，不是**验收没发生**。） |
| 2 | **重做语义没定义** —— 打回重做时哪些痕迹该清、哪些计数归零**没有声明**，各写入点自行其是。已经咬过：架构重做了、执行用的还是旧任务。 |
| 3 | **阶段契约没数据化** —— 「哪个阶段归谁推」只写在**一句注释**里，不是转移表 + 守卫测试。 |
| 4 | **项目层的回路接不上 —— 不是"没接"，是"接不了"。** QA 报告的 issue id 是**约束 id**，而任务对象上**没有任何约束标识** ⇒「哪条约束没过 → 该重跑哪个任务」这条边**在数据模型里不存在**。所以 `handle_gate3_reject` 的 impl 分支只能"**全案重跑**"——**它 docstring 写「只重做有问题的 task」，代码里没有这个筛选**。<br>（⚠️ 别跟"任务层"混淆：任务层是通的，见 §6 判断 A。） |
| 5 | **项目状态是「整份覆盖写」** —— `save()` 是 `to_dict()` 全量写，**无字段级合并、无版本号、不检查"盘上那份是不是比我新"**。⇒ **谁最后写谁全赢，手里那份越旧抹掉的越多**（能抹掉的是 `owner_confirm` 里人的批准、`task_ids`、`phase`）。已核实至少 5 类写入者。 |

## 6. 我们的判断 ⚠️ **以下是判断，不是事实 —— 请直接反驳**

> ⚠️ **本节已经被一轮对抗性阅读改过一次。** 下面 A、B、D 是**改过之后**的版本；
> 我们把它们放上来仍然是因为**不确定改对了没有** —— 上一版三处都错了，所以这一版同样可疑。

**判断 A：回路在「任务层」是通的，在「项目层」是断的 —— 而项目层断的原因是「接不了」。**

- **任务层真的在自动闭环**：执行器有个活的重试环（`while retry <= task.max_retries`），
  审查层撞顶前会自动回炉（阈值 2 轮），反馈会带着回到下一轮。
  **这一层有真 pytest、真 git diff。**
- **项目层的验收只出报告、不碰代码**，出完只能升门等人。
- **但这不是"忘了接"**（§5.4）：QA issue 的 id 是**约束 id**，任务对象上没有任何约束标识
  ⇒「哪条约束没过 → 重跑哪个任务」这条边**在数据模型里不存在**，
  所以打回只能"全案重跑"。
- ⇒ **闭环恰好闭在"证据可信"的那一层，开在"证据是模型嘴炮"的那一层。**
  我认为这不是疏忽的形状，是个说得通的取舍 —— **但请反驳这个"我认为"。**

**判断 B：commit log 里 26 条带「更正」的提交，说的是「根因来自上一版的诊断」。**
不是"需求来自失败"，是**测量问题**：上一次把根因判错了，这一次翻案。
（我上一版把它读成了"需求从失败来"的产品问题 —— **两者修法完全不同**。）

**判断 C：它的"位置"是——**
不是产品（没用户、没发布、没对外接口）·
不是玩具（3.3 万行、1,708 次提交、1,645 条测试）·
更像一个「**能端到端跑完、但交付质量不稳的 AI 软件工厂**」，
处在「能证明这条路走得通」和「能托付真实需求」之间。

**判断 D：门不是拐杖 —— 门是当前系统里唯一的「执行器」。**
代码里有**六处观察器**，注释各自写着"只报不改 / 不改变行为 / 把缺证据摆到台面上比卡死项目有用"。
而**零个执行器**。同时，批准那道门的函数会顺手把两个失败计数器清零
（源码注释原话：「**单向棘轮（全仓无一处清零）**」）
⇒ **"人点一下"是唯一能解开那两个棘轮的动作。**
所以这不是"人在回路的样板"，是**这套代码把人的点击写进了状态机**。
（我上一版说"分不清是资产还是拐杖" —— **那是没去读代码，不是分不清**。）

**判断 E：我们怀疑自己一直在「修写入者」，而不是「修机制」。**
同一个"整份覆盖写"的根，我们 09-17 修过一次（观察者的写回抹掉人的批准），
09-18 又找出**四个同形状的写入者**。
我们打算"先只报警、不拦" —— **不确定这条路对不对。**
