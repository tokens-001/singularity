## 确认对（追到调用层）

### 对 1：敏感文件/危险命令的**第三张表**——`permission.SANDBOXED` 没跟上

- **两边在哪**：`scheduler/permission.py` 的 `SANDBOXED`（内置 profile 的 `blocked_paths` / `blocked_commands`）↔ `scheduler/executors/base.py` 的 `_BLOCKED_PATTERNS` / `_BLOCKED_COMMANDS`。
- **现在各是什么**：`SANDBOXED.blocked_paths` 7 项（`.env`、`.env.*`、`*.token`、`*.key`、`.qidian/*`、`.git/*`、`venv/*`）；`SANDBOXED.blocked_commands` 5 项（`rm -rf`、`sudo`、`chmod 777`、`curl`、`wget`）。`base._BLOCKED_PATTERNS` 30 项（多出 id_rsa 全族、`*.pem/*.p12/*.pfx/*.secret/*.password/*.credential`、`.netrc`、`.flaskenv`、`.ssh/`、`.claude/`、`.venv/`、`users.json`、`config.toml`、`agents.toml` 等）；`base._BLOCKED_COMMANDS` 26 项（多出 `mkfs.`、`dd if=`、fork 炸弹、`shutdown/reboot/halt/poweroff`、`iptables`、`nc`、`python -c`、`bash -c`、`eval`、`chmod -R` 等）。
- **哪边现役**：**两张都现役，挂在同一次工具调用上**。执行器侧：`OpenAIAgentExecutor._tool_read_multi/_tool_write/_tool_run`、被 `AnthropicApiExecutor` 借用的模块级 `_read_file/_write_file/_run_command`、`ZhipuApiExecutor.apply_patch` 都调 `base.is_blocked_path/is_dangerous_command`。profile 侧：`_dispatch_exec` 的 `_run_executor` **每次 dispatch 都**构造 `_dispatch_skills._make_permission_checker` → `check_path`/`check_command`。
- **后果**：今天修 web↔base 那对时两边注释都没提这张表，它是“只改了一遍”里**没改的那一遍**，而且不一致是**双向**的：base 有、SANDBOXED 没有的（读 `id_rsa`、`server.pem` —— 这半恰好被 base 层兜住）；SANDBOXED 有、base 没有的（`rm -rf build/` —— base 只拦 `rm -rf /`、`rm -rf ~`、`rm -rf .`；以及无空格的 `sudo`）。也就是说：绑了 `sandboxed` 的 agent 才有 `rm -rf build` 拦截，没绑的就裸奔；而 profile 在界面上（`/api/permissions/profiles`）展示的拦截承诺与实际执行的黑名单是两张表。
- **怎么确认的**：两张表内容逐项 diff；两条闸的装配点（`_run_executor` → `_make_permission_checker`；执行器工具函数内部）都追到调用层，确认对同一次 `run_command`/`read_file` 双层都生效。

### 对 2：profile 工具门（白名单/审批通道）只有 openai 执行器真的执行

- **两边在哪**：`executors/openai_agent.py` 的 `OpenAIAgentExecutor._execute_tool`（第一步调 `self._check_permission`）↔ `executors/anthropic_api.py` 的 `AnthropicApiExecutor._execute_tool`（自己重写的分发，**整个文件无一处 `permission` 引用**）。
- **现在各是什么**：openai 侧：查 profile → `check_tool`（白名单）→ `check_path` → `check_command` → `needs_approval` 命中就走 `request_approval` 真挂起等人。anthropic 侧：checker 经 `BaseExecutor.__init__` 的 kwargs 循环存成 `self._permission_checker` 后**无人读**，`_execute_tool` 直接派给 `_read_file/_write_file/_run_command` 等模块级函数。
- **哪边现役**：`_run_executor` 对**所有**执行器一视同仁注入 `permission_checker`；`dispatcher._EXECUTOR_BY_TYPE` 里 `openai-agent` 和 `anthropic-api` 都是活类型，且 `_ensure_agent_type` 会把注册表模型**默认推断成 `openai-agent`**，`anthropic-api` 是显式配置项。
- **后果**：对 `anthropic-api` 型 agent，`allowed_tools` 白名单、`require_approval`（工具级审批通道）、profile 层的路径/命令拦截**整层静默死掉**——界面上 profile 显示“已绑定”，审批功能看起来存在，实际永远不触发。敏感文件那半被 base 表兜住（对 1），但工具白名单和审批那半没有任何兜底。另外 `claude-cli` 执行器连 base 表也不经过（自带工具循环，python 侧两层都不拦）。
- **怎么确认的**：`grep permission` 在 `anthropic_api.py` 零命中；`anthropic_api` 的 `run` → `_execute_tool` 调用链逐行读过；注入点（`_run_executor`）和类型映射表、默认类型推断（`_ensure_agent_type`）都追到底。

### 对 3：`_tool_run`（类方法）vs `_run_command`（模块级）——今天那对**没收敛完**的残余

- **两边在哪**：`executors/openai_agent.py` 的 `OpenAIAgentExecutor._tool_run` ↔ 同文件模块级 `_run_command`（由 `AnthropicApiExecutor._execute_tool` 派单）。
- **现在各是什么**：类方法把 `self._agent_env`（来自 `cfg["env"]`）并进 `os.environ` 再脱敏，`shell=True`；模块级只用 `os.environ` 脱敏（**没有 agent env**），`shlex.split` + `shell=False`。
- **哪边现役**：都现役——openai-agent 的 `run_command` 走类方法，anthropic-api 的走模块级。
- **后果**：今天修的只是“os.environ 脱敏”这一半（模块级 docstring 自己记了）；剩下两处分叉：① agent 配置的 `env` 字段在 anthropic 路上**静默丢失**（PATH、代理、endpoint 类变量没了，命令行为不同或直接失败）；② 同一个工具名 `run_command` 的 shell 语义两边不同（`&&`/`|`/`source` 在 openai 路可用、anthropic 路不可用）——模型在两个执行器下会看到同一工具的两种行为。
- **怎么确认的**：两个函数体逐行读过；派单点（anthropic_api 的 `_execute_tool`）、`_agent_env` 的唯一赋值点（openai_agent 构造函数读 `cfg["env"]`）都追过。

### 对 4：`route_type` 合法词表**三处各写一遍**，内容互不一致

- **两边（实为三处）在哪**：`web/app.py` 的 `_VALID_TYPES`（POST `/api/tasks` 的门）↔ `router.py` 的 `_VALID_TASK_TYPES`（LLM 分类器合法值）↔ `validator.py` 的 `_annotate_unverified`（字面量比较）。
- **现在各是什么**：web 收 `{default, bugfix, feature, refactor, docs, fusion}`（6 值）；router 只产 `{bugfix, feature, refactor, docs, default}`（5 值）；validator 只对 `bugfix/refactor/feature` 三个字面量加“未验证”标注。
- **哪边现役**：三处全现役——web 在建任务时真拦，router 在 `_parse_classify_reply` 里真拦，validator 在每次 `validate()` 时真跑。
- **后果**：数据流是闭合的（web 收下 → `task.route_type` → `_exec` 读回 → `validate(task_type=route_type)` → route_learner 也按它记账）。于是 web 独有的 **`fusion`** 能过门、落库、进统计，但下游**没有任何类型判据认识它**：validator 的 unverified 标注对它整段静默不发生——正是 router.py 注释里自己描述的那种“少做几件事、不报错”的坏法。反向：`docs` 类型在 validator 处也没有任何标注（三类之外全裸）。
- **怎么确认的**：三处定义各自读到；两条消费链（web 门 → `task_create` → `tracker`；`_exec` 读 `task.route_type` → `validate`）都追到底。

### 对 5：`task_timeline` 把状态机**重写了一遍**，与 `tracker` 语义已分叉

- **两边在哪**：`tracker.py` 的 `TaskStatus`（12 态）+ `_TERMINAL` ↔ `_api_tasks.py` 的 `task_timeline`（硬编码字符串集合）。
- **现在各是什么**：tracker 里 `DECOMPOSED`/`CONFLICT_HELD` **不是终态**、也不必然经过 dispatched/running；timeline 的集合却把 `"decomposed"`、`"conflict_held"` 和 `done/failed/rolled_back` 并列当成“走到 running 之后、进入终态”的端点；同文件 `task_list` 的 `duration_sec` 又只认 `("done","failed")`。
- **哪边现役**：tracker 是唯一状态机；timeline 是活端点（web 的 `/api/tasks/<id>/timeline` → `_api_handler.task_timeline`，且在 `_READONLY_ENDPOINTS` 白名单里）。
- **后果**：状态为 `decomposed` 或 `conflict_held` 的任务，时间线 API 会**编造出** dispatched→running→终态的完整历程（它们实际没跑、还会回到调度）；`rolled_back` 的任务拿不到 duration；`blocked`/`paused` 的时间线只有前两段。读侧对状态机撒谎，排障时“任务卡在哪”会被画错。
- **怎么确认的**：端点调用链（web route → facade → `task_timeline`）追过；timeline 的三个字符串集合与 `TaskStatus` 逐值比对过。

### 对 6：「本机 origin」判定写了两份，两份内容不同

- **两边在哪**：`web/app.py` 的 `_is_local_origin` ↔ `scheduler/_auth.py` 的 `_LOCAL_ORIGIN_RE`（经 `ws_allowed_origins`）。
- **现在各是什么**：web 版 urlparse 后判 hostname ∈ `{localhost, 127.0.0.1, 0.0.0.0, ::1}`（大小写不敏感、任意端口）；`_auth` 版正则 `https?://(127\.0\.0\.1|localhost|\[::1\])(:\d+)?`（**没有** `0.0.0.0`、大小写敏感）。
- **哪边现役**：都现役——web 版守每个 `/api` 写请求的 CSRF 门和 CORS 反射；`_auth` 版守两个 WS 服务（`bridge` 和 `observer/server` 的 `origins=` 参数）。
- **后果**：同一个来源在 HTTP API 门和 WS 门上的判定结果可以不同（大小写变体、`0.0.0.0`）。WS 那侧松一格就是绕行口——`_auth.py` 自己的注释写明了 observer 工具箱带 `create_task/delete_task/control_loop`，“能真正挡住这条路的只有 Origin 校验”。防线的两半各执一张“本机”定义。
- **怎么确认的**：两个判定实现都读过；四个使用点（CSRF、CORS、bridge、observer）都追到接线处。

### 对 7（低烈度）：两套“模板”词表，`project_lineage` 拿**项目 ID** 去**任务模板表**里查

- **两边在哪**：`project.py` 的 `TEMPLATES`（键：`product_dev/bug_fix/refactor/agent_dev/feature/test/review`，别名表 `_TEMPLATE_ALIASES` 只在 `project.create` 里收敛 `bugfix→bug_fix`）↔ `task_templates.py` 的 `TEMPLATES`（键：`bugfix/feature/refactor/test/review`）。交叉点：`_api_projects.py` 的 `project_lineage`。
- **现在各是什么**：`project_lineage` 里 `if project_id in TEMPLATES` 用的是 **task_templates 那张表**，传入的却是项目 ID（`project._next_id()` 的毫秒数字串，永远不在那张表的键空间里）→ 模板分支恒死；就算换成项目模板名，A 表的 `bug_fix` 在 B 表里也查不中。
- **哪边现役**：端点本身活着（web 路由 + 只读白名单都注册了）但模板分支是死功能；更进一步——前端 `Projects.tsx` 读的是 `project_detail.lineage`，而 `project_detail` **从不写这个键**，前端 api.ts 也没有任何地方调 `/lineage`：整条 lineage 链路三段各自“死着但互相不知”。
- **后果**：当前是纯死功能（无数据损坏）；但它是同一个“模板名”词表在该收敛处（别名表）之外的第三处裸用，下次谁往里接功能就会踩 `bug_fix`/`bugfix` 的老坑。
- **怎么确认的**：项目 ID 生成、别名收敛的作用域、端点调用链、前端消费点（api.ts 无调用、`Projects.tsx` 读不存在的键）全部追过。

### 对 8（低烈度）：`task_list` 的 `level_filter` 比的是 `route_type`

- **两边在哪**：`_api_tasks.py` 的 `task_list`（参数名 `level_filter`，比较却写 `t.get("route_type") != level_filter`）↔ 同函数响应里并排的 `route_level` 和 `route_type` 两个字段、以及 `web/app.py` 的 `/api/tasks` 路由（参数名 `level`）。
- **现在各是什么**：按参数名与响应字段，`?level=` 应该过滤 `route_level`；实际过滤的是 `route_type`。
- **哪边现役**：端点现役；捆绑前端当前**不传** `level`（`Tasks.tsx` 在前端自行过滤），所以是“公开 API 语义错、还没人踩”的活口。
- **后果**：任何脚本/第三方按 `level` 过滤会拿到按类型过滤的结果，或空表——静默错，不报错。
- **怎么确认的**：web 路由参数名 → facade → 比较字段追完；前端调用点确认（`api.ts` 的 `tasks()` 只在无参时拼接 URL）。

## 候选：没追到调用层

- **profile 绑定键的 level 词表**：`permission.bind_agent`/`get_agent_profile` 用 `f"{level}/{model}"` 做键。绑定侧 level 来自 API 调用者的任意字符串（无校验），检查侧是执行器的 `_agent_level`（dispatch 层级）。两个词表理论上可错位（绑成 `"E/..."` 而调度层级是别的值 → profile 静默不生效），但没有前端/CLI 实际调用绑定接口的证据（前端源码无 `permissions/bind` 调用），**不判**。
