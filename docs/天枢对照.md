## 二、判据层：两家独立收敛

天枢的核心主张，原文：

> 模型何以稳定地交付 —— 目标不漂移、**完成有证据**、验证有闭环，**不说"应该修好了"**。

它的四条审查纪律里，最有用的是**纪律 4**，原文：

> **"测试全过"声明 fail-closed。无"实际运行的命令 + 观察到的关键输出"的绿声明，一律按未验证处理。**

**这个说法可以直接用** —— 它给我们的 GATE 和 `validator.py` 起了个准确的名字。
我们做的是同一件事，只是没有用这个词。

| 我们做的 | 天枢叫它 |
|---|---|
| GATE 三关 | `deliver_task` + ReviewRouter（L1 nudge / L2 单对抗子代理 / L3 Squadron） |
| "不许说做完了" | **绿声明 fail-closed** |
| `validator.py` | `adversarial_verifier` / `Inspector` / `verifyWorkerEvidence` |
| 审查不许自己审自己 | **verifier 与 patcher 必须是不同子代理**（纪律 2） |
| worktree 隔离 + 合并 | `hands` role / 语义锁 5×5 矩阵 / Wait-For Graph 死锁检测 |
| 多模型委员会 | 星域 ↔ 模型路由 |
| 任务重试 | `RepairPipeline` |
| `CLAUDE.md` 的规矩 | `OBJECTIVE_REVIEW_STANCE` |
| `docs/失败形状.md` | `_templates/_analysis.md` |

**天枢比我们多的两条机制**（值得看，不一定值得抄）：

1. **重入护栏是结构性的**：`reviewDepth > 0 → 结构性跳过 ReviewRouter`，
   注释原文「**不依赖 prompt 服从**」。我们的对应物是"审查阶段不再触发审查"，
   但是靠流程约定还是靠代码挡的，**没核过**。
2. **客观审查姿态**（`OBJECTIVE_REVIEW_STANCE`）四条，其中第 4 条值得抄：
   「**复核"定义"是否真的接入调用边界**」—— 这一条如果早写进我们的清单，
   `result-hero` 那个"写死 `display:none`、十几条结构测试全绿"的洞会早一天被问出来。

## 三、两家独立踩的同一个坑

### DeepSeek 把工具调用吐在 `content` 里

- 天枢：`RepairPipeline`，专门处理这件事
- 我们：撤掉工具那一轮 + 模型吐的 XML 工具调用被捞回 ⇒ reasoning 被剥 ⇒ 400
  （见 `docs/防御模式.md` §85）

**同一个模型的同一个怪癖，两家各自撞了一遍。** 这说明那是 DeepSeek 的固有行为，
**不是我们的代码问题** —— 这条值得从"我们的 bug"改归到"目标模型的已知行为"。

**这一节是本对照最值钱的部分。** 我们担心"它 51 万行、我这 3.6 万行拿不出手" ——

## 五、前缀缓存：评估完了，结论是「先量，别先改」

天枢把前缀缓存当**架构级承诺**（原话「Prefix Cache 是架构级承诺」，不是事后加的补丁）：
冻结前缀 + 增量 appendix + 边界压缩，长会话命中 **95–99%**。
背景是 DeepSeek V4 **对缓存未命中按命中价的至多 50 倍**计费。

### 它的机制（代码层，已核）

- 消息顺序 = `[system][volatile 冻结段][历史 user 快照…]` + 尾部每轮追加 appendix
- 历史 user 消息走 **frozen 快照回填**，不用当前状态重建
- 不变量由测试钉死：`fresh.startsWith(frozen)`，且无动态字段时**字节相等**
- **`turn !== 0` 绝不改写历史**（三处硬编码守卫）—— 理由：中途重写会打碎 exact-prefix
- 压缩时头两条消息**永不动**（`CACHE_ANCHOR_MESSAGES = 2`）
- 报警判据（不是看板）：`cacheRead` **相对上一轮倒退** ⇒ `severity: 'error'`；
  平均命中率 < 90% ⇒ `ADVISORY`
- DeepSeek 的 provider 档位：`{ cacheType: 'exact-prefix', persistent: true, minCacheTokens: 64 }`
- 实测：缓存的 hit 恒为 **7808 = 64×122**（64 token 块量化）；
  **尾部不满一块的 27 token 恒 miss**；**10 token 的短 prompt 完全不缓存**

### 奇点能接吗 —— 三个结构冲突（都是代码里看到的）

1. **奇点没有 append-only 长会话。** `_exec.py` 的 `_build_effective_task(task, turn, …)`
   在 `while` 循环体内**逐轮重建**，executor 也**逐轮新建**（`_dispatch_exec.py` 里每次 dispatch
   都 `executor_cls(...)`）。**每个 turn 都是一次全新请求** —— 天枢 90% 的缓存复杂度
   （处理"怎么不打碎长会话前缀"）在奇点这里**没有对应物**。
   ⇒ **能缓存的最稳定前缀只有 `[system][tools]`**：

   | 常量 | 位置 | 字符数 |
   |---|---|---|
   | `SYSTEM_PROMPT` | `executors/openai_agent.py` | 1,033 |
   | `TOOLS`（4 个工具） | 同上 | 1,199 |
   | `_DEFAULT_SYSTEM`（anthropic 那条路） | `executors/anthropic_api.py` | **311** |

   ≈ **2,232 字符**（openai 路）。anthropic 那条路只有 311。

2. **多模型阵容和前缀缓存天然打架。** `dispatch()` 的 fallback 链**最多试 3 个不同模型**；
   `_premium_first` 在 `retry_count >= 2` 时**强制优先 premium**；
   委员会路径更是**同一次任务并行发 3 个不同模型**。
   **缓存不跨模型、不跨 provider 共享 ⇒ 一换模型全作废。**
   ⇒ 这**不是"补一层"的事，是"先选"的事**。

3. **固定内容被放在了最容易失效的位置。**
   `_construct_context` 把 `f" ({elapsed:.1f}s)"`（工具耗时秒数）拼在 user 消息**最前面**；
   而 `_GLOBAL_CONSTRAINTS`（386 字）、roles 角色提示词这些**真正固定的长文本**
   全拼在 user 里、排在它后面 ⇒ **从 elapsed 往后全部每轮失效**。
   另外 `_build_effective_task` 里 `if turn == 1:` 的门控，让**首轮和后续轮的 user 前缀长度完全不同**。

4. **请求组装没有统一入口。** 分发层统一了（`_EXECUTOR_BY_TYPE`），
   但请求体组装**分散在 4 个 executor 类**里（openai / anthropic / zhipu / claude_cli）。
   要接缓存得在 4 处分别加，或先抽一层公共 request builder。

### 结论

🔴 **先量一个数再动**：同一任务连续几轮里，**用同一个模型的占比是多少**？
若大量轮次都在换模型，**缓存收益 ≈ 0，改了白改**。（度量先于改动）

### 顺带一条它测出来的坑

Claude Code 会在 system message 注入每次不同的 `cch=xxx`，**导致 prefix cache 100% miss**；
它单独写了个反向代理把这层剥掉，命中恢复到 ~90%。
⚠️ **但它在 `src/` 里搜不到这个实现** —— 文档说了，代码里没有。
