## 四、新发现并**当天修掉**的：门禁说不出"哪条、为什么"（`3bd720e3` + `ec3e3f74`）

**症状**：任务 `error` 只有一句 `tests failed: 退出码 1（失败个数没能从输出里数出来）`，
`trace.unverified[0]` 里存的唯一证据是：

```
tests failed: .......F......................            [100%]
=================================== FAILURES ===================================
________________ test_common_options_ma
```

**测试名断在中间，断言一行都没有。** 真正的原因从第 **264** 字符才开始，
而落盘的是 `output[:200]` —— 那条线**根本够不到**。
⇒ **判了失败却说不出哪条、为什么**，只能把产物从 `refs/qidian/pending/` 捞出来重跑。

**三处，同一个病：证据的有效部分在末尾，代码掐的是头。**

| # | 位置 | 原来 | 现在 |
|---|---|---|---|
| ① | `_review.py` ×2 | `output[:200]` / `[:120]` | `validator.failed_output_tail`（掐头留尾 600 / 300） |
| ② | `run_project_tests` 的 4000 上限 | `_raw[:4000]` 只留头 | `_raw[:2000] + … + _raw[-2000:]` |
| ③ | 退出码非零那一支 | 直接 `return`，**一个正则都不跑** | 照常解析 `N failed`（解析不到仍保持 0，不编） |

②③ 的来历：pytest 把「哪几条」放在 `short test summary`、把「为什么」放在 `FAILURES` 段、
把「几条」放在最后一行 —— **全在末尾**。

**顺带改了一条既有判据**：`test_run_tests_pytest_fail` 原来断言 `failures == 0`，
注释写「数不出失败个数时不该编一个」—— 但代码**压根没去数**，
那条断言实际钉住的是"**我们不解析**"而不是"我们不编造"，而它挡住的正是这个修复。
2026-09-14 那个真 bug（拿退出码顶替失败数）**单靠"1 个失败"挡不住**（退出码恰好也是 1）
⇒ 补 `test_失败个数来自汇总行而不是退出码`：喂 3 条失败用例（pytest 退 1、失败数是 3）。

**变异复核（四处逐个咬）**：

| 变异 | 红法 |
|---|---|
| `_review` 接线换回 `[:200]` | 1 红 —— 报错文本**就是真机症状** |
| `failed_output_tail` 取头不取尾 | 1 红 |
| 4000 上限只留头 | 1 红 |
| 退出码非零时不解析失败数 | 3 红 |

🔴 **变异复核当场抓到两条我自己的毛病**（第一轮只咬中 1/2）：
- **「取尾巴」那条测试没有判别力** —— 喂的真机输出只有 500 来字符，而阈值是 600
  ⇒ `s[:600]` 返回**整串**，取头和取尾结果一模一样。**是测试没判别力，不是变异打偏。**
  已补一段 3000 字符的头噪声。
- **那个用例被写了两次（重名）**，后一个把前一个盖掉 ⇒ **前一份从没跑过**。
