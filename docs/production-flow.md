# 奇点生产流 v2

> 2026-06-24 对齐产物。本文档是奇点所有功能的流程基准，后续 spec 由此拆解。

## 流程总览

```
立项 → 调研(D层) → 你审 → 方案(D层) → 你审 → 执行(E/E+) → D层审代码 → 合并 → 测试 → 交付(你审)
  ↑                                                                    ↓ 有问题
  └──────────────────────── 返工(无上限) ←─────────────────────────────┘
```

---

## 一、立项

**输入**：用户提出需求
**输出**：立项书（结构化文档，明确需求边界）

D 层在立项阶段需要帮用户澄清：
- 要做什么、解决什么问题
- 目标用户是谁、使用场景是什么
- 范围边界（做什么、不做什么）
- 硬约束（时间/预算/技术栈/合规）

**立项通过标准**：需求清晰到 D 层可以开始调研。

---

## 二、调研（D 层执行，你审核）

六个必覆盖维度，缺一不可：

### 1. 竞品分析
- 同类产品拆解
- 核心技术方案对比
- 可借鉴的技术点
- 竞品的短板和本项目的差异化机会

### 2. 前沿理论与技术
- 项目相关的学术/工业前沿进展
- 关键技术的成熟度评估
- 前沿理论在本项目中的可行性论证

### 3. 用户研究
- 目标用户的痛点
- 交互需求和使用习惯
- 竞品无法满足的需求

### 4. 需求澄清
- 核心功能/次要功能/不做功能
- 用户故事的优先级排序

### 5. 技术预研（PoC）
- 关键技术的原型验证
- 证明"能做"，不是"理论上能做"
- 输出：可运行的 demo 或实验数据

### 6. 约束识别
- 性能约束（响应时间/吞吐量/QPS）
- 安全约束（数据加密/权限模型/攻击面）
- 合规约束（隐私/数据保护/行业规范）
- 兼容性约束（向后兼容/平台/浏览器）

**审核人**：你

**通过标准**：六个维度全部覆盖，你逐项确认。不通过的维度退回补充，直到通过。

---

## 三、方案（D 层出，你审核）

D 层基于通过的调研报告，产出三个方案文档：

### 1. 架构方案
- 技术选型及理由
- 模块划分和接口定义
- 数据流/状态管理
- 部署和运维方案

### 2. 任务拆解分配方案
- 从架构方案拆成独立可执行的任务
- 每个任务的输入/输出/验收标准
- 任务依赖关系和执行顺序
- 每个任务分配到合适的执行层（E/E+）

### 3. 测试方案
- 按同类产品的行业标准制定
- D 层根据项目类型判断用什么测试手段
- **必须包含需求追溯表**：每条立项需求 → 对应测试 → 通过标准
- 测试用例清单

**审核人**：你（架构方案、任务拆解方案、测试方案都审）

**通过标准**：三个方案你全部确认。

---

## 四、执行

### 编码（E/E+ 执行）
- 按任务拆解方案逐个执行
- 每个任务产出：代码 + 自测结果

### 代码审查（D 层验收）
- D 层 review E/E+ 的代码产出
- 检查：逻辑正确性/代码规范/安全/性能
- 发现问题 → 退回返工

### 合并（D 层操作）
- D 层确认代码无误后合并
- 合并后执行测试方案

---

## 五、测试

### 测试两层结构

测试分两层，缺一不可：

**第一层：需求符合性测试（必须有）**

把立项书的每一条需求映射为可验证的检查项。测试不是"代码能不能跑"，而是**做出来的东西是不是你最初要的**。

| 立项需求 | 对应测试 | 通过 |
|---------|---------|------|
| "支持 Markdown 导出" | 导出文档 → 用 Markdown 渲染器验证 | 渲染无误 |
| "登录响应 < 200ms" | 压测 login API → P95 < 200ms | 达标 |

D 层在方案阶段出**需求追溯表**（每条需求 → 怎么测 → 谁测 → 通过标准），你审核通过后再执行。

**第二层：行业标准测试（按项目类型）**

在此基础上，D 层按项目类型叠加行业标准测试：

| 项目类型 | 行业标准测试 |
|---------|------------|
| Web 应用 | 单元测试 + 集成测试 + E2E(关键路径) + 安全扫描 |
| CLI 工具 | 单元测试 + 集成测试 + 边界输入 |
| Python 库 | 单元测试覆盖率 ≥80% + API 合约测试 |
| 移动应用 | 单元测试 + UI 测试 + 设备兼容性 |
| 脚本/自动化 | 集成测试 + 干运行验证 |

### 测试不通过 → 返工

---

## 六、交付（你审核）

- D 层整理交付物清单（含需求追溯表 + 测试报告）
- 你最终审核(GATE3)
- **核心指标**：交付物是否符合最初立项要求（需求追溯表逐项核对）
- 其余审核项：代码质量/测试覆盖/文档完整性
- 不通过 → 返工
- 通过 → 归档，项目 DONE

---

## 七、返工

- **不设轮次上限**（废除 `MAX_FIX_ROUNDS=3` 硬编码）
- 发现问题 → 退回执行 → 修复 → 合并 → 重新测试
- 循环直到你通过为止

---

## 角色与职责

| 角色 | 职责 |
|------|------|
| **你** | 立项、审核调研报告、审核架构方案、审核任务拆解方案、审核测试方案、最终交付审核 |
| **D 层** | 调研、出方案、验收 E/E+ 代码、合并、测试组织 |
| **E/E+ 层** | 按任务执行编码 |

## 门禁清单

| 门 | 审核人 | 通过条件 |
|----|--------|---------|
| GATE 0 立项 | 你 | 需求清晰 |
| GATE 1 调研 | 你 | 6 维度全覆盖 |
| GATE 2 方案 | 你 | 架构+拆解+需求追溯表+测试方案全确认 |
| GATE 3 交付 | 你 | 需求符合性(需求追溯表逐项核对) + 代码/测试/文档全通过 |
| D 层代码审查 | D 层 | 代码无误 |
| D 层合并审查 | D 层 | 测试通过 |
