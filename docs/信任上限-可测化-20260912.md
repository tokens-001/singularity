# 信任上限 · 怎么把它变成一个能测的数

> 2026-09-12。起因：一份战略分析提出「**信任上限 = 机械证据覆盖的验证面比例**」，
> 方向对，但**没给这个比例的定义**。
>
> **本文只干一件事：把那个比例定义成一个能算的数。** 定义没定死之前不动代码。

---

## 一、照现在的写法，它会自证

分析里 P3 写的是"验收项里机械证据背书的比例"。问题出在**分母是谁产生的**：

**验收项是架构师（LLM）列的。** 架构师只列自己能机械验的 → 这数就是 100%。
架构师少列一条需求 → 分母跟着缩 → 比例纹丝不动。

所以它测的不是"覆盖率"，是"**自洽率**"：测架构师和自己一不一致，
**不测系统对需求负不负责**。

---

## 二、分母必须来自需求侧

| | 来源 | 谁产生 | 何时 |
|---|---|---|---|
| **分母**（需求条目） | 调研产出的 `scope_clarification.core` + 用户 `description` 里的硬约束 | **用户侧** | 早于架构 |
| **分子**（有机械证据的条目） | 实际**跑过且通过**的机械检查 | 验收层 | 晚于实现 |

**关键一条**：架构师**漏掉**某条需求 → 分母**不缩**，分子**不给分**。
只有这样，"漏掉"才会以**低分**的形式暴露，而不是被静默吸收进一个漂亮的比例里。

> 现成输入：今天探路2 的调研报告里 `scope_clarification.core` 正好 **5 条**，
> 可直接作为第一次实测的分母。

---

## 三、是两个数，不是一个

| 指标 | 定义 | 回答什么 |
|---|---|---|
| **覆盖率** | 有机械检查的需求条目 ÷ 需求条目总数 | 多少需求**由机器替我盯着** |
| **通过率** | 跑过且通过的检查 ÷ 跑过的检查 | 机器盯的那部分，**实际好不好** |

**必须分开显示。** 合成一个会掩盖最要命的组合：

> **覆盖率 20% + 通过率 100%** —— 面板全绿，实际 80% 的需求根本没人看。

---

## 四、机械检查本身要过三道闸

1. **GATE2 展示、人批准**。架构 JSON 来自委员会、受任务描述影响（prompt injection 面）。
   让"模型生成的字符串变成平台要执行的命令"，必须人在环里 —— GATE2 本来就是人对架构的门，
   批命令是它的自然延伸。
2. **命令白名单 + 不走 shell + 限在 worktree 内 + 超时 + 无网络**。
3. **跑过才算**。只声明不执行 = 分子不给分 —— 这正是 `constraints[].check` **今天的状态**：
   schema 承诺"可机器检查"，全仓五处消费**全在拼 prompt**，一次没执行过。

---

## 五、顺序：先定尺子，再做 P2

分析把 P3 排在 P2 **后面**（"P2 落地后几乎是免费的"）。

**建议调过来。** 先把上面这套定义落成代码，再让架构师去产机械检查 ——
否则 P2 做完，手上仍是一张**没有刻度的表**：涨了也不知道涨了多少，
跌了也看不出跌在哪。

---

## 六、补一维：地板（外部依赖可达性）

分析的三个乘数都在答"**能跑多好**"，漏了"**能不能跑**"。

**2026-09-12 实测**：外网一断，调研阶段直接死 ——
`sentence_transformers` 加载**本地**模型时仍要联网查 `huggingface.co` 的 metadata，
域名不通 → `http_backoff` 退避重试挂死；而那段整个包在 `try/except Exception: pass` 里
（`pre_search.py:126`），**挂起不是异常，拦不住、不留痕**。
加上 `HF_HUB_OFFLINE=1` 后同一份代码 50 秒跑完。

这不是乘数，是**地板**。但因为它是**静默的**，它比乘数更该被单独管：

> **跑阶段前探一次外部依赖**（HF / 模型 API / git remote），
> 探不通就 **fail-fast 写进 issues**，而不是挂在 `except: pass` 后面装死。
