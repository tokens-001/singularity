# 事故复盘模板（postmortem）

> 用于踩了 P0 / P1 之后。目标不是追责，是「下次怎么不再踩」。
> 防护措施必须是**可执行的代码 / 测试 / 规则**，不是「注意点」。
>
> 命名：`docs/postmortem/NNNN-<短横线标题>.md`（从 0001 起编号）。
> 骨架借鉴 DeepSeek Harness `docs/postmortem/`（那边英文 + 中文各一份，需要对外时再补英文）。

## 摘要

一段话：坏了什么、为什么测试没拦住、修了什么。

## 概述

哪个组件 / 入口、什么操作触发、报错字符串是什么。点明「有多少绿色测试也照样坏」。

## 影响

- 谁能碰到、坏到什么程度（功能不可用 / 数据丢失 / 性能）。
- 有没有数据损失，代价是什么。

## 时间线

- 何时引入（commit）、何时暴露。
- 排查中被推翻的假设（写下来，别只写最后正确的那条）。
- 什么时候找到根因 #1、修完后暴露的根因 #2。

## 根因

每个根因一节，贴关键代码，说清机制：

- 代码怎么写的 → 运行时实际怎么走的 → 为什么失败。
- 如果存在过「看起来合理但错」的解释，明确写出来，并说明被什么证据推翻。

## 为什么测试没拦住（真正的失败）

逐条说明现有测试为什么绕过了这条路径。常见四种：

- 手动构造对象挂载，而非走真实加载 / 入口；
- 在顶层调用，绕过了真实拓扑；
- 需要 key 的测试被 CI 跳过；
- 跑的是陈旧构建产物。

## 防护措施

可执行的动作清单，每条带文件 / 命令：

- 代码修复（贴出位置）；
- 新增测试（说明它为什么能拦住，并且**验证过「把 bug 放回去测试会失败」**）；
- 写进规则的教训（指向 `docs/防御模式.md` 的对应条目）。

## 教训

- 通用结论 1-3 条，能直接指导下次写代码。
- 引用 0001 的核心教训：**100% 覆盖率 ≠ 行为正确，测试要走真实入口路径。**
