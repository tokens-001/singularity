## 🔴 致命（崩溃/数据错误/流程断裂）

### F1. 集成合并阶段（D2）是死代码——workflow 根本进不去 INTEGRATING

**位置**：`workflow.py:701-703` ↔ `orchestrator.py:248-303`

**问题**：
- `workflow.py` 的 `run_phase` 处理 `Phase.EXECUTING` 时调 `_run_execution` 然后 `break`（等 orchestrator 跑任务）。
- `_run_execution` 创建完所有 tracker 任务后，phase **仍是 `EXECUTING`**（L1022），没有进 `INTEGRATING`。
- `orchestrator.py:253` 的 `_auto_trigger_test_fix` 判断条件是 `proj.phase.value == "executing"`，任务跑完后把 phase 改成 `INTEGRATING` 再跑 `_run_integration_merge`。

**表面看链路通了，但实际有 race**：
- `_auto_trigger_test_fix` 在 `_run_queue_v3` 主循环里**每个 reap/drain 周期都被调一次**（L242）。它遍历 `list_all()` 所有项目。
- 当任务全部 DONE 时，它把 phase 设为 `INTEGRATING` 并跑集成合并。**但这是在 orchestrator 的调度循环线程里同步跑的**——集成合并里有 `subprocess.run(..., timeout=120)` 的 pytest 和 `timeout=30` 的 docker check（L368-386），**会阻塞整个调度循环最长 150 秒**。这期间所有其他项目的任务派发、future 回收全部卡死。

**为什么是问题**：① 集成合并这种重操作塞在调度循环热路径里，单项目跑测试时全局停摆；② `_run_integration_merge` 里 `git status --porcelain` 检查工作区干净（L350），但多 worktree 合并完主仓库未必干净（merge_queue 只保证分支合并，主仓库可能还有未跟踪文件），容易误判失败回退 EXECUTING 死循环。

**怎么改**：集成合并不能在调度循环里同步跑。两种方案：
- **A（推荐）**：集成合并作为独立 phase（`INTEGRATING`），由专门的 worker/线程异步执行，完成后写回 phase。调度循环只读 phase、不跑测试。
- **B（最小改动）**：`_auto_trigger_test_fix` 只做 phase 状态机推进（executing→integrating），把集成合并扔进线程池异步，调度循环继续跑别的。

### F2. 任务路由仍硬编码 E/E+/D，重构没下沉到 workflow 层

**位置**：`workflow.py:965-991`

**问题**：
```python
LAYER_ROLE_MAP = {
    "frontend": ("E", "frontend_engineer"),
    "backend": ("E", "backend_engineer"),
    "data": ("E+", "data_engineer"),   # ← E+
    "devops": ("E", "devops_engineer"),
}
...
level_map = {"low": "E", "medium": "E+", "high": "D"}   # ← E/E+/D
architecture_level = level_map.get(tdef.get("complexity", "low"), "E")
...
if architecture_level == "D":
    level = "D"
    role_key = "system_architect"
```

**这是大重构的核心目标**（"砍掉 E/E+/D，改为模型自由选择"），但 `_run_execution` 依然按 E/E+/D 给每个任务打 `route_level`，并以这个 level 去选 agent。重构在 `dispatcher.py`（两档、`_all_agents_list`）和 `router.py`（只标 task_type）里做了，**但真正决定任务路由的 `_run_execution` 没动**。

**为什么是问题**：① 重构名不副实——下游 `dispatcher.pick_agent` 拿到的还是 "E"/"E+"/"D"，会按 `agents.get(level)` 去查 agents.toml 的对应层，如果 toml 里层名改了（见 F3），直接查不到 → `RuntimeError(f"无可用 agent (level=E)")`。② `data_engineer` 的 level 是 "E+"，但 `roles.py:3429` 的 `_DEFAULT_ASSIGNMENTS` 里 data_engineer 绑的是 "GLM-E+"，而 GLM-E+ 的 `level=""`（L3407），层级对不上。

**怎么改**：`_run_execution` 改用两档：实现层统一 `cheap`（或留空让 dispatcher 全池选），不再按 complexity 分 E/E+/D。`LAYER_ROLE_MAP` 只保留 layer→role 的映射，去掉 level 列。与架构文档 D2/S3 一致（实现层统一便宜）。

### F3. `models.toml` 的 `recommended_for` 值与 workflow 实际传的 phase 错位

**位置**：`models.toml` 全文 ↔ `model_registry.py:3165` `for_phase()`

**问题**：
- `models.toml` 的 `recommended_for` 用中文阶段名：`["架构","审查","实现","定义"]`。
- 但 `workflow.py` 里调 LLM 时传的 `level` 是 "E"/"E+"/"D"（L796 `"E"`、L841 `"D"`、L1078 `"D"`）。
- `model_registry.for_phase("架构")` 能查到模型，`for_phase("E")` 查不到任何东西。
- `dispatcher.pick_agent` 用 level 去查 `agents.get(level)`，而 `agents.toml` 没在审查范围里——如果它的 key 还是 E/E+/D，能跑；如果也改成中文阶段，`_run_execution` 传的 "E" 就全炸。

**为什么是问题**：配置层（中文阶段）和路由层（E/E+/D）的命名空间**完全错位**，中间没有任何映射。要么 `recommended_for` 形同虚设（没人按中文名查），要么运行时崩。`model_registry` 的 `for_tier()` (L3185) 还留着 backward compat，说明旧命名还在用。

**怎么改**：统一命名。建议 `recommended_for` 改成与 `for_phase` 入参一致的值，并在 `workflow._safe_dispatch` 传 phase 名（"实现"/"架构"）而非 "E"/"D" 给 dispatcher，dispatcher 内部 phase→模型池。需要先确认 `agents.toml` 的 key 方案后整体对齐。

### F4. `dispatcher.dispatch` 的委员会模式被 `if False:` 永久禁用

**位置**：`dispatcher.py:2542-2545`

```python
# ── D层委员会模式: 多模型并行 → 合成 ──
if False:   # ← 死代码
    return _dispatch_committee(task, level, task_id, agents, chain, feedback,
                               baseline_ref, cwd)
```

**问题**：架构阶段（`_run_planning`）调 `dispatch(prompt, "D", ...)`，期望 D 层走"3 模型并行→合成"。但 `dispatch` 里 `if False` 直接跳过委员会，走单模型 fallback 链。

**那 3 模型碰撞在哪发生？** 看 `workflow.py:862-873`：planning 完成后，去读 `config.QIDIAN_DIR / ".last_fusion.json"`——说明 fusion 是在**别的地方**（可能 observer 或更上层）预先跑好、把结果写文件，planning 只读元数据。但**这个写 `.last_fusion.json` 的调用点在审查的 24 个文件里找不到**。`fuse_architecture` 定义了却无调用方。

**为什么是问题**：① 架构文档核心卖点"架构师 3 模型碰撞"在代码里是断的——`fuse_architecture`/`_dispatch_committee` 都是死代码；② `if False` 是明显的重构残留，应直接删或接通。

**怎么改**：要么接通委员会模式（删 `if False`，在 planning 阶段显式调 `fuse_architecture`），要么彻底删掉 `_dispatch_committee` 和 `fuse_architecture` 并改架构文档。二选一，不能放着半死不活。

### S2. `_review.py` 的"审查超时"判定是假的——永远不触发

**位置**：`_review.py:3905-3944`

```python
def run_post_exec_checks(...):
    start_time = time.time()
    if validation.action == "pass" and changed:
        if time.time() - start_time > _REVIEW_TIMEOUT_SEC:   # ← 刚进来 0 秒，恒为 False
            ...审查超时处理...
```

`start_time` 在函数入口取，紧跟着就检查超时——此时只过了几微秒，**永远不会超时**。真正耗时的 `run_project_tests`/`multi_model_review` 跑完之后，没有再检查超时。**D1 的"审查超时判 FAIL 不默认通过"在这个函数里根本没实现**。

**怎么改**：超时检查要放在耗时操作之后，或用 `concurrent.futures` 带超时包装，超时即 abort。

## 汇总

| 严重度 | 数量 | 关键项 |
|--------|------|--------|
| 🔴 致命 | 4 | F1 集成合并死链 / F2 workflow 路由没改 / F3 配置命名错位 / F4 委员模式死代码 |

**最该立刻修的 3 件**：
1. **F2 + F3**：workflow 路由和配置命名——重构的核心，不修则整个调度在 E/E+/D 和中文阶段名之间错位，随时崩。

3. **S2 + S4**：审查超时和多模型 review NameError——D1 在审查层的实现是空的，安全审查形同虚设。

**整体判断**：**重构做了一半**。dispatcher/router/model_registry 已切两档，但下游消费方（workflow 任务路由、project phase 流转、_review 审查循环）还停在 E/E+/D 旧世界，且新加的 D1/D2/D3 防线多处没接通。建议优先补齐重构的"最后一公里"，再清理死代码。
