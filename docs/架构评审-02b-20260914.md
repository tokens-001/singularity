1. **对账循环（你们评：高）——同意高，补三个你们没写的坑**：① “定期”在现架构里有陷阱：`run_queue` 是阻塞的（一波全跑完才返回），对账若放 app 层循环，**忙时（最需要对账时）永远轮不到**——见方案甲，这是位置问题不是可行性问题；② “只报不改”需要分级：§65 你们已经划出了例外（“没有 future 就是没在跑，是确定的”），对账要明确两级——“确定的改（孤儿转 FAILED）+ 不确定的只报”，否则对账会退化成只能看不能用的摆设；③ 对账的判据本身会 B 族化：它比对的两份数据（project.task_ids vs 磁盘任务文件）都可能没人写，判据失效时对账**全绿地**瞎着——所以对账交付时必须同时交付“它的输入谁保证会写”的答案（性质 #12）。

3. **全量改 420 处（你们评：⚠️ 中）——我评：降为低，分两步走**。“先分类再动手”是对的，但分类的产出不该是“改哪些”，而是“清零哪些、白名单哪些”。按风险分：门禁/校验路径（validator、_review、_exec 的 QA 段）和记账路径必须清零；日志周边、纯展示、可选增强进白名单挂着。全量清零是把 420 个判断外包给未来的自己。
4. **线程池包一层（你们评：✅ 中高）——同意方向，收窄预期**：`pool.submit` 在正常路径几乎不会抛（唯一常见抛法是 executor 已 shutdown），真正的收益不在“submit 不抛”，在**结构上保证每个 future 必然被 reap、每个异常必然有主**。新静默：wrapper 自己的兜底如果把 execute 异常吞成一条告警而不影响 verdict，会造出“任务失败但判定通过”——verdict 判据必须显式含“executor 异常”这个三态（§44 的形状）。

## 五、第 5 题：你们最大的误判可能是什么

**写下来的判断里最可能错的，是第四节加粗那句：“成熟方案只能治 A 族；B 族治不了。”**

错一半。B 族的定义是“判据从一开始就不成立，而没有人验过它”——它的失效方式其实是**可枚举**的：判据的输入没人写（§44/§60）、守卫有盲区（§64）、计数器无清零事件（§45）、把上报口径的缺失当事实（§59/§63）、常亮=判据与配置脱节（§62）。这五种的治法是同一样东西：**变异验证**（“把 bug 放回去，判据真的会红”）。你们已经在做（9.2），只是把它当成了“修完的交付标准”，没认出它就是 **B 族的治法**。B 族确实不能靠换引擎治——但它能靠验证文化治，而验证文化是可以制度化、工具化、写进 CI 的（第 4 题第 2 条）。若这个判断错了——B 族真的不可治——结论会变成：接受静默失败持续新增，全部投入放在缩小爆炸半径（对账+守卫+watchdog），排序不变，但预期要从“能治”改成“能兜”。

第二候选（数据层面的，〔推断〕）：**用“事故库 30% 是静默失败”推“架构级病灶”有选择偏差**。事故库是“疼过的教训”的集合——静默失败特别疼所以特别容易被记下来，普通崩溃修完就忘、不进库。30% 是“被记住的事故里”的占比，不必然等于“系统中失败”的占比。这不推翻结论（静默失败确实是你们的头号形状），但用它论证“该换架构”时要打折扣——好在你们的结论也没往“换架构”推，所以这条偏差暂时没造成伤害。

第三候选：材料第六节教育读者“别被假前提带偏”，然后 8.2 自己带着一个假前提（见第〇节）。这不是单点笔误——它暴露的是“从权威文档抄结论”被当成了“核过代码”。**最该立的规矩**：文档里每一条事实断言，要么带 file:line 且被测试钉住，要么明写“未核”。

## 六、第 6 题：“默认怀疑”怎么落地才不会退化成告警淹没

先给反答案：不是“给 561 个 except 都加告警”，也不是“提高告警质量”这种口号。你们的仪器其实已经建了 80%（witness 按 key 聚合、三态字段、F821 守卫、reconcile、watchdog、heartbeat 落盘——我逐一核过都在），**缺的不是仪器，是预算和台账**：

1. **告警预算当门禁**：新增任何告警前必须答三问——聚合 key 是什么、见到它要做什么、它自己失效了谁知道。三问答不出，不许加。这条写进 CLAUDE.md，跟“守卫要变异验证”同级。
2. **常亮台账**：`alerts.jsonl` 现在累积 2255 条。给 `alert_summary()`（`witness.py:98`）加两列：`first_seen` / `days_chronic`。一个 key 常亮超过 N 天，自动从“事件流”升级成“判据审查事件”（§62 已经给出理论：常亮 = 判据与配置脱节；现在缺的是把它变成机器动作而不是人的记忆）。常亮 key 只有两个去处：修判据，或显式白名单（写理由+复审日期）。
3. **怀疑要落在“判据的台账”上，不是“告警的数量”上**。每个判据（守卫、对账、三态字段）登记一行：它防什么形状、在哪些输入上会沉默（性质 #11）、上次变异验证是什么时候。§64 的教训原样适用：判据过了要再问“它在哪些输入上沉默”。这张表比多加一千条告警都值。
4. **分层怀疑**（你们的 9.1 已经写对了，落地时别丢）：能静态扫的不上运行时（except 形状、未定义名、schema 字段集），能聚合看的不上实时（常亮、漂移、恒空），只能埋点再跑的才埋点（竞态、时序）。同一形状两层都覆盖是浪费，一层都没有是欠债。

5 处 strand_guard 是**按形状人肉扫**出来的——人肉扫的意思是：第 6 处 submit 写出来时没人拦。判：真。治法就是你们的方案 4（pool wrapper）：submit 只许走一个口，口内 try + strand_guard + 必登记，把“人肉扫”变成“结构保证”。成本一天。**不需要 async**（理由见第 2 题第 5 条）。

**6. 零数据库 —— 这个规模下的合理取舍。判：不是你们的主要债务，且与你们最疼的三案全部无关。**
逐案检验（这是判它最硬的方法）：
- 案例 A（三个函数没 import）：DB 治不了——这是代码错误，什么存储都拦不住；
- 案例 B（跑得最多的路不写清单）：DB 治不了——`constraints_checklist` 合法值就是空数组，NOT NULL 管不了“合法地空着”；
- 案例 C（先写状态、后登记 future）：DB 治不了——不变量横跨内存（future 注册表）和磁盘（任务 JSON），事务管不到进程内对象图。
DB 真正能治的只有两小类：**跨进程并发写坏 JSON**（§46，已被 pid tmp + 原子写修掉）和 **schema 漂移静默吞数据**（§40/§66：删字段→`TypeError`→`list_all` 静默跳过）。而第二类的正解不是 DB，是**读时 fail-closed 校验**（strict dataclass 载入 + 载入失败必 warn + 字段集漂移守卫——§61 的两份 schema 漂移检查你们已经建过样板）。反过来，零 DB 换来的 grep-ability 是几次关键排障的实际倚仗：案例 A 的 6 条 NameError 就是靠“聚合视图扫 alerts.jsonl”浮出来的，不是靠任何数据库。
**真正的债不是“没有 DB”，是“JSON 没有读时校验门禁”**——把门禁补上，DB 的大部分收益就拿到了。升级触发条件建议现在就写下来：若“多进程并发写”成为常态（后端 + CLI + role_probe 三个写者已经存在）或单文件状态大到读不动，→ 上 SQLite（单文件、零服务、保留可 grep 性）。今天不值。

**6 条之外的补充判断**〔推断〕：8.7 六条全是“推进/状态”层的，没有一条指向另一处我核实到的集中度——`web/app.py` 2265 行、全仓 except 最多的文件（我数 54 处）、audit/SSE/告警/心跳四个观测入口都散在它里面。观测层是你们最依赖的层，它自己的可观测性（“仪器坏了谁知道”）目前靠零散的 try+warn。这不是换架构的理由，是“方案乙清零优先级最高的文件应该是 app.py”的理由。

### 8b. 这个架构要不要改？改哪层？

**总判：不换进程模型。零件要拧，而且大部分已经在拧了。**

理由（事实链）：三条最疼的案例（A/B/C）全部与进程模型无关——一个是没 import，一个是路径没写，一个是内存-盘之间断了半步；6 条结构问题里 5 条半能在现进程模型内修（见 8d）；而换进程模型的迁移动作本身（新旧双写、口径切换、验证基线重铺）是静默失败的高发期，对单人维护项目是负期望。

**能在这个进程模型里改的（全部真问题的缓解都在这层）**：
1. phase-driver 表 + 调用点守卫（治 1+3，一天）；
2. 对账进忙时（治 2 残余，一天）；
3. pool wrapper 收口 submit（治 5 残余，一天）；
4. JSON 读时校验层（治 6 的真债，两天）；
5. silent-except 守卫 + app.py 优先清零（治观测债，一天建 + 分期清）；
6. 常亮台账 + 告警预算（第 6 题，半天）。

**必须换进程模型才能改的：只有一件——“线程杀不掉”（§59）。**
超时收割只能放弃等待，在飞的模型调用继续烧钱、继续改盘；协作式取消、单调用封顶、预算倒推（§63/§67 已落）都是缓解不是根治。要硬杀只能把执行器挪进独立进程（agent CLI 那路本来就是子进程；HTTP 那路在进程内线程）。**判：现在不值**——§67 的账算得很清楚，剩下的暴露面是“最后那次在飞的调用”，且已有 sidecar 把账兜成下界。触发条件写下来：再出现一次“超时后仍在花钱/改盘且协作取消追不上”的真机事故，才升级为独立进程执行器。

**还有半个候选（诚实列出，反对现在做）**：Web 与调度循环分进程。现在 Flask、loop、pool 同进程，loop 卡死时 `/health` 照样报活——你们已经用 `loop_tick.json` + 外部 watchdog 绕开了它的大部分伤害（我在 `app.py:499-505` 核到注释明确写了为什么不做心跳线程）。分进程要付 IPC 和状态传递的代价，买的是“loop 死了 UI 还能看”——watchdog 自动重启基本等价，不值。

### 8c. 有没有更好的架构？——用你们自己定的硬标准判：没有及格的候选

你们立的标准的原文：“**一个好架构应该让一批补丁直接作废，而不是让所有补丁照样都得打。**”我拿两个候选过这个标准：

**候选一：单写者 + 水位对账（K8s controller 式）**——loop 成为唯一状态推进者，事件只负责叫醒，每 tick 从盘重算“现在该发生什么”。
判：**这不是换架构，这是你们方案 1 的完全体。** 它“作废”的补丁：零——#1（对账）不是被作废，是被**升级成架构本身**（一周的活变成一个月的活）；#4（pool wrapper）变薄（单写者顺序化后 future 少）；#2（静态守卫）、#3（分类清零）、#7（性质清单）完全不受影响。

**候选二：Temporal / 事件溯源**（每步先落事件再往下走）。
判：作废 #1（对账内置）和 #4（引擎管 future 挂起与重试）——**7 条里作废 2 条**，其中 #1 本来就是你们一周能自己做完的。带过去的：静态守卫（代码还是会写错）、全量分类（except 还是要一个个人肉判）、B 族判据（引擎不校验你的判据语义）、模型输出不可信、观测口径（每条调用路径的记账还是各自接）。**批**：作废的是 A 族里最便宜的两条，带过去的是疼的全部。

**结论**：按你们自己的标准，两个候选都作废不了“一批”补丁——换设计在这个仓库**过不了你们自己定的测试**。修零件赢。但要说清“修零件”的最高形态是什么：**不是打补丁，是把已经付过学费的教训浇进结构里，让对应的那条补丁退休**——strand_guard（教训 §65）、effective_constraints 兜底（教训 §60）、字段集漂移守卫（教训 §61）、pid tmp（教训 §46）都是这个形态。你们真正该“换”的不是引擎，是把更多这类教训从“人肉纪律”搬进“结构约束”——方案甲乙丙全是这个方向。
