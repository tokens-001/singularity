## 一、背景

**奇点**：单体 Python 的 AI Agent 调度平台，多模型按角色协作完成软件开发任务。
约 28,600 行 Python + 3,900 行前端 + 16,700 行测试（核于 2026-09-12）。零数据库，状态全在 `.qidian/` 下的 JSON 文件里。

流程：立项 → 调研 → GATE1(人审) → 架构 → GATE2(人审) → 执行 → 集成合并 → GATE3(人审) → 交付。

**项目的核心资产不是代码，是 `docs/防御模式.md` 里 62 条「症状 → 根因 → 规则」** ——
那都是真金白银踩出来的。改这套代码之前必须先扫它。

## 二、问题陈述（**这是重点，别当成"修 12 个 bug"**）

用一天时间在这套系统里挖出 6 个缺陷，09-12 又补了 6 个（见第七至十二条），**没有一个报错**。它们的共同形状是：

> **系统"没做"或"做错了"，但从外面看一切正常。**

3. 在**单体 Python + 零数据库 + 文件持久化 + 明确反对过度设计**的约束下，
   最小可用的方案是什么？

## 三、十二个已证案例

> 前 6 个是 2026-09-11 一轮里挖的；**7–12 是 2026-09-12 从真机跑出来的** ——
> 同一形状、不同位置（11 是读代码挖的，12 是探路轮的死因）。
> **案例 8 至今没定位到根因**，如实标着；末尾另列了两件**至今无法解释**的现象。

### 案例 1：验收被跳过，只活在一条聊天消息里

- **症状**：到了 GATE3（交付审核），项目状态里 `issues` 永远是空数组；没有 QA 报告，没有任何地方说明"验收到底跑没跑"。
- **根因**：两处叠加。
  - `run_test_fix_loop()` 里 `project.issues = []` **写在验收调用之后**，把 `_run_verification()` 刚记进去的东西一并擦掉。
  - `_run_verification()` 在无约束清单时只 `return ["验收跳过 (无约束清单)"]` —— **一个字符串，不落盘**。
- **位置**：`src/singularity/scheduler/workflow.py`（`run_test_fix_loop` / `_run_verification`）
- **已修**：清空移到验收之前；跳过改为写入 `project.issues`。
- **注意**：「跳过」这件事本身可能合理（架构没产出约束清单时确实没得验），
  **不合理的是它不留痕**。

### 案例 2：计数器是单向棘轮 → 用户点一百次都出不去

- **症状**：用户在 GATE2 点「通过」，界面 2 秒后弹回同一个 GATE2，再点、再弹，永远出不去。
- **根因**：
  - `review_failures` 达到上限（2）后，`_run_integration_merge_async()` **在集成合并已成功的情况下**仍然把 phase 打回 GATE2。
  - 而 `review_failures` / `integrate_failures` **全仓没有任何地方重置** —— 只增不减。
  - 于是：批准 → 执行 → 合并成功 → 检查计数器仍超限 → 回 GATE2 → 批准 → …
- **位置**：`src/singularity/scheduler/orchestrator.py`(`_run_integration_merge_async`)、
  `_review.py`(`check_review_fail_limit`)、`project.py`(`confirm_gate`)
- **已修**：人工批准 GATE2 时重置这两个计数器（人工到场兜底 = 自动重试配额恢复）。
- **注意**：这个 bug 的可怕之处是**界面上一切正常**。没有报错、没有红色、
  用户只会以为自己点错了，然后反复点。

### 案例 3：后端花钱生成了报告，前端一个字都不显示

- **症状**：GATE3 的标签写着"请审核交付物"，屏幕上显示的是**几周前的**调研报告和架构方案。
  交付物本身（QA 报告、安全审计报告）看不见。
- **根因**：
  - 后端确实生成了：`_run_verification()` 花两次 LLM 调用产出 `qa-report.md` / `security-report.md`，
    还存了结构化的 `qa_report.json`，连 GATE3 打回的路由逻辑都读它。
  - 但 `ProjectState.to_dict()` 里**没有 qa_report 这个字段**，前端拿不到。
  - 而且 `GET /api/projects/<id>/traceability` 是一个**专门为 GATE3 写的端点**
    （docstring 明写 "GATE3: 返回需求追溯表 + 符合性检查结果"）—— **前端从来没有调用过它**。
- **位置**：`project.py`(`to_dict`)、`web/app.py`(traceability 端点)、`web/frontend/src/components/chat/GatePanel.tsx`
- **已修**：端点带出 `qa_report`；前端在 GATE3 拉取并渲染验收面板。

### 案例 4：状态文件被写坏 → 项目凭空消失

- **症状**：一个项目从界面上消失，没有任何提示。文件还在磁盘上。
- **根因**：
  - `save()` 用原子写：写 `<id>.tmp` → `os.replace()`。
  - 但 tmp 是**确定性路径**，而 `_LOCK` 是 `threading.RLock()` —— **只挡同进程的线程**。
  - 后端调度循环和 `tests/integration/role_probe.py`（独立进程）会同时 save 同一个项目：
    A 的 `replace` 成功后 tmp 就没了，B 的 `replace` 撞 ENOENT；或两边写入交错。
  - 结果是项目 JSON 末尾多出一个 `}` → `json.loads` 失败 → `list_all()` 静默跳过 → 项目消失。
- **位置**：`src/singularity/scheduler/project.py`(`save`)
- **已修**：tmp 路径带 pid。
- **注意**：`save()` 的注释显示，作者**专门加过锁**来防"两个线程共用同一 tmp"——
  **防住了线程，漏了进程**。

### 案例 5：扫描静默少一个模型

- **症状**：用户问「deepseek 怎么只能扫描出一个模型」。
- **根因**：模型扫描有两道过滤门：
  1. 在能力快照里吗？
  2. `_is_major_model(id)` 认得吗？
  
  白名单里 DeepSeek 那条是 `r'^deepseek-v\d+'` —— **要求 `v` 后跟数字**。
  而 `deepseek-flash` 既没有 `v` 也没有数字，两道门都没过 → 被丢掉。
  （同一份白名单里，Anthropic 那行**专门写了** `r'^claude-opus'...` 处理"名字不带代际"的情况。）
- **位置**：`src/singularity/scheduler/api_store.py`(`_is_major_model`、扫描主循环的过滤条件)
- **已修**：补 `r'^deepseek-(flash|pro|chat|reasoner)'`。
- **注意**：这个白名单**已经被补过两次**（一次是精确版本号滞后，一次是这次）。
  每次都只是补一条 pattern。**它会不会一直漏下去？** 这是设计问题的一部分。

### 案例 6：错误信息把原因吞了

- **症状**：点任务卡片上的「在文件夹中显示」，弹一句「定位失败」，没了。
- **根因**：
  - 前端 `.catch(() => toast('定位失败'))` —— **把后端返回的具体原因整个丢掉**。
  - 而后端确实有话说：接口把路径限制在**奇点自己的仓库**（`PROJECT_ROOT`），
    但项目产出的文件在**项目仓库**（`repo_dir(project_id)`）里，两个完全不同的目录 → 404。
- **位置**：`web/frontend/src/pages/Chat.tsx`、`web/app.py`(`api_files_reveal`)
- **已修**：前端带 `project_id`，后端按来源选根目录；toast 改带原因。

### 案例 7：任务超时被杀 —— 钱、痕迹、动作记录三样一起消失

- **症状**：任务撞 900s 超时被"杀"。trace 里 `changed_files: [] / elapsed: 0 / tokens: 0 /
  agent_output: ''` —— **看上去什么都没干**，而磁盘上 worktree 里文件是写全的。
  更怪的是：超时**8 分钟后**告警里还在刷 `collect_changes: [Errno 2]`（那个 worktree 早被删了）。
- **根因**：三层叠加，每一层都是"某条路没接上"，没有一处报错。
  - `concurrent.futures` 的 timeout **只让等的人放弃，杀不掉已经在跑的线程** ⇒
    "超时"不等于"停了"，线程还在改磁盘、还在调 API（**=还在花钱**）。
  - 记账的唯一入口在 `finalize` 那条路上，而超时分支**直接判失败、根本不进那条路**
    ⇒ 花掉的钱一条不落。执行器那个累计值在它线程里，超时方 `fut` 已被 pop，**本来就取不到**。
  - `tool_events` 平时只在内存和 SSE 里过一遍、**从来不落盘** ⇒ 超时任务的
    `tool_batches.turns` 恒为 0，"这一轮到底调了几次工具"根本没法算。
- **位置**：`orchestrator.py`(`_reap_futures` / `_salvage_timed_out`)、
  `_task_runner.py`(`_archive_task_outcome`)、`_exec.py`
- **已修**：执行器**边跑边把累计用量和工具事件落盘**，超时方读回来。
  ⚠️ **补出来的是下界**（超时那一刻正在飞的那次调用不在里面）—— 这点写进了产物里。
- **注意**：这三样**不是一个 bug**，是同一个形状（"正常收尾那条路没走到"）的三种表现。

### 案例 8：一份值写进去了、又没了 —— **至今没定位到是谁覆盖的**

- **症状**：项目跑完，机械检查的产物 `.qidian/projects/<id>.machine-checks.json` **不存在**。
  而**同一份 json 里** `architecture.constraints` 完好有 8 条，`constraints_checklist` 却是 `[]`。
- **根因**：`_run_execution` 里明明 `constraints_checklist = architecture["constraints"]`
  紧跟着 `save()`，**两个端点都验证过**（"应该写进去"和"盘上是空的"），
  **中间那一步没抓到**。全仓只有两处写它，第二处是**死代码**，所以覆盖只可能发生在
  save 那条线上 —— 而那是**时序竞态**。
- **位置**：`_workflow_phases.py:567`（唯一的活写入点）、读取点 `workflow.py`(`_run_verification`)
- **状态**：⚠️ **只修了症状，根因仍未定位**。读取时加了兜底（清单空而架构里有就用架构那份），
  **并且兜底会出声告警** —— 那条告警就是"根因还在"的信号。同时留了探针。
- **注意**：**读代码定不了这个案**。这是本材料里"为什么需要自证层"最直接的证据。

### 案例 9：一个功能"在代码里、有测试、但从来没执行过"

- **症状**：没有任何症状。功能真的没跑过，但**没有报错、没有告警、没有日志**。
- **根因**：判据挂在 `_consolidate_calls % 10 == 0` 上，而 `_consolidate_calls` 是
  **模块级变量、后端每次重启归零** ⇒ 只要单个进程生命周期内的调用次数 < 10，
  这一步**永远不触发**。实测那晚重启 4 次，没有一个进程跑到 10。
  确认方式：查它的产物字段，**全是 `None`**（有个任务有 3414 字真轨迹也没被处理）。
- **位置**：`_memory_consolidator.py`
- **已修**：判据改成**落盘**（重启不清零）+ 时间兜底。
- **注意**：**这一类的检测方式不是"看报错"，是"看产物里那个字段是不是永远是默认值"。**
  这一条对第五节的"自证层该管什么"是直接输入。

### 案例 10：告警常亮 ⇒ 真问题时被淹在噪声里

- **症状**：一次正常跑动里，三条"自己评自己"的告警**每轮都报**。
- **根因**：模型池只剩 2 个，而 `planning` 恰好用满这两个 ⇒ 委员会 = 整个池 ⇒
  裁判类角色必然撞上"自己评自己"。其中一条能兜住（剔掉写手换人），
  另一条**换不动**（兜底表里两个模型都被停用 ⇒ 表跟池**零交集**）。
- **位置**：`execution_judge.py`(`_V2_EXTRACT_FALLBACKS` 等)
- **已修**：扩池 + 把提取员指到委员会之外。
- **注意**：**"每轮都报"和"从不报"一样坏**。判据跟配置脱节时，告警会变成背景噪声，
  真出问题时没人会注意到。这也是自证层要处理的：**它得能区分"持续异常"和"配置使然"**。

### 案例 11：同一份契约有两个定义点 ⇒ 字段静默消失

- **症状**：重流程（开委员会）产出的架构里，8 条约束的 `check` **全是**结构化的
  `{"argv":[...],"expect_exit":0}`，但 `covers` **一条都没有**（**字段名都不存在**）。
  于是覆盖率只能报"8/8 条需求没人验"。
- **根因**：系统里**有两份架构 schema，内容不一致** ——
  - 架构师**席位**的 prompt（`workflow.py` `_ARCHITECT_CONTEXT`）：有 `covers`，`check` 是对象
  - 委员会**定稿**用的 schema（`execution_judge.py` `_ARCH_SCHEMA`）：**没有 `covers`**，`check` 是字符串

  而**最终架构是融合稿** ⇒ 定稿模型**根本没被告知有 `covers` 这个字段**。
- **为什么 `check` 却对了**（这是最容易误判的地方）：定稿 prompt 里带**各成员原稿全文**，
  原稿里是结构化的 ⇒ 它**照抄了形状**。**不是 schema 起了作用。**
  ⇒ 判"prompt 有没有生效"，要挑一个**原稿里没有、只有 schema 里有的字段**看。
- **位置**：`workflow.py:41`(`_ARCHITECT_CONTEXT`)、`execution_judge.py:205`(`_ARCH_SCHEMA`)
- **已修**：补齐字段 + 说清语义；并留了一条**漂移检查**
  （两份 schema 的字段集必须一致，变异验证过会红 —— 光修一次不解决复发）。
- **注意**：**同一份契约有两个定义点就一定会漂，而且漂的是其中一份** ——
  出问题时你盯着 prompt 找原因，**根因在另一个文件里**。

### 案例 12：错误信息**指向了错的方向**

- **症状**：任务报 `worker 异常: any 层所有 agent 均失败: <模型>: JSONDecodeError:
  Unterminated string`。读起来像"模型吐了个坏 JSON"，于是去查模型、查 prompt、查 max_tokens。
- **根因**：**不是模型的问题** —— 是一个**被截断的 SSE 流式分片**废掉了整条 fallback 链。
  报出来的错指向 JSON 解析，跟真正的原因（传输层帧被切断）**不在一个地方**。
- **位置**：`executors/openai_agent.py`
- **已修**：坏帧不再打死整轮。
- **注意**：**错误信息指向错的方向，比"没有错误信息"更费时间** ——
  它让你在一个错误的地方找很久，而且中间每一步看起来都合理。
  （跟案例 6 不同：案例 6 是把原因**丢掉**，这条是把原因**指错**。）

## 四·五、方法学：为什么"跑了几轮"也定位不到根因

> 这一节是 2026-09-12 实测出来的，**直接关系到第五节的第 2 问**（为什么补丁式修复反复失效）。

- **真机跑能回答"哪一步坏了"，回答不了"为什么坏" —— 只要坏在中间过程。**
  因为**一次跑只留终态**：写入点和读取点事后都能看见，但**"被谁覆盖的那一步"没记录**，
  事后翻不出来。案例 8 就是这样 —— 跑完就知道清单是空的，但**跑的时候没记那一步**。
  **这跟跑几次无关：跑 100 次也一样，只要没埋点。**
- **反过来，按"形状"静态扫一次，比跑几轮产出高。**
  同一个形状（"判据会被已提交的改动骗"）此前**被修过两次**，每次只修眼前那一处；
  2026-09-12 改成**按形状全仓扫**，**一次抓出 3 处** ——
  而那 3 处是任何一次真机跑都没找出来的（它们不会每次跑都触发，也不会自己报出来）。
- **⇒ 两类要分开打，别混**：
  - 判据撒谎 / 功能从不执行 / 静默降级 → **静态扫**能扫出来（案例 5、9 属此类）
  - 竞态 / 时序 → 静态扫**够不着**，只能**埋点后跑**（案例 8 属此类，所以至今没定位）
- **还有一条**：那些标着「已修」的，多半**只在单元测试里验过**。
  同一个系统在**桩测试全绿**的同时，案例 7 / 8 / 9 **全都活着** ——
  **桩测试测不出时序、测不出沉默**（它把外部依赖都 mock 掉了，而 bug 恰恰在接口的时序上）。
