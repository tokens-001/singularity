# 最小闭环方案 —— 让 REVIEWING 能自动回一次 EXECUTING

> 2026-09-18 · 状态：**方案，没写代码、没验**
> 起因：讨论「奇点自身的流水线符不符合软件开发的归路」时定下的判断 ——
> **路修齐了，回路没修。** 本文只解决回路，不碰别的。

---

## 一句话

**不重建 conductor。** 复用已经存在、已经跑通的 `handle_gate3_reject`，
只是在它前面加一个「自动点一次按钮」的条件。

---

## 一、为什么不重建

6/27 `d3c117e` 砍掉的是两样东西：

- `conductor.py`（303 行）—— **AI 自动推进门**
- `judge_monitor.py` —— AI 裁判监控

砍的是「**AI 决定要不要过门**」。这一环**今天仍然不该自动** —— 门是人给的输入。

现在缺的不是这个，是「**AI 发现实现写错了，能不能自己回炉**」。两者不是一回事。
所以别复活 conductor，那是把砍对的东西又装回去。

## 三、最小设计

改动只有一个函数：`run_test_fix_loop`，在 `_run_verification` 之后、
`set_phase(GATE3)` 之前插一个分支。

```python
# 伪码，不是最终写法
if _auto_rework_allowed(project):
    project.add_lineage({"action": "gate3_rejected", "auto": True, ...})
    return handle_gate3_reject(project, agents,
                               feedback="自动返工: QA 判实现层不合格",
                               auto=True)
project.set_phase(Phase.GATE3, "执行完成 → 验收报告完毕, 等人工审")
```

`_auto_rework_allowed` 四个条件全真才放行 —— **每一条都对应一次踩过的坑**：

| 条件 | 为什么 |
|---|---|
| 本轮 `verification_ran`（不是 `verification_skipped`） | 验收被整段跳过时，重跑执行层**修不了**「架构没产出 constraints」⇒ 纯空转烧钱 |
| `fix_route == "impl"` | 只自动回实现层。`design` 要清空架构重跑多模型委员会（实测 621 秒），且「理由进提示词 ≠ 模型照做」**已实测证伪**（`uncovered [7,8,9]` 三轮一字未动）⇒ 自动回设计层大概率白烧。`note` 本来就不阻断 |
| 本轮自动返工次数 < N（默认 **1**） | 防无限循环。N=1 的依据：上面那次实测说明「同一件事第二次会成」**没有证据支持** |
| 开关开着（`QIDIAN_AUTO_REWORK`，`0` = 关） | 出事能一句话关掉 |

---

## 四、四个刹车（缺一不可）

1. **轮数上限默认 1** —— 读 `lineage` 里 `auto: True` 的条数即可，
   **不新增状态字段**（少一个字段 = 少一处能对不上的地方）
2. **必须留痕** —— lineage 那条带 `auto: True` + route source。
   **这条是硬的**：查「这轮是它自己回的还是我点的」必须一眼看得出来。
   ⚠️ 现状 `handle_gate3_reject` 一律写 `action: "gate3_rejected"` —— 不改的话，
   自动和人工在账上**长得一模一样**，正好是「声明 vs 实际」那一族
3. **必须报到 GATE3 面板** —— 自动返工一轮仍不过时，issues 里写
   「**自动返工 1 次后仍不过**」。否则人以为是第一轮
4. **不自动点任何门** —— GATE1/2/3 一道都不碰

## 五、判据（怎么算验过）

⚠️ **必须真机，单测证明不了这套。** 单测只能验 `_auto_rework_allowed` 这个纯函数。

✅ **通过（四条全要）**：
1. `lineage` 里出现 `auto: True` 的 `gate3_rejected` 条目
2. 项目 phase 回到 `executing`
3. **回到 executing 之后，任务真的被派下去了** ← ⚠️ 见下，**这条最大**
4. 全程**没有任何** `gate-confirm` / `owner_confirm` 记录

❌ **反例（也必须成立）**：
5. 第二轮仍不过时**不再自动回**，老实升 GATE3
6. `QIDIAN_AUTO_REWORK=0` 时一次都不回

### ⚠️ 第 3 条是本方案最大的风险，别跳过

`project.py:38` 那条判据的原话：

> 判据不是「落到哪个枚举」，而是「**落过去之后项目还会不会动**」

回 EXECUTING 只是改了个 phase。真正派活得靠**调度循环**
（`orchestrator.py:884` 那个 `executing` 分支）。

**调度循环没开 ⇒ 自动返工 = 把项目扔在一个不动的地方**，
而且比「停在 GATE3 等人」**更糟** —— 人在 GATE3 至少看得见，停在 EXECUTING 看不见。

⇒ 两条路选一条：
- 要么在 `_auto_rework_allowed` 里**再加一条「调度循环在跑」**
- 要么接受「只在你跑真机时才生效」，并把这件事写进方案文档和代码注释

**没实测过。** 这条判据就是为它准备的。

## 九、2026-09-20 落地记录

**用户拍板：先补护栏再做。** 护栏 = §五 第 3 条那个最大风险（循环没开 ⇒ 项目被扔在一个不动的地方）。

### 落地的

| 方案里说要的 | 落地在哪 |
|---|---|
| 抽 `_resolve_fix_route()`（**搬，不复制**） | `workflow.py`：从 `handle_gate3_reject` 里**原样搬出来**，两处共用同一把尺子 |
| `_auto_rework_allowed` 四个条件 | `workflow.py`：纯函数，返回 `(结论, 理由)` —— 能单测 |
| `run_test_fix_loop` 加分支 | ✅ **另外把"为什么没自动"也写进消息** —— 不然"没自动"和"没走到"在界面上长得一样 |
| 留痕（自动 vs 人工分得开） | `handle_gate3_reject(..., auto=True)` 写 `auto: True`；**全仓只有这一个写入点** |
| 开关 | `QIDIAN_AUTO_REWORK=0` 关（**默认开**，按方案原文当"出事一句话关掉"用） |

### 🔴 护栏加在哪儿（§五 第 3 条那个风险，现在是第 ⑤ 条判据）

`_auto_rework_allowed` 的第五条：**调度循环在跑才放行**。

读的是 `_hooks.loop_status()` —— 那是 scheduler 找宿主（web/CLI）要"循环在不在跑"的**既有通道**
（`scheduler` 不该 import `web`，分层倒挂会造 import 环）。

⚠️ **"查不到"按"没在跑"处理**：无头 / CLI 跑时 `_hooks` 没注册，回的就是 `running: False`
—— 而那条路**本来就没人派活**，所以"不知道"和"没在跑"在这里是同一个结论（不是偷懒的兜底）。
