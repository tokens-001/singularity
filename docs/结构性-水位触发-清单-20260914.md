# 结构性那条：边沿触发 → 水位触发 · **落点清单**（2026-09-14）

> 起因：`OPEN.md` 里那条"结构性"说 —— 现在整套驱动是**边沿触发**：派发那一刻接一次、
> 之后**不再回头看**。成熟做法是**水位触发**：事件只负责叫醒，**判断永远从盘上当前状态重算**。
> 第一个落点（孤儿探测）已做（`dcbe4a4`）。**剩下的先列清单，别见一处改一处。**
>
> 这份就是那份清单。**只列，不动代码。**

---

## 0. 分类判据（先定尺子，再分类）

每条都问同一句：

> ### **"漏掉的那一刻，事实在哪？"**

| 事实的位置 | 归类 | 为什么 |
|---|---|---|
| **已经落盘**（任务文件 / sidecar / trace / alerts） | **该改成水位** | 事件只是叫醒闹钟。闹钟没响 → 下一轮重读现状**自己就自愈了**。改成每轮/节流重算，风险接近零。 |
| **只在内存里 / 只在那一刻的手里** | **必须留在事件侧** | 那一刻是**唯一的机会**。改成水位也重算不出来 —— 要么补持久化，要么认了它只是通知。 |
| 事实在盘上、但**登记动作**只在那一刻做 | **该改成"登记也重算"** | §65 那一族：改状态 → 登记的中间断了就留下孤儿。修法不是加 try，是**让登记变成派生数据**。 |

**这一条判据是本清单的主轴** —— 它把"看起来都像"的十来处切成了两类，
而这两类的**修法完全不同**（一类去改触发条件，一类去补落盘）。
⚠️ `§65` 原话说的是"状态和登记要么原子、要么失败可回滚"，那是**第二好的解**；
**第一好的解是"登记根本不该独立存在"**（能从盘上推出来就别存）。

## 1. 已做的样板（照它改）

**孤儿探测 `_warn_orphan_running`**（`orchestrator.py`，`dcbe4a4`）：

- 改前：只在"队列彻底空下来"那一刻调一次 ⇒ **任务一个接一个来时永远走不到那个分支**。
- 改后：**每轮对账**（节流 `_ORPHAN_SCAN_INTERVAL_S`），把"活任务表"传进去，
  判据仍是**精确的"不在表里"** —— 不是"多久没动静"那种超时猜。
- **样板的三条要点**：① 触发从"某个分支"挪到"每轮 + 节流"；② 判据必须**精确**（能全搜就全搜，
  别退化成超时猜测）；③ **只报不改**（自动"纠正"会把真问题抹平成假的一致）。

## 2. 🅰 该改成水位（事实已在盘上 —— 改了风险接近零）

### A1. `reconcile_projects` 的**触发**（★ 最该做的一个）

| | |
|---|---|
| 文件 | `web/app.py` 的 `_loop_worker`；函数本体在 `orchestrator.reconcile_projects` |
| 形状 | **只在某个分支里对账一次** |
| 现在的触发 | `if count == 0:` → `if idle_ticks % 100 == 0:` ⇒ **队列空 + 连续空转满 100 轮**（~5 分钟） |
| 漏掉的那一刻 | else 分支里 `idle_ticks = 0`。**只要持续有活，计数永远够不到 100** ⇒ 对账**一次都不跑** |
| 事实在哪 | **盘上**（它本身就是"从盘上重算 vs 状态说的"的比对器）—— 典型的水位逻辑 |
| 症状 | 状态漂移（`task_ids` 指向已删任务 / phase 与 lineage 对不上 / 预算超支）**无限累积**，而这是设计上**唯一**的漂移探测仪。**最该对账的时候（忙）恰恰不对账。** |

**✅ 我核过**：`grep -rn "reconcile_projects" src/` 只有**一个**调用点（`app.py`），
就在上面那个 `count == 0` 块里；else 分支确实 `idle_ticks = 0`。

**讽刺的是**：**同一个 if 块里**，孤儿探测今天已经改成水位了，对账**没跟上** ——
所以这条不是"新发现"，是**第一个落点做了一半**。

**最小改法**：把这段从 `if idle_ticks % 100 == 0:` 里**挪出来**，和孤儿探测同一个节流节奏
（对账比孤儿探测贵，可以给它单独一个更长的间隔，比如 300s）。**代价：极小。**

### A2. `_auto_trigger_test_fix` 的 `_merge_inflight`（两处）

| | |
|---|---|
| 文件 | `orchestrator.py`（`executing` 和 `integrating` 两个分支各一处） |
| 形状 | **先改状态、后登记**（§65 那一族） |
| 现在的写法 | `if proj.id not in _merge_inflight:` → `_merge_inflight.add(proj.id)` → `_get_merge_executor().submit(...)` |
| 漏掉的那一刻 | `submit` 抛（executor 已 shutdown / 解释器 shutdown）⇒ 那条 id **永远不会被清**（清理写在后台函数的 `finally` 里，而那个函数根本没起来） |
| 事实在哪 | **盘上** —— "这个项目该不该合并"能从 `proj.phase == integrating` + "有没有正在跑的 merge" 推出来 |
| 症状 | 此后该项目 `proj.id not in _merge_inflight` 恒为假 ⇒ **集成合并再也不会被派发**，项目无声卡在 `integrating`。外层 `except` 只记一条 `auto_trigger:{e}`，**不回滚这个集合** |

**✅ 我核过**：两处 write-site 的写法一致（`add` 紧接 `submit`）；外层 `except` 里只有
`witness.warn('orch', f'auto_trigger:{e}')`，**没有** `_merge_inflight.discard`；
`discard` 只出现在后台函数 `_run_integration_merge_async` 的收尾。

**两条改法（取舍写在下面，别混着做）**：
- **省事的**（第二好的解）：`add` 挪进 `try`，`submit` 抛了就 `discard` + 出声。3 行。
- **彻底的**（水位版）：不要 `_merge_inflight` 这个集合，每轮重算 —— "phase 是 integrating
  且没有活的 merge 就重新提交"。**代价大得多**（要能问出"有没有活的 merge"），
  **先别选这条**。

## 3. 🅱 该改，但要先想清楚（判据不够精确 / 要动数据模型）

### B1. `task_submit`：**建任务** 与 **登记进 `project.task_ids`** 不原子

- 文件：`scheduler/_api_tasks.py` · 形状：先改状态、后登记
- 顺序：`tracker.create(...)` 落盘 → 然后才 `proj.task_ids.append` + `proj_mod.save(proj)`
- 漏掉的那一刻：中间被杀 / `proj_mod.save` 抛 ⇒ **任务文件在盘上，但项目不认识它**
  （⚠️ 后半句是我从调用点推的：项目页任务数读 `task_ids`、orchestrator 也只认 `task_ids` —— **这两句我没全核，待核**）
- 症状：任务看着是条正常的 pending，**永远不被派发**
- **✅ 我核过**：这段**没有 try/except**，`save` 抛就直接 500、任务留下

**为什么是 🅱 不是 🅰**：三种改法代价差别巨大 ——
1. 回滚（删掉刚建的任务文件）：**脏**，删任务有它自己的一堆连带（反引用清理在 `_api_tasks` 里有一整段）。
2. 先 append 后 create：**做不到**，append 时还没有 id。
3. **把 `project.task_ids` 改成派生数据**（从 `tasks/` 里扫 `project_id` 反推）：
   这才是水位版，**也是唯一能从根上消掉这类 bug 的** —— 但要先扫清谁在读 `task_ids`。

⇒ **先扫读者，再决定**。别急着按 1 改。

### B2. `_heavy_due`：**把"跑过了"记在重活之前**

- 文件：`scheduler/_memory_consolidator.py` · 形状：一次性补救（失败被记成成功）
- 现在的写法：`_heavy_due()` 判 due → **函数内部**就 `_save_heavy_state(0, now)`（计数清零 + 打时间戳）
- 漏掉的那一刻：随后 `system2_extract` / `abstract` / 因果边**抛异常** ⇒ 账上已经记成"跑过了"
- 症状：一次失败让重活**再等 1 小时（或再攒 10 次）**才重试；而告警文本是裸异常串，不会聚合
- **✅ 我核过**：`_save_heavy_state(0, now)` 确实在 `_heavy_due` 返回**之前**执行

**为什么是 🅱**：改法要么把记账挪到调用侧（**动 `_heavy_due` 与调用点的契约**），
要么拆成"尝试/成功"两个字段。两条都得想清楚语义。

## 4. 🅲 **必须留在事件侧**（事实只在那一刻的手里）

### C1. `_push_event` / `_push_task_event` 的事件**传输**

- 文件：`web/app.py` · `tracker.py`
- 事实在哪：**状态已经在盘上**（`transition()` 先写盘再推事件）⇒ 丢的是**通知**，不是**事实**
- **判据**：**通知丢了会自愈**（下次读盘就对齐），所以**它的传输就该是边沿的** ——
  改成水位没意义（你不可能"重算出一条当时该推的消息"）。

⚠️ **但这条有下半句**：C1 **成立的唯一前提是"事实真的已经落盘了"**。
所以这条的真正动作不是改触发，而是**逐条核对每个 `_push_event` 调用点的状态是否已落盘** ——
**只要有一条是"先推事件、后写盘"，它就掉进 A 类**。这次的搜寻里我没把每个调用点都过一遍（**待核**）。

### C2. 取消 / 暂停 / 门禁的即时响应

等人的动作（点取消、点暂停、人审门回话）**必须**在那一刻生效，重算不出来。
**留事件侧，不改。**
