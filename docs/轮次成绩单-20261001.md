## 三、🔴 三个新发现（离线上门查过，逐条标"证实/嫌疑"）

### ① ✅ **证实：`_save_trace` 幂等 ⇒ 被重派过的任务，trace 永远停在第一次 run**

`_exec.py` 开头：

```python
# ponytail: 幂等保护 — 终态路径互斥但防误调用
trace_path = config.TRACE_DIR / f"{task.id}.json"
if trace_path.exists():
    return          # ← 已写过就不覆盖
```

**实测对照**（这一轮 5 个跑过的任务）：

| 任务 | 派发 | trace mtime | 侧车 mtime | |
|---|---|---|---|---|
| T1 done | 2 | 10:11:53 | 10:11:28 | 一致 |
| T2 done | 5 | 10:20:20 | 10:20:19 | 一致 |
| **T3 failed** | **16** | **10:25:24** | **11:06:12** | **stale 41 分钟** |
| **T4 打转** | **20** | **10:25:25** | **11:12:37** | **stale 47 分钟** |
| T5 done | 5 | 10:21:03 | 10:21:02 | 一致 |

⇒ 规律很干净：**一次 run 就完事的（done），trace 是终局的；被重派过的，trace 是第一轮的**。

🔴 **这条正是我上一版结论错的原因**：我拿 `trace.changed_files = ['logstat/filters.py']` 去对
终局判词「无文件改动」，得出"产物白丢"。**那不是两个数打架 —— 是我读了一份过期的 trace。**
（`_save_trace` 的注释写着"终态路径互斥"，可**重派路径下任务根本不是终态** —— 前提不成立。）

⚠️ **伤害面比这轮大**：**任何"从 trace 查重试任务死因"的诊断都会拿到第一次的账**。
h 轮那条"trace.changed_files=[] 而锚上有 186 行"的读法，**也得按这条重看**。
