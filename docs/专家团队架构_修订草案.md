## 【D1】审查阶段失败上限 + 取消"超时默认通过"

**位置**：阶段四表（L118-129）、失败上限表（L472-478）、超时表（L494-499）

**改前要点**：① 阶段四"不通过自动修一轮，还不过升级"——"升级"去向未定义；② 失败上限表无审查行；③ 超时表写"审查 10 分钟，超时默认通过，标记审查不完整"——安全项超时放行。

### 改为（A）阶段四正文（替换 L118-129 的标题与表）

```
### 阶段四：审查（强力模型，AI 自动）

AI 审查。每项检查有独立失败处理，不通过先自动修一轮；累计达到上限一律**降级为人工兜底**（升 GATE2），绝不放行进入验收。

| 检查项 | 谁做 | 模型 | 不通过 |
|--------|------|------|--------|
| 代码质量 | `_review.py` | 强力 | 自动修一轮（计入审查上限） |
| 架构合规 | `validator.py` | 强力 | 打回实现（不消耗自动修次数） |
| 安全扫描 | 安全规则引擎 | 强力 | 标记 → 等待验收阶段安全审计师深度复核（不在此放行） |
| 测试通过 | pytest gate | — | 自动修一轮（计入审查上限） |

通过 → 自动进入验收阶段
任何一项触顶/超时 → **不进入验收**，升 GATE2 人工兜底
```

### 改为（B）失败上限表（在 L478 后追加一行）

```
| 审查自动修不过（代码质量/测试） | 自动修 2 轮 | 仍不过 → 升 GATE2 人工兜底，不进入验收 |
```

### 改为（C）超时表（替换 L498 审查行）

```
| 审查 | 10 分钟 | 超时一律判 FAIL（"审查不完整"），不进入验收，降级人工——打回实现修复或升 GATE2 兜底。安全/合规项超时绝不容许默认通过 |
```

**取舍**：审查"选错代价大"（文档自定标准），却给了最弱的失败处理（超时默认通过）——反向激励。改为强制人工兜底，宁可在 GATE2 卡住让人决策，也不静默放行。上限设 2 轮（比实现的 3 轮更紧），因为审查修不动通常意味着架构/任务拆得有问题，该回 GATE2 而非继续磨。

4 路独立 worktree 必须合并成一份可构建的代码，才能进审查。合并与集成测试失败 = 实现失败，走 D1 上限。

## 【D3】GATE3 打回改为按问题分级路由

**位置**：打回路径表（L180-184）、QA 报告 schema（L303-308）、跨阶段任务依赖（L656-662）

**改前要点**：GATE3 一律回 GATE2 重做架构——为修一个 typo 触发整轮重新规划，并连锁触发 GATE2 上限（2 次→回定义→BLOCKED），把可修项目逼成 BLOCKED。

### 改为（A）打回路径表（替换 L180-184）

```
| 门 | 打回后去哪 | 什么情况 |
|----|----------|---------|
| GATE1 | 回到定义阶段修正对应部分 | 需求不对、方向偏了 |
| GATE2 | 打回具体架构师重做，不改动其他 | 某个架构方案有缺陷 |
| GATE3 | **按 issue.fix_route 分级路由**（见下） | 验收发现问题 |

GATE3 分级路由规则（由 QA 报告 issue.fix_route 字段驱动）：
  - `impl`    → 回实现层修复 → 重跑集成合并 + 审查相关项 → 重测   // bug/warning
  - `design`  → 回 GATE2 重新规划对应模块                                    // 架构性缺陷
  - `note`    → 记录进交付清单，不阻断交付                                  // suggestion
  - 多数 issue 为 impl 而 QA verdict 仍 no_go → 仍回实现层，不轻易升 GATE2
```

### 改为（B）QA 报告 schema（替换 L303-308，给 issues 加 fix_route）

```
输入：架构约束清单 + 代码 + 测试结果 + test_cases.json
输出：{
  "passed": [{"check": "...", "evidence": "..."}],
  "issues": [{"id": "..", "severity": "bug/warning/suggestion", "fix_route": "impl/design/note",
              "file": "...", "description": "...", "suggested_fix": "..."}],
  "summary": {"total_checks": N, "passed": N, "failed": N,
              "verdict": "go/no_go", "verdict_reason": "为何 go/no_go"}
}
边界：不写代码，不修改任何文件；fix_route 是建议，最终路由由 Observer 按 verdict 汇总判定
```

### 改为（C）跨阶段任务依赖（替换 L656-662）

```
实现层 4 个工程师的任务是架构阶段拆出来的

如果验收阶段发现问题：
  → GATE3 按 issue.fix_route 分级：
     impl  → 回实现层，只重做有问题的 task（依赖该 task 的下游一并重测）
     design → 回 GATE2，架构师出修复方案 → 只拆出受影响 task
  → 其他 task 不变，已通过的部分不重测
```

**取舍**：验收阶段 QA 发现的多数是实现级 bug（边界/回归/小功能），不是架构问题。一刀切回 GATE2 既浪费又会误触 BLOCKED。`fix_route` 让路由由数据驱动而非拍脑袋；但路由判定权留给 Observer（按整体 verdict），避免单条 suggestion 拖垮整个交付。注意：fix_route 由 QA 建议、Observer 裁定，仍保留人审在 GATE3 兜底。

## 【S2】明确审查阶段模型档位

**位置**：模型档位表（L148-151）、流程图（已在 D2 新流程图中标注）

**改前要点**：档位表只列 定义/实现=便宜、架构/验收=强力，审查阶段缺档；流程图审查框未标模型。

### 改为：模型档位表（替换 L148-153）

```
| 档位 | 适用阶段 | 要求 |
|------|---------|------|
| **便宜** | 定义、实现、交付 | 快、便宜、够用 |
| **强力** | 架构、**审查**、验收 | 推理强、仔细、贵 |

审查用强力，因为代码审查+架构合规+安全扫描的质量直接决定后续走向，错放行的代价与架构选错同级。

碰撞策略不变：只在选错代价大的地方用多模型。

**取舍**：审查夹在便宜和强力之间档位不明=实现层无法落地。统一用强力最简单；代码质量虽可降档，但审查是一锤子定走向的环节，统一强力避免"代码质量用便宜导致漏判"的风险。交付用便宜（机械打包，无判断）。

## 【S4】测试生成时序修正 + E2E 执行阶段

**位置**：测试策略表（L169-174）、测试用例生成（L509-526）

**改前要点**：① 安全测试用例声称"从安全审计 checklist 提取"，但安全审计在验收阶段，架构阶段时不存在——引用未来产物；② E2E 用例从 state_machine 生成，但实现只跑"单元+集成"、验收是"需求验证+回归+边界+安全"——**E2E 永远不执行**。

### 改为（A）测试策略表（替换 L169-174）

```
| 阶段 | 测什么 | 谁测 | 目的 |
|------|--------|------|------|
| 实现阶段 | 单元 + 集成（核心功能） | 自动跑 pytest | 跑绿才能进集成合并 |
| 集成合并 | integration 用例（跨工程师接口） | 自动跑 | 合并后基线可构建（见 D2） |
| 审查阶段 | 全量回归 + 合规断言 | pytest gate | 不通过自动修，触顶升 GATE2 |
| 验收阶段 | 需求验证 + 回归 + 边界 + 安全 + **E2E** | QA + 安全审计师 | 交付前最后验证 |

审查前测"对不对"，审查后测"全不全/安不安全"。E2E 在验收跑，对照交互 state_machine 验证 success_criteria（如"用户能在 3 步内完成任务"）。
```

### 改为（B）测试用例生成 — 安全用例来源（替换 L515）

```
  ├── 从系统架构师 constraints(security 类) + 通用安全规则库 提取 → 安全测试用例
     （不依赖验收阶段的安全审计——那时还不存在；验收阶段安全审计师在此基础上做深度复核）
```

### 改为（C）验收阶段角色表（替换 L136-138，QA 加 E2E）

```
| QA 工程师 | 需求验证、回归测试、边界覆盖、功能完整性、**E2E（对照交互 state_machine 跑）** | 强力 | 单模型 |
| 安全审计师 | 权限、注入、密钥、依赖漏洞、隐私合规 | 强力 | **3模型** |
```

**取舍**：安全测试用例不能引用尚未产出的 checklist，改从架构阶段的 security constraints + 通用规则库生成，验收阶段再深度复核。E2E 必须有运行阶段——它是验证 success_criteria（"3 步完成任务"这类）的唯一手段，造了不跑等于死代码。放在验收而非实现，因为实现阶段单工程师拿不到完整 state_machine 全貌。

## 【S5】落地顺序重排（消除依赖倒置）

**位置**：落地顺序（L387-411）

**改前要点**：① 先做架构（步骤1-2）再做定义（步骤3），与流程"定义→架构"相反，架构师无 PRD 输入；② 步骤2 测合成器"3 模型碰撞"，但此时只有系统架构师一个，**无东西可融合**；③ 拆解器是合成器子步骤却被埋没，实现层强依赖它。

### 改为：落地顺序（整体替换 L387-411）

```
第 1 步：定义层（Observer + 4 角色）
  改动 → observer_agent.py 挂 4 个 skill + 编排层 Observer schema/切换协议
  验证 → 4 份文档结构完整，Observer 身份切换正确

第 2 步：三个架构师并行（系统/AI/前端，各单模型先跑通）
  改动 → roles.py 三个架构角色 + skills/*
  验证 → 三人各自 schema 输出齐全（此时喂入第 1 步的真实 PRD）

第 3 步：合成器 + 拆解器（编排层）
  改动 → execution_judge.fuse_outputs() + task 拆解器 + context 片段提取
  验证 → 三人真实产出融合出统一架构 + 可执行 task（此时第 2 步已提供真实输入，3 模型碰撞可真测）

第 4 步：实现层（4 工程师 + 核心测 + 集成合并）
  改动 → _exec.py 多 worktree 并行 + 集成合并环节（D2）
  验证 → 代码能跑，集成测试能过

第 5 步：AI 审查
  改动 → _review.py + validator.py + 安全规则引擎
  验证 → 审查报告准确，失败上限/超时降级正确（D1）

第 6 步：验收层 + 交付（QA + 安全 + 交付）
  改动 → D 层挂 QA skill + 安全 skill + 交付打包（S1）
  验证 → 报告够详细含 E2E（S4），人能基于报告判断；交付物清单完整
```

**取舍**：严格按真实流程顺序落地，每步用上一步的真实产出做输入。把"3 模型碰撞"和"拆解器"挪到架构师齐备之后（步骤3），否则测了也是空跑。集成合并随实现层一起做（步骤4），不单独成步——它强依赖 worktree 并行先就位。
