# CI / 发布 / 台账 —— 外派审计的逐条核实（2026-09-19）

> 外派对象给了一份「结论先给」的审计（原文在用户手上）。本文**不是复述它** ——
> 规矩是「它自报的独立性不能信，每条承重的都自己跑过」。下面每条标了**我跑到的数**，
> 和**它哪里说错了**。凡它没提、但核的过程中冒出来的，单独放进 §5。

## 一、最重的一条：CI 从来没绿过，而红的位置把测试屏蔽了

**它说**：113 次运行全 failure，红在 lint，因此测试一次没在门里跑过。

**我跑到的**：

```
gh run list --limit 200 → 117 条，conclusion 全是 failure
时间跨度 2026-09-04T15:59Z → 2026-09-18T17:30Z
```

**它说 113，实为 117**（它取的是某一次 API 返回的快照）—— 结论不变，量级对。

`.github/workflows/test.yml` 的步骤顺序（我读的原文）：

| # | 步骤 | 最近一次 run |
|---|---|---|
| 1 | `pip install -e ".[dev]"` | success |
| 2 | `ruff check src/ --select=E,F` | **failure** |
| 3 | `python3 tests/test_imports.py` | **skipped** |
| 4 | `pytest tests/test_scheduler/ -q --cov=singularity --cov-fail-under=20` | **skipped** |
| 5 | `python3 tests/test_exec_run.py` | **skipped** |
| 6 | `mypy src/singularity/ --ignore-missing-imports \|\| true` | **skipped** |

⇒ **它是对的，而且这就是全部要害**：`ruff` 排在**第二位**，它一红，后面**四步一个都不跑**。
"1645 条测试全绿"是**只在本机成立、第三方通过仓库自己的自动化复核不了**的声明。

### ⚠️ 它这里有两条是错的

**(a) 它建议「门绿之后加 `pytest --cov-fail-under=20`，确认测试真跑到了」—— 那条命令一直在 workflow 里。**
它没读 workflow 原文。这条建议如果我照抄，会做出一个"新增了一个早就有的东西"的空动作。

**(b) `--select=E,F` 在命令行上会重开项目自己 ignore 的规则。**
`pyproject.toml:51` 是 `ignore = ["E501", "B904"]`，而 CI 那条命令跑出来 **E501 有 75 条**
⇒ **CI 在卡一条项目已经决定不管的规则**。（另：路径是 `src/`，Makefile 是 `src/singularity/`。）

## 三、同一个 lint 有两个互不预测的定义

| 入口 | 命令 | 我跑到的结果 |
|---|---|---|
| `Makefile:21` | `ruff check src/singularity/`（走 pyproject） | **1021 errors** |
| CI 第 2 步 | `ruff check src/ --select=E,F` | **757 errors** |

它说 1028 / 762，我跑到 1021 / 757（本机 ruff 0.16.7，`pyproject` 写的是 `ruff>=0.9` 无上限）。
**路径、规则集、ignore 生效性三样都不同** ⇒ `make check`（= `lint test-fast`）此役必然失败
⇒ **仓库自己定义的那个"完成判据"是不可运行的**，所以它不指导任何日常动作。

## 四、三条"看着有、其实不会红"的门 —— 两条坐实，第三条是耦合的

| # | 它说 | 我核的 |
|---|---|---|
| ① | `mypy ... \|\| true` 结构上不可能失败 | ✅ **属实**，workflow 原文就有 `\|\| true` |
| ② | dev 依赖有 `pre-commit>=4.0`，根目录无 `.pre-commit-config.yaml` | ✅ **属实**（`pyproject.toml:34`；`ls` 无此文件）⇒ 声明的本地钩子从未存在 |
| ③ | mypy `exclude` 屏蔽 `executors/`、`neijinglu.py`、`supervisor.py`，而后者是承重墙 | ✅ 配置属实（`pyproject.toml:63`），**但它的推理漏了一半 —— 见下** |

### 🔵 ③ 和 ① 是**耦合**的，它当成两条独立发现写的

`exclude` 让 mypy 看不见那三个文件 —— **而 mypy 现在因为 `|| true` 恒不卡**。
所以在当前状态下，**那个 exclude 一点后果都没有**。
它**只有在你把 ① 真修了之后**才变成"承重墙上的盲区"。

⇒ 这不是"两条缺陷"，是**一条缺陷 + 一个被它挡住的次生风险**。
修 ① 时必须**同时**处理 ③，否则等于没修（把恒绿的假门换成一个只在盲区外生效的真门）。

## 五、它没提、我核出来的

### 5.1 58 个 stash 提交在 main 的祖先链上（它说 1 个）

```
git log --grep="WIP on main" HEAD      → 58 条，2026-06-18 → 2026-09-05
git log --first-parent --grep="WIP on main" HEAD → 0 条
git rev-list --merges --grep="WIP on main" HEAD  → 58 条（全是 merge）
567451d1 parents=[2a287cea 1e46d85d]   ← 两个父
```

⇒ **它低估了 58 倍**，但**性质比它说的轻**：这 58 个**全部是 merge 的第二父**，
**没有一个在 first-parent 主线**上。所以"主线被 stash 污染"不成立，
成立的是"**stash 对象被当成合并来源用了**"——那是另一回事，得单独查（本次没查）。

## 六、我的判断：它对了，但有一处框架问题

**它说的三条必要条件我都认**：能变绿的自动门 / 可指认的版本 / 在版本控制里的工作状态。

**但它的处方顺序我认为要改一处，而且这一处能省掉大部分工作量。**

它建议：**先把 lint 债还干净（317 条自动 + per-file-ignores），再让门变绿。**
理由是"本地绿 ⇔ CI 绿"。

⚠️ **问题**：把 1021 条规则债清干净是**几周的事**，而在这几周里，
**"测试从没在门里跑过"这个真问题一天不解决** —— 我们只是把红从 ruff 挪到别处。

**更省的顺序**：CI 拆成**两个 job**（`lint` / `test`），各自独立跑。
- 一行级改动（把现在的 `steps` 拆成两个 `jobs`，约 10 行 yaml）
- 立刻恢复的**真信号**：测试那一半是绿的、而且是真的绿
- lint 那一半仍然红，但**它红不再掩盖测试**
- 然后 lint 债可以**按目录分批**慢慢还，不阻塞任何东西

⚠️ **不要**改成 `ruff ... || true` —— 那是把红藏起来，本仓 §78 自己写着"假门比没门坏"。
**重排/拆 job 和放行是两回事**：前者让红变得可读，后者让红消失。

**版本那条我完全同意它**，而且它是对的：这是**唯一一条能直接打到"修得比验得快"的**。
成本也确实约等于零 —— 每轮真机开局打个 tag，判据就变成 `git describe --tags`。

**台账那条我也同意**，但有个现实约束：`~/OPEN.md` 被一个 `UserPromptSubmit` hook
每轮 `cat` 给它自己看，路径是硬的。所以**不是搬走，是加一个进仓的镜像**
（或每次真机轮前 `pre-push` 存一份快照）。它说"git mv"，那会打断 hook。

---

## 七、如果只做一件事

**拆 CI 成两个 job。** 理由：它把"第三方复核不了"这个洞堵上，
而这件事的价值**不依赖**其余任何一条先做完 —— 其余五条都可以之后慢慢来。
