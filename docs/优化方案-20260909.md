## #6 通用模型适配层

### 现状（✅ 已核实）
- `models.toml` 能力快照：speed/reasoning/rating/max_turns/strengths/recommended_for
- `_benchmark.py` 一键基准：3 个金标准编码任务（fib/todo/sql），pytest 验收，定档 rating/speed/strengths/max_turns
- `route_learner.py` 动态权重：按历史成功率给模型加权（pick_agent 已用）
- `_build_agent_from_registry`（dispatcher.py:198）：模型不在 agents.toml 时，从 registry + api_store 自动构造 agent（roles=["generic"]、sandbox="worktree"、max_turns=registry 值）
- `for_phase`/`for_tier`/`fallback_for_tier`：按阶段/档位选模型

**结论**：奇点已经走「能力快照驱动」的路，基础很完整。「避免 per-model 手配」基本已达成——`_build_agent_from_registry` 让模型只要配了 API key 就能自动构造 agent，agents_custom.json 手配与默认值几乎一样。

### 缺口（🧠）
1. **benchmark 的 strengths 没接到调度**：benchmark 测出「数据查询」等能力标签，但 `pick_agent` 选模型时没用它匹配任务类型。这是「能力快照驱动调度」的最后一步。
2. **benchmark 维度窄**：只有基础编码（fib/todo/sql），测不出多文件重构、长程任务。
3. （不是缺口）架构能力不需要 benchmark——架构任务已走委员会（多模型碰撞），不靠单模型架构分。

### 方案（🧠，小步优先）
- **a（推荐先做）**：pick_agent 加「strengths 匹配」——任务描述含关键词（sql/数据库/查询 → 数据查询）时，优先选 strengths 含该 label 的模型。小改动，可落地。
- **b（可选）**：benchmark 加「多文件重构」任务（仍是 pytest 验收，跨文件 import），扩展 strengths 维度。
- **c（不做）**：加「架构」benchmark 任务——架构输出 JSON 无法 pytest 验收，且架构已走委员会，无必要。

## #7 SQLite 元数据层

### 现状（✅ 已核实）
- 数据全 JSON 文件：`.qidian/projects/{id}.json`（每项目一个 ProjectState）、`.qidian/tasks/*.json`、traces/memory/snapshots 等。零数据库，可 grep 排查（CLAUDE.md 有意设计）。

### 痛点（✅ 你提出的）
- 跨项目查询要 grep 一堆 JSON；多项目并发写会打架；定位项目文件代码。

### 方案（🧠）
SQLite 做「元数据索引层」，JSON 保留事件源：
1. 建 `.qidian/index.db`（SQLite），表：projects / tasks / models / usage
2. **先只读索引**：从 JSON 全量重建索引（启动时 + 变更时），前端查询/筛选/聚合走 SQLite，写入仍 JSON
3. 渐进第二步：写入时 JSON + SQLite 同步写（事务）
4. 代码检索不用 SQLite——项目代码在独立 git 仓库，ripgrep 比 FTS5 快

**关键**：SQLite 是单文件、`sqlite3` CLI 可查，不丢「可排查」；比 Postgres 轻，符合自部署。

## #8 多项目并发

### 现状（✅ 已核实）
- 单调度循环（orchestrator）；SSE 连接上限 `_MAX_SSE_CLIENTS=20`；worktree/内存/模型库全局共享；token 预算有 ProjectState.token_budget_total/spent（per-project 已建模）。

### 痛点（✅ 你提出的）
- 多项目同时跑时共享资源隔离。

### 方案（🧠）
1. **项目级资源隔离**（先做，小）：
   - worktree 已按 task 隔离，确认按 project 隔离
   - SSE 从全局 20 上限改成按 project/订阅分片
   - token 预算按 project 扣减（record_tokens 已传 project_id，确认扣减链路）
2. **调度循环并发**（后做，大）：orchestrator 单循环 → 多项目并行调度，涉及锁/状态机重构，风险高，需单独设计。

## 建议实施顺序
#6-a（strengths 匹配，小）→ #7 只读索引（中）→ #8 项目级隔离（中）→ #8 调度并发（大，最后）。
